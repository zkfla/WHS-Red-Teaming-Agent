# SQL Injection in /rest/products/search?q Parameter

**ID:** vuln-0001
**Severity:** HIGH
**Found:** 2026-09-04 14:53:35 UTC
**Target:** http://host.docker.internal:3100
**Endpoint:** /rest/products/search
**Method:** GET
**CWE:** CWE-89
**CVSS:** 7.5
**Confidence:** High
**Fix Effort:** Low

## Description

The application is vulnerable to SQL injection via the q parameter in the /rest/products/search endpoint. User-supplied input is concatenated directly into a SQL LIKE query without parameterization, allowing an attacker to inject boolean-based SQL conditions to extract all products from the database or manipulate query results.

## Evidence

**Request 1 - Baseline:**
```
GET /rest/products/search?q=apple HTTP/1.1
Host: host.docker.internal:3100
```

**Response 1:**
```json
{
  "status": "success",
  "data": [
    {"id": 1, "name": "Apple Juice (1000ml)", "price": 1.99},
    {"id": 24, "name": "Apple Pomace", "price": 0.89},
    {"id": 47, "name": "Pineapple Juice (1000ml)", "price": 2.99}
  ]
}
```
Result: 3 products

**Request 2 - SQLi Payload (Always True):**
```
GET /rest/products/search?q=%27%20OR%20%271%27%3D%271 HTTP/1.1
Host: host.docker.internal:3100
```
(URL decoded: q=' OR '1'='1)

**Response 2:**
```json
{
  "status": "success",
  "data": [
    {"id": 1, "name": "Apple Juice (1000ml)", "price": 1.99},
    {"id": 2, "name": "Orange Juice (1000ml)", "price": 2.99},
    ... (46 products total returned)
  ]
}
```
Result: 46 products (all products in database)

**Request 3 - SQLi Payload (Always False):**
```
GET /rest/products/search?q=%27%20AND%20%271%27%3D%272 HTTP/1.1
Host: host.docker.internal:3100
```
(URL decoded: q=' AND '1'='2)

**Response 3:**
```json
{
  "status": "success",
  "data": []
}
```
Result: 0 products

**Analysis:**
- Normal search returns 3 matching products
- Boolean OR condition returns 46 products (injection working, causing WHERE clause to match all)
- Boolean AND condition returns 0 products (injection working, causing WHERE clause to match none)
- Response count directly correlates to injected SQL condition evaluation
- Confirms SQL injection with response-time-independent oracle (response count)

## Impact

An attacker can extract the complete product database through boolean-based blind SQL injection. By manipulating the q parameter with SQL payloads like `' OR '1'='1`, all 46 products are returned regardless of search query. This allows unauthorized access to product data including names, prices, descriptions, and image references. With further exploitation, database schema enumeration is possible via SQLite's sqlite_master table. The vulnerability could potentially be extended to access other database tables if the application's database permissions are not properly restricted.

## Counterevidence

Counterargument: Could the response differentiation be explained by coincidence or application logic? Testing confirms: (1) Normal search terms return 3 items, (2) OR '1'='1 returns exactly 46 (total database count), (3) AND '1'='2 returns 0 (no matches), (4) Alternative payloads like OR 'x'='x also return 46, confirming consistent pattern. The 43-item difference (46-3) between normal and OR payload exceeds any coincidental variation. The database appears to contain exactly 46 products, and the OR injection causes all to be returned. No input validation, WAF, or SQL escaping detected on this parameter. Application returns JSON directly from database queries without filtering, confirming direct database access.

## What Would Change This Severity

Confirmation that the database contains other sensitive tables (users, orders, payments) with user-accessible privileges would increase severity to CRITICAL. If the application allows UPDATE/DELETE via SQLi, severity remains CRITICAL. If the endpoint is rate-limited or behind authentication, severity would reduce to MEDIUM/HIGH depending on privilege level.

## Technical Analysis

The application constructs SQL queries by directly concatenating user input from the q parameter into a LIKE clause. The vulnerable code pattern is approximately:

```
query = "SELECT * FROM products WHERE name LIKE '%" + userInput + "%'"
```

With payload `apple`, the query becomes:
```sql
SELECT * FROM products WHERE name LIKE '%apple%'
```

With SQLi payload `' OR '1'='1`, the query becomes:
```sql
SELECT * FROM products WHERE name LIKE '%' OR '1'='1'%'
```

The OR condition is always true, causing the WHERE clause to evaluate to true for all rows, returning all 46 products instead of the 3 matching the search term. This pattern demonstrates classic string-based SQL injection where the attacker breaks out of the intended string context by injecting a quote, adds a boolean condition, and comments out the remainder of the query. The application directly exposes the success/failure of injected conditions through response count differentiation, enabling boolean-based blind extraction of data.

## Proof of Concept

1. Identify baseline: Send GET /rest/products/search?q=apple - observe 3 products returned
2. Inject always-true condition: Send GET /rest/products/search?q=' OR '1'='1 - observe 46 products returned (all products)
3. Inject always-false condition: Send GET /rest/products/search?q=' AND '1'='2 - observe 0 products returned
4. Verify injection: Response count differs based on the boolean condition injected, confirming the application is executing the attacker-controlled SQL condition
5. Extract data: Use `' OR '1'='1` to retrieve all products with complete details from the JSON response

## Remediation

Replace the vulnerable string concatenation with parameterized queries using prepared statements. In Node.js with SQLite, use placeholders (?) for all user input. In the vulnerable query `SELECT * FROM products WHERE name LIKE '%' + userInput + '%'`, change to `SELECT * FROM products WHERE name LIKE ?` and pass `['%' + userInput + '%']` as a separate parameter array. Alternatively, use an ORM (Sequelize, TypeORM, Prisma) that handles parameterization automatically. The key principle is that SQL structure and user data must be submitted to the database engine separately, never combined as a string. Add input validation as defense-in-depth (whitelist allowed characters, limit length), but this is not a substitute for parameterization.

## Assumptions

Assumes the q parameter is intended for searching product names using a LIKE operator. The boolean differentiation in response count proves the injection without requiring error messages or time delays. The backend is confirmed to be using SQLite based on error messages from UNION SELECT attempts.
