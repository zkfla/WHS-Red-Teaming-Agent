요약

기존 범용 레드팀 에이전트(Decepticon)는 7개 컨테이너와 19개 전문 에이전트로 구성된다. 본 연구는 웹 애플리케이션 단일 타깃을 대상으로 할 때 이 구성의 상당 부분이 실행되지 않는다는 점에 착안하여, 동일 작업을 수행하는 경량 구조를 구현하고 두 시스템의 성능을 동일 조건에서 비교하였다.

모델을 claude-haiku-4-5로 양측 고정하여 구조 차이만을 분리 측정한 결과, 경량 구조는 인프라 컨테이너를 7개에서 1개로 줄이면서 실행 시간 11.1배 단축(t=13.47, p<0.001), 비용 3.8배 절감(t=10.96, p<0.001)을 달성하였다. 탐지 성능은 경량 구조가 평균 4.33건, 기존 구조가 3.29건으로 나타났으나 표본 내 분산이 커 통계적 유의성은 확보하지 못하였다(t=1.44).

1. 연구 배경 및 목적

Decepticon은 AD, 클라우드, 모바일, ICS/IoT, 무선, 리버싱, 포렌식 등 다양한 공격 표면을 다루는 범용 레드팀 에이전트로, 19개의 전문 에이전트와 7개의 인프라 컨테이너(오케스트레이션, 모델 라우팅, 그래프 DB, 관계형 DB, 스킬 서버, 도구 실행 환경, CLI)로 구성된다.

그러나 예비 관찰 결과, 웹 애플리케이션 단일 타깃을 대상으로 하는 인게이지먼트에서는 19개 에이전트 중 3개만이 실제로 실행되는 것으로 확인되었다 (오케스트레이터, recon, exploit). 나머지 16개는 해당 타깃 유형에 해당하지 않아 기동만 된 상태로 유지된다.

이에 본 연구는 다음을 검증하고자 하였다.

  1. 웹 타깃 처리에 필요한 최소 구조는 무엇인가
  2. 불필요한 인프라를 제거했을 때 탐지 성능이 저하되는가
  3. 구조 차이가 실행 시간과 비용에 미치는 영향은 어느 정도인가

2. 실험 방법

2.1 실험 환경

타깃은 의도적으로 취약하게 제작된 훈련용 웹 애플리케이션을 사용하였으며, 난이도 3 이하의 챌린지 54개를 평가 대상으로 한정하였다. 타깃과 도구 실행 환경은 외부 인터넷 접근이 차단된 격리 네트워크 (--internal)에 배치하여, 에이전트가 범위 밖으로 나가는 것을 구조적으로 차단하였다.

측정의 공정성을 위해 타깃의 실제 명칭은 양측 어느 쪽에도 제공하지 않았다. 널리 알려진 훈련용 애플리케이션의 경우 명칭만으로 모델이 학습된 풀이를 재현할 수 있어, 구조 비교라는 실험 목적이 훼손되기 때문이다.

2.2 측정 지표 및 채점

탐지 성능은 자동 채점으로 측정하였다. 대상 애플리케이션이 제공하는 스코어보드 API를 실행 전후로 조회하여, 새로 해결된 챌린지 수를 산출하였다. 에이전트의 자체 보고는 채점에 사용하지 않았다.

이 방식을 택한 이유는 예비 측정에서 확인된 괴리 때문이다. Decepticon은 매 회차 "공격 성공률 100%", "Critical 취약점 3건 발견" 등을 보고하였으나, 스코어보드 기준 실제 해결 건수는 1~5건(1.9~9.3%)에 그쳤다. 자체 보고만으로는 성능을 과대평가하게 된다.

실행 시간·LLM 호출 수·토큰 사용량·비용은 각 시스템에서 별도로 수집하였다. 경량 코어는 API 응답의 usage 필드를 직접 적립하였고, Decepticon은 LiteLLM 프록시의 지출 로그에서 추출하였다.

2.3 통계 처리

두 시스템의 지표 차이는 독립표본 t검정으로 검증하였으며, 유의수준은 0.05로 설정하였다. 표본 수가 작으므로 평균값 비교만으로는 결론을 내리지 않고, t값과 임계값을 함께 제시하였다.

2.4 측정 신뢰성 확보

측정 과정에서 결과를 왜곡할 수 있는 결함 4건을 발견하여 조치하였다. 발견 경위와 조치 내용은 표 5에 정리하였다.

4. 설계 근거 측정

경량 구조의 설계는 임의로 결정한 것이 아니라, 세 차례의 사전 측정 결과에 근거하였다.

4.1 실행 시간의 구성

전체 190초
├─ 도구 실행       5초  ( 3%)
└─ LLM 응답 대기 185초  (97%)

초기에는 도구 실행을 병렬화하였으나, 실측 결과 도구 실행이 전체 시간의 3%에 불과하여 개선 효과가 약 1초에 그쳤다. 병목이 아닌 구간을 최적화하고 있었던 것이다. 실행 시간을 단축하려면 LLM 응답 대기를 중첩시켜야 하며, 이것이 exploit 단계를 병렬 전문가 구조로 전환한 근거가 되었다.

4.2 비용의 구성

회당 비용 $0.295
├─ 캐시 쓰기  70.5%
├─ 출력       18.6%
├─ 캐시 읽기   6.4%
└─ 입력        4.6%

도구 실행 결과는 대화 이력에 누적되어 이후 모든 턴에서 반복적으로 입력에 포함된다. 9턴 대화라면 첫 턴의 결과가 최대 9회 재전송되는 셈이다. 전문가를 분리하면 각 대화가 짧게 유지되어 이 누적이 억제되며, 실제로 캐시 읽기 토큰이 9.4배 감소하였다(318만 → 34만).

4.3 탐지 성능의 결정 요인

탐지 성능은 지출 금액보다 LLM 턴 수에 더 강하게 연동되었다. 즉 컨텍스트를 확장하는 데 소모한 토큰은 성능에 기여하지 못하고, 턴 수를 늘리는 데 소모한 토큰이 기여한다. 이로부터 "턴은 늘리고 컨텍스트는 억제한다"는 설계 원칙을 도출하였으며, 최종 구성(전문가 5인 × 9턴)이 이 원칙의 적용 결과이다.

4.4 대조군 실험: 전문화 효과의 분리

병렬화의 성능 향상이 담당 영역 분리(전문화)에 기인하는지 독립된 짧은 컨텍스트에 기인하는지 구분하기 위해, 담당을 부여하지 않은 일반 탐색자 5인을 동일 인원·동일 턴 수로 실행하였다.

탐지 건수는 표본 분산 범위 내에서 동일하였으나 도구 호출 수는 42% 차이가 났다. 탐지 성능 향상은 독립된 짧은 컨텍스트에서 비롯되며, 담당 분리는 중복 탐색을 억제하는 효율 개선에 기여하는 것으로 판단된다.

5. 결과

5.1 회차별 원자료

경량 코어의 실행 시간은 59~84초로 안정적인 반면 기존 시스템은 556~990초로 변동 폭이 크다. 탐지 건수는 양측 모두 분산이 크게 나타났으며, 이것이 탐지 항목에서 유의성을 확보하지 못한 직접적 원인이다.

6. 고찰

6.1 성능 격차의 원인

두 시스템은 동일 모델을 사용하므로 성능 차이는 전적으로 구조에서 비롯된다. 핵심 기전은 대화 컨텍스트의 누적 방식이다.

기존 시스템은 단일 에이전트가 순차적으로 작업하며 모든 도구 실행 결과를 하나의 대화에 누적한다. 매 턴 이 전체가 다시 입력에 포함되므로 캐시 읽기 토큰이 회당 318만에 달한다. 경량 구조는 전문가 5인이 각자 독립된 짧은 대화로 동시에 작업하여 34만 토큰에 그친다. 이 9.4배 차이가 실행 시간과 비용 격차를 함께 설명한다.

6.2 측정 과정에서 발견한 결함

측정의 신뢰성을 확보하기 위해 자체 검증을 수행하였으며, 결과를 왜곡할 수 있는 결함 4건을 발견하여 조치하였다.

6.3 실패한 개선 시도

최종 구성을 확정한 이후에도 성능 향상을 위해 네 차례의 추가 실험을 수행하였으나, 모두 최종 구성을 상회하지 못하였다.

특히 네 번째 시도는 표본 수가 작을 때의 위험을 보여주는 사례이다. 초기 3회 측정에서 탐지 5.33건, t=3.50(p<0.05)이 관찰되어 유의한 개선으로 판단되었으나, 6회로 확장하자 4.17건, t=1.01로 역전되었다. 표준편차 역시 0.58에서 1.83으로 증가하였다. 본 연구에서 이러한 역전 사례가 4회 발생하였으며, 이후 판단 기준을 회귀 잔차와 결정론적 지표(비용·턴 수)로 전환하였다.

7. 한계

7.1 탐지 성능의 유의성 미확보

기존 시스템의 표본을 3회에서 7회로 확대하였음에도 탐지 항목의 유의성은 확보되지 않았다(t=1.44, 임계값 2.201). 초기 추정 효과크기가 Cohen's d = 1.15였으나 표본이 축적되며 d = 0.80으로 축소되었기 때문이며, 이 효과크기에서 유의성을 확보하려면 각 군 15회의 측정이 필요하다.

7.2 예산 제약 상태

전문가당 턴 수를 4 / 6 / 9로 변화시킨 결과 탐지 건수가 2.67 → 3.67 → 4.67로 지속 증가하였다. 이는 현 구성이 능력 한계가 아니라 예산 한계에 있음을 의미한다. 따라서 비용 효율 지표는 투입 예산 곡선과 함께 해석되어야 한다.

7.3 벤치마크의 대리지표 타당성

실행된 명령을 분석한 결과 대부분이 조회 요청과 상태 확인이었으며, 난이도 3 이하 챌린지의 상당수는 특정 엔드포인트에 접근하는 것만으로 해결되는 것으로 확인되었다. 즉 본 벤치마크는 심층 익스플로잇보다 광범위한 열거를 보상하는 구조이다. 실전 레드팀 역량의 대리지표로서는 한계가 있으며, "심층 탐색"을 유도하는 프롬프트가 두 차례 모두 실패한 것도 이로써 설명된다.

7.4 단일 타깃

측정이 단일 애플리케이션에서만 수행되어 "해당 타깃에 한정된 결과"라는 반론이 가능하다. 타깃 확대가 필요하다.

8. 결론

웹 애플리케이션 단일 타깃을 대상으로 할 때, 기존 범용 레드팀 에이전트의 인프라 상당 부분은 실행되지 않으며 제거가 가능하다. 인프라 컨테이너를 7개에서 1개로 축소한 경량 구조는 동일 모델 조건에서 실행 시간을 11.1배 단축하고 비용을 3.8배 절감하였으며, 두 지표 모두 p<0.001 수준에서 유의하였다.

탐지 성능은 경량 구조가 평균 4.33건으로 기존 구조의 3.29건보다 높게 나타났으나 통계적 유의성은 확보하지 못하였다. 따라서 현 단계에서 확언할 수 있는 것은 탐지 성능이 저하되지 않은 상태로 시간과 비용을 크게 절감하였다는 것이다.

성능 향상의 기전은 대화 컨텍스트의 누적 억제로 확인되었다. 단일 에이전트의 순차 실행은 도구 출력을 하나의 대화에 누적시켜 매 턴 재전송하는 반면, 독립된 짧은 컨텍스트를 갖는 병렬 전문가 구조는 이 누적을 억제하여 캐시 읽기 토큰을 9.4배 감소시킨다.

후속 과제로는 기존 시스템의 표본을 15회까지 확대하여 탐지 항목의 유의성을 검증하는 것, 상위 모델 적용 시 구조 이득의 유지 여부를 확인하는 것, 그리고 타깃을 추가하여 일반화 가능성을 검토하는 것을 제안한다.
