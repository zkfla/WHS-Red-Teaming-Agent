# 구현 프롬프트 4f — 그래프·설정/API 계약 수정과 최종 보장 대조

너는 중앙 전환 이후의 기능 보존과 회귀 검증을 마무리하는 담당자다. `AGENTS.md`, 관련 모듈 지침, `plan1.md`, `plan2.md`, `plan2e.md`, `plan4.md`와 `plan4a.md` ~ `plan4e.md`를 읽고 각 단계의 실제 구현·검증을 확인한다. F20·F21·F22의 공개 계약을 수정하고 F06과 남은 관련 소비자 연결을 점검한다. 4a~4e 담당 문제를 이 단계까지 미뤄서 구현하지 않는다. 웹 UI·새 관계 그래프·미지원 구형 엔진 복원이나 다음 계획은 시작하지 않는다.

## 1. 먼저 수행할 보장 대조

1. 현재 Git diff·미추적 신규 구현과 삭제 전 테스트를 함께 읽는다. `git diff --stat`에는 미추적 새 파일의 추가량이 빠질 수 있다. 삭제량만으로 기능 이전이나 손실을 판단하지 않는다.
2. 삭제된 함수/등록/설정/공개 진입점을 실제 기본 runtime·CLI·조립·원본 조회·resume·report 소비자에 대응시킨다. 이름이 남아 있거나 import가 되는 것을 기능 보존으로 취급하지 않는다.
3. 삭제된 테스트를 파일 이름이 아니라 검증 의미로 분류한다: 의도적으로 폐기한 구조만 검사함 / 중앙 테스트가 같은 보장을 검사함 / 필요한 보장이 빠짐 / 지원 범위 확인이 필요함. 각 판단에 현재 검사·실제 소비자 근거를 붙인다.
4. 재현된 문제와 소스 확인·추정·미확인을 구분한다. 4a~4e에서 새로 생긴 실패나 직접 관련된 연결 누락은 최소 수정으로 해결한다. 다른 재설계가 필요하면 구체적인 문제·영향을 보고하고 계획 범위를 늘려 감추지 않는다.
5. 이 대조는 완료 보고에 간단한 표로 남길 수 있다. 새 보장 레지스트리·대응 DB·상세 작업 기록 파일은 만들지 않는다. 옛 파일 전체를 restore하거나 사용자 변경을 덮어쓰지 않는다.

## 2. 그래프 갱신 순서와 공개 설정/API 계약 수정

### F20 — worker 로컬 step과 공유 그래프 순서

1. `central_runtime.ready_workers`·`observe`·`nodes/update`의 step 생산자, 그래프 provenance·철회·`predicates.merge_properties`/`_merge_attrs`, 공개 `AttackGraphService` 소비자를 읽는다. 이전 step 9 철회 뒤 더 늦은 새 worker의 step 1 관측이 무시되는 공개 API 사례를 먼저 재현한다. 기본 실행의 자동 철회가 현재 연결돼 있지 않다는 범위도 확인한다.
2. 서로 다른 worker/Run의 로컬 step을 같은 전역 시간으로 비교하지 않는다. 기존 중앙/그래프의 순서·row version·관측 lineage로 실제 최신 관측과 과거 snapshot을 구분할 최소 계약을 정한다. 이미 저장된 step의 소유 lineage와 새 순서의 버전/호환을 명시한다.
3. 실제 이후 관측은 해당 predicate를 복원할 수 있고, 진짜 철회 이전의 stale snapshot import는 복원하지 못해야 한다. worker별 원본·step·provenance는 보존하며 숫자를 키우는 임시 보정, 전체 graph fingerprint barrier, 새로운 순서 DB를 만들지 않는다.
4. bool sticky merge·명시적 철회·claim provenance의 현재 의미를 보존한다. 이 수정으로 임의 step TTL sweep·자동 철회·플래너 기동 같은 삭제 동작을 복원하지 않는다. 비교 불가능한 과거 원본은 불확실성을 보존하고 사용자 graph/DB를 자동 재작성하지 않는다.
5. 늦은 새 worker의 재관측, 철회 전 stale snapshot, 같은 worker 순서, 병렬 row 갱신·재전달·resume를 필요한 범위에서 검사한다. 실제 writer부터 공유 graph 조회까지 순서가 전달돼야 하며 서비스 내부 단위 검사만으로 연결 완료를 주장하지 않는다.

### F21 — 적용되지 않는 재시도 설정

1. `OrchestrationSettings.max_retries`·`retry_retryable_tool_failures`, 공개 config/CLI schema·예제, `nodes/execute.retry_enabled`와 현재 native 실패 feedback·재판단을 읽는다. retryable 실패·`retry_safe=true`·설정 활성화인데 자동 실행이 1회인 현상을 명시적 더블로 확인한다.
2. 기본 해결 방향은 적용되지 않는 설정의 공개 약속을 제거하고 실제 중앙 실패/재판단 계약을 문서화하는 것이다. 자동 재시도 기능을 복원하려고 별도 큐·Work 상태·도구 scheduler를 만들지 않는다. 이전 snapshot의 값은 필요하면 passive identity로 해석하고 실제 동작 설정으로 광고하지 않는다.
3. 공개 schema·명시적 입력 오류/폐기 안내·문서·예제와 원본 Run 호환을 함께 정리한다. 실제 호출 상한·UNKNOWN 보호는 유지한다. LOW risk만으로 반복 안전성을 인정하거나 비안전 호출을 자동 반복하지 않는다.
4. 새 설정 입력/공개 schema가 지원 동작과 일치하는지, 이전 Run decoding·재개 identity가 4b의 계약을 유지하는지, native 실패가 모델에 전달돼 합법적인 후속 판단이 가능한지 검사한다. 동작하지 않는 설정을 유지한 채 문구만 바꾸지 않는다.

### F22 — 무시되는 실행 API override

1. `app/bootstrap.run_engagement(orchestration_config=...)`의 실제 호출자·문서·예제·조립 계약을 읽고 비기본 제한을 전달해도 사용/전달되지 않는 사례를 확인한다. CLI에서 이미 조립된 설정이 정상 적용되는 경로와 구분한다.
2. 제한은 application 조립에서 확정하는 현재 경계를 유지한다. 사용하지 않는 override 인자를 제거하거나 명시한 폐기/거절 계약을 제공하고 호출자는 설정을 조립 지점에 전달하도록 이관한다. 인자를 조용히 무시하거나 실행 직전 deps의 제한/binding을 바꾸지 않는다.
3. 공개 API·호환/re-export·호출 예제·실제 소비자를 갱신한다. 지원 override가 있다면 실제 적용 범위와 저장/binding 의미를 명시한다. 원래 Run의 제한 변경을 새 budget처럼 승인하지 않는다.
4. 비기본 입력이 조용히 소실되지 않고 적용 또는 명확한 거절로 귀결되는지, 정상 조립의 실제 제한이 계속 작동하는지 필요한 최소 검사로 확인한다.

## 3. 반드시 확인할 실제 보장

- 승인 전 provider 진입 금지, 정확한 action/인자/대상/session에 대한 승인, 만료·변경·다른 Run 승인 거절.
- host/port/scheme/domain/path/redirect/target-free 도구의 현재 scope·Control·역할 선택 계약과 실제 gateway 전달.
- 관련 원본의 Run·Task·action·invocation·tool-call·입력 digest·review/receipt 연결, 손상·소실·mock·실패 원본의 성공 오인 방지.
- 완료 검토 중 관련 조건·증거 만료/변경, 무관한 그래프 변경 허용, 필수 미해결·정리·미확정 실행의 성공 거절.
- 공용 완료 API와 등록된 중앙 local tool의 confirmed/refuted/inconclusive/blocked 처리, 결과 질문·출처·보고 보존.
- 공유 worker/tool/target/LLM/request/token/time/네트워크 상한, 같은 Run 사용량 보존, 새로운 워커/역할/재개로 인한 예산 복제 방지.
- 자원 대기의 동일 호출 자동 재개, 승인 대기 중 독립 작업 진행, 활성 job/UNKNOWN 점유 유지, 재전달·재시작·owner 이전과 낡은 쓰기 거절.
- 전체 재개와 `--instance` 선택 재개의 범위, checkpoint 없는 진입 전 예약과 진입 후 원본 수집의 구분, 다른 Run·원본 설정으로의 자동 대체 방지.
- 운영자 안내·집중·우선순위·제외·pause/stop이 저장뿐 아니라 실제 플래너/선택/admission에 전달되는지, 늦은 입력과 마스킹이 유지되는지.
- 코드 생성·독립 리뷰·Artifact 보관/조회·명시적 fixture 정책의 실제 등록/조립/호출, 원본·격리·재전달·정리와 대상 성공의 구분.
- F12의 자원 domain 정체성과 생성/삭제 원본, F13의 새 ID를 통한 UNKNOWN 동일 호출 보호, F14의 실제 모델 요청 직전 시간 admission.
- F15의 제외/취소와 진짜 필수 조건 구분, F16의 실제 채택된 관련 증거 검사와 무관한 선택 작업 진단 분리.
- F17의 등록된 job 도구에서 중앙 원본 조회/수집까지의 연결, F18의 원래 설정 identity round-trip, F19의 활성/대기/과거 종료 사유 구분.
- F20의 관측 lineage·철회/재관측·stale snapshot 구분, F21·F22의 실제 지원 설정/API와 이전 Run decoding·binding 정합성.

기존 중앙 테스트가 이미 충분한 보장을 검사하면 재사용한다. 검증되지 않은 항목에만 필요한 최소 회귀를 추가한다. 안전성 보장을 모두 삭제됐다고 단정하지 않으며, 여러 주장을 한 테스트의 이름이나 총 통과 개수로 동등성을 판단하지 않는다.

## 4. 최종 통합 시나리오

제어 가능한 도구·원본 조회·fixture 더블, 명시적 fake LLM, 임시 SQLite와 체크포인트를 사용한다. 아래 흐름을 현재 실제 선택·조립·CLI 소비자를 통해 검사하고, 겹치는 개별 검사는 불필요하게 복제하지 않는다.

1. 목표 입력 → 같은 역할의 조사 작업 2개 → 독립 워커 진행 → 중간 원본·질문 공유 → 운영자 안내/우선순위 전달 → 후속 판단·실제 작업 선택.
2. 공유 자원 경합 → 첫 호출 정상 종료 → 같은 원래 호출의 자동 재개. 승인/job/UNKNOWN 대기 및 실제 상한·stop은 별도로 구분한다.
3. 중간 재시작 → 원래 action·승인·증거·사용량으로 재개. `--instance`는 다른 작업·플래너를 시작하지 않고 전체 재개만 후속 탐색을 허용한다.
4. 체크포인트가 없는 진입 후 실행 → 명시적 원본 수집 CLI → 결과 보존·held 유지. 새 provider 실행·actor·예산 정산을 만들지 않는다.
5. 관련 원본 → 코드 생성·독립 리뷰 → 보관/조회 → 명시적 합성 입력 검증 → fixture 결과 보존. 실제 대상 증거·Finding·목표 성공을 대신하지 않는다.
6. 완료 검토 중 증거 만료/조건 변경 → 성공 거절. 유효한 실제 원본 계약·충족된 목표·확인된 정리에서만 성공 → report/status/findings/approvals에 원본 상태가 일치한다.
7. 다른 domain의 같은 로컬 ID 자원 2개 생성 → 하나만 삭제 → 남은 의무 때문에 성공 거절 → 각 원본으로 모두 삭제한 뒤 성공 가능. 원본·정리 연결이 덮이지 않는다.
8. 비안전 UNKNOWN 실행 → 여유 슬롯과 새 작업 ID로 동일 호출 제안 → 신규 provider 진입 거절/보류. 기존 원본으로 UNKNOWN을 해소한 뒤 합법적인 후속 조사는 가능하다.
9. 시작 시 시간 소진 → 신규 모델 0회. 무관한 선택 작업 제외/조건 소실 → 본 목표의 정상 완료 가능. 진짜 필수 조건·실제 검토에 채택된 증거의 소실은 계속 성공을 막는다.
10. 비기본 과거 설정 identity를 가진 Run의 CLI 재개 → 원래 값·실제 제한 유지 → actor 응답 대기 중 status/report는 실행 중 → 정산 후 현재 종료 사유 표시. job local tool은 원래 결과만 수집하며 새 job을 제출하지 않는다.

앞 단계의 회귀가 이 흐름의 실제 소비자까지 이미 검증했다면 재사용하고 같은 더블 실행을 불필요하게 반복하지 않는다. 라이브 provider·대상 검증을 대신했다고 표현하지 않는다.

## 5. 검사 범위와 문서

- 앞 단계에서 통과한 관련 검사를 불필요하게 반복하지 않는다. 최종 코드 상태의 필요한 통합 검증과 현재 CI 필수 검사는 한 번 수행한다. 새 실패/변경이 생긴 범위만 다시 검사한다.
- 현재 `pyproject.toml`·`.github/workflows/ci.yml`에서 pytest, ruff, mypy, Compose 설정 및 컨테이너 검증 범위를 확인한다. 실행 환경 때문에 수행하지 못한 검사는 정확히 보고하며 더블·설정 검사로 실제 컨테이너 실행 완료를 대신 주장하지 않는다.
- 실제 대상·유료 LLM·사용자 DB 이전은 실행하지 않는다. synthetic lab 검증과 라이브 provider/대상 검증을 구분하고 운영 입력을 fake로 조용히 바꾸지 않는다.
- 실패를 없애려고 테스트 함수를 대량 삭제하거나 모든 테스트 helper를 AST 참조 여부만으로 정리하지 않는다. 문자열 fixture·동적 주입·monkeypatch·공개 계약 소비자도 확인한다.
- README·관련 `docs/agent/`·중앙 상태/완료/재개 계약과 설정 예제를 실제 지원 기능·제한에 맞춘다. `plan1`·`plan2`·`plan3`를 완료한 것으로 다시 쓰지 않는다.
- 현재 지원되는 이전 Run·원본 조회와 미지원 실행 형식, binding/설정 변경의 재개 조건을 명시한다. 구형 데이터 보존과 구형 실행 엔진 지원을 구분한다.

## 6. 완료 보고

`plan4.md` 5절 형식에 더해 F01~F22 각각을 해결/보장 확인/미완료로 보고한다. 주요 삭제 기능·테스트 의미의 현재 대응, 실제 end-to-end 소비자, 합성 시나리오 결과, 필수 검사·미실행 항목과 이유, 남은 기능 누락·호환 제한을 명시한다. F06의 보장 대조와 F20의 공개 API/기본 실행 범위, F21·F22의 계약 정리를 기능 복원 개수로 합치지 않는다. 근거가 없는 항목에 ‘기능 이관 완료’나 ‘다른 문제 없음’을 쓰지 않는다. 필수 문제가 해결되면 종료하고 요청하지 않은 커밋·push·다음 계획 실행은 하지 않는다.
