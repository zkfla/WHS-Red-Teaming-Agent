# 구현 프롬프트 4c — 시간 예산·작업 제외와 운영자 지시·만료 재판단

너는 메인 플래너의 입력·알림 연결을 수정하는 담당자다. 루트와 core·orchestration·control·app의 `AGENTS.md`, `plan1.md`, `plan2.md`, `plan4.md`, `plan4a.md`, `plan4b.md`를 읽고 선행 구현을 확인한다. F02·F07·F08·F14·F15를 구현·검증한다. 웹 UI나 다음 단계는 구현하지 않는다.

## 1. 먼저 확인할 경로

- `OperatorIntentType`, `operator_intents/interpreter.py`, `OperatorIntentService`, `central_runtime.process_controls`: 사용자 입력 → 분류 → 저장 → 적용 결과.
- `engine.context`, `specialist_planner._advance_central`: 현재 Mission·작업·지시가 전략 제안과 작업 분해의 실제 모델 입력으로 전달되는 경로.
- `CentralRun.run`, `EventWakeup`, outbox·이벤트 소비와 제한적인 상태 재확인.
- `evidence_validity.py`의 원본 조건·`valid_until`·현재 상태, 4a의 최종 완료 검사.
- 작업 선택·배정의 소비자와 기존 operator selector의 정확한 대상/Task 참조 검증.
- `reasoning_time.py`, `engine.guard_reasoning`, structured decision client·`metered_llm`: 플래너 전략/분해/repair의 실제 요청 admission.
- `StrategyDraft`·`AtomicTaskProposal`·`MissionTask.required`, 중앙 Task 상태 전이와 `goal_inputs`: 필요한 작업의 판단·취소·필수성 조정.

안내가 `applied`인데 실제 플래너 요청에는 빠지는 상황과 `reprioritize`가 거절되는 상황을 먼저 회귀로 재현한다. 새 쓰기 이벤트 없이 관측된 유효시간만 지나서는 플래너가 깨지 않는 상황도 더블로 재현한다.

실제 application 조립에 시간 한도 0과 명시적 fake LLM을 주입해 새 모델 요청이 1회 발생한 뒤 종료되는 F14를 재현한다. 본 목표의 독립 근거가 확보된 뒤 추가 미시작 작업을 제외하면 `applied`·worker 0인데 필수 READY 작업 때문에 완료가 거절되는 F15도 재현한다.

## 2. 운영자 입력 전달

1. 적용된 안내·집중 영역·정확한 작업/endpoint 선택과 조사 우선순위 요청을 현재 목표·작업 상태와 함께 전략 제안·작업 분해의 실제 입력에 전달한다. 기존 Mission preferences와 지시 원장을 사용하고 별도 지시 DB·복사 원본을 만들지 않는다.
2. 지시 ID·Run·목표 버전·적용/거절 상태·순서를 보존한다. 최신 유효 지시와 필요한 제한된 이력만 읽는다. 거절된 지시를 실행 허가로 취급하거나 오래된 지시가 최신 지시를 덮게 하지 않는다.
3. `reprioritize`를 기존 enum·분류·공개 처리 계약으로 지원한다. 현재 존재하는 조사 목적·작업·대상에 대한 요청만 다루고, 새 target·scope·승인·예산을 만들지 않는다.
4. 우선순위 요청의 의미는 플래너의 조사 선택과 이후 실제 작업 선택·배정까지 연결한다. 이미 등록된 작업을 우선해 달라는 요청을 입력에만 넣고 완료로 보고하지 않는다. 현재 계약으로 표현할 수 없는 최소 의미는 이유·생산자·소비자·저장·resume 영향을 설명해 추가할 수 있다.
5. 정수 priority 큐·도구 호출별 스케줄러·조사 순서 DAG를 복원하지 않는다. 실제 호출 전제조건·자원 충돌·Control 한도는 계속 코드가 검증한다. 지시가 실행 중인 외부 호출을 임의로 취소하거나 재실행하게 하지 않는다.
6. `applied`의 의미와 사용자 안내는 실제 반영 수준에 맞춘다. 코드로 보장하는 입력 전달·배정 반영과 LLM의 의미 판단을 구분한다. 특정 문구·역할·도구 이름으로 지시 준수나 성공을 판정하지 않는다.

## 3. 증거 만료·조건 변경 알림

1. 원본에 근거해 관측된 조건과 만료 시간만 사용한다. 모르는 TTL을 추측하지 않고, 과거 관측의 진실성과 현재 재사용 가능성을 구분한다.
2. 유효성이 바뀌면 실제 관련 증거 참조·변경 사유를 기존 이벤트/알림 소비자에 전달해 플래너가 재판단할 수 있게 한다. 현재처럼 새 sequence만 기다리다 시간 경과를 놓치지 않게 한다.
3. 기존 bounded wakeup·상태 재확인 루프에 다음 관측 만료를 연결한다. 별도 timer 테이블·작업·데몬·상태 DB, busy polling, 매 tick LLM 호출은 만들지 않는다.
4. 같은 변화의 중복 알림은 합칠 수 있다. 이는 같은 증거를 재조사하지 못하게 하는 의미적 fingerprint 차단과 다르다. 변경 없는 이미 처리된 만료가 무한 재판단을 만들지 않게 한다.
5. 재시작·알림 누락 후에도 원본 조건을 읽어 상태를 복구한다. pause/stop/종료 시 신규 모델·도구 호출을 막고, 만료 알림을 scope·승인·자동 대상 호출 허가로 취급하지 않는다.
6. 4a의 최종 유효성 검사가 권위다. 알림이 늦거나 누락돼도 만료된 근거로 완료를 확정할 수 없으며, 알림이 왔다고 원본·Finding·작업 결과를 삭제하지 않는다.

## 4. 시간 admission과 작업의 필수성·취소

1. 메인 플래너의 전략 제안·작업 분해·repair도 기존 reasoning time/ROE·Mission 상태 검사와 Run 공유 LLM 예산을 거친다. engine의 기존 guard와 요청 client hook을 사용하며 중앙 루프에 시간 정책을 따로 복제하지 않는다.
2. 시작 시 이미 시간이 소진됐다면 새로운 모델 요청은 0회다. semaphore·cooldown 대기나 앞선 전략 요청 이후 시간이 소진되면 다음 실제 요청 전 현재 제한을 다시 확인한다. admission 이후 이미 진행 중인 요청의 종료·불명 사용량은 기존 계약대로 보존한다.
3. 소진은 구조화된 예산 종료/보류로 처리하고 빈 성공 제안·일반 설정 오류로 숨기지 않는다. 재개·알림·새 역할로 시작 시간을 초기화하거나 요청 예산을 다시 지급하지 않는다.
4. 플래너가 현재 목표·criteria·결과 관계를 근거로 기존 조사 작업의 필요 여부와 취소/필수성 변경을 제안할 최소 계약을 제공한다. 코드는 해당 Run·Task·goal revision·현재 상태·참조를 검증한 뒤 중앙 상태로 반영한다. 모든 제안을 기본 `required=true`로만 만드는 제한과 unowned READY 작업을 조정할 진입점이 없는 문제를 함께 해결한다.
5. 운영자 제외는 실행 금지와 목표 필수성 면제를 구분한다. 목표에 불필요한 선택 작업은 명시한 판단으로 취소/비필수 처리해 완료를 막지 않게 하고, 목표의 진짜 필수 확인을 제외한 경우에는 필요한 조건을 충족했다고 간주하지 않는다. 정확한 사유를 보고하며 `exclude`만으로 성공 gate를 모두 풀지 않는다.
6. 실행 중 작업의 소유권·pending 승인·job·UNKNOWN·정리 의무는 유지한다. 외부 결과 미확인을 단순 `CANCELLED`로 덮거나 제외 시 외부 호출을 자동 재실행하지 않는다. 상태 변경·알림·후속 선택·완료 검사가 같은 현재 사실을 소비하게 한다.
7. immutable한 원래 작업 목적/완료 조건과 현재 필요성 판단을 구분한다. 취소·비필수 조정은 근거·판정·원래 결과를 보존하고 관련 owner/version CAS를 지킨다. 별도 조사 DAG·우선순위 큐·필수 작업 DB를 만들지 않는다.

## 5. 최소 회귀 검증

- 안내·집중·정확한 작업 선택 지시가 저장 상태부터 전략/분해 요청까지 전달된다. 거절/오래된/다른 Run 지시는 현재 유효 지시로 소비되지 않는다.
- 기존 작업에 대한 `reprioritize`가 처리되고 이후 실제 선택·배정에 반영된다. 없는 작업·범위 확대·권한 변경 요청은 거절되며 기존 실행·승인 ID가 보존된다.
- 관측된 만료만 발생해도 제한된 재판단 기회가 생긴다. 중복 알림·재시작·알림 누락에서도 무한 호출이나 동일 호출 재실행은 없다.
- 만료가 없는 원본에 임의 TTL을 붙이지 않는다. pause/stop/종료 상태에서는 알림으로 실행이 재개되지 않는다.
- 무관한 그래프 변경은 기존 관련 판단·정확한 승인을 무조건 폐기하지 않는다. scope/승인 거절과 공유 예산 검사는 유지된다.
- 원래 started_at이 있는 duration 0 Run은 신규 모델 0회로 종료한다. 제어 가능한 시계로 전략/분해 사이와 실제 요청 슬롯 대기 중 소진도 검사하고 현재 정상 예산에서는 전략·분해가 진행된다.
- 목표와 무관한 미시작 작업의 제외/취소/비필수 조정 후 새 worker가 생기지 않고 그 작업만으로 완료가 막히지 않는다. 목표의 진짜 필수 조건이 미해결인 반대 사례는 완료가 거절된다.
- 플래너의 기존 작업 조정은 실제 중앙 상태·선택·완료·보고에 반영된다. 잘못된 Task/Run·낡은 revision·늦은 owner 제안은 거절되고 활성 job·UNKNOWN·정리 의무는 보존된다.

변경한 입력·이벤트·선택 계약과 이전 Run 처리 조건을 문서에 반영하고 관련 최소 검사와 린트·타입 검사를 수행한다. `plan4.md` 5절 형식으로 결과를 보고하라.
