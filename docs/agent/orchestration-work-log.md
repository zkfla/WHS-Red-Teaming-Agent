# 오케스트레이션 작업 기록

작성일: 2026-10-01. 작업 브랜치: `dev-orchestration`.

## 확정 방향

- 최초 조사·경로 생성·경로 검토·다음 행동·결과 의미 검토·재계획은 LLM이 결정한다. 운영에서 가짜 모델 또는 규칙 실행으로 대체하지 않는다.
- 규칙 후보는 검토용 참고 자료다. 실행 후보를 채우거나 점수 차이로 자동 선택하지 않는다.
- 기존 그래프와 증거 저장소를 활용한다. 제공 정보, 원문에 근거한 관측 사실, 가설, 검증된 발견을 논리적으로 구분한다. 같은 노드의 항목별·리스트 원소별 출처와 값이 확인되어야 관측 사실에 포함한다.
- LLM이 제안한 조사 경로를 버전과 함께 저장한다. 선행 단계·대상·계정·허용 행동·완료 조건을 코드로 검사한다. 최초부터 전체 경로를 확정할 필요는 없고 수정·대안 전환이 가능하다.
- 행동 등록 시와 실제 호출 직전에 활성 경로·버전·단계·사용자 지시·실제 도구 인자를 재검사한다. 기존 정책 계층의 승인을 통과해야 실행된다.
- 원본 결과를 먼저 보존한다. 가설 성립·반박·불확실, 보안 위반, 단계 완료, 사용자 목표 완료는 각각 따로 판단한다.
- 승인 대기에서는 실행 소유권을 반환하고 재개할 때 다시 획득한다. 장기 작업은 실제 어댑터가 제공하는 상태·결과만 수집한다. 저장 결과 재처리는 도구를 재호출하지 않는다.

## 역할과 실제 사용 의존성

루트가 설계·통합·판단·커밋을 담당한다. 오케스트레이터는 `opencode-go/deepseek-v4.1-flash`/`max`, 워커는 `opencode-go/muse-spark-1.3-contributor`/`xhigh`를 사용한다. 동시에 최대 7개까지이며 워커는 추가 하위 에이전트를 만들지 않는다.

기존 LangGraph, LiteLLM, Pydantic, jsonschema를 사용한다. NetworkX 3.4.2를 DAG 구조 검사에 추가했고 Tenacity 9.1 계열을 실제 요청 횟수 기준의 공통 시도 예산에 사용한다. 중복 에이전트 실행기·새 지식 데이터베이스는 추가하지 않았다. 기존 LangChain·hackingBuddyGPT 연동은 유지한다.

## 현재 구현 경계

- `orchestration/engine.py`: LLM 경로·행동·수정·증거 조회·가설 갱신·단계/목표 완료의 연결. 실제 호출 횟수 예산을 공유하고 검사 실패를 다음 LLM 요청의 피드백으로 제공한다.
- `orchestration/paths/`: 조사 경로 스냅샷·진행·버전 경쟁 검사. 메모리 또는 기존 작업 그래프 SQLite 파일을 사용한다. 현재 경로 ID와 버전을 모두 비교한다.
- `orchestration/knowledge.py`, `attack_graph/predicates.py`, `attack_graph/service.py`: 항목별 출처·확인 상태. 같은 실행의 원본 증거와 값이 일치하는 관측만 투영한다. 과거 자료와 증거 조회 실패도 명시한다.
- `orchestration/cognition.py`: JSON Schema와 요청 예산 검사. 형식·전송·의미 오류 때문에 내부·외부 재시도가 곱해지지 않게 한다. SDK 자체 재시도는 사용하지 않는다.
- `orchestration/analysis.py`, `nodes/verify.py`, `completion.py`: LLM 의미 판단과 실행·원문·대상·행동·계정 대조. 모델의 판단과 최종 코드 인정 결과를 증거 저장소에 별도 기록한다.
- `orchestration/recovery.py`: 저장된 결과의 해석·반영 복구. 새로운 게이트웨이 호출은 하지 않는다.
- `orchestration/work/`, `nodes/execute.py`, `runner.py`: 실행 소유권·승인 재개·등록된 장기 작업 수집. 결과 수집 시 원래 호출 ID까지 대조한다.
- `app/bootstrap.py`, `core/config.py`, `orchestration/settings.py`: 실제 운영은 LLM 필수. 예전 비제안 설정은 운영 모드를 선택하지 않으며 false 설정을 거부한다.

## 첫 외부 리뷰와 루트 판정

`agy`로 `gemini-3.8-flash-high`, effort high, 읽기 전용 리뷰를 실행했고 완료 결과를 수령했다. 외부 보고서에는 실제 코드에 없는 이름과 예시도 포함되어 있어 그 보고서의 전체 통과 주장이나 가상 코드 인용을 검증 결과로 채택하지 않았다. 루트가 실제 소스에서 확인한 문제만 수정 대상으로 채택했다.

| 실제 소스에서 확인한 문제 | 반영 내용 |
|---|---|
| 요청 예산 소진의 내부 예외가 공개 실패로 정리되지 않음 | 명시적인 계획 실패로 변환 |
| 승인 재개에서 실행 기록 연결과 소유권이 끊김 | 원래 기록 ID 보존·대기 시 반환·재개 시 재획득 |
| 장기 결과 수집 뒤 실행 기록이 미정 상태에 남음 | 등록된 작업 ID와 일치하는 실제 종료 상태로 정리 |
| 새 사용자 지시가 실행 직전 검사에 반영되지 않음 | 실제 지시 저장소의 최신 행동 지시 확인 |
| 의미 오류를 LLM에 수정 피드백으로 제공하지 않음 | 동일 요청 예산 안에서 오류 피드백 제공 |
| 인자 바인딩으로 LLM 제안 순서가 달라짐 | 제안 순서 보존 |
| URL·대상 참조 인자가 제안 대상과 다를 수 있음 | 실제 호스트·포트·스킴·등록 참조 검사 |

루트 추가 검토에서는 리스트의 일부 관측으로 제공된 리스트 전체가 사실로 올라가는 문제, 계정 별칭을 문자열만으로 인정하는 문제, 관측 전용 결과의 가설 확정, 인증 대조 후 이전 성공 판정이 남는 문제도 확인하여 보완했다. 최종 코드 인정 결과가 완료 조건에 연결되는지는 마지막 검증 대상이다.

## 두 번째 외부 리뷰와 루트 판정

두 번째 읽기 전용 리뷰도 완료했다. 실제 소스와 대조하여, 실행 전 경로 변경으로 취소된 작업의 재제안, 가설 재사용 시 기존 상태 보존, 세션 별칭과 대상 참조의 증거 대조, 변경되지 않은 단계의 이전 버전 증거 재사용, 저장 계층 자체의 후손 진행 초기화, 가설 반영 실패의 명시적 진단을 채택했다.

보류된 경로를 자동 재시도하자는 제안은 채택하지 않았다. 보류는 유효한 판단이며 변경 제안으로 재검토할 수 있다. 반복 가능한 행동이라는 필드를 가정한 지적, 실패한 장기 작업의 결과 정리가 없다는 지적, 시스템 주석을 원본 도구 증거처럼 취급한 지적은 실제 계약·구현과 일치하지 않아 채택하지 않았다. 외부 보고서의 전체 통과 주장은 검증 결과로 사용하지 않는다.

루트는 추가로 마지막 도구 호출 뒤 예산이 0이 되어 증거 기반 완료 검토까지 중단되는 문제를 확인했다. 추가 도구 호출은 제한하되, 이미 수집한 결과의 제한된 완료 검토는 수행하도록 보완했다. 예전 제안 설정의 환경 문자열은 참으로 정규화하며 거짓은 운영 대체 모드로 허용하지 않는다.

## 최종 확인 원칙

세 번째 외부 리뷰는 계정 별칭의 원본 증거 대조, 계정 이름과 세션 이름 구분, 경로 버전 계보·선행 단계 변경, 목표 완료 저장 버전 증가에 한정했다. 해당 범위에서 추가 재현 가능한 문제를 보고하지 않았다. 실제 테스트 결과는 루트가 실행하여 별도로 확인했다.

첫 최종 검사에서 관측 출처·경로 SQLite·실행 기록·설정 25개, 의미 검토·경로 엔진·실제 실행 루프 18개가 통과했다. 목표 완료 저장 시 버전 증가 누락은 검사에서 발견하여 수정한 뒤 관련 18개를 다시 통과시켰다. 기존 파일별 검사에서는 1,364 통과·215 실패·6 생략, 시간 초과 4개 파일을 확인했다. 이를 전체 통과로 기록하지 않는다. 규칙 자동 선택·가짜 운영 모델·관측 그래프에 정책 거부 기록을 요구하는 기대는 새 계약으로 검토하고, 승인·동시 실행·재시도 등 유지할 계약에는 명시적인 LLM 경로·행동과 활성 경로를 제공하는 테스트 준비를 추가한다.

Windows에서 `O_NOFOLLOW`·`fchmod`가 없는 기존 증거·도구 구현은 이번 브랜치의 해당 영역 변경이 없는 것을 확인했다. 이 영역의 실패는 오케스트레이션 수정으로 해결했다고 주장하지 않는다.

리뷰 수정 후 새 핵심 검사 43개를 다시 실행하여 모두 통과했다. 소스 린트는 통과했고 전체 소스 타입 검사에는 위 Windows 전용 기존 오류 3개만 남았다. 간편 조립 진입점도 명시적인 LLM 클라이언트를 요구하도록 바꿨고 실행 예시는 운영 조립과 환경 설정을 사용한다. 목표 완료 시 조사 작업 완료 이벤트를 함께 남긴다. 기존 테스트의 이관과 최종 전체 재검사는 계속 진행한다.

구현과 리뷰를 마친 뒤 필요한 검증을 실행한다. 새 통합 시나리오와 기존 회귀 검사를 함께 사용한다. 예전 규칙 선택·비제안 모드를 기대하는 테스트는 새 계약에 맞춰 검토하며, 실제 오류를 숨기기 위해 일괄 건너뛰지 않는다.

아직 전체 테스트 통과나 외부 실서비스 검증을 주장하지 않는다. 실제 모델·MCP 서비스·운영 장기 작업 어댑터를 사용하지 않은 확인은 최종 결과에 그 한계를 기록한다.
