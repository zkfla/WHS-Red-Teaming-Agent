1. **등록 조건과 정산 조건의 불일치는 재현됐다.** 질문·분해·직접 등록 경계가 최종 판정형 완료 조건의 후보 참조 누락을 허용했지만 정산은 이를 거절했다. 새 등록에서는 질문/Task에 이미 연결된 후보가 정확히 하나일 때만 그 ID를 결속한다. 연결이 없거나 여러 개면 추측하지 않고 등록 전에 필드 위치와 수정 조건을 반환한다. 기존 행은 다시 쓰지 않는다. 원문 요청을 복사한 뒤 정규화하므로 같은 객체나 같은 원문으로 등록을 재시도해도 요청 해시가 달라지지 않는다.

2. **활성 Planner 출력에서 상태 생략과 검토 참조의 무효 소비 가능성을 확인했다.** 도메인 모델의 기본값은 과거 데이터 조회를 위해 유지하고, 활성 단일/분리 Planner 출력에서는 `status`를 명시하도록 schema와 실제 응답 검사를 맞췄다. `open/held/inconclusive`에 최종 검토 참조만 넣은 응답은 구체적인 수정 피드백을 받는다. 실제 Run의 원래 모델 응답이 상태를 생략했는지는 저장된 정규화 기록만으로 확정할 수 없다. 주장 내용과 개정이 달라진 뒤 예전 검토를 제외하는 동작은 정상이며 완화하지 않았다.

4. **종료한 원래 실행의 과거 승인 대기가 현재 대기처럼 표시되는 사례가 확인됐다.** 보고 projection은 동일 Run/Task/invocation/action의 canonical 상태와 검증된 원본 실행 영수증을 대조해 과거 대기의 해소 여부를 표시한다. 원본 기록은 보존한다. 실제 보고서의 해당 요청은 종료했지만 응답404로 필요한 자료를 얻지 못했으므로, 별도 증거 부족과 Task blocked/Run unresolved는 그대로다. 이 문제를 이유로 도구별 승인 예외를 추가하지 않았다.

Root가 `native_local_tools.task_settle_descriptor`, `semantic_completion.complete_task`, `prove_original`, `task_completion_contract.check_task_conditions`와 기존 원본/검토 테스트를 대조했다. Task 정산의 성공 증거는 먼저 보존된 실행 원본을 검증하고 독립 의미 검토를 수행한다. 공개 사후 검토 기록은 해당 원본 자체가 아니므로 직접 원본처럼 제출한 경우 `origin_raw_missing` 거절은 현재 경계와 일치한다. 다른 완료 소비자에 검토 기록을 원본 참조로 전개하는 기능이 있다는 사실만으로 Task 원본 검사를 우회해야 한다고 결론 내릴 수 없다.

따라서 이 항목은 현재 **코드 결함 확정에서 제외**한다. 별도 신뢰 전개 계약을 새로 추가하거나 검토 기록을 원본으로 인정하지 않는다. 실제 실행의 반복 실패와 직접 연결된 조건 참조 누락은 등록 경계에서 수정하며, 검토 기록의 후보 판정 활용은 기존 최신 revision/purpose 결속을 유지한다. 이전 관찰자의 동일 결론도 참고했지만, 이 판단은 현재 생산자·소비자 소스를 기준으로 했다. 라이브에서 확인되지 않은 비용 절감이나 최종 결과 성공을 주장하지 않는다.
