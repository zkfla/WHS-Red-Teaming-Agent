# 검증 계약 완화와 공개 조회 연결 구현 계획

작성일: 2026-10-04. 기준: dev `ce7893a2a15f448e977b4643b68b18972c743e02`.
상태: 구현 기준 확정. 독립 GPT-6.1 Sol xhigh 재검토에서 R1~R8 및 요청별 사용량 연결의 필수 잔여 없음 확인. 제품 구현 착수, 테스트는 전체 구현·리뷰 뒤 수행한다.

## 1. 목적과 기준

루트 LLM이 목표와 근거를 보고 조사 경로를 제안·수정하고, 위임받은 워커가 목적 안에서 조사 방법과 도구를 선택하게 한다. 코드는 실제 실행 권한·입력·출처·필요한 선행 정보와 결과의 근거를 확인한다. 임시 계획의 단계·역할·도구 이름을 실행 권한이나 사용자 목표 자체로 취급하지 않는다.

기준 자료는 기존 `validation-contract-research-and-proposal.md`의 7~12절과 공개 조회 정책 초안이다. 연구와 오픈소스 대조는 기존 산출물을 재사용한다. 이번 계획이 옛 폐쇄 루프 계획의 완료 계약 유지 제한보다 우선한다. 기존 문서에 명시적으로 후속 범위로 남긴 전역 대화 압축·기능 설명의 단계적 공급·다중 모델 전환·자동 스킬 생성·UI·모바일 확장은 이번 필수 구현에 넣지 않는다.

작업 순서는 조사·계획 → 별도 계획 검토·문서 확정 → 구현과 작업별 최소 확인·checkpoint 커밋 → 별도 전체 코드리뷰·수정 → 필요한 최종 테스트 → dev 반영·푸시다. 테스트·실행 검증은 구현과 전체 코드리뷰 이후 수행한다.

전체 소스의 실제 최종 줄 번호는 변경 후 달라진다. 위 숫자는 기준 커밋의 위치다. 팀원 실패 실행의 원본 JSON은 확보하지 못했으므로 동일 실행 재현을 완료했다고 주장하지 않는다.

## 3. 함께 확정할 의미와 책임

### 3.1 계획, 실제 실행, 결과

LLM 입력 정리는 `paths/writing.py`의 생성용 schema와 defined path 필드의 정규화에서 담당한다. 저장 `PathPlan`은 유지한다. 실행·경로 귀속, 버전·상태·목표, 진행·검토 기록은 생성용 필수 입력에서 제거하고 현재 실행 문맥으로 채운다. 등록 단계는 모델이 보낸 운영값도 코드의 권위값으로 다시 연결한다. 단일 기준의 배열/객체/설명 문자열은 같은 결과 조건으로 정리하며 설명과 의미상 필요한 참조만 요구한다. 일반 자연어 결과 조건은 공통 의미 판정으로 받는다. 가설 조건에 필요한 가설 참조 등 실질적인 필수 정보는 생략하지 않는다. 도구 인자나 자유 텍스트의 임의 키를 경로 입력으로 탐색하지 않는다.

계획 단계는 목적·의존성·현재 근거·미해결 사항·선택 가능한 수행 제안이다. 실행 가능한 동작이 없거나 미래 값이 미정이어도 전체 계획을 거절하지 않는다. 이미 알려진 참조의 오기, DAG 순환, 다른 실행의 증거 주장은 거절하거나 명확히 진단한다. 아직 발견할 대상은 미정으로 표현하고 실행 시 실제 관측·사용자 제공 참조로 해결한다.

실제 실행에는 선택 도구와 입력, 목적 연결, 실제 대상·주체가 필요하다. 단일 의미로 확인되는 카탈로그 연결과 코드 소유 정보만 자동 연결한다. 애매한 역할·동작·대상은 추측하지 않는다. 준비된 독립 행동은 실행하고 종속·거절된 행동에는 각각 대기·실패 이유를 반환한다. 새 행동을 허가할 때 기존 제안이나 승인 기록의 대상·입력을 바꿔 재사용하지 않는다.

임시 단계의 예상 역할·동작·대상은 권한 허용 목록이 아니다. 위임 목적과 운영자 제한, 실제 등록 역할의 지원 기능, 살아 있는 도구 연결, 현재 정보·정책·승인이 실행 경계다. 다른 도구로 같은 목적을 달성한 결과는 실제 출처대로 인정한다. 실제 위험도 집계와 승인 정책은 기존 의미를 유지한다.

완료는 실제 증거와 해당 목적·결과 조건의 의미를 비교한다. 도구 실행 성공을 목표 달성이나 취약점 확인으로 승격하지 않는다. 자유로운 자연어 결과 조건에는 근거를 받은 기존 LLM 판정을 사용하고, 직접 확인 가능한 취약점·주체·가설 조건에는 기존 전문 검사를 결합한다. 특정 정리 단계 이름을 예외 목록에 추가하지 않는다.

관련 증거는 다른 단계·다른 워커의 원본을 참조할 수 있다. 실행·조사·사용자 목표의 귀속을 실제 저장 자료로 확인하고, 목표 대상·계정·환경과의 관련성을 확인한다. 임시 수행 방식만 변경된 경우에는 근거를 재사용하고, 실제 결과 조건·대상·계정이 달라진 경우에는 재판정한다. 원본의 경로·단계·도구 식별정보를 현재 단계로 덮어쓰지 않는다.

단계 종합의 증거 출처 검사는 `completion.py`의 기존 실제 실행/주체 검사를 재사용한다. 원본에 적힌 경로·버전·단계가 같은 실행의 실제 저장 경로에 존재하고 관련 목표에 속하는지 확인하되, 현재 완료 단계와 동일한 번호일 필요는 없다. 최초 실행의 제안·도구 결과·대상·행동 연결은 보존하며 현재 단계의 예상 동작과 맞추는 검사는 제거한다. 현재 단계에 필요한 대상·주체·결과 조건과의 관련성은 여전히 확인한다. 기록 조회 실패는 성공으로 처리하지 않는다. 기존 강한 가설/취약점 확인에 필요한 최종 판정 근거는 유지한다.

작업 완료와 전체 목표 완료는 별도다. 작업은 맡긴 목적과 관련 증거를 검토하여 종료하고, 전체 목표는 원래 사용자 결과 조건과 필수 작업·정리 의무를 확인한다. 임시 계획 단계 개수를 세어 완료하지 않는다. 미정 실행·승인 대기·취소·예산 소진은 성공과 구분한다.

원래 전체 결과 조건은 기존 `MissionPlan.success_criteria`, 개별 위임 작업의 목적은 기존 `MissionTask.objective`에서 읽는다. 임시 `PathStep.required`를 원래 사용자 필수 조건으로 승격하지 않는다. `complete_task`/`complete_goal`은 실제 저장한 관련 실행 근거를 공통 검사로 확인하고 기존 LLM 완료 검토에 목적·조건·반증·공백을 전달한다. 코드가 사용자 조건의 빠짐, 무관한 증거, 미정 실행·필수 정리를 확인한 뒤 기존 원자적 coordinator 변경으로 완료 상태를 기록한다. 수행하지 않은 임시 단계는 실제 수행으로 기록하지 않는다.

### 3.2 도구 결과와 폐쇄 루프

실행 성공/실패와 자동 해석 상태(해석됨·정상 빈 결과·해석기 없음·해석 실패), 지식 적용 상태(완료·부분 적용·실패·불명)를 분리한다. 동일 요청에는 대응 결과가 남는다. 원본은 기존 증거/아티팩트 영역에 보존하고 모델에는 관련 발췌와 원본 참조를 제공한다. 해석 복구는 저장된 결과를 처리하며 도구를 재실행하지 않는다.

검사 공백은 원래 사용자 결과 조건과 관련 근거에서 읽기 전용으로 투영하고, 실제 수행 이력과 구분한다. 집계는 완료 판단의 참고 자료다. 기존 원본 기반 중복 식별, 진행 판정, 승인 재개, 실제 관측과 가설·취약점의 구분을 재사용한다. 새 증거 번호·승인 번호를 같은 행동의 새 의미로 취급하지 않는다.

### 3.3 자율 위임과 종료 전 정리

공통 조사 루프는 목적·위임 범위·관련 근거·남은 예산을 받아 LLM의 후속 도구 제안을 같은 정책·실행·증거 흐름으로 수행한다. 역할별 루프를 복제하지 않는다. 현재 단일 행동 워커를 여러 단계 조사에 연결하고, 루트는 반환된 관측·증거·판정·미해결 사항을 받아 전체 경로를 재계획한다. 워커가 전체 목표 달성을 직접 선언하지 않는다.

다른 워커의 실행 기록과 실패 결과도 관련 범위로 조회할 수 있게 한다. 전체 대화를 복제하지 않고 기존 증거·이벤트·원장의 조회를 사용한다. 원장 lease, 동일 실행의 중복 억제, 승인 대기/재개, 모든 실제 호출의 예산·동시성 계산을 유지한다.

정리 여유는 기존 작업 예산 안에서 확보한다. 정상 종료·예산 소진·오류 시 이미 얻은 증거 참조와 미해결 사항을 반환·보존한다. 사용자 즉시 중지나 허용 시간 종료 뒤에는 새 LLM 호출·외부 작업을 시작하지 않는다. 정리 실패도 기존 결과와 원래 종료 사유를 잃게 하지 않는다.

### 3.4 공개 조회 정책

명백한 자격증명 형태와 운영자 외부 전송 금지 규칙을 공통 판별로 연결한다. Control의 거절 판단과 Capability의 네트워크 직전 검사는 같은 의미를 사용하되 마스킹을 전송 허가의 대체물로 쓰지 않는다. 안전한 사유·규칙 참조만 기록하며 차단된 검색어의 자격증명이 로그·이벤트·체크포인트·증거·오류에 남지 않도록 실제 저장 경계에 연결한다.

대상별 허용 행동은 기존 범위·ROE와 함께 적용하며, 같은 대상을 Host·URL·Endpoint로 바꾸어 제한을 피할 수 없게 한다. 공통 계약에 없는 부분만 추가하고 LLM이 임의로 정책을 설정하게 하지 않는다. 공개 자료 조회 허용이 공격 허용으로 확대되지 않는다.

승인 대상과 실제 URL은 동일한 정규화 의미로 비교한다. 허용 origin·DNS/IP·TLS·크기·시간 제한을 재사용한다. 리다이렉트는 목적지에 연결하기 전에 후보 목적지를 반환하고 루트/워커가 새 행동을 제안해 Control 판단을 거친다. 검색 결과·이동 주소는 권한이나 확정 취약점이 아니다. 일반 실행 중 continuation 프레임워크를 추가하지 않는다.

### 3.5.1 참조 후보 대상의 실행 연결 (R8, W1·W2)

검색 결과 URL과 리다이렉트 목적지는 관측 사실·허가로 승격하지 않으면서 실제 후속 행동에 연결한다. 대상 편입 상태를 셋으로 나눈다.

1. 선언(declared): 운영자가 제공한 범위. 기존 동작 유지.
2. 관측 확정(observed·confirmed): 이번 실행의 grounded 측정 근거가 있는 대상. 기존 동작 유지.
3. 참조 후보(referenced·unconfirmed): 이번 실행의 검증된 원본·증거가 참조한 주소. 편입 근거는 원본의 실행 일치와 출처 식별자(source evidence id·run)뿐이다. 다른 실행 주장은 과거로만 둔다.

참조 후보는 사실 내용 필드(`fact_refs`, 관측 확정 표시)에 넣지 않는다. 실제 주소·서버 존재 측정이 있을 때만 fact_refs에 들어간다. 원본 노드 앞에 후보 주소를 `observed_target`으로 채워 관측 확정으로 취급하지 않는다.

실행 게이트는 매 검사 새로 수집한 재료에서 참조 후보를 수용해 후속 페이지 읽기 같은 실제 행동이 `unresolved_target`으로 막히지 않게 한다. 참조 후보의 실행 허가는 기존 Control 범위 검사가 실제 대상에 그대로 판정한다(알려짐과 허용은 다른 층). 변경 소유는 B(재료·게이트: `knowledge.py`의 대상 편입 규칙, `knowledge_validation.py`의 대상 상태 의미, `engine.py`의 게이트 소비)와 C·D(매퍼)다.

검색·페이지 읽기는 기존 본문 계약과 구분되는 최소 부분 결과 표현을 쓴다. 요청 URL·실제 응답 URL/상태와 선택적인 redirect_url을 보존한다. 본문을 받지 않은 이동 응답은 본문 없음으로 표현하고 미방문 목적지의 성공을 만들지 않는다. MCP 노출·출력 스키마·카탈로그 발견 검사를 같은 변경에 포함한다. 페이지 리더는 한 요청 결과만 반환하고 자동 이동은 하지 않는다. 후속 행동은 전역 실행/위임 예산과 동일 행동 중복 억제로 제한한다. 옛 max_redirects는 자동 이동 설정으로 더 이상 사용하지 않으며 호환 입력만 유지하고 문서에 의미 변경을 적는다. 매 새 행동에 별도의 이동 예산을 초기화하지 않는다. 범용 continuation은 추가하지 않는다.

참조를 전달할 공통 형태는 GraphMutation의 사실/노드 변경과 별개인 target references다. D는 처리 동반 증거에 원본 evidence ID·호출과 TargetRef 참조를 연결한다. B는 같은 실행의 실제 원본이 확인된 참조만 재료에 포함하고, 그래프 노드가 아직 없으면 해당 실제 TargetRef로 행동을 컴파일한다. 사실이나 서버 존재 측정으로 합성하지 않는다. 해석기가 없는 도구에서도 기존 원본 열람을 통해 주소 위치와 원본 참조가 확인되면 같은 해결 경계로 처리한다.

### 3.5.2 민감 검색어 공통 판별과 첫 저장 경계 (R6, W1)

차단은 공통의 좁은 판별 규칙(명백한 자격증명 형태 + 운영자 설정 금지 규칙)으로 하고, 저장 마스킹은 별도로 유지한다. 저장 가림 함수의 변환 여부를 차단 술어로 빌리는 안은 기각한다(3.5.7). 비공개 판별 함수를 import하거나 정규식을 복제하지 않고 공개 계약·설정 공급으로 공유한다.

계획 노드 다음에 정책 노드가 오므로 정책 거절 전에 계획 체크포인트·분배 상태에 원문이 저장될 수 있다(R6 확인 근거). 실제 선택 ToolDescriptor가 외부 전송 텍스트 인자의 이름을 선언하고 등록 카탈로그로 공급한다. B의 컴파일/준비 단계는 공통 판별로 차단 대상인 입력만 첫 WorkItem·분배 상태·체크포인트에 넣기 전에 기존 Control.evaluate로 실제 거절을 확정한다. 안전한 정책 결과/차단 증거만 반환하고 원문 인자를 상태에 넘기지 않는다. 일반 허용 행동은 기존 정책 노드로 처리하므로 이 사전 차단이 정상 행동을 이중 승인하거나 예산을 이중 소비하지 않는다. 실제 선택 tool ID는 시스템이 만드는 ControlContext로 전달한다. 허용된 실행의 원본 인자를 임의 마스킹하지 않고, 마스킹된 검색어로 새 실행을 만들지 않는다. 네트워크 직전 검사는 같은 좁은 공통 판별을 사용한다.

### 3.5.3 대상별 행동 제한의 실제 계약 (R7, W1)

대상별 읽기·공격 제한은 기존 전체 범위·ROE만으로 구현되지 않으므로 Engagement에 기본 빈 목록의 대상별 정책을 추가한다. 각 정책은 기존 EngagementScope 형태의 selector, 선택적인 allowed_action_keys, denied_action_keys를 가진다. 전체 scope/ROE를 먼저 통과하고 매치한 모든 대상별 제한도 충족한다. 거절 우선이며 겹치는 허용 제한은 교집합으로 적용한다. 허용 목록 없음은 해당 규칙의 추가 허용 제한 없음, 명시적 빈 허용 목록은 허용 행동 없음이다. 매치 규칙이 없으면 기존 정책 의미를 유지한다.

같은 대상의 Host·URL·Endpoint 표현은 core.scope_rules의 공통 공개 주소 해석으로 같은 제한에 도달한다. 포트 미정 표현은 해당 호스트의 포트 지정 제한을 우회하지 않도록 가능한 제한을 적용한다. selector 해석은 실행 권한을 새로 부여하지 않는다. 이 제한은 최초 정책 판단과 실행 직전 재검사, 승인 재개 이후 및 추가 호출 판단에 같은 의미로 연결한다. 페이지 자원의 경로·쿼리 일치는 별도 공통 URL 비교로 유지하며 대상별 정책의 주소 단위와 혼동하지 않는다.

### 3.5.4 폐쇄 루프 D 최소 변경 (W2 수용)

A~E 판정은 A·B·C·E 부분, D 없음(기준 커밋에 없는 추가 예정 모듈)이다. 최소 변경은 다음으로 확정한다.

1. 해석을 맡는 쪽: 반환 모양을 유지하고 호출별 상태를 함께 돌려준다. 상태 있는 마지막 실패 보관 대신 호출별 불변 결과(MappingOutcome)를 부가 API로 반환하고, 옛 진입점(`map_result`)은 같은 의미의 래퍼로 유지한다.
2. 처리를 맡는 쪽: 적용 확정·중간 실패 지점·미확정을 구조 기록으로 남긴다(개수 요약 문자열 대체). 처리 시도 기록의 중복 방지 키는 기존 호출·증거 식별자에 처리 시도를 더한 값으로 하고, 실행 의미 키에 새 기록 식별자를 추가하지 않는다.
3. 문맥을 맡는 쪽: 해석 상태·반영 상태·복구 가능 근거·공백을 다음 판단에 전달한다. 원본 본문은 기존 읽기 통로에서만 읽는다. 중앙 루트 문맥의 증거 요약 필터(engine.py)도 같은 계약을 읽어야 하며 `context_projection.py`만 바꾸면 부족하다.
4. 집계·보고를 맡는 쪽: 기존 보고 옆에 읽기 전용 투영 하나를 두고 현재 목표 공백과 과거 수행을 가른다. 기존 보고 키를 지우지 않고 기본값 있는 공백 요약을 더한다. 과거 보고는 구버전 없음·불명으로 읽고, 새 기록을 관측 사실·판정 근거로 승격하지 않는다.
5. 검색·리다이렉트: 3.5.1의 참조 후보 읽기로 연결한다.

D 문서가 후속으로 남긴 자율 워커 항목은 D 소유 밖이며 프로젝트 E 범위다(전체 후속으로 재분류하지 않는다).

### 3.5.5 자율 위임 공통 실행 계약 (W3 수용, R4)

워커 후속 행동은 새 엔진 없이 기존 LangGraph 실행 경로(정책→실행→검증→반영)와 원장 등록·임대·중복 규칙을 그대로 밟는다. 컴파일 강제(경로 봉투·목표 범위·역할·도구 결합·불확실 실행 거부)를 우회하지 않는다.

합산은 초기 발송 항목만 읽는 현재 구조를 넓힌다. 결과 봉투에 후속 1건당 `work_id`·`action_id`·`parent_action_id`·`candidate_key`·`executed`·`succeeded`·`retry_attempts`·정책 판정 필드·`approval_id`·`verdict`·`evidence_ids`·`last_event_id`·`error`·`runtime_observations`를 싣고, 합산은 계산식을 바꾸지 않고 입력만 늘려 실행 수·예산·역할별 계수·연속 실패·최종 판정·사건·승인 대기·거부 요약·관찰 접기에 포함한다. 후속 승인은 워커가 직접 해소하지 않고 조정자 승인 재개 절차로 올린다. 장기 작업 수합은 기존 `reconcile_job`으로만 끝낸다.

종료 의미를 구분한다. 위임 조사 종료는 위임 목적에 대한 결과·미해결·종료 사유를 루트에 돌려주는 사건이고, 전체 목표 달성 선언은 루트 판단 자리에서만 낸다. 자체 계획만 반복하고 선택을 루트에 되돌리는 단일행동 반복을 자율 루프 완료로 부르지 않는다.

그래프 구조(루트 대안 반영): 워커 전체를 단일 async 노드 while 루프로 반복하지 않는다. 기존 상위 LangGraph의 실제 호출별 계획→정책→실행→증거→합산→다음 판단 저장·재개 경계를 재사용하고, 체크포인트의 위임 상태가 다음 판단 소유자를 지정한다. 새 worker subgraph의 interrupt/continuation과 기존 단일 승인 재개를 중복 조립하는 안 대신 기존 저장·승인 경계를 선택한다. [LangGraph 공식 문서](https://docs.langchain.com/oss/python/langgraph/use-subgraphs)의 하위 그래프 대안도 조사했으나 이번에는 새 중첩 실행 경계를 만들 필요가 없다.

루트 응답에 단계·등록 역할·목적·WorkBudget을 담은 위임 제안을 받을 수 있게 한다. 코드는 위임 ID·현재 mission/task/path/step 귀속을 연결하고, RuntimeState에 목적·역할·누적 실행/판단 소비·증거 참조·현재/대기 행동·종료 사유를 저장한다. E의 공통 위임 판단은 별도 역할 맥락과 worker_next_action 단계로 기존 PlanningProvider를 호출하고 행동/근거 읽기/위임 종료를 받는다. 실제 후속 행동은 B의 컴파일과 scheduler/enqueue/acquire를 통해 각각 새 원장·행동·호출이 된다. 준비된 위임별 행동을 현재 실행 슬롯 안에서 병렬 분배한다. 위임이 있는 단일 행동도 같은 분배/합산 경로로 연결하여 원장·계수·대기 상태를 재사용한다. 코드 소유 상태를 모델이 복창하지 않게 한다.

워커는 목적 안에서 여러 실제 행동을 선택하며, 조사 종료/수정 필요/미해결과 실제 증거를 루트에 돌려준다. 전체 목표 완료나 전체 계획 교체를 직접 적용하지 않는다. 활성 위임의 다음 판단을 다시 루트에게 맡기는 것으로 끝내지 않는다. 합산은 이번 실제 호출만 위임/전역 계수에 반영하며 이미 센 누적 결과를 다시 세지 않는다. 후속 승인은 기존 정확한 제안·단계·work ID 및 해당 위임 상태와 함께 부모 체크포인트에 남긴다. 기존 승인 재개가 그 행동을 처리한 뒤 같은 위임 목적과 남은 예산으로 돌아간다. 프로세스 재개는 기존 원본 실행/원장 확인과 장기 작업 수합을 사용하며 불확실한 실행을 다시 호출하지 않는다.

예산: 실제 위임 max_actions는 기존 WorkBudget을 활용한다. 별도 위임 판단 한도는 기존 실행 설정 max_steps 안에서 배정하고 누적 소비한다. 요청 묶음의 DecisionBudget 재시도와 위임 전체 소비를 구분한다. 위임 시간은 실제 시작 시각과 누적 경과, 토큰 한도를 설정한 경우는 실제 모델 usage로 계산한다. usage가 확인되지 않으면 토큰 예산을 0으로 간주하거나 집행 완료를 주장하지 않고 추가 모델 조사를 중단하여 원인과 부분 결과를 반환한다. 전역/위임 잔여 중 작은 한도를 적용하며 후속 제안마다 초기 예산을 다시 주지 않는다.

기존 LLMClient는 JSON dict만 반환하여 usage가 소비되지 않으므로 A/F가 선택적 사용량 반환 포트를 추가한다. 이 포트는 요청별 정규화된 JSON 값과 nullable usage를 반환하고, 기본 complete_structured의 반환형과 기존 제공자는 그대로 지원한다. 실제 LiteLLM 어댑터가 SDK 응답의 usage를 변환하고 cognition이 요청·재시도마다 해당 위임의 사용량/판단 소비에 연결한다. 병렬 호출이 공유하는 last_usage 속성을 두지 않는다. 토큰 한도를 설정한 위임에서 제공자가 계측을 지원하지 않거나 usage가 누락되면 이미 저장한 결과와 한도 확인 불가 사유로 종료한다. 새 LLM SDK나 통계 저장소는 추가하지 않는다.

종료 전 정리: 기존 포기 절차와 부분 결과 저장을 쓰고, 위임 판단 예산 안에 마지막 정리 요청 여유를 둔다. 정리 단계는 새 조사 도구를 실행하지 않고 이미 저장된 증거·실패·미해결·종료 사유만 반환한다. 허용 시간/판단 예산이 없으면 코드가 기존 기록으로 반환한다. stop·강제 취소·deadline 이후에는 정리 LLM도 호출하지 않는다. `plan`·`router`·`graph`·`runner`·`state` 공유 파일은 F가 소유하고 E가 위임 모듈 및 분배/합산 API를 제공한다.

### 3.5.6 루트 B 추가 소유 — 종료 정산 공통 계약과 중지 후 호출 금지 (R5)

실제 앱 종료 경로(`app/bootstrap.py` 1030행 이후 → `replanning.finalize_mission` → `_terminal_criterion_results`)는 루프 안 완료 계약과 다른 기준을 쓴다. 완료된 필수 작업이 생산한 성공 도구 증거만 골라 심사하고, 즉시 중지가 제외 조건에 없어 중지 이후에도 추가 모델 호출에 도달할 수 있는 경로가 있다(정적 대조이며 재현은 아니다).

루트 B가 이 경로를 같은 완료 계약으로 통합한다. 루프에서 검증한 작업·조건 결과를 공통 계약으로 읽고 입력 근거·조건이 바뀌지 않았으면 다시 심사하지 않는다. "도구 성공" 필터를 일반 결과 충족의 선행 조건으로 쓰지 않는다. 즉시 중지·강제 취소·허용 시간 종료 뒤에는 저장 기록만으로 부분 결과와 원래 사유를 투영하고 새 LLM 호출·외부 작업을 시작하지 않는다. 정상 종료·예산 소진의 선택적 모델 정리는 남은 허용 예산 안에서만 한다. 옛 종료 조건 평가의 목표 문자열 접두어·역할별 직접 분기 목록에 새 종류를 추가하지 않고 등록 기반 판정 제공자와 통합한다.

### 3.5.7 기각·보류 기록

기각(루트 판정):

1. 저장 가림 함수(`redact_sensitive_text`)의 변환 여부를 차단 검사로 사용하는 안 — 마스킹은 더 넓은 목적이므로 공통 좁은 판별과 저장 마스킹을 분리한다(3.5.2).
2. 대상별 읽기 정책을 기존 전체 ROE·태그만으로 처리하는 안 — target selector + allowed_action_keys 공통 계약과 Control 소비가 필요하다(3.5.3).
3. `final_url`만 반환하고 리다이렉트 후속 연결을 후속 범위로 미루는 안 — 현 목표 범위상 새 목적지 연결 전 반환 구현과 부분 결과 스키마가 필요하다(3.5.1).
4. 원본 노드 앞에 `observed_target`=후보 주소를 넣어 관측 확정으로 취급하는 안 — 참조 후보는 출처 원본·run만 확인하고 fact_refs에 넣지 않는다(3.5.1).
5. 실행 대상 집합 검사를 그대로 두고 참조 후보를 절대 집합에 넣지 않는 안 — 후속 페이지 읽기가 `unresolved_target`으로 막히므로 참조 후보 수용으로 바꾼다(3.5.1).

6. (워커3 판정) 정리 여유 계산·후속 토큰/시간 상한·재생 안전성을 전부 후속으로 미루는 안 — goal 필수 요구와 충돌하며 이번 범위로 회수한다(3.5.5).

보류·미확인: 운영자 금지어 실설정 존재, 가림 함수 차단 전용의 과차단 오탐률, 연결 실패 별도 분류 코드, 등록 프로필 위험도 명시 요구 원문, 원장 임대 횟수와 도구 시도 횟수의 대응. 일감별 예산(시간·토큰)의 현재 소비 지점은 이번 범위에서 확인·구현한다.

### 3.5.8 완료 저장·변경 의미·생성 입력의 확정 (R1~R3)

입력 변환은 `_ask` 이후 PathPlan/TurnDecision/ReviewDecision 검증 전에 defined path 슬롯에 적용한다. 저장 모델은 유지하고, 새 자연어 조건은 semantic 종류·설명·기본 증거 요구로 표현한다. 옛 저장 unknown 조건을 자동으로 성공 가능한 조건으로 바꾸지 않는다. 직접 선택한 원본 발췌·반증·공백을 기존 구조화 완료 심사에 넘기며 최근 20개 요약에만 의존하지 않는다.

작업 완료의 권위 근거는 기존 완료 검토 동반 증거를 확장한 영수증이다. task ID·판단 목적의 내용 해시·검토 당시 mission revision·수용한 원본 evidence IDs·결과/사유를 기록하고, 기존 coordinator 검토 토큰으로 작업의 완료 상태와 그 영수증 참조를 함께 원자적으로 변경한다. MissionTask에 기본값 없는 참조(null)의 완료 영수증 필드만 추가한다. 작업을 재개/변경해 완료가 해제되면 그 참조도 해제한다. 전체 목표와 종료 정산은 현재 완료된 작업이 실제로 참조하는 영수증과 현재 목적·원본을 확인하여 목적-근거 관계를 구성한다. 미확정 accepted 기록, 바뀐 목적, 없는/무관한 원본은 통과시키지 않는다. 검토 당시 mission revision은 이력으로 보존하고 최종 목표는 현재 사용자 조건으로 다시 판단하므로 임무 revision 번호 변경만으로 과거 관측을 폐기하지 않는다. 참조 없는 legacy 완료 작업은 기존 저장 경로/단계의 실제 근거 검사를 통해서만 읽으며 조용히 새 영수증을 만들어내지 않는다. 생산 작업과 사용 작업은 별도이고 수행하지 않은 단계는 완료했다고 기록하지 않는다. 새 DB나 영수증 서비스를 만들지 않는다.

변경 비교는 수행 제안(예상 역할/동작·미해결 서술)과 결과 의미(대상·주체·조건·필수 사실·실제 선행 관계)를 나눈다. 수행 제안만 바뀌면 검증된 결과 연결은 보존하되 미실행 구체 행동은 현재 조건으로 재확인한다. 결과 의미가 바뀌면 해당 판정과 실제 영향을 받는 후손을 다시 확인한다. 기존 버전 저장·후손 전파를 재사용하며 단계 정의 비교·이전 출처 검사·원장 무효화에서 같은 의미를 사용한다. 자연어 의미 동등성을 코드로 추측하거나 모든 의존성을 자동 해제하지 않는다.

## 5. 계획 검토와 변경 관리

외부 GPT-6.1 Sol xhigh가 계획과 실제 소스를 별도로 확인한다. 정확성·단순성·확장성, 실제 소비 경로, 책임 중복과 강한 결합을 검토한다. 지적은 근거·발생 상황과 함께 반영/대안 반영/기각/후속 과제로 기록한다. 조사 통합 후 변경된 부분을 재검토하고 근거 있는 필수 문제가 없으면 계획을 확정한다. 점수나 반복 횟수를 목표로 삼지 않는다.

검토 1(`no-git/validation-contract-implementation-20261004/plan-review-1.md`, R1~R8)과 수정본 재검토 2(`plan-review-2.md`)가 완료됐다. 구현 착수 가능 및 필수 잔여 없음 판정으로 계획을 확정한다. 요청별 사용량 포트 보완 문단도 같은 검토자가 해당 실제 세 파일과 대조해 확인했다. 구현 뒤 전체 코드리뷰와 필요한 최종 검증은 별도 수행한다.

구현 중 범위/공유 의미 변경은 오케스트레이터와 루트가 계획 변경으로 기록한다. 임시 우회·도구 이름 분기·중복 판정으로 병렬화를 만들지 않는다. 각 작업 완료 후에는 범위 충족·계약 경계·명백한 연결 오류만 확인하고 checkpoint 커밋한다.

## 6. 구현 후 마지막에 수행할 최소 검증

전체 구현과 독립 코드리뷰를 마친 뒤 실제 변경 경계를 검증한다. 기존 테스트를 먼저 재사용하고 바뀐 계약과 실제 실패 유형에 필요한 사례만 보완한다.

1. 전체 다단계 계획 수용, 미래 값 대기, 준비된 독립 행동 진행, 정리 단계의 선행 증거 참조.
2. 허용된 대체 도구와 방법의 결과 인정. 잘못된 입력·무관한 대상/계정·없는 증거·다른 실행의 증거는 거절.
3. 임시 필수 단계가 미완료여도 원래 목표/작업 결과가 증명되면 완료 가능. HTTP 성공·요약·빈 후보만으로 목표나 취약점을 확인하지 않음.
4. 워커의 두 번 이상 자율 조사와 같은 정책 진입점, 호출/예산 계수, lease/중복, 승인 대기/재개, 중지/예산 종료 시 부분 결과 보존.
5. 해석기 없음·정상 빈 결과·해석/적용 실패·복구를 구분하고 원본 조회, 루트 후속 판단과 보고까지 전달. 같은 결과로 도구를 중복 호출하지 않음.
6. 민감 검색어는 외부 호출 없이 거절·안전하게 기록. 대상별 읽기/공격 제한은 표현 변경에도 유지. URL 경로/쿼리 변경과 미허가 redirect 목적지는 실행되지 않음.
7. 이번 변경의 구조 경계와 등록 기반 확장성을 확인하는 기존 정적 검사 및 변경 파일에 필요한 품질 검사.

실패하면 원인 수정→변경 영역 재리뷰→관련 검증을 반복한다. 기존 팀원 실행의 자료 부재와 실제 회귀 재현은 구분한다. 토큰·형식 수리·중복 실행 감소는 동일한 통제 사례에서 얻은 수치만 보고하고 실전 성능 향상을 미리 단정하지 않는다. 불필요한 전체 테스트·라이브 외부 공격은 수행하지 않는다.

## 7. 산출물과 완료 조건

이 계획과 `work-log.md`를 저장소에 포함하고, 연구 원본·개인 첨부와 기존 미추적 파일은 포함하지 않는다. 모든 필수 항목 구현, 실제 소비 경로 연결, 독립 리뷰의 필수 지적 해소, 필요한 최종 검증 통과를 모두 확인한 뒤 dev에 통합하고 푸시한다. 작업 종료나 일부 테스트 통과를 완료로 취급하지 않는다.
