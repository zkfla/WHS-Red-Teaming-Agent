### 리뷰 지적의 처리

1. **R1 대상 정합성 의미 — 대안으로 반영.** 현재 초안 쓰기는 인용의 존재·같은 실행/작전을 검사하며, 명시 대상은 노드 존재를 검사한다(`graph_recording.py:341`, `:691`). 원본이 그 대상을 입증하는 검사는 후속 확정용 검수기에도 있다(`analysis.py:694`). 이를 초안 등록의 새 필수 증명으로 이식하면 근거 없는 open 추론을 허용한다는 완화 목적을 훼손한다. 수정 계획은 초안의 대상 존재/신원과 추론 참조를 구분하고, 실제 원본 대상 증명은 발견/행동 확정 검수에 남긴다. 증거 없는 초안에 발견용 원본·영수증·새 대상 필드를 강제하지 않는다.

2. **R2 기존에 읽은 원본의 손실 — 반영.** 현재 판단 문맥에는 요청한 원본 윈도우가 복원된다(`engine.py:979`, `evidence_access.py:98`). 단계의 별도 원본 조회는 앞부분을 표시하고, 작업/목표 발췌는 2,000자·8개 상한이 있다(`engine.py:2652`, `semantic_completion.py:80`, `:453`). 전체 문맥을 삭제하면서 이미 조회한 관련 후반부 윈도우나 상한 밖의 검증 원본 ID까지 버리면, 원래 읽었던 근거를 검수기가 보지 못하는 실제 상황이 생긴다. 검수 응답 스키마는 판단 결과이며 별도 원본 조회 도구 호출 경로가 없다. 수정 계획은 해당 검증 원본의 조회 윈도우, 전체 검증 원본 ID와 증명된 작업 소유권을 전달하고 기존 발췌 상한은 내용 표시에만 적용한다. 운영자 범위/제약·지시와 실제 선행 상태도 보존한다. 새 캐시·영수증·옵션·검수용 도구를 만들 필요는 없다.

### 저장·재개·보고 소비 경계

- R1의 open 상태는 기존 가설 조회에서 추론으로 표시되고, 추가 관측 필요 안내에 소비된다(`knowledge.py:1101`). 근거 있는 확정/반박만 결론 입력에 포함하는 기존 경계를 유지한다(`knowledge.py:1754`). 실제 행동은 가설이 있으면 기존 검수 경로를 거치며(`nodes/verify.py:177`), 발견 제출도 원본·대상·영수증·승격 검사를 유지한다. 초안 저장만으로 기존 완료의 확정 가설/발견 요건을 충족하지 않는다.
- R2는 표시 요청만 축소한다. 저장 정본, 목적 무효화 의미, 경로 스냅샷 비교와 원자적 검수 토큰을 보존한다(`engine.py:1316`, `:1330`, `:1335`). 작업 영수증의 목적·원본 결합 및 목표의 필수 작업 원본 검증도 유지한다(`semantic_completion.py:620`, `:830`). 전체 문맥을 없애는 일을 전체 검증 집합 삭제와 혼동하면 안 된다.
- R3의 단계 미해결 저장 성공은 기존 `last_control_succeeded`와 `continue_planning` 경로를 유지한다(`engine.py:1922`, `:2027`). 작업/목표 미해결은 기존 `task_blocked`/`investigation_finished` 종료 의미와 미해결 기록을 사용한다(`engine.py:1939`, `:1967`, `semantic_completion.py:661`). 미완료 실행/승인 검사는 이미 적용되는 소비 경로에서 유지하며, 이번 완화로 새 실행 순서 강제나 추가 정산 조건을 만들지 않는다.
- 보고의 필수 범위 미해결/정리 의무/목표 기준 판정은 유지한다. 필수 범위 밖의 open 가설은 이미 deferred로 보고되고 그것만으로 배포 가능 상태를 막지 않는다(`reporting.py:567`). R1 이후 모든 초안을 필수 미해결로 새 분류하는 변경은 승인 범위에 없다.

### 부담 완화와 완료 판단

R1은 추론 등록 뒤 자동 모델 호출을 제거하고, R2는 의미별 검수 요청에서 무관한 판단 문맥을 덜어낸다. R3은 실제 추가 모델 호출이 없는 미해결 정산에 여유 요청 수를 요구하지 않으며, R4는 자연어 표현에 의존하는 중복 판정을 삭제한다. 이 네 변경은 새 상태·전역 캐시·영수증·옵션 없이 기존 담당과 공개 계약에서 수행할 수 있다.

필수 원본·권한·승인·임대·확정 의미 검수는 이번 완화 대상이 아니다. 기존 검사의 관련 회귀와 최종 소스의 양성/미해결 라이브에서 수용·저장·보고까지 확인해야 한다. 정적 리뷰, 자동 검사, 실제 모델 효과를 구분해서 결과를 보고한다. 라이브 429 시 account 1/2 전환은 사용자 승인된 검증 운용이며 제품 자동 순환 조건으로 추가하지 않는다. 최종 변경은 `dev-orchestration` 커밋·푸시까지만 하고 `dev`에 통합하지 않는다.
