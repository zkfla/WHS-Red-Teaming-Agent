## 목표와 범위

정상 판단에 요구하는 검증 부담을 줄이고 잘못된 확정은 막는다. ‘중간에 가까운 중상’은 정성적 목표이며 검사 수·거절 수·임의 개선율로 달성했다고 판단하지 않는다. 검증 코드·스키마·설명과 실행/실패/보정/재개/저장/보고 소비를 책임별로 조사한다. 관련 없는 전체 저장소, 후속 DB·컨트롤 플레인 개편, 피드백 전항목 구현은 범위 밖이다.

## 구현 단위와 의존성

### R1 — 잠정 가설은 모델 검수 없이 open으로 보존

- 소유: graph recording 담당. 공통 초안 필드와 기존 저장 구조를 재사용한다.
- standalone 가설을 등록할 때 자동 확정/반박 검수·영수증 호출을 제거한다. 같은 호출에 findings가 있다면 그 명시적 발견의 기존 검수는 유지한다.
- 기존 참조의 존재·실행·작전과 초안의 명시 대상 존재/신원은 검사한다. 이 연결은 추론의 참조이며 원본이 그 주장을 입증한다는 의미가 아니다. 실제 원본 대상 증명은 findings/행동 확정 검수에 유지한다. 새 대상 필수 조건을 추가하지 않는다. 근거가 없어도 표현 가능한 open 초안은 근거 없는 관측/발견으로 승격하지 않는다.
- 신규 확정 옵션/상태표/검수 캐시는 만들지 않는다. 실제 실행 검수와 명시 findings 경로가 후속 결론을 처리한다. 기존 확정 가설의 단순 재등록은 상태를 임의 초기화하지 않는다.
- 제품 스키마 설명·계약 문서·테스트 기대값을 이 의미로 맞춘다. 예전 standalone 자동확정 검사는 open 등록→명시 검수 경로로 재구성한다.

### R2 — 완료 검수 문맥을 목적에 맞게 줄임

- 단계: 자기 단계 목적/기준, 완료 제안과 실제 원본, 의존 단계 상태, 경로/작업/실행 신원·현재 버전, 대상/주체, 운영자 범위·제약만 제공한다.
- 작업/목표: 해당 목적과 원래 기준 및 검증된 원본·소유권을 제공한다. 불필요한 도구목록·기존 오류·전체 실행 이력·다른 미완료 계획을 제거한다. 목적이 다른 기존 모델 검수는 유지한다.
- 기존 문맥 담당/해당 검수 담당의 표시 함수를 사용한다. 정본 상태는 삭제하거나 잘라서 저장하지 않는다. 기존 허용된 원본 조회 방식과 마스킹을 보존한다.
- 검수에 별도 원본 조회 도구가 없다는 점을 반영한다. 이미 조회한 requested_evidence 중 해당 검증 원본의 윈도우는 보존하며, 원본 ID와 증명된 작업 소유권 전체를 제공한다. 기존 발췌 상한은 내용 표시만 제한하고 검증 집합을 자르지 않는다. 단계 검수에는 실제 선행 상태, 모든 검수에는 운영자 범위/제약·유효한 지시를 보존한다.
- 현재 작업이 이미 정산됐는지와 이후 판단 대상은 기존 정본 조회로 안내한다. 별도 자동 차단·행동 순서 강제를 만들지 않는다.
- 검수 문맥 크기는 같은 fixture/context에서 전후 비교하고 실제 모델 효과와 구분한다.
- 구현 중 확인한 소비 경계: 단계 제안이 최종 검수 영수증을 인용하면 기존 완료 검사에서 원본 ID로 확장되지만, 검수 입력은 영수증(no_raw)만 조회하던 부분이 있다. 기존 CompletionIssues 반환에 호출 내 검증된 원본 ID를 부가하여 같은 확장 결과를 검수 본문/관련 조회 윈도우에 사용한다. 별도 영수증·캐시·지문·저장 상태를 만들지 않으며 승인 결과가 통과할 때만 제공한다. 해당 델타는 구현 독립 리뷰에 포함한다.
- 소비 대조에서 확인한 두 조회 전달 누락도 포함한다. 같은 루트 판단 루프에서 방금 읽은 창은 현재 검수 문맥으로 복원하고, 전문 워커가 읽은 창은 완료 호출의 지역 문맥에 복원한다. 같은 원본의 앞·뒤 또는 서로 다른 검색 창을 원본 번호만으로 중복 제거하지 않는다. 기존 조회 복원·마스킹을 재사용하고 루트 정본이나 다른 워커 문맥은 변경하지 않는다.

### R3 — 미해결 정산에는 추가 모델 검수 예산을 요구하지 않음

- 소유: 실행기의 기존 완료 분기.
- 구조화 완료 제안의 inconclusive/blocked를 확인한 경우 추가 `_ask`를 위한 permits 선검사를 적용하지 않는다. 기존 출처 검사·미해결 저장·원자적 상태 전이·미완료 실행/승인 검사는 유지한다.
- success/refuted의 실제 모델 검수는 기존 정상 예산·시간 가드를 지킨다. 새 예산 레인이나 한도 증가는 없다.
- 마지막 정상 판단이 유효한 미해결 제안을 했을 때, 보정 횟수만 남았거나 총 요청 한도가 끝난 경우 정산을 검사한다. 허위/다른 실행의 참조는 여전히 거절한다.
- 자동 재현에서 목표 미해결 상태 저장이 기존 임무 버전 증가를 누락하여 거절되는 제품 결함을 확인했다. 미해결 목표를 원자적으로 정산할 때 현재 버전을 한 번 증가시키는 기존 저장 계약을 준수하도록 좁게 수정한다. 새로운 판정 조건이나 저장 체계는 추가하지 않는다.

### R4 — 후보 없음 문구 기반 중복 판정 제거

- 소유: 완료 계약 담당.
- 표현 목록과 그 별도 조건을 제거한다. 기존 증거 없음·출처 불일치·기준 불충족 진단으로 거절한다.
- 같은 상태에서 이유 문구가 달라도 결과가 같고 유효한 원본 없이 성공할 수 없음을 확인한다.

R1은 기록 담당, R2의 단계/실행 문맥과 R3은 한 워커(공유 engine), R4는 완료 계약 담당으로 나눈다. 작업/목표의 문맥 R2는 semantic_completion 담당이 맡되 공통 표시 계약은 루트가 조정한다. 승인·임대·원본 검증 자체는 완화하지 않는다.

## 리뷰·검증·완료

- 계획 독립 리뷰 후 구현한다. 지적을 반영/대안/기각/후속으로 결정한다. 구현 후 독립 의미 리뷰와 통합 소비 검토를 수행한다.
- 기존 자동 검사를 우선 사용하며 open 가설의 무검수 등록/명시 발견 검수, 범위를 좁힌 검수의 제약 보존, 마지막 턴의 미해결 수용/허위 참조 거절, 표현 독립성의 회귀만 보완한다.
- 같은 최종 소스에서 CI 필수 Python 3.10/3.14 pytest·Ruff·mypy와 변경 영향 검사를 수행한다. 관련 없는 smoke를 반복하지 않는다.
- 신규 live batch에 원본을 보존하고 작은 양성 관측 목표와 의도된 미해결 목표를 반복 확인한다. 같은 최종 소스·각 사례의 동일 목표/범위/예산을 유지하고 계정 전환은 별도 기록한다. 기존 하네스의 관측·보고 연결을 재사용하며 제품에 테스트 시나리오 분기를 넣지 않는다.
- 실제 MCP→보존 원본 조회→공통 기록 수용→후속 판단→근거 있는 정산→정본/렌더 JSON·Markdown을 대조한다. 양성은 목표 달성을, 음성은 미해결 의미와 미확정을 확인한다. 종료·파일 개수로 통과하지 않는다.
- 자동에서 줄어든 모델 호출/문맥과 라이브 실측을 구분해 보고한다. 두 계정 모두 외부 제한으로 막히면 가능한 작업을 완료하고 목표는 완료로 선언하지 않는다.
- 사용자 기존 미추적 자료는 보존한다. 최종 dev-orchestration 커밋·푸시만 수행하고 dev는 변경하지 않는다.

## 구현 중 확인한 범위 보완과 현재 상태

R2에서 도구 원본만 남기면, 같은 원본을 실제 사실로 등록하기 전과 후를 검수자가 구분할 수 없었다. 검수 직전에 기존 공개 지식 조회와 해당 실행/전문 작업자의 내부 호출 결과 조회를 재사용한다. 검증된 원본에 연결된 등록 사실과 항목별 출처, 부분 수용·거절 결과만 전달하며 기존 생략·조회 진단을 보존한다. 조회 목록에 없는 사실을 부재로 확정하지 않도록 설명한다. 새 승인 조건·저장 상태·모델 호출은 추가하지 않는다. 해당 소비 보완은 독립 리뷰 승인과 실제 등록 턴→완료 턴 회귀를 거쳤다.

상태: R1~R4 구현과 독립 계획·제품 의미 리뷰를 마쳤다. 최신 관련 자동 검사 94개, 최종 Python 3.10/3.14 각각 2887 passed / 52 skipped, 두 버전 mypy 582 files / no issues, 전체 Ruff와 compose 구성이 통과했다. 이전 전체 검사의 공유 테스트 대역 및 후속으로 발견한 금융 실행 예제의 옛 검수 입력 소비를 공개 원본 목록에 정렬하고 독립 승인했다. 같은 최신 제품 소스의 양성·미해결 사례를 각각 두 번 실제 모델/MCP로 확인하고 원본·기록·정산·JSON/Markdown을 대조했다. 금융 Agent 승인/도구/그래프 흐름과 다섯 MCP smoke도 통과했다. 이전 소스의 라이브 성공과 전체 결과는 합산하지 않았다. 구체적 범위·효과·남은 한계 및 정본 로그는 final-validation.md에 기록한다. 최종 결과의 전달 대상은 dev-orchestration 커밋·푸시이며 dev 통합은 하지 않는다.
