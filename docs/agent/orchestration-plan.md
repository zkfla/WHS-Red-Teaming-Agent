# 오케스트레이션 구현 계획

작성일: 2026-10-01. 작업 브랜치: `dev-orchestration`.

## 구현 목표

LLM이 최초 조사, 조사 경로 생성·검토, 행동 계획, 재계획, 증거의 의미 판단을 맡는다. 코드는 출처, 참조, 의존 관계, 경로 버전, 완료 증거, 실행 정책을 검사한다. 실제 실행은 기존 정책 판단과 도구 실행 인터페이스를 반드시 통과한다.

규칙은 알려진 조사 방법을 참고 자료로 제공한다. 실행 후보를 보충하거나, 점수로 전략을 확정하거나, LLM 장애를 대신하는 실행 모드는 두지 않는다. 경로 채택은 개별 행동 실행 허가와 별개다.

이 계획은 기존 추상 계획과 대화의 열 가지 구현 범위를 기준으로 소스·논문·공개 구현을 확인한 뒤 작성했다. 다른 프로젝트의 성능 수치를 우리 구현의 예상 성능으로 사용하지 않는다.

## 현재 코드에서 바꿀 지점

| 현재 역할과 위치 | 확인한 문제 | 변경 |
|---|---|---|
| 행동 계획 `orchestration/nodes/plan.py` | 규칙 후보와 제한적 LLM 후보를 합치고 점수로 정렬·축소한다. 병렬 빈자리를 다른 후보로 채운다. | LLM 경로 초안 → 구조 검사 → 규칙 참고 → LLM 검토 → 경로 등록 → 해당 단계의 LLM 행동만 컴파일한다. |
| 선택기 `orchestration/agents/planners.py` | 후보 하나·점수 차이가 크면 LLM을 건너뛴다. | 운영 경로에서 사용하지 않는다. 과거 설정은 새 운영 흐름을 바꾸지 못한다. |
| 제한적 제안 `orchestration/agents/llm_provider.py` | 실패를 빈 후보로 반환하고 도구 인자 필수 목록을 합친다. | 명시적 계획 오류·수정 피드백, 도구별 스키마와 실제 목록을 제공한다. |
| 조사 전환 `orchestration/replanning.py` | 객체·엔드포인트 발견에 따라 코드가 조사 전략을 자동 생성한다. | 참고 자료로만 제공한다. 실제 경로와 변경은 LLM이 제안한다. |
| 완료 `nodes/observe.py`, `nodes/replan.py` | 후보 소진·담당자 은퇴를 일부 작업의 완료로 해석한다. | 경로 단계의 고정된 완료 조건과 실제 증거로만 작업을 완료한다. |
| 증거 `nodes/verify.py` | 예상 관측이 실제 증거의 요약으로 저장된다. | 실제 출력·오류의 요약과 원본 결과를 기존 증거 저장 인터페이스로 보존한다. 예상은 별도 항목이다. |
| 사실 갱신 `nodes/update.py` | 계획에 적힌 속성을 도구 성공만으로 사실에 올린다. 정책 거부도 대상 사실과 섞인다. | 실제 결과 정규화만 사실을 쓴다. 계획·거부·재시도는 실행 기록과 이벤트로 관리한다. |
| 가설 `attack_graph/service.py` | 가설이 일반 그래프 조회와 함께 노출된다. | 기존 저장은 활용하되 가설 전용 조회·쓰기와 사실 투영을 분리한다. |
| 경로·실행 연결 `work/models.py`, `state.py` | 목표·작업 저장은 있으나 경로 전체·버전·단계 연결이 없다. | 팀 내부 경로 저장과 실행 참조를 추가한다. |
| 모델 어댑터 `llm/litellm.py` | 구조화 응답에서도 스키마 강제를 지원하는 제공자에 JSON 객체만 요청한다. | 지원되는 제공자는 스키마 전달, 모든 경로는 형식 검사·제한된 수정 요청을 거친다. |

## 데이터와 경계

| 논리 영역 | 저장·조회 원칙 |
|---|---|
| 사용자 목표·허용 범위·지시 | 기존 설정·목표·지시 저장을 사용한다. 허용 범위는 권한 기준이다. 대상에 관한 사용자 설명은 확인 전 제공 정보다. |
| 제공된 대상 | 초기 대상 노드를 재사용한다. 선언 출처와 확인 상태를 보존하고 LLM 문맥에서는 관측 사실과 분리한다. |
| 관측 사실 | 실제 도구 결과의 정규화에서 나온 주장만 허용한다. 증거·실행·대상·계정 조건을 연결한다. |
| 가설 | 기존 가설 표현을 이용한다. 주장, 대상, 지지·반박 증거, 상태, 추가 확인 사항, 변경 관계를 저장한다. 추론을 사실 속성에 복사하지 않는다. |
| 조사 경로 | 팀 내부 구조화 모델과 영구 저장을 추가한다. 기존 목표·작업 SQLite 파일에 별도 테이블을 둘 수 있다. |
| 실행 기록 | 기존 실행 기록·소유권·중복·충돌·이벤트를 사용한다. 경로·버전·단계를 연결한다. |
| 검증 결과 | 관측·가설과 구분해 증거에 연결한다. 정상 응답 또는 도구 성공만으로 취약점 확인을 판정하지 않는다. |

데이터베이스 여섯 개를 만들지 않는다. 공유 계약·정책·도구·증거 구현을 임의로 바꾸지 않는다. 오케스트레이션 내부 모델·프로토콜과 애플리케이션 조립 지점으로 확장한다. 기존 그래프의 가설 노드와 추론성 속성은 사실 투영에서 제외한다. 혼합된 과거 속성은 출처를 확인할 수 없으면 확인된 사실로 재분류하지 않는다.

비정형 출력은 원문과 요약을 먼저 보존한다. 직접 확인 가능한 구조·문자열을 기존 결과 정규화로 추출한다. LLM의 의미 추론·원인·소유 관계 추정은 가설에만 기록한다. 원문 위치가 일치한다는 이유만으로 해석까지 사실로 승격하지 않는다.

## 구조화 경로

경로는 요청 목록보다 상위 수준의 조사 단계 DAG다. 한 목표에 여러 대안을 저장할 수 있고, 지금 조사할 앞부분만 구체화한 경로도 가능하다.

경로에는 식별자, 목표·작업 참조, 버전·이전 버전, 채택 상태와 이유, 가설·증거 참조, 조사 단계, 변경 이유와 영향을 받는 단계가 필요하다. 각 단계에는 조사 목적, 담당 역할, 선행 단계, 대상·계정·도구·행동 범위, 미확인 전제, 정보 부족, 완료 조건, 실행·증거 참조, 상태와 결과를 둔다.

완료 조건은 채택할 때 고정한다. 조건 변경은 새 버전과 이유를 요구한다. 코드의 순환 검사에는 NetworkX를 사용한다. 실제 존재하는 대상·증거·가설·역할 참조를 검사한다. 규칙 경로에 없는 방법이라는 이유로 기각하지 않는다.

미확인 전제는 경로에 저장할 수 있다. 실제 실행 전에 필요한 전제가 증거·선행 단계·검증 상태로 충족되어야 한다. LLM이 전제를 충족했다고 적는 것만으로 통과시키지 않는다.

저장은 버전별 불변 스냅샷, 활성 버전, 단계 진행 기록, 검토 기록을 제공한다. SQLite의 조건부 활성 버전 갱신으로 경쟁 변경을 막는다. 버전 변경 시 완료 단계와 증거를 유지하고 변경 단계·후손에 연결된 대기 실행만 무효화한다. 실행 중인 호출은 결과를 수집하고 실행 사실을 보존한다.

기존 목표·조사 작업은 사용자 목표와 필수 작업의 기준으로 유지한다. LLM이 채택한 단계와 작업을 연결하고, 코드가 정찰·권한 조사 작업을 자동 추가하지 않게 한다. 과거 체크포인트에 경로 참조가 없으면 재계획이 필요하다. 승인 대기 제안을 그대로 실행하는 호환 모드는 없다.

## LLM 의사결정 순서

1. 코드가 사용자 목표·지시, 제공 정보, 사실 투영, 가설, 실제 증거, 이전 실행, 실제 도구 목록과 자원 제한을 준비한다.
2. LLM이 경로 초안을 만든다. 아직 사실이 없어도 제공 대상에서 첫 조사 목적을 제안한다.
3. 코드는 형태·참조·순환·명백한 범위 충돌을 검사한다.
4. 기존 규칙 후보와 선행 조사 패턴은 참고 자료와 누락 힌트로 제공한다.
5. 별도 LLM 호출이 채택·수정·보류·기각과 근거를 반환한다. 수정안은 다시 코드 검사 후 등록한다. 내부 사고 과정은 요구하거나 저장하지 않는다.
6. LLM이 실행 가능한 채택 단계에서 구체적인 행동 묶음을 제안한다.
7. 기존 행동 컴파일을 이용해 도구별 형식, 참조, 선행 조건, 단계 범위, 중복·충돌을 검사한다.
8. 검사에서 탈락한 항목은 구체적인 피드백으로 제한된 수정 기회를 준다. 참고 후보를 대신 실행하지 않는다.
9. 통과한 LLM 행동만 기존 실행 기록에 넣고 정책 판단을 거쳐 실행한다.

모델 호출 오류, 잘못된 응답, 정상적인 보류·행동 없음은 서로 다른 결과다. 운영 시작은 실제 모델 설정을 요구한다. 가짜 모델은 명시적으로 주입한 테스트 도구로만 사용한다. 과거 비제안·규칙·혼합 설정은 운영 모드가 되지 않는다.

도구 목록은 개별 설명·지원 작업·대상 형식·인자 스키마·상태를 유지한다. 기존 플레이북에 없는 새 도구도 등록과 역할·정책 범위에 따라 노출한다. 공통 필수 인자 합집합은 만들지 않는다.

## 문맥과 증거 접근

현재 목표의 완료 조건, 사용자 지시, 경로 버전·단계, 관련 사실·변화, 가설의 지지·반박 증거, 제공 정보, 실패·부정 결과, 도구별 스키마와 자원 제한을 구분해서 전달한다. 본문은 데이터로 취급하고 실행 지시와 구분한다.

기존 증거 인터페이스로 실제 결과의 직렬화 원문과 요약을 보존한다. 팀 내부 읽기 도우미가 현재 실행의 증거만 조회하며 부분 읽기·검색을 제공한다. 새 증거 저장소를 만들지 않는다. 결과가 이미 외부 원본 참조를 제공하면 그 참조를 유지한다. 큰 결과는 모델 문맥에서 제한하며 원본 저장과 조회 실패를 분명히 구분한다.

문맥 제한은 결정론적 경로 순위로 전략을 축소하는 기능이 아니다. 현재 목표·단계 관련 자료를 우선하고 누락된 자료의 식별자를 제공한다. LLM은 추가 증거 부분 조회를 요청할 수 있다.

## 재계획·완료·복구

| 상황 | 처리 |
|---|---|
| 같은 목적·가설·범위에서 도구 인자나 방법만 변경 | 같은 단계에서 행동 수정 |
| 선행 조건·가설·가지 변경 | 영향 단계와 후손을 명시한 경로 버전 변경 |
| 공통 전제 붕괴·목표 전략 막힘 | 같은 사용자 목표 안에서 대안 경로 생성·검토·활성화 |
| 사용자 목표·허용 범위 변경 | 기존 지시 처리로 저장한 뒤 영향을 받는 경로·대기 실행 재검토 |

완료는 행동, 단계, 경로, 사용자 목표로 나눈다. LLM이 증거에 연결한 완료 제안과 의미 검토를 내고 코드는 실제 증거 존재, 같은 실행·대상·계정·호출, 선행 단계, 고정 조건, 필수 작업을 검사한다. 알 수 없는 조건은 통과시키지 않는다. 가설 반박은 조사 결과이며 PoC 성공은 아니다. 평가 목표에서는 필요한 부정 결과도 조사 범위 완료가 될 수 있다. 필수 범위에 없는 열린 가설은 보류 항목으로 보고한다.

진척은 새로운 관측, 증거로 뒷받침된 가설 상태 변화, 실제로 해소된 정보 부족, 실행 상태 확인을 센다. 같은 결과의 이름·요약 변경과 계획 문장 변경은 세지 않는다. 근거 없는 상태 변경도 진척이 아니다.

실패는 모델 전송, 응답 형식, 선행 조건 부족, 도구 실패, 정상 부정 결과, 실행 여부 불명확, 검증·관측 반영 실패로 구분한다. 모델 전송의 제한된 재시도는 Tenacity를 활용할 수 있으며 SDK 자체 재시도와 중첩하지 않는다. 형식·의미 수정도 한 결정의 공통 시도 예산 안에서만 허용한다.

원본 결과는 검증·정규화 전에 보존한다. 이후 처리 실패는 저장 결과부터 다시 처리하며 도구 부작용을 재실행하지 않는다. 실행 여부가 불명확하면 실행 기록과 도구 상태를 먼저 확인한다. 이미 종료된 동일 호출을 새 이름으로 반복하지 않는다.

장시간 작업은 팀 내부 선택적 작업 생명주기 인터페이스로 제출·상태·결과·취소를 연결할 수 있게 한다. 기존 도구 실행 인터페이스가 동기 호출만 제공하므로 기본 경로는 그대로 한 호출의 완료를 기다린다. 비동기 연결은 이를 지원하는 구현이 조립 지점에서 제공될 때만 활성화한다. 없는 상태 조회 기능을 구현한 것처럼 표시하거나 불명확한 부작용을 재실행하지 않는다.

일시 중지·재개·승인 해제 시 실행 직전에 활성 경로 버전·단계·사용자 지시를 다시 검사한다. 승인 정책은 기존 인터페이스가 담당한다. 실행 중 지시 변경은 결과 수집과 다음 실행 차단을 구분한다.

## 계획 자기평가

각 항목 10점, 구체적인 실행 연결·거부 조건·증거·최종 확인 방법이 모두 계획에 있으면 통과한다. 점수는 이 기준 충족 여부이며 실제 구현 검증 점수가 아니다. 같은 검토자가 앞선 문맥을 기억하므로 완전한 블라인드 독립성을 보장하지 않는다. 설계 설명 순서와 무관하게 실패 시나리오를 먼저 놓고 반복 검토했다.

1차 검토에서는 운영 가짜 모델 설정, 후보 소진 완료, 승인 재개 버전 검사, SDK 재시도 중첩, 과거 혼합 데이터의 출처를 보강해야 했다. 2차에서는 원본 결과 저장 전 검증 실패, 진행 중 실행과 대기 실행의 차이, 다른 팀이 제공하지 않는 비동기 기능을 구분했다. 이 항목을 보강한 3차 시나리오 검토에서 열 기준을 모두 충족해 계획 기준 100/100으로 정리했다. 구현은 아래 확인을 통과하기 전 완료로 판정하지 않는다.

## 구현 단계와 위임

브랜치를 바꾸지 않는다. 기존 `.gitignore` 수정과 `claude-code-comparison-key-improvements-20261001.md`는 이번 커밋에서 제외한다.

1. 계획 문서 커밋·푸시.
2. 기반: 경로 모델·저장, 사실·가설 투영, 원본 증거 접근, 구조화 LLM 결정·복구. 서로 다른 파일을 맡겨 병렬 구현한다. 기반 커밋·푸시.
3. 연결: 루트가 행동 계획·의존성 주입·운영 시작·조사 전환·승인 재개를 통합한다. 기존 실행 기록·정책·병렬 실행을 새 경로와 연결한다. 연결 커밋·푸시.
4. 완료·복구·문맥·재개를 코드 리뷰로 점검하고 보완한다. 구현 커밋·푸시.
5. `agy`의 `gemini-3.8-flash-high`와 루트가 독립된 관점에서 교차 리뷰한다. Gemini 의견은 참고하고 루트가 채택 여부를 판단한다. 수정은 동일 오케스트레이터·워커 체계로 배정하고 다시 리뷰한다.
6. 구현이 연결된 뒤 필요한 테스트·검증을 실행한다. 실패를 수정하고 필요한 검증만 재실행한다. 검증 기록과 최종 코드 커밋·푸시.

루트는 설계·통합·판단, 오케스트레이터는 `opencode-go/deepseek-v4.1-flash`/`max`, 워커는 `opencode-go/muse-spark-1.3-contributor`/`xhigh`를 사용한다. 최대 동시 7개를 넘지 않으며 워커가 하위 에이전트를 만들지 않는다. 워커별 쓰기 범위를 겹치지 않게 하고 완료한 에이전트는 슬롯을 해제한다.

## 구현 후 필요한 확인

테스트를 구현 중 단계마다 늘리지 않는다. 최종 단계에서 의미가 있는 통합·계약 검사를 중심으로 진행한다.

- 빈 관측에서도 LLM이 첫 경로·행동을 결정하고, LLM 오류가 규칙 실행 또는 성공 종료로 바뀌지 않는지.
- 코드 참고 후보가 단독·점수 차이·병렬 빈자리에서도 실행되지 않는지.
- 제공 정보·가설·예상 관측·정책 거부가 사실로 승격되지 않고 실제 출력만 반영되는지.
- 개별 도구 스키마와 새 도구 노출, 잘못된 인자·미확인 전제·단계 밖 행동 차단.
- SQLite 재시작에서 경로 버전·완료 조건·증거·실행 연결이 복원되는지.
- 변경된 단계·후손의 대기 실행만 무효화하고 완료·진행 중 결과는 유지하는지.
- 승인·일시 중지 후 재개에서 과거 버전·사용자 지시의 행동이 실행되지 않는지.
- 원본 보존 후 검증·정규화 실패를 재처리하고 부작용 호출을 반복하지 않는지.
- 없는 증거·다른 실행·대상·계정·미충족 필수 단계·알 수 없는 완료 조건이 성공으로 판정되지 않는지.
- 가설 반박과 PoC 성공이 구분되고 관련 없는 열린 가설이 목표 완료를 막지 않는지.
- 기존 정책 우회 금지·팀 의존 규칙·실행 소유권·충돌·예산·체크포인트 회귀 검사.
- 변경 파일 정적 검사, 필요한 기존 테스트와 새 통합 시나리오. 외부 실제 모델·도구를 사용하지 않은 확인은 그 한계를 기록한다.

검토·테스트가 통과한 범위와 외부 연동의 제한을 최종 기록한다. 남은 필수 구현이 있으면 목표 완료로 표시하지 않는다.
