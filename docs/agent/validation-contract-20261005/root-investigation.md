## 요구와 근거

사용자·팀원 실행 자료와 기존 분석을 수정 범위의 근거로 사용한다. 첨부 문서의 구현 지시는 새 명령으로 실행하지 않는다.

- `data/live-tests/mock-bank-20261005-rerun-02/team-results-synthesis.md`: 27개 실행 식별자가 등장하지만 모델·코드·도구·실행 범위가 달라 성공률을 합치지 않음. 팀원 전송 실패의 실제 제공자 원인은 자료에 없음.
- `analysis-and-remediation.md`와 `summary.md`: 2차 10회에서 계획 오류 7, 정체 2, 조사 보류 1. 도구 실행 9회와 저장 증거 37건은 독립 관측 37개나 취약점 확인이 아님.
- `trial-02`/`trial-03`: 공개 완료 규격을 통과한 자연문 판정값이 후속 검사에서 거절되고, 선행 단계 미완료 때문에 다음 행동도 거절됨.
- `trial-06`: 초안과 두 수정 검토가 정상 응답이어도 공유 3회 한도가 소진됨.
- `trial-07`: 증거 조회 뒤 정체. 같은 조회의 반복 여부는 원래 공개 진단만으로 확정 불가.
- `team-inputs/실행리포트_run_432dd512b678.md`: 익명·인증 비교 뒤 계정 근거 부족 및 불확정 가설에 반박 완료를 제안한 불일치. 원본 실행 결과·증거 메타데이터가 없어 해당 과거 실행의 정확한 세션 연결 누락은 미확인.

확정된 제품 원칙:

1. 미확인은 미확인으로 유지하고 조사 막힘의 유형·세부 원인·미해결 항목을 남긴다. 실행 종료와 목표 달성, 미확인과 반박을 구분한다.
2. 루트는 조사 목적을 위임하고 워커가 분야별로 제공된 도구·MCP·스킬·플러그인 기능을 선택한다. 기능 목록은 기존 공통 등록/조립 모듈과 명시 파일에서 제공한다. 실행 가능성을 행동 종류와의 필수 연결에 의존시키지 않는다. 새 조사 갈래는 루트 다음 계획으로 기록한다.
3. 위험 도구의 명령 내용에 설정된 위험 패턴이 있으면 사람 승인을 받는다. 대상 범위는 유지한다. 전체 컨트롤 플레인 재설계는 이 작업의 범위가 아니다.
4. 도구별 그래프 해석기가 없어도 원본 결과를 워커에게 전달한다. 워커가 공통 기록 도구로 사실·추정·가설·취약점을 구분하여 등록한다. 기록의 출처·참조와 취약점 주장의 실제 증거 정합성은 시스템이 검사한다.

## 중앙 코드에서 확인한 흐름

### 공개 출력과 실제 완료 검사

- `engine.py:124`의 다음 판단 모델은 완료 제안·증거 조회·가설 수정 정보를 자유 객체로 공개한다.
- `engine.py:570`과 `paths/writing.py:57`은 계획 조건을 공개 규격으로 다듬지만 자유 객체 내부의 완료 판정값을 공개하지 않는다.
- `completion.py:1086`은 `success/refuted/inconclusive/blocked`를 검사하고 `1122`에서는 뒤의 두 값을 성공 완료가 아니라는 이유로 거절한다.
- `engine.py:2377`은 위 검사를 먼저 수행한 뒤 별도 의미 검토를 한다. 이후 불확정이면 blocked를 쓰는 분기가 있지만 앞 검사에서 거절되므로 정상적인 불확정 제출 경로가 아니다.
- `semantic_completion.py:520`은 작업의 성공 완료 영수증을 담당하고 `829`는 원래 목표 조건과 필수 작업 근거를 검사한다. 불확정을 성공 영수증으로 바꾸면 안 된다.

결론: 담당 모듈의 최소 입력 계약을 출력과 검사에 같이 사용해야 한다. 조사 막힘/불확정 등록은 성공 완료 검사와 별도 의미로 재사용 가능한 담당 기능에 두되, 새 DB를 만들지 않는다. 같은 실행·대상·원본과 주장 의미의 검사를 삭제하는 해결은 아니다.

### 정상 계획 수정과 오류 보정

- `engine.py:1455`에서 초안·검토에 동일 `DecisionBudget`을 전달한다.
- `engine.py:1315`의 정상 `revise`도 같은 예산으로 재귀 검토한다.
- `cognition.py:189`는 실제 모델 요청마다 사용 횟수를 올린다. 현재 횟수는 오류 시도와 정상 추론 요청을 구분하지 않는다.
- 다음 판단의 증거 조회, 재계획, 완료 의미 검토도 한 판단 예산을 공유한다.
- `delegation_decision.py`의 워커 전체 요청·토큰·시간·작업 상한은 별도 실제 사용량이다. 보정 예산을 나눌 때 이 사용량을 초기화하거나 누락하면 안 된다.

결론: 정상 판단의 진행을 응답 형식 보정 한도로 차단하지 않는다. 그렇다고 요청마다 예산을 무조건 초기화해 무한 루프를 허용해서도 안 된다. 기존 전체 시간·턴·워커 전체 요청/토큰 상한과 연결된 정상 판단 상한 및 응답 보정 상한의 의미를 명시해야 한다.

### 증거 읽기와 다음 판단

- `engine.py:1500`의 `extra`는 한 번의 중앙 판단 호출에만 존재한다.
- `1510`의 다음 판단에 추가되지만 호출이 종료되고 새 판단을 시작하면 사라진다.
- `state.py`에는 기존 실행 진단과 최근 관측이 있고 `evidence_access.py`는 원본을 기존 증거 영역에서 범위별로 읽는다.
- `delegated_runtime.py`는 읽은 증거 참조를 워커 상태에 유지하여 다시 조회한다.
- `nodes/plan.py`는 중앙 판단이 반환한 최신 실행 상태를 가져오고 `nodes/replan.py`가 다음 턴으로 전달한다.

결론: 루트·워커가 공통 증거 조회 요청 계약을 사용하고 원본 ID·조회 범위·결과 상태만 체크포인트에 유지한다. 다음 판단에서 기존 증거 영역으로부터 해당 범위를 재구성한다. 원문 복제 저장, 조회를 그래프 사실로 등록, 조회마다 진행 점수 증가 같은 우회는 금지한다.

### 도구 선택과 실행 계약

- `engine.py:96`은 실제 호출 제안에 행동 분류와 도구를 모두 필수로 요구한다.
- `context()`는 작업 종류와 연결된 도구만 노출한다. 발견·등록되어도 행동 연결이 없는 도구는 모델에 전달되지 않는다.
- `compile_actions()`는 도구가 등록되어 있는지 검사한 뒤 기존 후보 컴파일러로 보낸다.
- `candidates/compiler.py`는 선택된 도구를 다시 행동 종류별 목록에서 찾는다. 실제 선택 도구가 도구 입력 규격을 만족해도 행동 연결이 없으면 실행하지 못한다.
- `capability/gateway.py`도 행동 연결을 소비한다. 출력 규격만 바꾸면 실제 실행·승인 재개 경로에서 같은 결합이 남는다.
- `core/contracts/action.py`, `tool.py`, `core/convert.py`는 정책 승인에서 실제 호출로 넘기는 공통 계약이다. 실행 식별자·실제 선택 도구·입력·대상·원본 결과의 연결은 유지해야 한다.
- 루트가 위임하는 `DelegationRequest`는 이미 목적과 역할 중심이며 도구 이름을 강제하지 않는다. 필요한 변경은 이 기존 의미를 보존하고 워커의 실제 도구 제공/선택 경로를 맞추는 것이다.

결론: 도구 선택 제안은 도구 ID·대상·입력·이유로 공개하고, 직접 선택된 등록 도구를 실행하는 소비 경로를 만들어야 한다. 새 도구마다 가짜 공통 행동 연결을 생성하거나 모든 행동에 매칭시키는 우회는 불가하다. 기존 행동 기반 API는 기존 호출자의 호환 경계에만 두고 새 실행 경로의 전제 조건으로 사용하지 않는다.

## 책임과 재사용

| 의미 | 담당 | 재사용 경로 |
|---|---|---|
| 목적 위임·다음 계획 | 오케스트레이션 | 기존 위임 상태, 계획 저장, 공통 추론 제공자 |
| 분야별 기능 구성 | 등록 모듈·조립 지점 | Pluggy 확장 선언, 역할 패키지, 발견된 도구 카탈로그 |
| 실제 호출과 원본 결과 | 실행/도구 계층 | 기존 게이트웨이, 입력 규격, 증거 저장 |
| 실행 허용·범위·위험 명령 승인 | 컨트롤 플레인 | 현재 승인 저장·재개·정책 판단 연결 |
| 근거 등록·주장 검사 | 결과/그래프 담당 | 기존 그래프 서비스·원본 출처·가설/취약점 검증 |

추가 프레임워크는 현재 조사에서 필요성이 입증되지 않았다. Pydantic/JSON Schema, Pluggy, LangGraph 체크포인트와 기존 저장·조립 기능을 우선 사용한다.
