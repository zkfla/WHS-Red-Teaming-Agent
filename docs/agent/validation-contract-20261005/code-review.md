# 독립 전체 코드리뷰

검토 기준: `5bf746844c8fc0c9db4d322e24b10729ee0e3ad8` → `b38fa6ef02274d10598f5de1164f9c6c66abfc10`.

현재 작업 트리의 제품 소스를 기준으로 입력·조립·정책·실행·원본 저장·검수·그래프 기록·완료·재개·보고 경로를 대조했다. 비교 범위는 90개 파일이며, 선행 CLI 변경과 동반 테스트 변경도 읽었다. 확정 구현 계획, 이전 계획 리뷰, 원본 실패 분석 및 구현 진행 기록은 요구사항과 검토 배경으로 사용했다. 과거 계획이나 워커의 완료 보고를 현재 구현 사실로 대신하지 않았다.

**판정: 필수 수정 사항이 남아 있다. P1 7건, P2 5건이다.** 특히 사람 승인 누락과 반박된 주장으로 취약점이 등록되는 경로를 먼저 고쳐야 한다. 아래 항목은 소스에서 확인한 분기와 계약 불일치다. 실제 서비스에서 발생했다고 주장하는 재현 보고가 아니다.

이 리뷰에서는 제품 수정, 테스트 실행, 실제 LLM/MCP 호출, 커밋, 푸시를 수행하지 않았다. 작성한 파일은 이 문서뿐이다. 루트가 보고한 AST 문법 분석과 공백 검사도 기능 검증으로 취급하지 않았다. 검토 도중 다른 작업자가 진행 기록을 변경한 것은 제품 스냅샷 변경과 구분했다.

## CR01 — 일반 승인 판정의 조기 반환이 사람 승인 필수 판정을 가린다

**근거:** `src/redteam/control/policy.py:308-319,335-345,362-397`; `src/redteam/control/service.py:393-403`.

정책을 판단하는 구성요소는 기존 기능/행동 승인 규칙이나 제공자 선언 승인 규칙이 맞으면 즉시 반환한다. 위험 명령 규칙은 그 뒤에 검사한다. 자동 승인을 처리하는 구성요소는 판정 근거에 `command:` 또는 `policy_semantics_unavailable`이 있어야 사람 승인을 강제한다.

**실제 실패 조건:** 선택 도구에 정상 명령 필드 선언이 있고 입력이 위험패턴과 일치한다. 동시에 그 도구의 제공자 선언이 기존 승인 목록에 포함되고, 자동 승인 상한이 해당 위험도를 포함한다. 앞의 일반 승인 판정만 반환하므로 위험패턴 표식이 생기지 않으며 사람이 승인하지 않아도 허용된다. 명시적 승인 규칙을 추가했는데 사람 승인 필수 의미가 사라지는 조합이다.

**수정 방향:** 정책 담당에서 동시에 적용되는 승인 근거를 합치거나, 일반 승인 반환 전에 위험 명령의 사람 필수 의미를 계산해야 한다. 오케스트레이션에 특정 명령 도구 예외를 넣을 이유는 없다. 기존 외부 전송 금지의 거부 의미는 유지한다.

## CR02 — 내장 명령 실행 제공자의 명령 필드 선언이 빠졌다

**근거:** `src/redteam/core/contracts/tool.py:59-60`; `src/redteam/capability/adapters/mcp/streamable_http.py:119-135`; `src/redteam/capability/servers/execution.py:1143-1158`; `src/redteam/control/policy.py:380-391`. 인접한 `execution_manifest.py`, 명령 실행 어댑터 및 상위 분석 어댑터에도 명령 필드를 채우는 경로가 없다.

새 검사 계약의 기본값은 빈 목록이다. 원격 제공자 메타데이터를 읽는 경로는 생겼지만 내장 명령 서버의 등록에는 그 선언이 없고, 명령 실행 어댑터에서도 보충하지 않는다. 정책 담당은 선언이 `None`일 때만 의미 미확인으로 처리한다. 빈 목록은 정상 선언으로 지나가며 검사 후보가 하나도 만들어지지 않는다.

**실제 실패 조건:** 내장 명령 도구를 선택하고, 운영자가 명령 승인 규칙에 허용된 실행 파일 이름을 지정한다. 예를 들어 실행 정책이 허용하는 `grep`을 사람 승인 대상으로 설정해도 해당 입력은 검사되지 않는다. 자동 승인 상한이 HIGH까지 허용하면 명령 승인 규칙이 작동하지 않는다. 이 지적은 서버가 별도로 금지한 명령까지 실제 실행된다는 주장이 아니다. 실행 서버의 옵션 제한과 운영자가 설정한 사람 승인 정책은 별개다.

**수정 방향:** 명령 의미를 소유하는 서버/어댑터에서 검사할 입력을 선언하고 발견된 도구 설명까지 전달해야 한다. 선언 없음과 명령을 사용하지 않음을 구분할 필요가 있다면 그 구분도 담당 계약에서 표현한다. 모든 일반 도구에 명령 필드를 강제하거나 중앙 도구 이름 목록을 추가하는 방식은 피한다.

## CR03 — 인자 배열을 개별 문자열로만 검사한다

**근거:** `src/redteam/control/policy.py:248-264,275-291`; 기본 규칙 `policy.py:117-126`.

검사 대상이 문자열 배열이면 각 원소를 독립 후보로 넣는다. 실행 파일 필드와 인자 필드 사이도 연결하지 않는다. 기본 규칙에는 `rm -rf`, `dd if=`, `del /s`, `rmdir /s`처럼 실행 파일과 인자를 함께 봐야 맞는 패턴이 있다.

**실제 실패 조건:** 정상 선언된 명령 도구가 실행 파일 `rm`과 인자 배열 `['-rf', '/workspace/example']`을 따로 받는다. 검사 후보에는 `rm`, `-rf`, 경로만 있으므로 `rm -rf`는 어느 후보에도 포함되지 않는다. CR02의 선언 누락을 고쳐도 이 문제는 남는다. 내장 실행 서버가 이 명령을 허용한다는 뜻은 아니며, 이 입력 형식을 지원하는 등록 제공자에서 발생하는 정책 누락이다.

**수정 방향:** 제공자가 선언하는 명령 표현에 맞춰 실행 파일/인자 배열을 한 명령 단위로 검사해야 한다. 서로 무관한 텍스트 필드를 전부 이어 붙이는 식의 중앙 추측은 하지 않는다.

## CR04 — 가설과 발견 사항을 함께 기록하면 검수 성공이 상태에 반영되지 않는다

**근거:** `src/redteam/orchestration/graph_recording.py:759-777,843-844,985-1012,1053-1079`; `src/redteam/orchestration/findings.py:100-112`.

함께 제출한 가설은 미확정 상태로 먼저 저장된다. 발견 사항도 있으면 일괄 가설 검토는 생략한다. 개별 발견 사항 검토는 새로 자동 생성한 가설만 상태를 갱신한다. 요청에서 가설을 지정했거나 같은 호출에서 하나의 가설을 선택했을 때는 그 갱신을 하지 않는다. 이후 승격 단계는 저장된 가설이 확정 상태인지를 요구한다.

**실제 실패 조건:** 워커가 같은 원본을 참조하는 가설 1개와 취약점 주장 1개를 한 번에 제출한다. 개별 검토가 성공/위반을 반환해도 가설은 미확정이므로 `hypothesis_not_confirmed`로 거절된다. 이전 호출에서 미확정 가설만 기록한 뒤 그 가설을 지정해 발견 사항을 제출해도 같다. 발견 사항만 제출할 때 자동 생성하는 경로와 결과가 달라진다.

**수정 방향:** 가설의 대상/주장 연결을 확인한 다음 이번 검토 결과를 해당 가설에 적용해야 한다. 확정 가설을 요구하는 최종 승격 조건을 삭제하는 방식은 부적절하다. 제출 순서 때문에 검토 성공이 버려지는 연결을 고쳐야 한다.

## CR05 — 반박된 취약점 주장도 위반 판정으로 반환한다

**근거:** `src/redteam/orchestration/analysis.py:746-772`, 특히 760-767; `graph_recording.py:987-990,1053-1079,1113-1129`; `findings.py:100-112`.

사후 주장 판정은 반박 결과와 거짓인 주장 지원 여부를 유효한 조합으로 인정한다. 그 다음 내부 위반/통과 판정은 결과 종류를 보지 않고 취약점 검토인지 여부만으로 정한다. 따라서 취약점 검토에서는 반박 결과도 위반으로 반환된다.

**실제 실패 조건:** 워커가 이미 확정된 가설을 참조하여 새 원본으로 취약점 주장을 재검토한다. 검토 결과가 `refuted`와 `claim_supported=False`이어도 내부 판정은 VIOLATION이다. CR04의 기존 가설 상태 갱신 누락 때문에 저장된 상태는 여전히 확정이다. 최종 승격은 위반과 확정 상태만 검사하므로 반박된 주장이 발견 사항으로 등록될 수 있다. 새 자동 가설 경로에서는 반박 상태로 갱신되어 막히지만, 공개 입력은 기존 가설 참조도 허용한다.

**수정 방향:** 사후 판정 담당에서 확인/반박 결과에 맞는 위반·통과 의미를 반환해야 한다. 발견 사항 승격까지 전달하는 결과가 주장 지원 여부와 일치하는지도 확인한다. CR04만 수정하고 이 잘못된 판정 변환을 남기는 것은 충분하지 않다.

## CR06 — 명시한 취약점 대상이 원본과 무관해도 코드 검사를 통과한다

**근거:** `src/redteam/orchestration/graph_recording.py:940-984`; `src/redteam/orchestration/analysis.py:604-630,644-713`.

주장에 대상이 없을 때는 원본들의 대상이 하나인지 검사한다. 반대로 대상을 명시하면 그 검사 전체를 건너뛰고 그래프에 그 대상이 존재하는지만 확인한다. 사후 검증 담당도 원본 대상은 모델 입력에 넣을 뿐 주장 대상과의 관계를 코드로 검사하지 않는다. 계정을 명시한 경우에만 별도의 계정 증명 검사가 있다.

**실제 실패 조건:** 같은 실행 안에 무관한 대상 A/B가 있고, 원본은 A를 실제 호출한 결과다. 워커가 계정 없는 B의 취약점 주장을 A의 증거와 함께 제출하면 코드의 대상 정합성 검사를 통과한다. 모델이 이를 성공으로 잘못 판정하면 B에 확정 가설과 발견 사항을 저장한다. 모델 판정이 반드시 오판한다는 주장이 아니라, 계획에서 코드 책임으로 정한 관련 대상 검사가 모델 판단에 넘어갔다는 문제다.

**수정 방향:** 원본 실행 대상 또는 증거로 입증된 관련 대상 연결을 기존 출처/그래프 계약으로 확인해야 한다. 원본에 등장한 새 대상과 실제 호출 대상은 구분한다. 관련 원본을 종합하는 정상 경로를 막는 단순한 동일 ID 강제보다는 입증된 관계를 소비하는 쪽이 맞다.

## CR07 — 사후 가설 연결은 저장되지만 완료 판정에서 사용할 수 없다

**근거:** `src/redteam/orchestration/analysis.py:1459-1503`; `src/redteam/orchestration/completion.py:1235-1248,1314-1333,1540-1541,1592-1618`; 관측 원본 저장 경로 `nodes/verify.py:166-176`.

가설 없이 수집한 원본은 그 시점의 가설 참조가 없다. 사후 기록은 새 가설과 원본 증거의 관계를 별도 최종 영수증에 저장한다. 그러나 가설 확인/반박 완료 조건은 영수증을 읽기 전에 원본 자체의 가설 참조가 같아야 증거 후보에 남긴다. 영수증에는 가설 참조가 있지만 원본 실행 경로·원본 결과가 없어, 영수증 ID를 직접 완료 증거로 제출해도 원본 정합성 검사에서 탈락한다.

**실제 실패 조건:** 처음에는 관측만 수집하고, 이후 발견 사항만 제출하여 사후 가설·확정 상태·최종 영수증을 정상 생성한다. 해당 가설을 확인하는 완료 조건에 원본 ID를 제출하면 가설 참조 필터에서 후보가 없어진다. 영수증 ID를 대신 제출하면 경로 연결 검사에서 거절된다. 가설만 제출하는 검토 경로는 상태를 갱신하지만 최종 영수증을 작성하지 않는 점도 같은 소비 연결에서 해결해야 한다. 모든 종류의 완료가 실패한다는 뜻은 아니며 가설 확인/반박 조건의 문제다.

**수정 방향:** 완료 담당에서 검증된 사후 영수증의 가설→원본 증거 연결을 읽은 뒤 기존 원본 정합성 검사를 적용해야 한다. 원본 가설 참조를 소급 변경하거나 원본 실행 검사를 삭제하면 안 된다. 주장 검토 생산자와 완료 소비자를 함께 수정한다.

## CR08 — 실행 하나에 대한 서로 다른 주장 영수증이 충돌한다

**근거:** `src/redteam/orchestration/completion.py:319-347`, 특히 337; 사후 영수증 생산 `analysis.py:1473-1479`; 발견 사항별 호출 `graph_recording.py:1081-1095`.

완료 담당은 실행/호출 쌍마다 가장 최근 영수증 하나만 남긴다. 새 기록 경로는 동일 원본을 여러 주장/가설이 인용할 수 있으며, 각각 같은 실행/호출 쌍으로 영수증을 작성한다. 다른 주장의 검토까지 이전 판정을 대체한 것으로 취급한다.

**실제 실패 조건:** 하나의 원본에서 서로 다른 취약점 주장 2개를 검토하여 각 가설의 최종 영수증을 저장한다. 두 번째 영수증이 최신이면 첫 번째 가설의 영수증은 완료 조회에서 사라진다. 첫 번째 주장만 만족해야 하는 PoC 조건도 정확한 가설 참조가 있으면 최종 판정을 찾지 못한다. CR07의 연결 필터를 고쳐도 이 문제는 남는다.

**수정 방향:** 같은 주장의 재검토와 서로 다른 주장의 검토를 구분하여 최신 판정을 선택해야 한다. 실행 출처는 유지하고, 이미 저장한 가설/주장 식별 의미를 소비한다. 단순히 전체 영수증을 무조건 인정해 오래된 반박/확인 판정을 되살리는 수정은 피한다.

## CR09 — 요청 세션 반향이 현재 결과에서도 실제 사용 증거가 된다

**근거:** `src/redteam/orchestration/session_proof.py:33-37,40-64,109-117`; `src/redteam/orchestration/analysis.py:380-388,425-437,681-713`.

실제 사용 필드가 한 곳이라도 있으면 요청 반향을 제외하는 규칙은 구현되어 있다. 하지만 실제 사용 필드가 전혀 없는 결과는 저장 시점이나 계약 버전 확인 없이 전부 옛 형식으로 분류하고 요청 세션 필드를 사용 증거로 반환한다. 새 직접 선택 도구의 결과에도 같은 대체 규칙이 적용된다.

**실제 실패 조건:** 현재 등록한 일반 MCP 도구가 요청의 `session_ref`를 응답에 그대로 돌려주지만 실제 세션을 사용하지 않으며 실제 사용 영수증 필드도 제공하지 않는다. 저장된 요청과 응답의 세션명이 같고 주장 계정명이 그 값과 같으면, 계정 검사는 요청 반향을 실제 사용 증거로 인정할 수 있다. 사후 검수에는 계정 증명 부족이 전달되지 않는다. 이것은 설정 목록만으로 증명하는 문제와 별개다.

**수정 방향:** 새 결과에서 실제 사용 증거가 없으면 실제 사용은 미확인으로 처리한다. 옛 저장 자료를 읽는 호환 범위가 필요하면 신뢰할 수 있는 기존 저장 출처/계약으로 그 범위를 제한해야 한다. 필드 부재만으로 현재 원본을 옛 형식이라고 추측하지 않는다. 자료를 읽을 수 있다는 호환성과 사용 사실을 입증했다는 판정은 다르다.

## CR10 — 전체 잔여량을 정상 판단에 먼저 배정해 보정 여유를 없앤다

**근거:** `src/redteam/orchestration/delegated_runtime.py:380-385`; `src/redteam/orchestration/cognition.py:152-159`.

워커는 전체 잔여 요청에서 제한값을 계산한 다음 정상 판단에 먼저 최대 8회를 배정하고, 남는 부분만 보정 상한으로 사용한다. 전체 잔여량이 줄어든 일반적인 후반부에는 정상 판단 상한 이하가 되므로 보정 상한은 0이다.

**실제 실패 조건:** 워커 전체 요청이 6회 남고 조사 판단이 허용되는 상태다. 현재 계산은 마지막 요청 1회를 남겨 현재 체인을 5회로 제한한 뒤 정상 5회/보정 0회로 만든다. 첫 응답이 JSON 형식을 어기면 실제 요청은 1회만 썼는데도 보정을 허용하지 않는다. 전체 한도 안에 4회가 더 남은 상황과 보정 상한 소진을 혼동한다.

**수정 방향:** 정상 상한과 보정 상한을 유지하면서 실제 전체 잔여량을 별도 더 좁은 총상한으로 적용해야 한다. 기존 단독 총횟수 호출자 의미는 유지한다. 전체 한도를 늘리거나 워커별 임시 예산으로 우회할 필요는 없다.

## CR11 — 워커의 제공자 실패 진단이 다음 판단과 보고에서 사라진다

**근거:** `src/redteam/orchestration/delegated_runtime.py:449-472`; `src/redteam/orchestration/delegation_decision.py:622-637`; 보고 소비 `src/redteam/orchestration/reporting.py:392,536` 및 `app/cli/commands/report.py:84-94`.

제공자 오류와 구조화된 진단 계약은 추가됐지만 워커 호출자는 예외를 클래스 이름으로 축소한다. 결과 처리 단계는 그 문자열을 일회 반환 결과에 넣고, 호출자는 사용량이 갱신된 워커 상태만 보존한다. 오류나 원인 진단을 상태·미해결 증거·보고 참조에 연결하지 않는다. 제공자 상세를 표시하는 보고는 루트 계획 진단만 읽는다.

**실제 실패 조건:** 워커의 모델 요청이 인증 실패 등 재시도 불가 오류를 반환한다. 해당 요청 안의 보정 재시도는 중단되지만, 다음 루트/워커 판단에는 원인과 재시도 불가 여부가 전달되지 않는다. 워커는 여전히 활동 상태여서 동일 조건에서 다시 요청할 수 있고, 이후 한도로 종료되면 보고에는 원래 제공자 실패 대신 한도 종료만 남을 수 있다. 임시 오류나 형식 실패도 같은 이름으로 뭉개진다.

**수정 방향:** 새 예외의 공개 진단을 기존 미해결 정본 또는 진단 경로에 보존하고 워커 상태에는 참조/요약을 연결한다. 다음 판단과 보고가 같은 원인 코드를 읽게 한다. 원문 예외 문자열이나 비밀 입력 전체를 기록할 필요는 없다.

## CR12 — 문자열 원본은 공통 측정 사실 기록에서 항상 거절된다

**근거:** `src/redteam/core/contracts/tool.py:125`; `src/redteam/capability/adapters/mcp/transport.py:152-156`; `src/redteam/orchestration/graph_recording.py:104-112,399-405`.

도구 결과 계약은 문자열을 허용하고, 단일 MCP 텍스트 응답도 문자열 그대로 저장한다. 공통 사실 기록은 출력이 딕셔너리인 경우만 허용한다. 원본 위치도 길이 1 이상인 키 배열이라 문자열 출력 전체를 가리킬 수 없다.

**실제 실패 조건:** 전용 결과 해석기가 없는 등록 도구가 배너, 확인 값 또는 주소를 단일 텍스트 응답으로 반환한다. 워커가 원본을 조회해 정확히 같은 문자열을 측정 사실로 제출해도 `no preserved output`으로 거절된다. 해석을 가설로 기록할 수 있는 것과, 실제로 받은 텍스트를 측정 사실로 보존하는 것은 서로 다르다.

**수정 방향:** 기존 원본 결과 계약의 문자열에도 정확한 원본 위치/전체 값 또는 제한된 텍스트 구간 참조를 제공해야 한다. 공통 기록이 원본 일치를 검사할 수 있으면 충분하다. 도구별 전용 해석기나 임의 문자열 파서를 중앙에 추가할 이유는 없다.

## 정확성·단순성 검토 결과와 수정 범위

역할별 YAML 선택자를 기존 역할 등록/카탈로그에 연결하고, 실제 선택 도구를 제안·실행·재개에 전달하는 구성은 확인했다. 로컬 기록 도구도 공개 필드만 생긴 것이 아니라 기존 확장 조립에서 등록되어 실제 제공자 호출과 다음 판단 결과 전달까지 연결되어 있다. 원본 조회 요청을 참조로 보존하고 재구성하는 경로와 실제 모델 사용량을 누적하는 생산자/집계/재개 연결도 읽었다. 이 사실을 정상 실행을 통과했다는 표현으로 대신하지 않는다.

대상별 명시적 빈 허용 목록의 거부 의미와 ROE의 빈 목록 의미를 구분한 변경, 선택 도구 승인 지문, 외부 전송 금지의 별도 거부 의미는 유지하는 쪽이 맞다. 기존 사용자 제한, 원본 불변성, 실제 계정 증명, 확정/반박 상태 검사를 ‘너무 엄격하다’는 이유로 제거하는 것을 해결책으로 권고하지 않는다.

필수 지적의 수정은 대부분 기존 담당 모듈과 소비 연결 안에서 가능하다. CR02/CR03은 명령 제공자와 명령 검사 계약, CR04~CR08은 주장 검수와 영수증 소비, CR09는 공통 실제 사용 증명, CR10은 현재 판단 예산, CR11은 기존 진단/미해결 기록, CR12는 원본 위치 계약이 책임을 가진다. 새 도구 이름별 허용 목록, 별도 증거 저장소, 중앙 역할별 분기는 필요하지 않다.

권고 판정은 위 12건 모두 **필수 수정 대상으로 반영**이다. 실제 반영·대안 반영·기각 결정과 근거는 구현 담당자가 기록해야 한다. 이 문서에서 구현 완료나 지적 해결을 선언하지 않는다. 사소한 이름·주석·형식 정리 때문에 수정 범위를 늘리는 선택적 지적은 추가하지 않았다.

## 후속 검증과 미확인 사항

수정 후에는 지적의 실제 실패 조건을 최소 관련 사례로 확인하고 해당 소비 경로를 재리뷰하면 된다. 사람 승인 조기 반환/선언 누락/인자 배열 검사, 긍정·반박·미확인 사후 검수, 함께 제출한 가설, 동일 원본의 복수 주장, 사후 가설 완료, 현재 결과의 요청 반향, 전체 잔여량 내 형식 보정, 워커 제공자 실패 보고, 문자열 원본 기록을 다뤄야 한다. 관련 없는 전체 검증을 반복하거나 구현을 그대로 따라 쓰는 테스트를 추가할 필요는 없다.

실제 LLM의 계획 품질, 실제 MCP 세션·취약/정상 비교, 제공자의 상태 코드·재시도 동작, 실제 승인 재개 및 중단·복구의 실행 결과는 이 리뷰에서 미확인이다. 기존 실패 자료에서 HTTP 상세가 없는 전송 실패의 원인은 여전히 미확인이다. 조건이 다른 이전 실행들을 합산한 성공률이나 이번 수정의 개선률은 계산하지 않았다.

최종 기능 검증과 실제 로컬 실행 증거는 이 리뷰 이후 별도 수행·기록해야 한다. 소스 리뷰, 문법 검사, 가짜 모델 사례, 실제 LLM/MCP 실행을 서로 구분해 보고해야 한다.

### CR13 [P1] — 관계 속성의 측정 출처를 관계 자체의 입증으로 받아들인다

**근거:** `src/redteam/orchestration/graph_recording.py:398-417,442-468`; `src/redteam/attack_graph/service.py:401-439`; `src/redteam/orchestration/analysis.py:282-293`; 완료 소비 `src/redteam/orchestration/completion.py:1429-1443`.

새 대상 관련성 검사는 두 대상 사이의 관계에 현재 원본 ID/실행 ID/측정 등급이 있으면 관련성을 인정한다. 이 저장 형식은 실제 그래프 서비스가 생산하는 형식과 맞는다. 문제는 공통 기록이 관계를 만들 때, 값 하나가 원본과 일치하고 두 끝점 중 하나가 호출 대상이면 임의의 기존 다른 끝점과 관계를 허용한다는 점이다. 측정 출처는 그 값의 일치를 증명할 뿐, 다른 끝점이나 관계 유형이 원본에 존재함을 증명하지 않는다.

**실패 조건:** A의 원본 출력에 `status_code=200`만 있고 무관한 B가 그래프에 존재한다. 워커가 정확한 200 값을 사실로 제출하면서 A→B 관계를 같이 지정하면 양쪽 노드 존재 검사 후 관계가 측정 출처로 저장된다. 같은 호출에서 B에 대한 취약점 주장을 제출하면 새 대상 검사는 그 방금 만든 관계를 입증된 관계로 인정한다. 모델의 취약점 의미 판정 전에 차단하려던 대상 무관성이 다시 모델 판정에 넘어간다. A의 증거에 B의 주소가 없어도 가능하다.

**수정 방향:** 관계 생성 담당이 끝점/관계에 관한 원본 근거를 검사하고, 관련성 소비자는 그 입증된 의미를 읽어야 한다. 원본에 주소가 있는 새 대상 등록과 기존 노드에 속성 하나를 기록하는 작업을 같은 관계 증명으로 취급하면 안 된다. 중앙 도구 이름 예외나 단순 동일 대상 강제는 필요하지 않다.

### CR14 [P1] — 가설 미해결로 등록을 거절한 영수증이 기존 발견 사항과 결합해 PoC를 통과한다

**근거:** `src/redteam/orchestration/graph_recording.py:1084-1122,1160-1163`; `src/redteam/orchestration/completion.py:860-871,1779-1781,1809-1826`; `src/redteam/attack_graph/service.py:571-576`.

새 주장과 참조 가설의 결과를 분리한 생산자는 가설이 미해결이면 발견 사항 등록을 거절한다. 그러나 그 전에 최종 영수증을 저장하며, 영수증에는 새 주장 성공/위반과 가설 미해결이 함께 들어간다. PoC 완료 검사는 새 주장 성공/위반만 읽고 참조 가설 결과를 검사하지 않는다. 발견 사항도 그 영수증으로 등록된 항목인지 확인하지 않고, 원본 ID와 가설 ID가 겹치는 기존 검증 항목 하나가 있으면 인정한다. 새 발견 사항에는 검토 영수증 참조를 저장하도록 바뀌었지만 완료 소비자는 그 참조를 사용하지 않는다.

**실패 조건:** 원본 E와 가설 H로 기존 발견 사항 F가 이미 저장돼 있다. 같은 원본/가설을 참조한 다른 주장은 새 주장 자체는 지원되지만 H의 의미는 미해결이라는 판정을 받는다. 기록 도구는 새 발견 사항을 거절한다. 그럼에도 최신 영수증은 성공/위반으로 남고, PoC 완료는 이 영수증과 기존 F를 각각 찾아 합친다. 새 주장에 대한 등록이 거절됐다는 결과와 반대로 완료 근거가 인정될 수 있다.

**수정 방향:** 완료에서 주장/가설 판정과 실제 승격된 발견 사항의 같은 검토 연결을 소비해야 한다. 거절된 승격의 최종 영수증을 다른 기존 발견 사항에 붙여 사용하면 안 된다. 옛 발견 사항의 호환은 기존 판정 의미를 보존하는 별도 읽기 경계로 유지한다.

### CR15 [P2] — 새 주장은 확인되고 참조 가설은 반박된 경우 반박 완료 영수증을 거절한다

**근거:** `src/redteam/orchestration/analysis.py:797-805,840-855`; `src/redteam/orchestration/graph_recording.py:1123-1129`; `src/redteam/orchestration/completion.py:817-827`.

참조 가설의 반박 여부는 별도 결과에서 읽도록 변경됐지만 완료 담당은 여전히 새 주장에 대한 위반/통과 판정을 반박 영수증의 필터로 사용한다. 새 취약점 주장이 성공하면 위반이 되고, 같은 증거가 더 넓은 참조 가설을 반박할 수 있다. 그래프 가설은 올바르게 반박 상태로 바뀌어도 완료 담당은 VIOLATION이라는 이유로 영수증을 건너뛴다.

**실패 조건:** H가 ‘해당 자원의 접근 통제가 정상적으로 동작한다’이고 새 주장이 실제 우회 가능성을 설명한다. 검수는 새 주장 성공/지원 참, H 반박을 반환한다. 가설 상태는 rejected이고 영수증도 그 반박을 보존한다. 가설 반박 완료 조건은 결과 종류를 올바르게 읽은 뒤 위반 판정 필터에서 거절한다. 새 주장과 가설 결과가 다를 수 있다고 공개 규격으로 허용한 정상 조합이다.

**수정 방향:** 별도 가설 결과가 있는 새 영수증에서는 가설 결론의 입증 여부와 새 주장 판정을 분리해 소비한다. 별도 결과가 없는 옛 영수증에 적용하는 지원 여부/위반·통과 검사는 그대로 보존해야 한다. 확인과 반박을 무조건 허용하는 필터 완화는 필요하지 않다.

### CR16 [P1] — 복수 원본의 첫 참조 순서가 바뀌면 최신 반박이 이전 확인을 대체하지 못한다

**근거:** `src/redteam/orchestration/graph_recording.py:943-946,951-955,1094-1099`; `src/redteam/orchestration/analysis.py:1484-1501,1553-1565`; `src/redteam/orchestration/completion.py:334-349,860-889,1779-1826`.

생산자는 복수 원본의 출처 배열을 보존하지만 영수증의 대표 실행/호출은 첫 원본에서 가져온다. 최신 조회 키는 그 대표 쌍과 가설/주장 식별값이다. 같은 가설·같은 원본 집합이라도 첫 참조를 바꾸면 서로 다른 최신 그룹으로 남는다. PoC 검사는 그중 어느 하나의 과거 성공 영수증과 기존 발견 사항이 있으면 통과하며 최신 반박이나 현재 가설 상태는 확인하지 않는다.

**실패 조건:** 서로 다른 호출에서 나온 E1/E2를 `[E1,E2]` 순서로 인용해 H 확인 및 발견 사항을 저장한다. 같은 근거를 재검토하거나 판정을 보정하며 `[E2,E1]` 순서로 제출해 H/주장 반박을 저장한다. 가설은 반박 상태가 되지만 최초 성공 영수증은 다른 대표 실행 키로 보존된다. 원본과 H를 제출한 PoC는 최초 성공 영수증과 기존 발견 사항을 찾아 통과할 수 있다. 같은 원본 집합의 순서만 바뀌어도 발생하므로 역사적으로 유효했던 다른 재현을 지워야 한다는 요구와는 다르다.

같은 조회에서 `hypothesis_id or claim_identity`를 쓰므로 가설이 같으면 별도 새 주장 식별값도 무시한다. 같은 가설 아래 서로 다른 주장 영수증을 보존하는 요구 역시 현재 키만으로 표현되지 않는다.

**수정 방향:** 기존 저장된 주장 식별과 정규화된 복수 출처 의미를 기준으로 같은 주장 재검토와 다른 주장을 구분한다. 완료가 최신 관련 판정을 소비하게 해야 한다. 원본의 대표 출처를 덮어쓰거나 모든 과거 성공 영수증을 무조건 인정하는 방향은 부적절하다.

### CR17 [P1] — 완료 계정 검사는 현재 세션 사용이 없어도 과거 별칭 증명을 빌린다

코드·검증 기록의 최종 판정은 **CR21 수정 및 해당 소비 경로 재리뷰 필요**, 실제 LLM 전체 라이브 흐름은 **제공자 한도로 미검증**이다. 이 리뷰어는 새 자동 테스트나 실제 호출을 수행하지 않았으며, 읽은 루트 실행 증거와 독립 소스 검토를 분리해 기록했다.

### CR21 — 명시한 주장 그룹을 최종 PoC 소비까지 보존

`src/redteam/orchestration/completion.py:1293-1320`은 최신 영수증 조회와 기존 출처 일치 검사를 통과한 명시 참조에서 주장 그룹 키를 보존한다. 원본 ID 확장은 유지하므로 기존 실행·경로·원본 검사를 우회하지 않는다. 오래되거나 출처가 불일치한 영수증은 기존 오류를 남기며, 원본만 남겨 성공으로 돌아가는 경로로 처리하지 않는다.

보존한 키는 최종 PoC 후보 선택(`completion.py:1824-1829`)으로 전달되고, 후보 담당은 다른 그룹을 먼저 제외한 후 성공·위반·주장 지지·가설 결과와 원본/실행 연결을 검사한다(`877-925`). 따라서 CR21의 별도 주장 B 영수증만 인용한 경우, 같은 가설과 원본을 공유한 주장 A의 성공 영수증은 후보가 되지 않는다. B 자체는 미해결 가설 결과 때문에 성공 후보를 통과하지 못해 완료 오류를 반환한다. 발견 사항 연결도 제한된 후보만 사용한다(`1887-1914`). 기존 주장 그룹 계산 담당을 재사용했고 새 저장 상태나 전체 과거 성공 무효화 규칙을 추가하지 않았다.

정상 재확인과 최신 반박 의미도 유지한다. 최신 조회는 여전히 주장·가설·정규화한 원본/실행 그룹별로 동작한다(`319-373`). 같은 그룹의 후속 성공은 기존 발견 사항의 최초 영수증과 그룹을 대조하여 사용할 수 있고, 같은 그룹의 최신 부정 결과는 성공 후보에서 제외된다. 원본 ID를 직접 제출하는 기존 경로에는 명시 영수증 그룹 제한을 새로 적용하지 않는다. 관련 정상 재확인·최신 반박 사례(`tests/unit/test_semantic_completion_receipts.py:959-1003`)의 기대값은 유지됐다. CR21 회귀 사례의 `1035-1041`은 이제 검증 오류 목록이 비어 있지 않음을 요구해 테스트 이름과 같은 거절 의미를 검사한다. 이 리뷰에서는 해당 테스트를 실행하지 않았다.

### 직접 선택 입력과 테스트 대역의 계약 대조

`src/redteam/orchestration/paths/writing.py:105-123`은 옛 기능·행동 힌트를 선택 입력으로 허용하면서 실행 경로 전환 값은 공개 입력에서 계속 제거한다. 모델이 그 값을 제출하면 추가 필드 금지와 실제 응답 스키마 검사(`engine.py:108-116,647-653`)에 걸리며, 힌트를 제출하거나 생략한 정상 입력은 직접 선택 기본값을 유지한다. 루트의 중첩 행동 응답(`engine.py:679-692`)과 워커의 개별 행동 응답(`delegated_runtime.py:399-412`)은 같은 스키마 작성 담당을 사용한다.

실제 선택 도구는 컴파일의 직접 선택 분기와 등록 정보로 해석한다(`candidates/compiler.py:146-190,253-275`). 대상 검사는 선택 도구의 대상 계약을 우선 사용한다(`engine.py:2128-2136`, `target_binding.py:60-65`). 실행 후보 식별도 직접 선택에서는 옛 행동 힌트를 포함하지 않고(`engine.py:2288-2309`), 승인 판단은 제공자 선언을 사용하며(`control/policy.py:351-365`), 실제 호출은 선택 도구를 일치시키고 옛 행동 값은 비운다(`core/convert.py:58-72`). 확인한 소비 경로에서 힌트를 실행 바인딩이나 승인 우회 조건으로 다시 사용하지 않는다. 추가된 스키마 테스트는 힌트 생략·제출과 실행 경로 전환 값의 거절을 구분한다(`tests/unit/test_path_writing.py:205-232`).

직접 컴파일을 호출하는 실행 레시피·APK 테스트의 옛 실행 경로 명시는 기존 레시피 계약을 검사하기 위한 코드 입력이다(`tests/integration/test_agent_mcp_contract_admission.py:99-145,235-246`). 모델 응답의 전환 값 허용으로 연결되지 않는다. 핀 고정 대상 테스트는 컴파일 결과의 실제 선택 도구와 실행 경로를 승인 제안에 전달하도록 맞췄다(`78-83`).

인증 후속 조사 테스트 대역은 요청된 세션의 적용 여부로 응답 상태를 선택하고, 세션을 사용할 수 없는 경우 실패를 반환한다(`tests/integration/test_authentication_followup.py:100-116`). 추가된 실제 세션 참조(`125-127`)는 이 적용 결과와 일치한다. 익명 요청에는 null 실제 참조를 남기고 요청 에코는 별도 항목으로 유지한다. 공통 실제 세션 증거 담당은 여전히 요청 에코를 실제 사용 증명에 포함하지 않는다(`src/redteam/orchestration/session_proof.py:29-52,65-77`). 제품의 실제 증거 요건을 약화하는 테스트 전용 예외는 추가되지 않았다.

### 검증 상태와 후속 범위

이번 재리뷰에서 제품·테스트 수정, 자동 테스트, 실제 도구/LLM 호출, 커밋·푸시는 수행하지 않았다. 리뷰 문서 외 작업 트리는 변경하지 않았다. 기존 전체 실행에서 남은 실행 루프 테스트 실패 5건은 루트가 다음 단계에서 단독 재현할 대상이며, 이번 소스 판정만으로 해결·통과로 변경하지 않는다. 기존 실제 LLM의 429 종료 역시 **전체 라이브 흐름 미검증** 상태를 유지한다. 필수 소스 지적이 없는 이번 수정부터 관련 실행 검증을 진행할 수 있지만, 전체 목표의 완료 판정은 남은 실패 분석과 필요한 최종 검증 이후에 해야 한다.

검토 대상은 `2c9fc6c8` 이후 작업 트리의 `tests/integration/test_engine_live_run_flow.py:141-155` 변경이다. 제품 diff는 없고, 테스트 조립에서 기존 카탈로그를 한 번 생성해 실행 의존성과 실제 정책 판정 담당의 선택 도구 조회에 함께 주입한 6줄 추가·2줄 삭제다. 루트의 `work-log.md` 변경과 기존 미추적 산출물은 이번 판정 범위에서 제외했다. 리뷰 문서에 이 절만 추가했으며 제품·테스트 수정이나 실행 검증은 수행하지 않았다.

### 누락 연결과 실제 앱 조립의 일치

실제 앱의 두 조립 경로는 도구 카탈로그의 공개 조회를 정책 판정 담당에 주입한다(`src/redteam/app/bootstrap.py:356-365,640-653`). 실행 의존성에도 해당 카탈로그를 전달한다(`396,726`). 수정한 테스트 조립 역시 동일 카탈로그 객체의 공개 조회를 전달하므로, 후보를 구성할 때 본 도구와 정책이 해석하는 선택 도구 설명이 같은 정본을 사용한다. 별도 도구 허용 목록, 이름별 예외, 새 정책이나 저장 상태는 없다. 테스트 카탈로그 조회는 등록된 설명만 반환하고 미등록 ID에는 None을 반환한다(`tests/integration/_engine_llm_harness.py:164-172`).

승인 단계는 실제 선택 도구 ID를 문맥에 넣어 실제 정책 판정 담당을 호출한다(`src/redteam/orchestration/nodes/policy.py:165-174`). 그 담당은 주입된 조회가 없으면 선택 도구 설명을 얻지 못한다(`src/redteam/control/service.py:1430-1439`). 선택 도구가 명시됐는데 설명을 해석하지 못하면 위험도를 미확인으로 처리하고, 명령 정책 역시 해석 불가 사유를 남겨 사람 승인을 요구한다(`service.py:312-337,398-405`, `control/policy.py:316-331`). 따라서 수정 전 조립은 정상 모델 제안이어도 선택 도구를 알 수 없는 승인 대기 경로로 들어갈 수 있다. 이는 루트가 보고한 호출 0건·승인 대기와 소스상 일치한다. 해당 단독 재현의 실행 출력은 이 리뷰어가 다시 실행하거나 독립 확인한 것으로 표현하지 않는다.

### 정책 경계와 회귀 기대값 유지

정책 담당은 계속 실제 구현이다. 선택 도구 설명의 위험도·명령 선언을 기존 규칙에 제공할 뿐, 범위·교전규칙·대상 행동 정책·승인·속도·예산 검사와 사람 승인 필수 처리는 유지된다(`control/service.py:261-418`). 실행 직전 현재 판정도 ALLOW가 아니면 호출을 거절한다(`orchestration/nodes/execute.py:133-137`). 기존 테스트 도구의 LOW 위험도와 빈 명령 입력 선언(`_engine_llm_harness.py:187-204`, `core/contracts/tool.py:60-63`)을 판정 담당이 읽을 수 있게 된 것이며, 승인 정책이나 도구 설명을 통과에 유리하게 수정하지 않았다. 미등록 도구를 성공으로 돌려주는 조회 대체도 없다.

영향 소비자는 공통 조립을 직접 쓰는 실행 루프 2건(`test_engine_live_run_flow.py:164-215`), 이를 기존 테스트 세계 조립에서 재사용하는 종단 간 흐름 2건(`tests/integration/test_end_to_end.py:24-29,32-99`), 같은 세계 조립을 사용하는 저장 상태·발견 사항·보고 CLI 사례 1건(`tests/integration/test_cli_smoke.py:68-87`)이다. 호출 1회, 실제 원본 증거, 단계/목표 완료, 실행 예산 1회 제한, 정책→승인→도구 실행 이벤트 순서 및 저장 보고에 대한 기존 assertion은 변경하지 않았다. 같은 원인으로 막혔을 가능성은 공유 조립 경로에서 설명되지만, 나머지 4건도 이 수정만으로 통과한다고 미리 확정하지 않는다.

이 재리뷰의 결론은 **공개 조회 주입 누락을 기존 조립 지점에서 바로잡은 적절한 테스트 수정**이다. 남은 5건은 관련 검증 대상으로 유지하며, 필수 CI 및 최종 기록 갱신은 루트의 다음 단계다. 기존 실제 LLM 전체 흐름의 429 미검증 상태는 이번 테스트 조립 수정으로 해소된 것으로 취급하지 않는다.

## 작업 완료 테스트 응답 계약의 영향 재리뷰 — 작업 트리 후속 수정

이번 범위는 직전 조립 수정에 이어 추가된 `tests/integration/test_engine_live_run_flow.py:126-142`의 작업 완료 응답 보완이다. 현재 해당 파일의 누적 diff와 공개 완료 제안·명시 증거 선택·실제 작업 완료 소비를 대조했다. 직전에 검토한 동일 카탈로그 주입 변경도 그대로임을 확인했다. 동시 수정 중인 공통 정책 테스트 대역과 위험도·후보 제공자 테스트의 타입 변경은 검토·승인 범위에 포함하지 않았다. 제품·테스트 수정, 자동 테스트, 라이브 호출, 커밋 없이 이 절만 추가했다.

**판정: 반영 타당, 새로운 필수 지적 없음.** 누락된 필수 결과 값과 설명을 테스트 모델 응답에 추가하면서 기존 명시 증거 ID와 모든 회귀 기대값을 유지한 계약 보정이다. 이 수정의 소스 리뷰는 종료할 수 있으며, 루트는 같은 5사례를 다시 검증할 수 있다. 통과 여부와 전체 목표 완료를 선행 판정하지 않는다.

### 기존 실패 기록과 공개 응답 계약

루트가 남긴 `data/validation-resume-loop-tests.txt`는 도구 호출 1회 assertion을 지난 뒤 임무 상태가 blocked라서 첫 사례가 실패한 출력을 기록한다. `data/repro-live-run-02/diagnostics.txt`는 단계 완료 검수까지 통과했고, 증거 ID만 있는 작업 완료 제안이 `schema_anyOf at $.completion`으로 거절된 뒤 보정 예산이 소진됐다고 기록한다. 후속 보정에서 테스트 대역의 메시지 JSON 해석 실패도 기록돼 있다. 이 자료는 루트의 기존 재현 증거를 읽은 것이며, 이번 리뷰어가 재현을 새로 실행한 결과가 아니다.

공개 계약(`src/redteam/orchestration/completion_proposal.py:37-49`)은 결과 값을 필수로 요구하며 설명은 기본값 있는 선택 항목이다. 실제 다음 행동 응답의 완료 영역은 그 계약 또는 완전히 빈 객체만 허용한다(`engine.py:679-692`). 증거 ID가 있는 객체는 빈 객체 대안을 만족하지 못하므로, 결과 값 누락은 계약상 거절이 맞다. 새 응답은 유효한 성공 결과 값과 설명을 제공하고 기존 증거 ID 목록을 유지한다. 제품의 스키마나 보정 예산을 약화해 잘못된 응답을 허용하지 않았다. 이번 기록과 소스 대조는 **해당 최초 거절을 테스트 응답 계약 불일치로 분류하는 근거**이며, 모든 남은 실패의 원인을 확정한 판정은 아니다.

### 명시 증거와 작업 완료 권한의 유지

테스트 모델은 현재 실행의 저장 원본 중 실제 도구 결과가 있는 증거를 모으고, 빈 목록이 아님을 확인한 후 그 목록을 작업 완료 제안에 전달한다(`test_engine_live_run_flow.py:113-139`). 명시 증거 선택 담당은 제안의 비어 있지 않은 증거 목록을 우선 사용하며, 이번 응답은 단계 증거 폴백으로 전환되지 않는다(`semantic_completion.py:321-345`). 호출의 실제 원본을 인용하는 소비 경로가 유지된다.

작업 완료 담당은 현재 실행 중인 작업과 경로의 작업 연결을 확인하고 제안을 공개 계약으로 읽는다(`semantic_completion.py:530-553`). 성공 결과 값을 제출했다고 곧바로 완료하지 않는다. 선택된 증거별 실행·참여 범위·보존 원본·실행/저장 출처·대상 관련성을 검사하고(`353-411,558-573`), 미확정 실행을 확인한 후 의미 검수와 결과 주장 검증을 거친다(`574-619`). 오류가 없을 때만 검수 영수증을 저장하고 기존 원자적 작업 상태 전환으로 완료한다(`620-662`). 제안의 성공 문구를 관측 사실이나 목표 달성 권한으로 승격하는 새 우회는 없다.

현재 diff는 테스트의 호출 1회·단계 증거·임무 완료·목표 종료 assertion을 변경하지 않는다. 종단 간 흐름 2건과 CLI 1건도 같은 테스트 세계 조립/모델 응답을 소비하지만, 수정 후 결과는 아직 실행으로 확인하지 않았다. 루트의 다음 검증 대상은 동일한 5사례이며 필수 CI와 최종 기록은 이후 실제 결과에 따라 갱신해야 한다. 다른 워커가 준비하는 사용자 지정 계정의 실제 LLM 검증은 이번 소스 판정과 분리한다. 기존 전체 라이브 흐름 미검증 상태를 이번 보정만으로 해소한 것으로 표현하지 않는다.

## 필수 타입 검사 대역 계약의 영향 재리뷰 — 3파일 작업 트리 수정

범위는 `tests/fakes/control_plane.py`, `tests/unit/test_risk.py`, `tests/unit/test_llm_candidate_provider.py`의 최종 작업 트리 diff와 승인 재개·카탈로그·프롬프트 소비 경로다. 직전 실행 루프 응답 리뷰는 반복하지 않았다. 제품 포트·제품 소스·개별 소비자의 cast/ignore 변경은 없다. 루트의 기존 `data/validation-resume-mypy-linux-py310.txt`에는 **19 errors in 13 files (checked 577 source files)**가 기록돼 있으며, 오류 위치는 테스트 파일이다. 제품 파일의 비타입 함수 몸체 안내는 오류와 구분했다. 이 출력은 수정 전 결과이며 수정 후 타입 검사 통과를 뜻하지 않는다.

**판정: 카탈로그 두 보완은 반영 타당. 공통 승인 대역의 공개 시그니처 보완도 방향은 타당하지만 파생 대역의 재정의 누락이 남아 CR22(P2) 필수 수정 1건을 확인했다. 현재 스냅샷을 필수 지적 없음으로 종료할 수 없다.** 새 타입 검사·자동 테스트·라이브 호출을 실행하지 않고 소스와 기존 실행 기록을 대조했다. 이 리뷰어는 제품·테스트를 수정하지 않고 이 절만 추가했다.

### CR22 [P2] — 공통 승인 대역의 확장 시그니처를 파생 대역이 좁힌다

**근거:** 공통 대역 `tests/fakes/control_plane.py:57-65`; 이를 상속한 승인 조회 계수 대역 `tests/unit/test_stage6_resume_safety.py:54-64`; 공통 대역 타입으로 받는 조립 소비 `92-112` 및 실제 파생 인스턴스 전달 `156-169`; 공개 포트 `src/redteam/core/ports/control_plane.py:27-29`.

공통 대역은 공개 포트와 같이 현재 제안을 선택 인자로 받을 수 있게 됐다. 그러나 승인 조회 횟수를 세는 파생 대역은 여전히 승인 ID 하나만 받는 메서드로 재정의한다. 부모 타입을 요구하는 소비자에 이 자식을 전달하고 있으므로, 부모가 허용하는 선택 인자 호출을 자식이 거절하는 명백한 시그니처 불일치다. 수정 전에는 부모도 인자가 하나여서 이 재정의 자체는 같은 시그니처였지만, 이번 부모 변경으로 새로운 불호환 재정의가 된다. 필수 검사는 tests 전체를 포함하며 해당 클래스와 재정의는 타입이 명시돼 있다. `pyproject.toml:85-89`에는 override 오류를 제외하는 설정이 없다.

**문제가 생기는 조건:** 이번 수정 후 필수 타입 검사에서 공통 대역의 확장 계약과 기존 계수 대역의 좁은 재정의를 함께 검사한다. 원래 13파일의 공통 대역 할당 문제를 고쳐도 이 파생 대역의 계약 누락이 남는다. 현재 재개 러너는 승인 ID만 넘긴다(`src/redteam/orchestration/runner.py:824`). 따라서 이 지적을 기존 러너 테스트에서 이미 TypeError가 발생했다는 실행 주장으로 표현하지 않는다. 다만 공개 포트가 허용하고 실제 직접 선택 승인 단계가 사용하는 현재 제안 인자(`nodes/policy.py:136-141`)를 자식도 받을 수 있어야 한다.

**수정 방향:** 승인 조회 계수 대역의 재정의도 부모와 같은 선택 인자를 받게 하고, 기존 조회 횟수 증가 및 설정된 반환값을 그대로 유지한다. 새로운 stale/불일치 판정은 넣지 않는다. 이 계약을 직접 소유하는 파생 대역 한 곳을 맞추는 것으로 충분하며, 13개 소비자에 cast/ignore를 추가하거나 공개 포트·제품 검사를 약화할 이유는 없다. CR22는 **필수 수정 반영 권고**다. 수정 후 그 재정의와 실제 소비 경로를 다시 확인하고 관련 검증을 진행해야 한다.

### 다른 보완의 판정과 동작 경계

공통 승인 대역의 본체는 새 선택 인자를 받아도 기존 승인 ID별 설정 판정을 그대로 반환한다(`control_plane.py:53-65`). 미설정 ID는 None으로 남고 새 거절 판단이나 상태를 만들지 않는다. 승인 재개 담당은 None이면 대기를 유지하고 반환된 판정이 있으면 그 판정을 사용한다(`src/redteam/orchestration/nodes/policy.py:130-161`). 기존 설정 판정 소비 사례(`tests/unit/test_runtime_feedback.py:197-230`, `test_stage6_policy_task_semantics.py:504-530`)의 의미도 변경하지 않았다. 실제 제품의 현재 제안 불일치 검사는 여전히 실제 정책 담당에 있다(`src/redteam/control/service.py:530-550,602-613`). 이 대역 보완을 그 제품 검사의 검증으로 표현하지 않는다.

위험도 테스트의 전체 목록 조회(`tests/unit/test_risk.py:74-75`)는 기존 등록 목록의 복사본을 반환한다. 개별 조회·기능 조회·전체 목록이 같은 정본을 사용하고 별도 목록이나 필터를 복제하지 않는다. 위험도 소비자는 기존 행동별 조회에서 최고 위험도를 선택하며(`src/redteam/control/risk.py:72-81`), 그 조회와 최고 위험도/빈 목록 기대값(`test_risk.py:105-113`)은 유지됐다. 전체 목록 공개 포트 요구(`core/ports/tool_catalog.py:19-25`)만 기존 대역에 보완한 적절한 변경이다.

후보 제공자 테스트의 지역 카탈로그 삭제는 공용 도구 대역의 기존 카탈로그 기능을 재사용한다(`tests/fakes/tool_gateway.py:25-53`). 한 도구의 기존 필수 입력 스키마를 유지하고, 공용 행동별 조회가 실제로 선택할 수 있도록 기능·행동 선언을 같은 도구 설명에 넣었다(`tests/unit/test_llm_candidate_provider.py:202-223`). 제공자는 주어진 단일 행동의 도구 스키마에서 필수 입력 이름을 모아 정렬한다(`src/redteam/orchestration/agents/llm_provider.py:247-267`). 기존 프롬프트의 필수 입력 기대값도 그대로다(`test_llm_candidate_provider.py:228`). 옛 지역 대역의 정확한 조회 쌍 assertion은 제거됐지만, 새 공용 조회는 등록된 기능·행동과 맞아야 도구를 반환하며 잘못된 쌍에서는 필수 입력 문구 assertion을 만족할 수 없다. 새 대역의 호출 실행 기능은 이 사례에서 사용하지 않는다. 중복 제거가 테스트의 목적을 약화한 근거는 확인하지 않았다.

이 스냅샷의 수정 후 테스트·타입 검사는 아직 미실행이다. 전달받은 이전 관련 111건 결과도 이번 3파일 수정 이후 통과 증거로 사용하지 않는다. **CR22의 좁은 후속 수정 및 영향 재리뷰가 먼저 필요**하며, 이후 관련 테스트와 필수 타입 검사의 실제 결과를 기록해야 한다. 실제 LLM 검증 상태는 이 판정과 분리한다.

## CR22 후속 및 종단 간 실행 기록 비교의 영향 재리뷰 — 작업 트리 수정

이번 범위는 `tests/unit/test_stage6_resume_safety.py`와 `tests/integration/test_end_to_end.py`의 작업 트리 diff 및 관련 공개 승인 계약·실행 기록 소비다. 앞선 공통 대역·카탈로그·실행 루프 응답 변경은 이번 두 수정의 경계 확인에 필요한 부분만 참조했다. 제품·테스트를 수정하거나 새 테스트·타입 검사·라이브 호출·커밋을 수행하지 않고 이 절만 추가했다.

**판정: CR22는 반영·해결. 종단 간 실행 기록 비교 수정은 반영 타당. 이번 두 diff와 영향 경로에서 새로운 필수 지적은 없다.** 루트는 관련 테스트와 필수 CI 묶음의 최종 검증으로 진행할 수 있다. 이 판정은 소스 리뷰의 종료이며 수정 후 검증 통과나 전체 목표 완료를 대신하지 않는다.

### 승인 조회 계수 대역의 계약과 부모 조회

파생 계수 대역의 승인 결과 조회가 부모와 같은 선택 현재 제안 인자를 받도록 수정됐다(`tests/unit/test_stage6_resume_safety.py:62-70`, `tests/fakes/control_plane.py:57-65`). 인자를 생략하는 기존 러너 호출과 현재 제안을 전달하는 공개 포트 호출을 모두 받을 수 있으므로 CR22의 좁은 재정의 불일치는 해소됐다. 횟수는 호출마다 한 번 증가하고 마지막 반환값은 기존 설정 판정이다. 기존 거절 재개 시 조회 0회, 정상 임무/옛 실행 시 조회 1회, 교차 실행/참여 범위 거절 시 조회 0회 기대값도 변경하지 않았다(`test_stage6_resume_safety.py:162-209`). 새로운 stale 판정이나 반환 상태를 추가하지 않았다.

추가된 부모 조회는 승인 ID와 현재 제안을 전달하지만 그 반환값을 사용하지 않는다(`68-69`). **호환성을 확보하는 데 필요한 것은 동일 시그니처이며 이 부모 조회 자체는 필요하지 않다.** 현재 부모는 설정된 승인 목록을 읽기만 하고 전달된 제안으로 판단하거나 상태를 변경하지 않는다. 따라서 이 호출은 현재 결과·계수·승인 상태를 바꾸지 않으며, 부모의 설정 판정과 파생 대역의 설정 판정을 통합하는 의미도 없다. 단순성 관점에서 삭제 가능한 중복 조회로 판단하되, 실제 실패나 책임 침범의 근거가 없으므로 새로운 필수 수정 지적으로 올리는 것은 **기각**한다. 삭제를 선택하더라도 시그니처·계수·기존 반환값만 유지하면 된다. 이 선택적 정리 때문에 검증을 다시 미루거나 범위를 늘릴 필요는 없다.

### 실제 직접 호출과 그래프 실행 기록의 비교

직접 선택 실행의 공개 표시 키는 실제 선택 도구 ID다(`src/redteam/core/tool_binding.py:21-30`). 계획된 행동의 기록 키는 별도 시도 키가 없으면 그 표시 키를 사용하며(`orchestration/agents/base.py:208-216`), 결과 갱신 담당은 그 키로 대상 노드에 시도를 기록한다(`orchestration/nodes/update.py:40,105-107`). 이 테스트의 모델 행동은 실제 등록 도구를 선택하고 별도 시도 키를 지정하지 않는다(`tests/integration/_engine_llm_harness.py:351-372`). 그러므로 직접 도구 ID 기록에 옛 기능·행동 키를 기대한 기존 마지막 assertion은 현재 계약과 맞지 않았다.

새 비교(`tests/integration/test_end_to_end.py:83-85`)는 실제 게이트웨이에 전달된 호출의 도구 ID가 대상 노드의 저장 시도 목록에 있는지를 검사한다. 저장 결과를 읽어 기대값으로 되돌려 쓰는 자기 확인이 아니라, 독립된 실제 호출 기록과 그래프 저장을 대조한다. 잘못된 도구 키나 누락된 시도 기록이면 계속 실패한다. 호출 1회, 실제 원본의 제안/호출 ID 연결, 단계 증거, 이벤트 순서, 목표·임무 완료 및 저장 보고 assertion은 그대로다(`43-85`). 제품의 기록 방식을 옛 이름에 맞추거나 이름별 예외를 추가하지 않았다.

루트의 기존 `data/validation-resume-loop-tests.txt`는 **1 failed, 2 passed**를 기록하며 실패는 종단 간 사례의 마지막 키 비교다. 그 출력에서 앞선 호출·증거·이벤트·임무 완료 assertion을 지난 사실과, 실제 목록 `['recon.inventory']`에 옛 키 `recon.service_discovery`가 없다는 실패를 확인했다. 이 기록은 수정 전의 좁은 원인 분류 근거다. 워커의 후속 단일 진단을 최종 통과로 사용하지 않았고, 이번 두 수정 이후 관련/필수 CI 통과 결과는 루트의 다음 검증에서 확인해야 한다.

사용자 지정 계정의 실제 LLM 시도에서 도구 호출 3회와 미해결 종료가 있었다는 전달 내용은 이번 소스 판정과 분리한다. 주장 기록 호출이 증거에 없으므로 전체 라이브 계약 검증은 여전히 미완료다. 이번 리뷰의 필수 소스 지적 없음이나 테스트 대역 보완을 그 라이브 흐름의 성공 근거로 사용하지 않는다.

## 공통 실행 파이프라인의 선택 도구 조회 조립 재리뷰 — 작업 트리 수정

이번 범위는 `tests/integration/test_common_action_pipeline.py:280-284`에서 실제 정책 담당에 동일 게이트웨이의 공개 도구 조회를 추가한 한 곳과 그 테스트의 세 실행 조합이다. diff는 해당 생성자 인자 추가와 줄바꿈뿐이며 제품 소스·입력·정책·assertion 변경은 없다. 기존 실행 루프/타입 대역 리뷰는 반복하지 않았고, 별도 실행 잠금 실패와 실제 LLM 실험은 범위에서 제외했다. 리뷰어는 이 절만 추가했으며 제품·테스트 수정, 새 실행, 커밋을 하지 않았다.

**판정: 반영 타당, 이번 수정과 확인한 영향 경로에서 새 필수 지적 없음.** 선택 도구를 해석하는 공개 조회의 누락을 테스트 조립 지점에서 보완했다. 루트는 관련 세 조합과 필수 CI 검증을 진행할 수 있다. 전체 검사나 라이브 흐름의 통과 판정은 별도 실행 결과가 필요하다.

### 기준선 실패와 실제 앱 조립의 대조

기존 `data/validation-resume-pytest-py310.txt`는 **1 failed, 168 passed, 4 skipped**를 기록한다. 첫 실패는 페이지 읽기·프로세스 내부 실행 조합이 조사 보류 대신 승인 대기로 끝난 것이다. `data/repro-live-run-04/diagnostics.txt`도 실행 담당이 선택 도구 ID를 전달했지만 정책 담당의 설명 조회가 빠져 위험도와 명령 정책이 미확인으로 처리됐다고 기록한다. 이 기록은 루트/워커의 기존 재현 증거를 읽은 것이며 리뷰어가 새로 재현한 결과가 아니다.

소스에서도 선택 도구가 있는 경우 정책 담당은 해당 설명의 위험도를 사용하고, 조회가 안 되면 미확인 위험도로 사람 승인을 요구한다(`src/redteam/control/service.py:312-337`). 명령 해석 불가 역시 사람 승인을 요구하며 기존 LOW 자동 승인 상한으로 이를 무시하지 않는다(`control/policy.py:316-340`, `control/service.py:398-405`). 새 인자는 이 검사를 제거하는 대신 실제 선택한 도구의 등록 설명을 제공한다. 실제 앱의 두 조립 경로도 카탈로그의 공개 조회를 같은 인자로 주입한다(`src/redteam/app/bootstrap.py:356-365,640-653`). 게이트웨이 조회는 내부 등록 카탈로그에서 설명 스냅샷을 가져오며(`capability/gateway.py:97-100`), 이 테스트의 실행·후보 카탈로그도 같은 게이트웨이다(`test_common_action_pipeline.py:286-291`). 별도 허용 목록·이름별 예외·무조건 허용 판정을 추가하지 않았다.

### 세 실행 조합과 유지된 검사

영향 범위는 페이지 읽기·프로세스 내부, 웹 검색·프로세스 내부, 웹 검색·stdio의 세 조합이다(`test_common_action_pipeline.py:203-208`). 두 프로세스 내부 조합은 실제 MCP 서버 객체와 클라이언트를 사용하고, 페이지 요청은 HTTP 모의 응답에, 검색 요청은 합성 제공자에 연결한다(`76-104`, `tests/integration/test_page_text_mcp.py:64-93`). stdio 조합은 기존 설정 경로·해시와 테스트 자식 서버를 사용해 MCP 게이트웨이를 구성한다(`test_common_action_pipeline.py:217-239`, `tests/integration/_web_search_stdio_fake.py:11-30`). 전송을 선택한 뒤 같은 정책 조립으로 합류하므로 새 조회 연결은 세 조합 모두에서 그 전송이 발견한 등록 설명을 읽는다. 합성 HTTP/검색 또는 stdio 호출을 이번 리뷰에서 실제 수행했다는 의미는 아니다.

모델 행동은 등록 도구를 직접 선택하고 페이지 URL 또는 검색어를 전달한다(`test_common_action_pipeline.py:265-274`). 기존 대상·입력 컴파일, 실제 정책/승인, 호출 직전 현재 판정, 게이트웨이의 등록 도구/서버·건강·입출력 처리 및 공통 원본 저장 경로를 그대로 사용한다. 이번 인자 추가는 해당 소비 경로의 코드나 데이터 규격을 변경하지 않는다. 실제 정책 담당과 기존 위험도 담당도 유지됐으며 범위·교전규칙·예산·속도·승인 설정을 바꾸지 않았다.

검사 기대값은 그대로다(`test_common_action_pipeline.py:308-328`). 실제 호출 1회, 페이지/검색 제공자 호출 수, 성공 도구 원본 1개, 모델에 제공한 실제 도구 설명·행동 목록을 확인한다. 검색 반환 URL이 새 승인 대상으로 등록되지 않는 것, 허용 호스트가 변하지 않는 것, 조사용 자료를 취약점 발견으로 승격하지 않는 것도 계속 검사한다. stdio 조합은 프로세스 내부 제공자 호출 목록 대신 실제 도구 원본 검사를 사용한다는 기존 검증 범위도 변경하지 않았다.

같은 파일 앞부분의 별도 정책 생성자는 현재 선택 도구 ID를 주지 않는 옛 행동 제안/문맥을 검사한다(`161-183`). 따라서 해당 지점을 이번 직접 선택 조립 누락과 동일한 실패로 판단할 근거가 없다. 미확인 생성자들을 일괄 수정하지 않은 것은 적절하며 이번 리뷰도 그 범위를 늘리지 않는다.

현재 세 조합의 수정 후 실행 결과는 아직 확인하지 않았다. 기준선에서 첫 조합만 실패 관측됐고, 다른 두 조합은 같은 조립을 소비한다는 소스 근거와 실제 통과 여부를 구분한다. 별도 실행 잠금 실패의 분류 및 실제 LLM 두 번째 실험은 이번 판정으로 해결·통과 처리하지 않는다. **이 조립 수정의 독립 소스 리뷰는 종료할 수 있으나, 전체 필수 검증과 라이브 계약 검증의 완료 여부는 별도로 남는다.**

## 루트 조회 공개 계약 및 역할 선택 의존 경계 — 수정 전 독립 소스 조사

이번 요청은 수정안 판단을 위한 두 경로의 소스 조사다. 루트 조회 계약 공개, 공통 조회 담당과 다른 제어 행동의 입력 소비, 역할 선택의 조립/런타임 소유자를 대조했다. 제품·테스트 수정, 자동 검사, 실제 호출을 수행하지 않고 이 절만 추가했다. 전체 Linux 검사 38개 실패를 이번 두 문제만으로 설명하거나 전체 수정 완료로 판정하지 않는다.

**판정: 루트 조회 계약의 공개 누락(CR23)과 기능 계층 직접 import 경계 위반(CR24)을 확인했다. 두 수정 방향은 아래 조건으로 반영 권고한다.** 공통 조회 모델 재사용 및 역할 선택 책임 이관으로 해결할 수 있으며, 판단 예산 증가·고정 도구 순서·새 조회 저장소·아키텍처 검사 예외는 필요하지 않다. 아직 수정 결과를 승인하거나 전체 검증 완료로 판단한 리뷰가 아니다.

### CR23 [P2] — 루트 모델에게 공개하지 않은 조회 요청 규격을 소비 단계에서 요구한다

**소스 근거:** 루트 다음 행동의 조회 영역은 임의 객체다(`src/redteam/orchestration/engine.py:137-165`). 응답 스키마 작성은 완료 영역만 공통 모델로 구체화한다(`679-692`). 루트 조회 소비는 그 임의 객체를 공통 조회 요청 모델로 다시 검증한다(`1690-1705`). 해당 모델은 단일 증거 ID를 필수로 요구하며 offset·limit·query와 그 범위를 정의한다(`orchestration/evidence_access.py:62-69`). 시스템 문맥은 주소 참조의 target/source_evidence_id/raw_path만 설명한다(`engine.py:247-248`). 계획 §2.7 및 B0/E1의 조회 계약 공개 요구(`implementation-plan.md:90-96,185`)에 대한 루트 입력 공개가 빠졌다.

**실제 관측과 한계:** `data/live-tests/validation-contract-20261005-resume/trial-04/data/reports/run_a1d596f9a0f5.json`은 호출 2회, 조회 이력 빈 목록, planning_error 종료를 기록한다. 마지막 진단은 정상 판단 한도 8/사용 8, 보정 한도 3/사용 0, 총 상한 11이며, 보존된 시도 5~8은 응답 검증 통과 → read_evidence 제안 → `model_validation at $` 거절을 반복한다. `obs.jsonl`에도 조회 행동 제안이 반복된다. **원문 요청 객체와 정확한 ValidationError 필드/종류는 저장돼 있지 않아, 실제 잘못된 값이 증거 ID 누락인지 복수 ID 형식인지 범위 값 오류인지 확정하지 않는다.** generic 진단의 ‘required model fields and validation rules’는 특정 필수 필드 누락만을 뜻하지 않는다. 소스의 숨겨진 계약은 확정된 문제이고, 이 실험이 그 문제와 일치하는 거절 경로를 보여준다는 판단을 실제 요청 모양을 복원한 주장과 구분한다.

**반례 검토:** 워커는 같은 모델의 스키마를 응답의 조회 요청 항목에 명시하고, 실행도 동일 조회 담당을 사용한다(`delegated_runtime.py:413,551-560`). 이는 공통 계약의 존재·재사용 근거이며 루트 문맥의 공개를 대신하지 않는다. 루트 문맥에는 실제 증거 ID/인덱스와 이전 읽기 결과가 있다(`engine.py:940-945`). 완료 검수도 코드를 통해 원본을 직접 읽어 전달한다(`2577-2594`). 그러나 둘 다 루트가 생성해야 하는 조회 요청의 필수 필드·범위·질의 규격을 공개하지 않는다. 이전 성공 조회가 있어야 생기는 복원 결과나 증거 출력의 ID를 요청 스키마 공개와 동일하게 볼 수 없다. 확인한 실제 루트 입력/시스템/로컬 도구 노출에서 이 누락을 해소하는 별도 요청 계약은 찾지 못했다.

**수정 설계 — 최소 반영 권고:** 조회 모델을 새로 복제하지 말고 기존 공통 모델의 JSON Schema를 루트 판단 문맥에 사용 모드·입력 위치와 함께 명시한다. 루트의 read_evidence가 `evidence_request`에 단일 증거 ID·범위·질의를 받는다는 연결까지 공개하고, 소비 단계는 같은 모델/조회 담당을 유지한다. 이는 현재 임의 객체 영역을 유지하면서 공통 계약을 실제 모델 문맥에 전달하는 좁은 해법이다. 응답 스키마 자체에 검사를 붙이는 구현을 택한다면 **읽기 모드에만** 해당 모델을 적용해야 한다. 현재 모델 제공자 경로에서 확인하지 않은 조건부 스키마 지원이나 모든 행동의 새 거대 분기 스키마를 필수 해법으로 삼지 않는다. 잘못된 조회 입력의 보정 안내도 필요하다면 기존 진단 경로에 공개 모델의 필수 필드/위치만 전달하며 원문 값이나 내부 추론을 기록하지 않는다.

**전역 조회 스키마 치환은 기각:** 증거 복구는 같은 영역에서 증거 ID를 꺼내고(`engine.py:1787-1798`), 실행 작업 재확인은 증거 ID 없이 작업 ID를 받는다(`1819-1823,2432-2443`). hold/actions 등에서 빈 조회 객체를 제출하는 기존 계약도 있다. 해당 영역 전체를 필수 증거 ID가 있는 조회 모델로 바꾸면 유효한 작업 재확인과 다른 행동을 거절한다. 복구/재확인의 기존 실행·저장 소비는 유지하고 조회 계약 공개만 모드에 맞게 연결해야 한다. 예산·보정 분류 변경, 숨겨진 필드 추정, 고정 행동 순서나 새 기능을 이번 수정에 섞을 근거는 없다. CR23은 **필수 수정 반영 권고**다.

### CR24 [P2] — 역할 선택 소비가 기능 계층의 파일/선택 구현에 직접 의존한다

**근거와 실제 실패:** 루트 `engine.py:18`과 워커 `delegated_runtime.py:6`은 `redteam.capability.role_manifest`에서 직접 선택 함수를 가져온다. 저장된 Linux 3.14 전체 로그는 두 파일을 지목한 `test_orchestration_never_imports_capability_or_control_directly`와 역방향 경계 검사의 실패를 기록한다(`data/validation-resume-linux-pytest-py314.txt`; 검사 소스 `tests/unit/test_control_plane_bypass.py:70-94`). 실행 의존성의 기존 설명도 다른 팀은 공통 포트로 연결하고 역할 등록은 오케스트레이션 내부 책임으로 구분한다(`orchestration/context.py:1-6,20-42`). 이 import는 현재 명시된 계층 경계와 맞지 않는다. 단지 이름에 capability가 있다는 추정이나 선택이 실제 정책 승인을 우회한다는 주장은 아니다.

**실제 소비 책임:** 역할 정의는 실행 도구 선택 메타데이터를 소유한다(`orchestration/agents/definition.py:61-85`). 루트는 도구 문맥 구성, 행동 컴파일 시 역할 가시성, 실행/재개 시 현재 역할 가시성을 소비한다(`engine.py:814,2012,3045-3048`). 워커는 같은 역할 도구 뷰와 방법론 참조 범위를 소비한다(`delegated_runtime.py:353-375`). 현재 기능 계층 모듈은 이 공통 소비 규칙뿐 아니라 YAML 파일 읽기, 기본 파일 선택, 별칭 정규화와 조립까지 함께 소유한다(`capability/role_manifest.py:56-62,103-179,183-236`). 실제 도구 설명 조회에는 이미 `core.ports.ToolCatalog`의 개별/전체 목록 계약이 있다. 이 런타임 소비에 기능 계층의 구체 모듈이 필요하지 않다.

**수정 설계 — 책임 이관으로 반영 권고:** 파일 경로 해석·사용자/패키지/기본 우선순위·별칭의 물리 도구 ID 정규화·선택 지문 연결은 기존 앱 조립에서 수행한다(`app/bootstrap.py:346-353,735-741`). 확정된 선택은 기존 역할 정의에 주입한다. 순수 선택 데이터와 여러 영역이 재사용하는 술어는 다른 제품 영역을 import하지 않는 공통 계약 담당으로 이관하고, 역할 정의를 받아 도구 뷰/가시성/방법론 범위를 적용하는 런타임 담당은 역할 영역에 둔다. 도구 목록은 기존 공통 카탈로그 포트로 읽는다. 공통 계층에 역할 등록부나 파일 I/O를 옮기거나, 별도 역할별 카탈로그 저장소·새 포트를 만드는 것은 필요하지 않다. 기존 파일 로더가 공통 계약/순수 술어를 재사용하도록 연결하면 판단 규칙도 복제하지 않는다.

이관 시 유지할 의미는 사용자 파일→인라인/패키지→기본→역할 기능의 기존 우선순위, 명시 빈 선택의 도구 없음, 선택 없음의 기존 폴백, 별칭 정규화, AND/OR 선택 의미, 방법론 참조가 도구를 필터하지 않는 것, 조립된 선택 지문의 재개 비교다. 조립을 생략한 테스트가 기본 선택 의미를 필요로 한다면 기존 공용 조립을 사용하거나 같은 소유 담당의 초기화를 연결해야 한다. 런타임이 몰래 파일을 다시 읽거나 조립 누락을 무조건 허용으로 처리해 경계를 해결해서는 안 된다. 루트 문맥·워커·컴파일·현재 행동/재개 검사에 동일 선택 의미를 전달해야 한다. 이 의미들은 기존 역할 파일 테스트(`tests/unit/test_role_tools_manifest.py:52-128`)의 확인 대상이며 이번 조사에서 테스트를 실행했다는 뜻은 아니다.

직접 import를 이름만 바꾼 중계로 숨기거나 아키텍처 검사에 예외를 넣는 안은 **기각**한다. 현재 기능 선택은 실행 권한이 아니므로 실제 정책/승인 책임도 유지한다. CR24는 **필수 수정 반영 권고**이며, 소유 책임을 이관한 최종 diff와 모든 실제 소비를 수정 후 재리뷰해야 한다.

두 조사 외 전체 CI 실패의 원인 분류는 구현 담당의 별도 범위다. 이번 소스 판단은 실제 조회 재개 성공이나 전체 LLM→도구→기록→완료 검증을 확인하지 않았다. **CR23/CR24의 수정·독립 재리뷰와 관련 검증이 남아 있으며 전체 완료 판정은 불가**다.

## 지역 카탈로그 및 실행 MCP 탐색 대역의 독립 묶음 재리뷰

범위는 `tests/unit/test_orchestration_nodes.py`, `tests/integration/test_execution_agent_e2e.py`, `tests/integration/test_execution_mcp.py`의 작업 트리 diff와 직접 영향받는 카탈로그·탐색·고정 규격·정책/실행/증거 소비다. 진행 중인 루트의 CR23/CR24 구현과 다른 워커 파일은 승인 범위에서 제외했다. 제품·테스트 수정이나 새 실행 없이 이 절만 추가했다.

**판정: 세 diff 자체는 반영 타당. 다만 수정한 실행 Agent 종단 간 파일의 루프 조립에 선택 도구 설명 조회가 아직 빠져 있어 CR25(P2) 필수 잔여 지적 1건을 확인했다.** 목록 조회와 탐색 메타데이터 수정이 승인·고정 매니페스트 검사를 약화했다는 근거는 없다. 그러나 이 묶음의 실제 루프 소비까지 필수 지적 없음으로 종료할 수는 없다. 전체 CI/라이브 완료 판정도 하지 않는다.

### 카탈로그 정본과 탐색 메타데이터 보존

지역 카탈로그의 전체 목록 조회(`test_orchestration_nodes.py:157-158`)는 개별·기능·행동별 조회와 같은 기존 도구 사전의 값을 반환한다(`140-155`). 별도 등록 목록이나 도구별 분기를 만들지 않는다. 공통 카탈로그의 전체 목록 계약(`src/redteam/core/ports/tool_catalog.py:19-25`)을 보완한 변경이며, 도구의 행동 목록이 비어 있어도 전체 조회에는 남는다. 기존 계획의 가설 선등록·빈 후보·실패/보류 등 소비 사례의 제안과 assertion은 diff에서 변경되지 않았다. 기존 Linux 로그에 해당 지역 대역의 전체 조회 누락과 관련 8개 실패가 있다는 사실을 수정 후 통과 결과로 바꾸어 읽지 않는다.

두 탐색 대역은 SDK의 실제 서버 목록에서 원격 도구를 만들 때 기존 공개 수집 도우미 `remote_tool_metadata`로 부가 메타데이터도 전달한다(`test_execution_agent_e2e.py:90-100`, `test_execution_mcp.py:80-90`). 이 도우미는 서버가 광고한 meta와 annotations를 복사할 뿐, 고정 매니페스트에서 정답을 채우거나 도구 이름을 보고 필드를 만들어내지 않는다(`capability/adapters/mcp/transport.py:29-42`). 실제 SDK 전송도 같은 도우미를 사용한다(`116-136`). 실제 SDK 탐색 결과와 테스트 전송 사이에서 누락됐던 정보를 보존하는 적절한 변경이다.

생산 실행 서버는 실행/작업 시작 도구의 명령 입력 선언을 메타데이터로 광고한다(`capability/servers/execution.py:1163-1165`). 어댑터는 기존 공통 제공자 키만 해석해 도구 설명의 명령 입력과 대상 계약으로 전달한다(`adapters/mcp/streamable_http.py:76,119-135`). 고정 실행 규격은 계속 필수·선택 입력, 행동, 대상 유형, 출력 스키마, **명령 입력 필드의 일치**, 고정 자산·입력 타입·배열 상한을 검사한다(`capability/execution_manifest.py:66-98`). 테스트도 발견된 각 설명에 이 검사를 그대로 적용한다(`test_execution_agent_e2e.py:147-153`, `test_execution_mcp.py:214-218`). meta가 없거나 다른 명령 필드를 광고하면 검사는 여전히 불일치로 거절한다. 한 줄 보완은 이 검사를 우회하거나 서버 결과를 고정 규격 값으로 덮어쓰지 않는다.

### 유지된 허가·거절·실행 소비와 기준선 한계

실행 MCP 통합 사례는 실제 정책 담당의 승인 요구, 승인 전 호출 구성 거절 및 프로세스 시작 0회, 승인 후 실제 서버 호출 성공과 시작 수, 다른 자산의 정책 거절을 유지한다(`test_execution_mcp.py:261-300,346-356`). 실행 Agent 사례도 실제 실행/원본 저장, 교전규칙 거절 시 시작 0회, 서버의 미허용 실행 파일 거절 시 시작 0회 assertion을 유지한다(`test_execution_agent_e2e.py:312-401`). Docker 프로세스 대역, MCP 서버와 전송, 실제 Docker 선택 실행의 조건·검사는 변경하지 않았다. 이 리뷰에서 대역 프로세스나 stdio/Docker를 실행한 것은 아니다.

기존 Linux 전체 로그(`data/validation-resume-linux-pytest-py314.txt`)의 네 탐색 실패에는 실행 도구의 명령 입력 목록이 빈 것으로 기록돼 있고 고정 매니페스트 대조에서 거절된다. 실제 전송과 서버는 위 메타데이터를 생산/보존하므로, 이번 대역 보완은 이 차이를 바로잡는다. 소스의 일치 판단을 생산 stdio 전체 실행 성공으로 확대하지 않는다. 탐색 실패를 해소한 뒤 처음 도달하는 소비 경로의 잔여 문제는 다음 지적과 별개다.

### CR25 [P2] — 실행 Agent 루프 조립에 선택 도구 설명 조회가 남아 있다

**근거:** `tests/integration/test_execution_agent_e2e.py:292-305`의 공통 루프 조립은 실제 정책 담당에 위험도 조회만 전달한다. 같은 게이트웨이를 실행·도구 카탈로그에 넣지만, 선택 도구 설명의 공개 조회 연결은 없다. 공용 테스트 조립은 전달받은 정책 객체를 그대로 사용하며 그 누락을 보충하지 않는다(`tests/fakes/bootstrap.py:51-54`). 해당 파일의 모델 행동은 도구 ID를 제출하며(`test_execution_agent_e2e.py:237-265`), 기존 공개 행동 계약의 기본은 직접 선택이다. 정책 단계는 실제 선택 도구 ID를 문맥에 전달한다(`src/redteam/orchestration/nodes/policy.py:165-174`). 진행 중인 루트 구현 자체를 새로 리뷰하거나 승인한 지적은 아니다.

**실패 조건:** 메타데이터 전달 보완으로 고정 탐색 검사를 통과한 뒤, 실제 루프가 첫 선택 도구 행동을 정책에 제출한다. 설명 조회가 없으면 해당 도구 설명은 None이며, 직접 선택의 위험도를 미확인으로 처리하고 명령 해석 불가를 사람 승인 사유로 남긴다(`src/redteam/control/service.py:312-337`, `control/policy.py:316-340`). 시험 설정의 HIGH 자동 승인 상한(`test_execution_agent_e2e.py:183`)도 해석 불가 사람 승인을 무시하지 않는다(`control/service.py:398-405`). 그래서 기대하는 실행/원본 저장과 후속 hold에 도달할 수 없다. 이 경로를 수정 후 새 테스트에서 실제 관측했다는 주장은 하지 않는다. 기존 앞선 탐색 실패가 이 조립 누락까지 검증한 것도 아니다.

**수정 방향:** 공통 루프 조립의 실제 정책 담당에 같은 게이트웨이의 공개 도구 조회를 주입한다. 생산 조립과 앞서 검토한 다른 루프의 동일 연결을 재사용하는 한 곳 수정이며 정책을 대역/무조건 허용으로 바꾸거나 승인 상한·기대값을 약화할 필요는 없다. 같은 파일의 별도 교전규칙 거절 사례와 실행 MCP 통합 사례는 선택 도구 ID 없는 기존 행동 문맥을 사용하므로, 이를 동일 실패로 보고 모든 생성자를 일괄 변경하지 않는다. CR25는 **필수 수정 반영 권고**다. 이 좁은 후속 diff를 재리뷰한 뒤 해당 독립 묶음의 관련 검증으로 진행해야 한다.

CR23/CR24 구현 및 다른 Linux 실패의 분류는 별도 범위로 남는다. 이번 세 diff가 바르게 원본 목록/메타데이터를 전달한다는 판단과, 해당 파일들의 모든 기능 기대값이 최종 통과했다는 판단은 구분한다. 제품의 새로운 변경이나 실제 LLM 전체 흐름을 이번 대역 리뷰로 승인하지 않는다.

## 사용자 추가 요구의 거절 입력 상세 진단 — 독립 설계 검토

검토 대상은 `implementation-plan.md` 상단의 ‘사용자 추가 요구 — 거절 입력을 구분할 수 있는 상세 진단’과 그 구현 경계다. 사용자가 조회 요청의 번호 누락·복수 값 형태·범위 오류를 구별하는 기록과 그 기록을 통한 수정을 명시 요구했으므로, 이 진단 보완은 가상의 문제를 위한 확장이 아니다. 제품·테스트 수정이나 실행 없이 실제 기존 진단 생산→판단 trace/피드백→상태→저장 보고 경로를 대조하고 이 절만 추가했다.

**설계 판정: 기존 제안 구조 투영과 공통 진단 계약을 확장하는 방향으로 반영 권고한다. 아래 조건은 구현에서 필요하다.** 별도 저장소·로거, 전체 모델 응답/프롬프트 기록, 입력 판정·예산·정상/보정 분류 변경 없이 요구를 표현할 수 있다. 설계 승인 범위이며 아직 구현이나 새 관측의 성공 판정은 아니다. 앞선 독립 테스트 묶음의 CR25 잔여 판정 및 CR23/CR24 구현 리뷰와도 별개다.

### 기존 누락과 실제 연결 지점

현재 제안 투영은 행동 모드·이유·일부 참조만 보존하고 조회 요청을 남기지 않는다(`src/redteam/orchestration/diagnostics.py:116-158`). Pydantic 진단은 입력·context를 제외한 오류를 받아도 첫 오류의 일반 요약만 남기며, 조회의 증거 ID·범위·질의 필드는 공통 위치 목록에 없어 위치가 `$`로 축약된다(`18-63,160-170,235-263`). 이 상태로는 같은 거절 요약에서 누락과 배열 제출, 수치 범위 오류를 구분할 수 없다.

루트의 기존 제안 trace와 결정 이벤트는 응답이 반환된 이후에만 만들어진다(`engine.py:565-585`). 구조화 응답 담당은 파싱한 후보를 바로 스키마 검사하고 실패하면 반환하지 않는다(`cognition.py:504-520`). 따라서 제안 투영만 늘리면 **스키마에서 먼저 거절된 후보의 모양은 여전히 유실된다.** 같은 안전한 구조 요약을 파싱 후·스키마 검사 전에 기존 판단 trace에 연결하고, 외부 제공자 내부 검증 예외 경로도 공개 오류 정보만 같은 진단으로 전달해야 한다. 현재 예산 기록은 stage·attempt·결과를 이미 보존하고 기록 자체로 요청 수를 증가시키지 않는다(`cognition.py:187-199,597-624`). 새 로그 항목 때문에 실제 요청·토큰 사용량이나 정상/보정 계수를 변경하면 안 된다.

### 구조 투영과 공개 규격의 정본

제안된 존재 여부·JSON 형태·배열 개수/항목 형태는 적절하다. 요청 영역 없음, 빈 객체, 잘못된 영역 타입, 필수 항목 없음, 필수 문자열 자리에 배열, 범위 항목의 수치 타입/값을 구분할 수 있다. 문자열 내용, 증거 본문, 질의 문구는 필요하지 않다. 투영기는 **검증되지 않은 후보를 입력으로 받는 담당**이므로, 후보가 객체가 아니거나 조회 영역/행동 목록/항목이 잘못된 타입이어도 `.get`·인덱싱·반복 처리에서 실패해서 원래 거절을 덮으면 안 된다. 이런 경우 타입과 제공 가능한 개수만 보존한다.

공개 필드·필수 여부·위치의 기준은 소비자가 실제 사용하는 모델의 필드/JSON Schema로부터 가져와야 한다. 기존 `_schema_fields` 투영과 공통 조회 모델(`diagnostics.py:173-184`, `evidence_access.py:62-69`)을 재사용할 수 있다. 진단 담당이 루트 모델을 직접 import하여 순환 의존을 만들거나, 조회 모델을 복제하거나, 필수 필드·min/max 값을 별도 목록에 다시 정의하면 안 된다. 실제 소비자가 사용한 계약/입력 위치를 진단으로 넘겨 공개 위치를 구성하는 방식이 맞다. 예컨대 루트의 조회 요청 내부 오류와 워커의 요청 배열 내부 오류를 각자의 실제 공개 입력 위치에 연결해야 한다.

알 수 없는 키는 필드 이름·경로 조각·값을 그대로 기록하지 않는다. 알 수 없는 항목 수, JSON 타입, 제한된 배열 개수/항목 타입 분포 같은 구조 요약만 허용한다. 번호 목록으로 보이는 임의 별칭들을 진단용 고정 목록에 추가하거나 그 값을 보고 ‘올바른 증거 번호’로 보정하지 않는다. 필수 증거 ID 누락과 알 수 없는 배열 항목의 존재는 구별해 기록하되, 알 수 없는 키의 실제 이름을 보존하지 못한 경우 특정 별칭을 썼다고 추정하지 않는다. 목록/중첩 깊이/샘플 수를 제한하고 전체 개수와 요약 대상 개수·생략 여부를 구분한다.

### 읽기 범위 숫자와 구조화 오류

사용자가 허용한 읽기 범위 숫자는 조회 동작의 제어 값이므로 해당 공개 제어 항목에 한해 실제 값을 로그에 남기는 것이 적절하다. 모든 숫자 입력이나 예외 입력을 기록할 근거는 아니다. 숫자 표시 허용은 조회 계약 담당의 제어 의미에 묶고, 필드 규격이나 검증 범위를 재정의하는 별도 상태로 만들지 않는다. bool을 숫자로 오인하거나 문자열을 강제로 숫자로 바꾸지 않는다. 유효 범위를 벗어난 정상 크기 숫자도 그대로 보여야 범위 오류를 진단할 수 있으므로 **로그에서 범위를 clamp하거나 원래 입력을 수정하지 않는다.** 비유한 수치나 지나치게 큰 수치/표현은 타입·생략 상태 등의 제한된 요약으로 남기고 숫자 직렬화가 로그 크기/처리를 깨지 않게 한다. 이 제한은 로그 투영에만 적용하며 실제 입력의 수용 규칙은 유지한다.

기존 진단에 기본값이 빈, 길이가 제한된 검증 항목 목록을 추가하여 라이브러리의 오류 규칙과 공개 위치만 보존하는 안도 타당하다. 누락, 문자열 타입, 정수 파싱/타입, 최소·최대 위반 등은 원문 메시지 없이 규칙 식별자로 구분한다. Pydantic은 기존 `include_input=False`, `include_context=False`, `include_url=False`를 유지하고, 반환된 오류의 msg·input·context나 예외 문자열을 복사하지 않는다. JSON Schema 오류 역시 validator와 계약으로 확인한 위치/필수 항목만 투영한다. required 오류는 부모 객체 위치만 나올 수 있으므로 실제 스키마의 필수 항목과 입력의 존재 여부로 누락된 **공개** 필드를 표시할 수 있다. anyOf/oneOf 내부 오류를 사용할 경우에도 제한된 규칙/공개 위치로만 변환하고 예외 context 객체 자체는 저장하지 않는다. 사용자 입력이 섞인 사용자 정의 오류 코드·알 수 없는 경로는 그대로 출력하지 않는다.

첫 안전 오류 규칙/위치를 기존 모델 피드백에 전달하고, 제한된 전체 항목은 저장 진단에 남기는 구성으로 충분하다. code·kind·재시도 여부의 기존 의미를 로그 개선만으로 바꾸지 않는다. 스키마 거절과 모델 검증 거절의 세부 원인은 공통 투영 규칙을 사용하며 제안의 구조 요약과 동일 stage/attempt에 연결한다. 추가 프레임으로 기존 20개 trace가 빨리 밀려날 수 있으므로, 구조와 거절 원인이 다른 시도처럼 보이거나 마지막 원인이 사라지지 않도록 기존 프레임 안에 통합하거나 최소한의 연결을 유지한다. 이를 위해 trace 상한/모델 예산을 늘릴 필요는 없다.

### 피드백·저장 보고·미확인 정보의 경계

진단의 원인은 이미 상태의 현재 진단/이력과 보고로 전달된다(`state.py:92-93`, `reporting.py:396-397,538-539`). 기본값 있는 공통 진단 필드를 추가하면 기존 `model_dump_json` 저장 경로를 재사용할 수 있고 옛 보고도 상세 항목 없는 상태로 읽을 수 있다(`app/cli/commands/report.py:42`). JSON 저장과 모델 피드백의 실제 전달을 확인해야 한다. Markdown 출력은 현재 cause에서 요약만 표시하므로(`74-103`), 그 화면에서도 세부 원인을 보여줄 범위가 있다면 공통 상세 항목을 투영하면 되고 별도 사본을 저장하지 않는다.

모델 제공자 내부에서 거절되어 파싱한 후보가 없는 경우에는 전체 요청 구조를 로그에서 새로 얻을 수 있다고 보장하지 않는다. 공개 예외에서 안전하게 확인할 수 있는 부분 구조/규칙/위치만 투영하고 구조 미확인을 명시한다. invalid JSON에서도 문자열 원문을 저장하거나 정규식으로 비밀 포함 응답을 뜯어 복원하지 않는다. 과거 trial04의 미저장 요청은 여전히 복원 불가이며 새 로그를 그 과거 응답의 증명으로 읽지 않는다.

**반영 권고:** 공개 계약을 정본으로 한 안전 구조 투영, bounded 규칙/위치 목록, 형식 거절 전 기존 trace 연결, 같은 원인의 모델 피드백/저장 보고 전달. **기각:** 원문 응답·프롬프트·예외 input/context/msg 저장, 알 수 없는 키 공개, 숫자 전체 기록, 필드/검증 규격 복제, 새 로거/저장소, 로그를 위한 입력·예산·분류 변경. 구현 완료 후 이 생산→거절→피드백→저장 소비 경로를 독립 재리뷰해야 하며, 실제 원인 판정은 새 관측 로그를 얻은 뒤에 해야 한다. 전체 CI/라이브 완료 판정은 이번 설계 검토에 포함하지 않는다.

## 상세 진단 구현 및 CR23 문맥 공개 — 독립 소스 묶음 재리뷰

범위는 `orchestration/diagnostics.py`, `orchestration/cognition.py`, `orchestration/engine.py`의 조회 문맥/거절 진단 부분, `app/cli/commands/report.py`, `tests/unit/test_orchestration_diagnostics.py`의 작업 트리 diff다. 역할 도구 뷰 import 이관과 다른 워커 변경은 이번 승인에서 제외했다. 제품·테스트 수정이나 새 실행 없이 생산→거절→피드백→trace→저장 보고를 대조하고 이 절만 추가했다.

**판정: CR23의 루트 조회 문맥 공개는 소스 기준 반영·해결. 상세 진단은 주요 정상 경로가 연결됐으나 CR26·CR27(P2) 필수 수정 2건이 남아 이 묶음을 종료할 수 없다.** 두 지적 모두 이번 구현의 실제 소비 경로에서 확인한 문제이며 새로운 기록 저장소나 예산 변경으로 해결할 필요가 없다. 역할 이관, 전체 CI와 라이브 완료를 승인하는 판정은 아니다.

### 확인된 공통 계약·로그·보고 연결

루트 문맥은 공통 조회 모델의 스키마를 조회 모드와 실제 입력 위치까지 연결해 제공하고 시스템 안내도 그 계약을 가리킨다(`src/redteam/orchestration/engine.py:249,894-898`). 조회 입력 영역을 전역 조회 전용 모델로 치환하지 않았으므로 증거 복구·실행 작업 재확인의 기존 입력은 유지된다. 이 범위에서 CR23의 공개 누락은 해결됐다. 새 라이브에서 조회가 성공했다는 실행 판정은 아니다.

조회 구조 요약은 공통 요청 모델에서 필드 규격을 얻는다(`diagnostics.py:18-21,167-183`). 문자열·질의·증거 ID의 실제 값은 복사하지 않고 형태/길이를 남긴다. 현재 숫자 제어 항목은 실제 모델의 offset/limit이며 bool·문자열을 강제 변환하지 않는다. 큰 정수는 비트 수로, 비유한 실수는 finite=false로 제한하고 알 수 없는 키는 이름 없이 개수·최대 10개 얕은 형태만 남긴다(`124-183`). 실제 입력이나 범위를 clamp하지 않고 별도 검증 규격을 복제하지 않았다.

새 진단 목록은 기본값이 빈 최대 10개 항목이고, Pydantic에서 input/msg/context를 복사하지 않으며 공개 위치와 규칙을 남긴다(`101,330-375`). JSON Schema required 거절은 스키마에 선언된 누락 필드를 위치로 투영한다(`294-309`). 첫 규칙은 기존 피드백에 포함되고 모델 거절 trace도 상세 목록을 받는다(`118-121`, `engine.py:1967-1975`). 구조화 응답 담당은 파싱한 후보의 투영을 스키마 검사 전에 계산하고 기존 response_validated/response_rejected 프레임에 붙인다(`cognition.py:513-532,620-636`). trace 프레임 수나 실제 판단/보정 소비·요청/토큰 계측을 늘리는 변경은 확인하지 않았다.

보고 JSON은 기존 공통 진단 직렬화를 재사용하고, Markdown도 현재 진단·last_cause의 상세 규칙/위치를 출력한다(`app/cli/commands/report.py:93-103`). 미파싱/미반환 응답은 구조 미확인으로 남기는 경로도 있다. 신규 테스트는 조회 번호 누락·번호 자리에 배열·음수 범위·범위 상한 위반, 질의/알 수 없는 키 제외, 스키마 거절 trace→보고 전달을 구성한다(`tests/unit/test_orchestration_diagnostics.py:183-260`). 이 테스트를 실행한 것은 아니다. 아래 두 경로는 이 테스트 묶음에서 다루지 않는다.

### CR26 [P2] — 대체 계획 제공자의 최종 제안 거절은 상세 진단 전에 유실된다

**근거:** `src/redteam/orchestration/engine.py:606-655`, 제안 프레임/이벤트의 후행 생산 `565-585`; 공개 대체 계획 계약 `orchestration/planning.py:96-106`. 공통 반환 경계는 대체 제공자가 반환한 객체를 스키마 검사한 후에야 제안 투영으로 넘긴다. 스키마 실패는 여전히 일반 ValueError로 바뀌므로 오류의 validator·공개 위치와 입력 구조가 남지 않는다.

**실제 문제가 생기는 상황:** 등록된 대체 계획 제공자가 추론 호출 없이 캐시/자체 절차의 제안을 반환하거나, 내부 추론 결과를 조합한 최종 객체를 반환한다. 그 최종 조회 영역이 잘못된 배열이거나 다른 필수 항목이 빠진 경우, 구조화 응답 담당의 새 파싱 전후 기록을 거치지 않고 공통 최종 경계에서 거절된다. 내부 추론을 거친 경우에도 보존된 프레임은 내부 결과이지 후처리한 최종 실패 제안의 구조가 아니다. 이후 generic ValueError에서 원래 오류 규칙·위치를 복구할 수 없고, `_ask`의 제안 이벤트도 실행되지 않는다. 공개 포트가 이 대체 절차를 지원하므로 가상의 새 제공자를 위한 확장이 아니다.

**수정 방향:** 최종 제공자 반환 경계에서 공통 안전 투영을 검증 전에 계산하고, 기존 스키마 진단으로 만든 공개 규칙/위치를 기존 trace/첨부 진단에 연결해 상위 소비자가 받을 수 있게 한다. 비객체/직렬화 불가 반환은 관측 가능한 형태와 기존 실패 의미를 유지한다. 이미 내부 추론에서 같은 결과를 기록한 경우 불필요한 프레임 증가를 피하고, 제공자 반환 경계와 실제 모델 요청 계측을 혼동하지 않는다. 기본/대체 제공자 모두 입력 수용 규칙, 정상/보정 분류와 요청·토큰 계측을 그대로 유지해야 한다. 새 로거/저장소는 필요 없다. CR26은 **필수 수정 반영 권고**다.

### CR27 [P2] — 검증 전 투영이 잘못된 타입의 비조회 항목 원문을 거절 로그에 복사한다

**근거:** 안전 투영을 스키마 검사 전에 호출하는 `cognition.py:515-517`; 조회 영역 외 제안/행동 값을 그대로 고르는 `diagnostics.py:209-221,227-241`; 이 문맥을 거절 trace에 넣는 `cognition.py:632-636`; 공통 마스킹의 실제 범위 `core/contracts/mission.py:69-93`, `core/redaction.py:21-57`.

조회 영역은 형태만 남기지만 같은 투영의 이유·단계 참조·accepted 및 행동 참조는 여전히 raw 값을 복사한다. 특히 이유의 잘못된 객체/배열은 str()로 내용까지 변환한다. 예를 들어 조회 제안의 단계 참조 자리에 민감한 본문 문자열을 담은 배열이 있거나, 이유 자리에 `{"body": "opaque-private-value"}` 같은 객체가 있으면, 스키마는 타입 오류로 거절하지만 그 **거절 전 투영**에는 배열 원문 또는 객체를 문자열로 만든 내용이 들어간다. 행동의 도구/대상 참조에 잘못된 컨테이너를 넣은 경우도 같다. 해당 키/값은 비밀 이름·문구 정규식에 해당하지 않아 기존 마스킹만으로 제거되지 않는다. 그러므로 전체 잘못된 입력을 저장하지 않는다는 경계를 조회 필드 하나의 안전 투영만으로 보장할 수 없다. 큰 컨테이너를 참조 항목에 넣으면 얕은 형태 제한도 우회한다.

이 입력 조합은 소스 경로를 따라 확인한 실패 조건이며, 이번 리뷰에서 실제 입력 실행이나 비밀 유출을 재현했다는 주장은 하지 않는다. 현재 추가 테스트는 조회 필드와 알 수 없는 키 안의 원문만 확인하며, 위 비조회 참조/이유의 잘못된 타입은 검사하지 않는다.

**수정 방향:** 검증 전의 공통 투영은 허용된 고정 모드 값과 안전한 형태만 남기거나, 각 공개 항목을 실제 규격에 맞는 스칼라로 확인한 뒤 기존 공개 참조 투영을 적용해야 한다. 잘못된 컨테이너·타입은 str()로 바꾸지 말고 제한된 형태로 남긴다. 같은 원칙을 이유, 단계/행동 참조, 스키마에 없는 mode/decision에도 적용한다. 검증 뒤의 기존 공개 이유·정상 참조 소비는 유지한다. 입력 모델을 더 엄격하게 만들거나 마스킹 정규식/키 목록에 새 이름을 반복 추가하는 해결은 부적절하다. 기존 마스킹은 마지막 방어로 재사용하되 검증 전 투영 자체가 원문을 복사하지 않아야 한다. CR27은 **필수 수정 반영 권고**다.

두 지적을 반영한 최종 경계와 안전 투영을 재리뷰한 뒤 이 독립 묶음의 관련 검증으로 진행해야 한다. 이번 판정은 정상 경로에서 상세 진단이 연결된 소스 사실과, 모든 잘못된 입력/제공자 경계에서 요구를 만족했다는 결론을 구분한다. 실제 새로운 조회 거절 원인은 아직 실행으로 확인하지 않았으며 과거 trial04의 요청 모양도 계속 미확인이다.

### 상세 진단·보고·역할 이관의 해결 범위

CR27의 검증 전 투영은 명시한 미검증 경로에서 모드·이유·단계 참조·accepted·행동 목록까지 모두 제한된 형태로 남긴다(`src/redteam/orchestration/diagnostics.py:186-222`). 잘못된 이유 객체를 str()로 변환하거나 행동 참조 컨테이너를 복사하는 이전 경로를 타지 않는다. 기본 구조화 응답 담당은 이 투영을 검사 전에 만들고 스키마 거절 프레임에 연결한다(`cognition.py:513-534,633-638`). 악성 모양의 이유·참조를 구성한 새 회귀 사례도 그 소스 경로를 대상으로 한다(`tests/unit/test_orchestration_diagnostics.py:265-286`). 조회 필드·숫자 제어 값·알 수 없는 키 투영은 직전 승인 설계의 제한을 유지한다. CR27은 해결로 판단한다.

대체 계획 반환 경계도 같은 미검증 투영을 먼저 만들고 스키마 규칙/위치와 최종 형태를 기존 진단이 붙은 ValueError 하위 오류로 전달한다(`engine.py:652-674`). 입력 수용 규칙과 제공자 호출·사용량 계측은 유지됐다. 실제 모델 요청이 없는 제공자는 기존 진행 계수만 증가하며, 새 단위 사례는 요청/토큰/미확인 사용량 0과 진행 1을 기대한다(`test_orchestration_diagnostics.py:289-313`). 검증 상세 목록은 기본값이 빈 최대 10개 필드로 기존 진단·last_cause·상태/JSON/Markdown을 재사용한다(`diagnostics.py:101,118-121,348-393`, `reporting.py:538-539`, `app/cli/commands/report.py:93-107`). 옛 진단에는 새 필드가 없어도 빈 기본값으로 읽히므로 복원 계약을 필수 새 입력으로 바꾸지 않는다. 그러나 대체 제공자의 **실제 루트 소비**는 아래 CR26 잔여가 있다.

CR23의 루트 조회 계약 공개는 유지되며, 같은 조회 입력 영역의 복구/작업 재확인은 전역 조회 스키마로 치환되지 않았다. CR24는 순수 모델·선택 술어·정규화가 공통 계약으로, 파일을 읽지 않는 역할 도구 뷰가 역할 담당으로 이관됐다. 공통 담당은 다른 제품 영역을 import하지 않으며 새 카탈로그/포트를 만들지 않는다. 실제 도구 목록은 기존 공통 포트에서 읽는다(`core/contracts/role_selection.py`, `orchestration/agents/role_view.py`).

루트의 문맥 구성·컴파일·현재 행동/재개 검사와 워커의 도구 뷰·방법론 선택은 이 역할 담당을 함께 사용한다(`engine.py:28,834,2042,3075-3078`, `delegated_runtime.py:6,355,373`). 기능 영역의 파일 해석·우선순위·별칭 정규화·선택 지문과 두 실제 앱 조립은 유지된다(`capability/role_manifest.py:60-94,111-195`, `app/bootstrap.py:346-353,735-741`). 조립된 정의는 확정 선택 스냅샷을 사용하고, 독립 역할 뷰의 미설정 선택은 정의의 기능으로 폴백하는 계약을 역할 정의 설명에도 명시했다(`agents/definition.py:85-88`). 명시 빈 선택·AND/OR·방법론 비필터 의미도 같은 공통 술어를 사용한다. 파일 변경 후 스냅샷·별칭·빈 선택의 실제 런타임 뷰 일치 assertion이 추가됐다(`tests/unit/test_role_tools_manifest.py:78-83,104-105`). 아키텍처 검사 예외나 기능/정책 담당을 우회하는 중계 import는 없다. CR24는 소스 기준 해결이다.

CR25의 실행 루프 정책 조립에는 같은 게이트웨이의 공개 조회가 추가됐다(`tests/integration/test_execution_agent_e2e.py:298-302`). 기존 실제 정책/승인 담당을 유지하고 설명 조회 누락을 보완했으므로 그 지적은 해결이다. 앞서 검토한 카탈로그·메타데이터·직접 실행 제안의 선택 도구/바인딩 전달도 그대로이며, 아래 CR28은 이 연결을 통과한 뒤의 다른 계약 문제다.

### CR26 잔여 [P2] — 최종 제안 상세 진단을 초기 거절 분기가 공통 trace에 보존하지 않는다

**근거:** 새 생산 `src/redteam/orchestration/engine.py:652-674`; 실제 다음 행동의 첫 거절 소비 `1666-1692`; 다른 제어 행동 처리 후의 거절 소비 `1986-1998`; 최종 원인 조립 `1585-1598`.

대체 제공자의 최종 스키마 오류는 다음 행동의 **첫 번째** try, 즉 `_ask`/외부 응답 모델 검증에서 발생한다. 이를 받는 초기 except는 모델 피드백과 budget.last_failure만 갱신하고 continue한다. 새로 추가한 상세 목록/문맥의 공통 rejected 프레임은 이후 제어 행동을 처리하는 **두 번째** try의 except에만 있다. 따라서 생산 진단의 한 프레임이 실제 공통 판단 trace로 전달되는 새 연결은 이 스키마 오류 경로에서 실행되지 않는다.

**실패 조건:** 대체 제공자의 최종 제안 A가 잘못된 이유/조회 영역으로 스키마 거절된다. 첨부 진단에는 A의 안전한 형태와 규칙이 존재하고 다음 모델 피드백도 규칙/위치를 받는다. 다음 제안 B가 다른 의미/모델 오류로 거절되면 last_failure가 B로 바뀐다. 최종 예산 진단의 공통 trace에는 A의 거절 형태 프레임이 없고, last_cause도 B이므로 A의 형태는 저장 보고에서 찾을 수 없다. B가 성공하여 진행한 경우도 A의 첨부 진단만으로 기존 trace/이벤트에 형태가 보존되는 것은 아니다. 이 범위에서 마지막 오류 하나가 끝까지 남은 경우의 진단 JSON과 모든 제안 거절의 실제 소비 보존을 구분해야 한다.

현재 대체 제공자 테스트는 `_propose`를 직접 호출해 첨부 진단과 계수만 검사한다(`test_orchestration_diagnostics.py:289-313`). 루트가 그 오류를 받은 뒤 다음 제안으로 진행하는 초기 소비는 확인하지 않는다. 위 조건은 소스 대조이며 새 테스트 실행으로 관측한 결과는 아니다.

**수정 방향:** 실제 초기 거절 소비에서도 생산된 안전 문맥/검증 상세를 같은 시도의 기존 공통 trace에 보존한다. 초안의 동일 제공자 반환 오류 소비도 같은 경계를 대조한다(`engine.py:1633-1649`). 공통 진단·기록 경로를 재사용하고, 이미 구조화 응답 담당이 남긴 프레임은 불필요하게 중복하지 않는다. 입력 수용·재요청·정상/보정·요청/토큰/무모델 진행 계수는 그대로 유지한다. 새로운 저장소나 원문 기록은 필요 없다. CR26은 **부분 해결·잔여 필수 반영 권고**다.

### CR28 [P2] — 직접 선택 실행 대역이 미허용 모델 명령의 옛 레시피 덮어쓰기를 기대한다

**근거:** 실행 성공 대역의 모델 응답 `tests/integration/test_execution_agent_e2e.py:237-265`, 허용 실행 파일 설정 `125`, 성공 기대 `327-339`; 공개 직접 선택 기본값 `src/redteam/orchestration/engine.py:108-116`; 옛 레시피 적용 조건 `2055-2089`; 일반 자산 기본값 담당 `2724-2757`; 서버 거절 `capability/servers/execution.py:587-595`.

이 파일은 모델 응답에 직접 선택 도구 ID를 제출하면서 실행 파일은 python, 인자는 `-c/bad`를 넣고 ‘브리지가 이를 교체한다’고 설명한다. 그러나 새 직접 선택 경로는 모델이 선택한 입력을 실행하며 옛 레시피 덮어쓰기는 legacy_action 코드 입력에만 적용한다. 일반 자산 바인딩은 자산 참조 같은 누락 기본값을 채울 뿐 실행 파일과 인자를 wc로 바꾸지 않는다. 이 대역의 서버 허용 목록에는 wc만 있다.

**실패 조건:** 탐색 메타데이터와 CR25 정책 조회가 보완돼 이 대역이 실제 직접 호출 경로에 진입한다. 미허용 python 입력이 정책 승인 또는 서버 실행 거절 경계를 통과해 wc 실행으로 변환될 수 없으므로, ‘프로세스 시작 1회·/usr/bin/wc·성공 원본’을 요구하는 성공 assertion과 입력이 맞지 않는다. Docker 선택 실행 사례도 같은 루프/모델을 재사용한다(`test_execution_agent_e2e.py:412-431`). 실제 어느 경계에서 먼저 거절되는지는 새 실행으로 확인하지 않았지만, 현재 계약에 wc로 바꾸는 생산 경로가 없다는 소스 불일치는 확정된다.

**수정 방향:** 직접 선택 성공 사례의 모델 대역이 실제 공개된 유효한 도구 입력을 제출하도록 맞추고, 현재 프로세스/인자/성공 원본 assertion은 유지한다. 미허용 실행 파일은 기존 별도 서버 거절 사례로 계속 검사한다(`377-408`). 옛 레시피의 적대적 모델 입력 덮어쓰기는 기존 브리지 단위 사례가 별도 담당한다(`tests/unit/test_execution_agent_bridge.py:118-159`). 공개 모델 응답에 숨겨진 바인딩 전환 값을 넣거나 제품 직접 선택 경로에 레시피 덮어쓰기를 재도입하지 않는다. 허용 목록·승인 검사·기대값을 완화할 필요도 없다. CR28은 **필수 수정 반영 권고**다.

### 나머지 신규 테스트 정합과 검증 경계

모바일/분석의 세 정책 조립 조회 추가는 실행·카탈로그와 같은 정본을 실제 정책에 제공하며 새 무조건 허용 대역이나 정책 상한 변경은 없다. 스키마/최종 목표 거절 사례의 정상 판단 상한 3·2·1은 유한한 대역 응답 수와 거절 횟수를 맞추고, 실제 호출 0건·어댑터 호출 없음·목표 미달 및 상태 변경 감지 assertion은 유지한다(`test_mobile_analysis_agent_e2e.py:529-556`, `test_terminal_mission_criteria.py:209-223,277-287`). 제품 예산의 기본값이나 판정 규칙은 바꾸지 않았다.

직접 호출 표시 키 두 사례는 실제 컴파일 도구 ID와 비교하고, 기존 원본 권한 전달 사례는 계획의 실제 바인딩/도구를 승인 제안에 전달한다. 방법론 사례는 조립으로 주입된 선택 메타데이터만 기본 정의 비교에서 제외하고 다른 정의 항목은 유지한다. 브리지 사례는 옛 실행 옵션의 opt-out과 등록된 직접 도구의 가시성을 구분하며 도구 목록 외 문맥 일치를 계속 검사한다. 실패 인과 사례는 외부 제안 이전의 준비 이벤트를 부모로 인정하되 그 이벤트의 이전 결정 연결도 검사한다. 이 변경들에서 기대값을 무조건 통과시키거나 정책·원본 검사를 제품에서 제거한 수정은 확인하지 않았다.

두 번째 계정 목표 검수 대역은 임의 경로 묶음 대신 실제 검수 문맥에 제공된 원본 발췌의 증거 ID를 인용한다(`test_second_principal_mission.py:111-125`). 생산 목표 검수/결과 주장 검사는 그대로다. `data/baseline_second_principal.json`은 수정 전 목표 검수 단계의 invalid_json→보정 한도 종료를 기록하며, 이번 대역이 현재 공개 payload를 읽게 만든 근거로만 사용했다. 그 진단을 수정 후 목표 달성 결과로 읽지 않는다.

읽은 Linux 3.14 기준선 JUnit은 2874 사례, 실패 38, skip 52이며 실행 잠금 관련 주요 사례는 실패가 없다(`data/validation-resume-linux/results/pytest-py314.xml`). 실행 잠금 제품 소스는 이번 diff에 없다. 별도 Windows 관측 실패를 이번 제품 수정의 해소나 Linux 재실행 성공으로 표현하지 않는다. 이전 111/50/11 결과도 현재 최종 diff의 통과 증거가 아니다. 리뷰어는 관련·전체 테스트, 타입 검사, 실제 LLM/MCP를 새로 실행하지 않았다.

**남은 작업은 CR26 초기 소비 보존과 CR28 성공 대역 입력의 좁은 수정·영향 재리뷰다.** 그 후 관련 검사·필수 CI·사용자 지정 계정 라이브를 수행하여 실제 새 거절 로그와 원인 수정의 결과를 확인해야 한다. 이 통합 소스 판정만으로 전체 작업 또는 라이브 계약 검증 완료를 선언할 수 없다.

## CR26·CR28 좁은 후속 수정의 독립 재리뷰 — 소스 리뷰 종료

직전 통합 판정 이후 새 거절 기록 연결, 실제 엔진 소비 회귀 사례, 실행 성공 대역의 입력 정렬만 검토했다. 대상은 `src/redteam/orchestration/engine.py`, `tests/integration/test_merged_agent_runtime.py`, `tests/integration/test_execution_agent_e2e.py`의 후속 변경과 직접 영향 경로다. 기존 승인 영역은 반복하지 않았다. 제품·테스트 수정, 타입/자동 검사, 라이브 호출, 커밋 없이 이 절만 추가했다.

**판정: CR26·CR28은 반영·해결. 이번 좁은 수정에서 새 필수 지적은 없다. 앞선 통합 소스 리뷰의 필수 잔여가 해소됐으므로 소스 리뷰를 종료하고 최종 관련 검사·필수 CI·사용자 지정 계정 라이브 검증으로 진행할 수 있다.** 이것은 실행 검증 통과나 전체 목표 완료 판정이 아니다.

### CR26 — 초기 거절 소비에서도 최종 안전 형태를 보존

작은 기록 어댑터는 기존 판단 예산의 record 기능에 피드백·검증 상세·생산자의 최종 안전 문맥을 전달한다(`engine.py:1556-1564`). 초안의 초기 거절(`1653-1654`), 다음 행동의 외부 제안/응답 모델 초기 거절(`1701-1702`), 기존 제어 행동 처리 후의 거절(`1997-2002`)이 모두 이를 사용한다. last_failure 할당과 모델 피드백, 분기별 continue/수용 동작은 기존 위치에 유지된다. 그래서 대체 제공자 오류가 초기 분기에 들어온 뒤 다른 오류로 마지막 원인이 바뀌어도 앞선 구조가 공통 trace에 남는다. 생산자 첨부 진단만 마지막 원인에 의존하던 CR26 잔여 경로가 해결됐다.

기록 함수는 요청·토큰·정상/보정 계수를 변경하지 않는다. 실제 요청 없는 제공자의 기존 진행 처리도 그대로이며, 형식 거절을 의미 거절로 바꾸거나 입력을 보정해 수용하지 않는다. SDK 자체 스키마 실패는 `DecisionFailure(Exception)`으로 전파되고 초기 거절의 ValueError/TypeError/PathError catch에 들어오지 않는다(`cognition.py:58`, `engine.py:1642,1687`). 구조화 응답 담당의 기존 response_rejected와 이 어댑터가 같은 SDK 실패를 두 번 남기는 경로는 없다. 새 저장소·로거·오류 원문 기록도 추가하지 않았다.

신규 회귀 사례는 `_propose` 단독 검사 대신 실제 `InvestigationEngine.decide`를 사용한다(`test_merged_agent_runtime.py:110-160`). 대체 제공자 A의 잘못된 조회 배열은 실제 최종 반환 스키마에서 거절되고, B의 미등록 도구는 실제 컴파일에서 거절되며, C는 후보로 컴파일된다. 마지막 다음 행동 준비 이벤트의 공통 예산 trace에서 A의 공개 위치/규칙과 배열 형태가 남는지 확인하므로, 마지막 원인이 B로 교체된 뒤에도 초기 형태가 보존되는 소비를 검사한다. 사적 값은 준비 이벤트 직렬화에서 제외되는지 확인한다. 실제 모델 대역 호출은 초안·검수 두 경로만 요구하며 다음 행동은 제공자의 기존 무모델 진행 의미를 사용한다. 이 사례의 ‘성공’은 후보 컴파일이며 실제 도구 실행/목표 달성을 주장하지 않는다. 앞선 잘못된 컴파일 보정 사례의 repair_references/feedback assertion은 원래 함수 안에 그대로 유지됐다(`68-107`). 신규/기존 테스트를 실행했다는 뜻은 아니다.

### CR28 — 직접 선택 성공 입력과 기존 거절 책임의 일치

성공 대역은 이제 선택 도구에 실제 허용된 `wc -l input.txt` 입력을 제출한다(`test_execution_agent_e2e.py:251-254`). 단일 자산 참조의 기존 바인딩, 실제 정책/승인, MCP 서버와 입력 검사 경로를 그대로 사용하며 직접 선택에 옛 레시피 덮어쓰기를 재도입하지 않는다. 기존 프로세스 시작 1회, `/usr/bin/wc`와 실제 argv, python 제외, 성공 도구 원본 1개 assertion은 변경하지 않았다(`327-340`). Docker 선택 실행도 같은 유효한 성공 대역을 소비한다.

미허용 python 호출은 별도 서버 거절 사례에서 계속 실패·정확한 오류 코드·프로세스 시작 0회를 요구한다(`378-408`). 옛 레시피의 적대적 입력 덮어쓰기 단위 사례도 그대로다(`tests/unit/test_execution_agent_bridge.py:150-159`). 허용 목록·승인 상한·기대값을 약화하거나 공개 응답에 숨겨진 바인딩 전환 값을 추가하지 않았다. CR28의 성공 입력/기대값 불일치는 해결됐다.

소스 종료 판정 이후 루트는 현재 최종 diff에 대해 관련 테스트와 필수 검사, account 1 실제 흐름을 실행하고 그 결과를 구분해 기록해야 한다. 이전 통과 수치와 기준선 실패는 수정 후 통과 증거가 아니며, 새 상세 로그를 통해 실제 조회 거절 모양/원인을 확인한 것도 아직 아니다. 과거 미저장 요청의 정확한 모양은 계속 미확인이다. **필수 소스 지적 없음과 전체 목표·라이브 계약 검증 완료를 구분한다.**

## 최종 관련 실행에서 발견한 피드백 형태 회귀 및 기존 행동 대역의 독립 재리뷰

이번 범위는 객체형 피드백의 안전한 로그 투영(`src/redteam/orchestration/diagnostics.py:197-212`), 그 집중 회귀 사례(`tests/unit/test_orchestration_diagnostics.py:130-139`), 거절 대역의 기존 행동 형식 명시 한 줄(`tests/unit/test_orchestration_nodes.py:1446`)이다. 실제 생산·모델 소비·후보 컴파일과 기존 거절 assertion을 소스로 확인하고, 이미 저장된 `data/validation-resume-new-related-linux.txt`만 읽었다. 제품·테스트 수정, 신규 실행·타입 검사·라이브 호출·커밋 없이 이 절만 추가했다.

**판정: 두 좁은 변경 모두 반영 승인. 새 필수 소스 지적은 없으며 관련 검사를 재실행할 수 있다. 수정 후 통과와 전체 목표 완료를 확정하는 판정은 아니다.**

### 객체형 최종 검수 피드백은 원본 입력을 유지하고 형태만 기록

최종 목표 검수는 잘못된 기준/증거 연결을 거절한 뒤 진단의 JSON 객체를 다음 검수 입력의 feedback에 넣는다(`replanning.py:733-734`). 이는 정상적인 생산 계약이다. 공통 모델 입력은 해당 작업 문맥을 JSON으로 직렬화하므로 객체형 진단 자체가 다음 요청에 전달된다(`cognition.py:438-445`). 저장된 실행 기록의 네 실패는 메모리/SQLite와 증거/작업 불일치 조합 모두에서 두 번째 검수의 공통 로그 투영이 이 객체를 리스트처럼 자르다가 TypeError를 낸 것이다. 도구 성공을 목표 성공으로 인정한 문제가 아니다.

변경된 투영은 문자열 리스트라면 앞 10개 안의 문자열만 기존 마스킹·길이 제한 함수로 기록한다. 리스트가 아니면 표시용 feedback은 빈 리스트로 두고 기존 얕은 형태 함수로 타입·크기만 기록한다(`diagnostics.py:142-164,197-212`). 객체의 키·값이나 임의 리스트 항목을 문자열로 복사하지 않는다. 원본 payload와 proposal을 변경하지 않으며 기존 검증 전/후 기록 경로에서 같은 처리가 적용된다. 모델에 전달되는 진단, 정상/보정 예산, 실제 기준·작업·증거 연결 거절 규칙은 이 수정에 포함되지 않는다.

집중 사례는 객체형 진단의 형태와 검증 전 제안 형태가 함께 보존되고 사적 값이 직렬화되지 않는지 요구한다(`test_orchestration_diagnostics.py:130-139`). 기존 문자열 피드백 마스킹 사례도 유지된다(`115-127`). 실제 최종 검수의 기존 네 조합은 목표 BLOCKED, 만족 기준 없음, 모델 호출 2회, 증거 연결 오류 코드가 남는지를 계속 요구한다(`test_terminal_mission_criteria.py:67,209-223`). 이 소스는 실제 소비 회귀를 확인할 적절한 검사 경로지만, 리뷰어가 실행하거나 통과를 관측한 것은 아니다.

### 거절 대역 한 줄은 직접 선택과 기존 행동 바인딩을 구분

다음 행동의 기본 바인딩 형식은 직접 도구 선택이다(`engine.py:117`). 기존 실패 기록에서도 작업 힌트와 도구의 등록 작업이 달라도 직접 선택 제안이 생성됐고, 그 결과 제안 없음 assertion에서 실패했다. 이번 한 줄은 잘못된 제안을 기존 행동 형식으로 명시한다(`test_orchestration_nodes.py:1443-1447`). 선택 도구는 service_discovery만 등록하고, 제안은 endpoint_discovery를 요구하는 기존 불일치가 유지된다(`127-136`). 후보에 형식이 그대로 전달되며(`engine.py:2271-2285`), 후보 컴파일은 직접 선택이면 선택 도구 조회를 사용하고 기존 행동이면 작업 이름·작업별 도구 바인딩을 검사한다(`candidates/compiler.py:140-172,247-251,290-345`). 실제 실행 직전 재검사도 작업 바인딩 검사를 기존 행동 형식에 한정한다(`engine.py:3056-3065`). 제품에 옛 작업 매핑 제약을 직접 선택 경로로 추가한 변경은 없다.

정확한 근거 표현은 **기존 행동의 작업/도구 바인딩 거절 경로로 대역을 정렬했다**이다. 현재 엔진에서 경로의 allowed_operations 목록을 직접 검사하는 거절은 확인하지 못했으므로, 기존 주석의 “outside step envelope” 또는 요청에 적힌 “legacy 전용 envelope check”를 경로 허용 목록 검사의 실행 증거로 읽지 않는다. 이 사례는 해당 목록 검사나 단일 오류 원인을 단언하지 않으며, 제안 없음·REPLAN·게이트웨이 호출 없음의 기존 단언은 그대로다(`test_orchestration_nodes.py:1471-1473`). 한 줄 변경의 타당성과 별개로 수정 후 어떤 거절이 관측되는지는 실행 결과로 확인해야 한다.

읽은 관련 실행은 **7 실패·206 통과·10 skip**이며 이번 두 수정 이전의 결과다. 객체 슬라이싱 네 건과 대역 형식 누락 한 건의 원인·좁은 소스 보완을 검토했을 뿐, 다섯 건을 수정 후 통과로 바꾸어 기록하지 않는다. 두 번째 계정 관련 두 실패는 이번 델타에서 미수정·조사 중으로 남는다. 관련 재실행·필수 CI·사용자 지정 계정 라이브와 실제 새 조회 진단 확인은 루트의 후속 검증 범위다.

## trial05 이후 JSON 파싱 위치 진단 확장의 구현 전 설계 검토

**판정: 제안 설계 반영 승인. 구현 전 필수 반대 지적은 없다. 실제 코드와 소비 연결은 다음 델타에서 별도로 리뷰한다.** 파서가 제공한 위치·문서 길이·고정된 첫 토큰 범주만 기존 거절 trace에 기록하는 것은 관측된 원인 정보 부족에 대응하는 좁은 변경이다. 새 파싱·입력 보정·판정·저장 체계나 예산 정책은 필요하지 않다. 이번 절은 소스/저장 산출물의 읽기와 설계 리뷰이며 실행 검증이 아니다.

읽은 trial05 보고서(`data/live-tests/validation-contract-20261005-resume/trial-05/reports/run_7af7611fce95/report.json`)는 failed/planning_error, ready_for_release=false다. 마지막 원인은 invalid_json이고 위치는 빈 문자열, 거절 trace의 검증 상세도 빈 리스트이며 보정 예산 소진이 기록돼 있다. 현재 공급자 호출의 JSON 예외와 로컬 파싱 예외는 각각 같은 일반 설명의 진단을 만들고, 공통 response_rejected 기록은 진단 상세와 예외의 안전 문맥을 전달한다(`cognition.py:487-496,524-535,628-638`). 그러므로 파서 위치 진단과 최소 구조 정보는 실제 빈틈을 메우며 새 로그 저장소를 만들 이유가 없다.

구현 시 지켜야 할 정확성 경계는 다음과 같다. JSONDecodeError의 lineno/colno/pos와 doc의 문자 수만 사용하고, 첫 공백 제외 토큰은 empty/object/array/other의 고정 범주로만 투영한다. doc, msg, 예외 문자열, 실제 문자·본문·주변 발췌는 기록하지 않는다. 규칙도 오류 메시지를 가공하지 않고 파싱 실패를 뜻하는 고정 식별자를 사용한다. UnicodeDecodeError와 정상 JSON의 비객체 거절에는 JSON 파서 좌표를 만들어 붙이지 않으며 기존 거절 의미를 유지한다.

위치와 문서 길이는 **예외가 가리키는 파서 입력 기준**이어야 한다. 기존 로컬 파서는 공백과 코드블록을 제거하고 빈 입력을 객체로 대체하며(`cognition.py:331-350`), 공급자 어댑터의 파서도 비슷한 전처리를 한다(`llm/litellm.py:89-102`). 따라서 파서 doc의 위치를 원본 모델 응답의 좌표·원본 길이라고 설명하면 틀리다. doc의 첫 토큰 분류만으로 마크다운·설명문·잘림 등 구체적 원인을 확정할 수도 없다. 전처리 방식이나 빈 입력 수용 동작을 이번 진단 변경에서 고칠 필요는 없다.

두 예외 경로가 공통 담당의 투영을 사용하고, 생성된 안전 문맥이 기존 _RetryableDecisionError → response_rejected → 예산 trace → 보고서까지 전달되는지 코드 리뷰에서 확인해야 한다. 특히 공급자 예외 경로는 현재 안전 문맥을 따로 넘기지 않아 기본 unavailable 형태를 쓰므로, 도우미만 추가하고 이 소비 연결을 빠뜨리면 제안 목적을 충족하지 못한다. 기존 last_cause·위치·규칙 연결과 자동 JSON/Markdown trace 출력은 재사용하고 같은 거절을 새 프레임으로 중복 기록하지 않는다. 모델별 분기·오류 원문 저장·새 로그 옵션은 필요하지 않다.

원본 마지막 파싱 본문과 과거 조회 요청은 저장되지 않았으므로 이 설계로 소급 복원할 수 없다. 사용자 전달의 성공 조회·일부 사실 수용·근거 있는 미결론 영수증은 부분 흐름의 관측이며 전체 목표 완료 근거가 아니다. 이번 추가 진단으로 실제 원인이 확정됐다는 판단도 다음 구현·관련 검사·후속 라이브 관측 전에는 하지 않는다.

## 두 번째 계정 비교 대역의 실제 사용 영수증 추가 — 독립 소스 리뷰

이번 범위는 `tests/integration/test_second_principal_mission.py`의 비교 결과에 중첩 actual_session_ref 두 필드를 추가한 후속 델타다. 앞서 승인한 목표 검수의 실제 발췌 조회 변경은 반복하지 않았다. 실제 HTTP 도구·응답 생산·공통 세션 사용 수집·완료 소비와 저장된 수정 전 진단(`data/validation-resume-second-principal-step-diagnostic.txt`)을 읽었다. 제품·테스트 수정과 실행 없이 이 절만 추가했다.

**판정: 실제 공개 결과 형태를 맞추는 방향은 타당하지만 CR29의 좁은 대역 정합 보완 후 승인한다. 제품의 영수증 판정이나 기존 성공/거절 assertion을 완화할 이유는 없다.**

공개 비교 도구는 두 세션의 등록·대상·서로 다른 계정을 확인하고 각 요청을 실행한 뒤 각 응답 summary와 등록 계정 참조를 같은 중첩 응답에 조립한다(`src/redteam/capability/servers/web_http.py:71-112`). 네트워크 응답은 요청에 세션 헤더를 적용하고 응답을 받은 뒤 actual_session_ref를 넣는다(`network.py:207-244`). 따라서 first/second 내부에 해당 영수증을 추가한 위치는 공개 결과와 맞다. 공통 수집은 실제 사용 키만 읽고 요청 echo나 등록 목록을 사용 증명으로 인정하지 않는다(`session_proof.py:1-8,103-120`). 수정 전 진단은 목표 종료가 goal_achieved인데 경로 단계는 pending/증거 없음이며, 계정 참조에 정확한 원본 사용 영수증이나 근거 있는 바인딩이 없다는 완료 거절을 기록한다. 누락된 결과 계약을 고치는 이유로는 충분하지만 제품 거절이 잘못됐다는 근거는 아니다.

### CR29 — 대역의 각 계정 결과와 추가 영수증이 순서 변경에서 불일치 (P2, 필수 보완 반영 권고)

**소스 근거와 실제 상황:** 입력 단언은 두 세션의 집합이 alice/bob인지만 확인하여 first=bob, second=alice도 통과한다(`test_second_principal_mission.py:324-327`). 신규 actual_session_ref는 입력의 각 위치에서 가져오지만(`332-333,342,348`), 기존 first 결과는 alice-principal/200/a digest, second는 bob-principal/403/b digest로 고정돼 있다(`338-348`). 역순 입력에서는 bob 사용 영수증 옆에 alice의 계정·응답을 반환한다. 관측 매핑은 같은 위치의 계정과 요청 세션을 연결하므로(`observations/web_http.py:158-200`) 잘못된 계정 연결을 가진 대역 결과가 완성 증거에 들어갈 수 있다. 현재 스크립트가 정순만 제출하는 것은 이 대역이 허용하는 역순 결과의 정합을 보장하지 않는다.

**좁은 수정 방향:** 고정 응답 대역을 유지한다면 입력 순서도 first=alice/second=bob임을 단언하여 지원 범위를 정확히 제한한다. 순서를 허용하려면 고정된 세션별 응답 fixture에서 각 계정·상태·digest와 영수증을 함께 선택한다. 둘 중 하나면 충분하며 실제 HTTP 실행, 새 공통 계층, 제품 정책 변경은 필요하지 않다. 같은 계정 부정 사례는 선택된 첫 응답의 계정으로 두 번째 계정을 맞춰 유지한다. 잘못된 대상·양쪽 거절·이용 불가 등 기존 부정 변형과 단계 증거 존재 assertion은 그대로 유지한다.

신규 주석의 “runs ... sequential scoped GETs”/“what ran on the wire”는 현재 구현 사실과 맞지 않는다(`328-331`). 상위 SessionGateway도 도구 대역 결과를 만들며 비교 분기는 그 결과를 교체할 뿐 두 HTTP 요청을 실행하지 않는다(`test_authentication_followup.py:102-138`, `test_second_principal_mission.py:318-334`). 주석은 검증된 fixture 세션의 **모의 도구 응답 영수증**을 만든다고 설명해야 한다. 입력 참조를 결과 필드에 복사했다는 사실만으로 실제 네트워크 적용이 검증됐다고 표현하지 않는다. 고정 fixture/순서 정합이 있는 모의 결과는 통합 소비 검증에 적절하고, 이 테스트 범위에서 별도 네트워크 harness를 요구하지 않는다.

성공 사례의 임무/기준/단계 증거 존재, 실제 대역 호출·대상·경로·두 계정, 저장 비교 결과·그래프 관측·발견 없음 assertion과 부정 사례의 held/BLOCKED·미달 기준·발견 없음·호출 여부 assertion은 유지돼 있다(`451-536`). 기대값 약화는 확인하지 않았다. 리뷰어는 수정 후 관련 테스트를 실행하지 않았고 현재 두 실패의 해소를 확정하지 않는다. CR29의 대역 결과/지원 입력/주석 정합 보완을 재리뷰한 뒤 관련 실행으로 소비 결과를 확인해야 한다.

## JSON 파싱 위치 진단의 구현 델타 — 독립 소스 승인

**판정: 파싱 진단 델타 소스 승인. 설계에서 요구한 소비 연결이 구현됐으며 새 필수 지적은 없다. CR29는 이 스냅샷에서 미수정 상태로 유지된다.** 대상은 `src/redteam/orchestration/diagnostics.py`의 JSON 파싱 안전 투영/진단, `cognition.py`의 공급자·로컬 예외 연결, `tests/unit/test_orchestration_diagnostics.py`의 두 경로 회귀 사례다. 이전에 승인한 상세 진단 영역은 반복하지 않았다. 리뷰어는 이 절만 추가했고 테스트·타입 검사·실제 호출을 실행하지 않았다.

공통 투영은 JSONDecodeError의 doc를 저장하지 않고, 공백 제외 첫 문자와 비교한 고정 범주 및 파서의 line/column/position/문자 수만 새 중첩 문맥에 넣는다(`diagnostics.py:187-201`). coordinate_source=decoder_input을 명시하여 코드블록/공백 전처리 전 원본 응답 좌표와 구분한다. 오류 메시지·예외 문자열·실제 문자·본문·주변 발췌를 결과에 복사하지 않는다. 진단은 같은 invalid_json/format/retryable 의미를 유지하면서 고정 json_decode 규칙과 파서 입력의 행·열 위치를 추가한다(`355-361`). 본문 기반의 구체적 실패 원인 추정이나 새 모델별 규칙은 없다.

공급자 호출에서 올라온 JSONDecodeError도 공통 진단과 투영을 만들고 기존 재시도 예외에 함께 전달한다(`cognition.py:481-517`). 로컬 반환 파싱 실패도 같은 두 기능을 사용한다(`529-533`). 공통 catch가 해당 문맥과 규칙을 기존 response_rejected 한 프레임에 기록한다(`636-645`). 따라서 공급자 경로에서 도우미 결과가 default unavailable 문맥으로 사라지는 구현 누락은 없다. Unicode 오류와 비객체 거절의 기존 의미·형태는 유지되며, 파싱·빈 문자열 대체·스키마 수용 규칙은 변경하지 않았다. 요청/토큰 계수와 보정 전환·예산 소진 분기도 이 델타에서 바뀌지 않았다.

기존 예산 기록은 추가 details를 마스킹 후 기존 20프레임 trace에 넣고(`cognition.py:190-202`), 소진 진단은 예산의 상세와 마지막 원인을 포함한다(`559-568`). 상태/보고서가 기존 진단 계약을 소비하고 JSON은 전체 진단을, Markdown은 기존 trace 항목을 출력하므로 별도 저장·표시 계층 없이 새 안전 문맥을 전달할 수 있다(`reporting.py:396-397,538-539`, `app/cli/commands/report.py:42,94-105`). 실제 저장·재개·보고서 실행을 검증했다는 뜻은 아니다.

새 매개변수 회귀 사례는 공급자가 파서 예외를 직접 올리는 경우와 코드블록에 싸인 응답을 반환하여 로컬에서 전처리/파싱하는 경우를 같은 실제 요청 담당으로 검사한다(`test_orchestration_diagnostics.py:174-200`). 기존 모델 대역은 Exception 응답을 실제로 raise한다(`34-45`). 거절 trace의 좌표/길이가 코드블록 전 원문이 아닌 파서 doc와 맞고, 마지막 원인의 규칙/위치가 보존되며, 요청이 1회이고 사적 sentinel이 진단 JSON에 없다는 단언이 있다. 구현 함수만 직접 호출하는 검사보다 두 소비 경로의 연결을 확인하는 사례다. 신규 두 사례와 기존 본문 비저장 사례를 통과했다고 표현하지 않는다.

### 시간 판단 담당의 명시된 종료 원인만 전달

시간 판단 담당은 기존 ROE 시간 검사·지속 시간·시작 시각을 재사용한다. 지속 시간 경계만 reasoning_duration_exhausted와 budget_exhausted를 함께 반환하며, ROE 닫힘과 시작 시각 누락은 각각 다른 원인 코드와 종료 원인 없음으로 반환한다(`reasoning_time.py:11-36`). 기존 bool 인터페이스는 같은 결과의 허용 여부를 계산하므로 나머지 실행/검수 소비자의 허용 조건을 바꾸지 않는다. 중앙 모델 요청 전 검사는 이 값을 그대로 명시된 중단 예외에 넣는다(`engine.py:678-704`). 문자열의 budget/time 일부나 오류 종류만으로 종료 이유를 추정하지 않는다.

기존 진단의 kind=budget은 형식 보정 소진·토큰 한도·중단·잘못된 시작 상태 등도 표현하여 정상 시간 종료와 계획 실패를 구별하기에 부족하다. 새 선택 종료 의미는 기존 진단 계약에 Literal[budget_exhausted] 또는 None으로 추가되고 기본값은 None이라 기존 진단/이력은 계속 읽힌다(`diagnostics.py:103`). 이는 모델의 제안 필드가 아니라 시스템 예외/진단의 계약이다. 외부 계획 절차나 요청 전 검사 콜백이 명시된 진단을 만들 경우 그 담당 코드가 종료 원인을 책임진다. 형식상 허용된 종료 값이 실제 시간 만료를 독립 증명하는 것은 아니며, 확인한 생산 경로에서는 시간 담당만 이 값을 결정한다. 임의 모델 응답이나 예외 문자열에서 이 값을 추출하는 경로는 없다.

중단 예외는 정상 생성 시 진단의 선택 값을 검증하고(`cognition.py:296-308`), 요청 담당은 단계/실제 사용 횟수와 이전 last_failure를 last_cause로 보존해 DecisionFailure로 전달한다(`589-597`). 그 복사는 새 종료 값을 추론하거나 덮어쓰지 않는다. 일반 guard 오류는 기존 계획 실패 경로를 유지하고 요청 전에 거절하므로 새 호출/토큰 소모가 없다. 엔진의 기존 요청 catch는 예산 상세를 첨부한 채 진단을 전파하며(`engine.py:570-575`), 계획 노드는 최상위의 명시된 종료 값만 소비한다. 값이 없으면 planning_error이고 있을 때만 planning_error 표시를 비운다(`nodes/plan.py:64-97`). 과거 last_cause의 종료 값을 찾아 현재 진단을 승격하지 않는다.

재계획의 기존 종료 판정은 budget_exhausted를 FINISHED로 처리하지만 GOAL_ACHIEVED로 바꾸지 않는다(`nodes/replan.py:63-90`). 기존 임무 정산은 실제 시간 만료 시 추가 검수 모델 호출을 막고 기록·기준·작업 상태를 별도 검토하며(`replanning.py:815-834,887-900`), 보고서의 완료/출시 가능 판단도 예산 종료만으로 만족하지 않는다(`reporting.py:386-389,559-579`). 따라서 정상적인 제한 종료와 목표 달성은 계속 구분된다. 이번 변경이 분석 검수·최종 검수의 기존 bool 거절 전부에 새 종료 값을 부여하는 확장은 아니다.

## trial08 후속 정상 검토 예산 경계 정렬 — 독립 소스 리뷰

**제품 델타 판정: 반영 승인, 새 필수 소스 지적 없음.** 이번 범위는 `engine.py`의 네 후속 검토 진입 조건과 `_propose`의 사전 예산 진단 재사용이다. 실제 요청 허용·경로 수정·단계/작업/목표 완료·다음 그래프 턴·저장 소비를 소스로 읽고 trial08 저장 보고서를 대조했다. 요청 시점에 추가 중인 최소 경계 회귀는 아직 미포함이며 완료 전달 뒤 같은 묶음에서 추가 확인한다. 리뷰어는 제품/테스트를 수정하거나 실행하지 않았고 이 절만 추가했다.

trial08 보고서(`data/live-tests/validation-contract-20261005-resume/trial-08/reports/run_1deaf4d41e63/report.json`)는 failed/planning_error, completion_review에서 decision_budget_exhausted, 실제 요청 10/전체 상한 11, 정상 8/8, 보정 2/3, ready_for_release=false를 기록한다. outcome은 197.77초, 외부 timeout 아님을 기록한다. 즉 전체 잔여 1은 새 정상 검토를 허용하는 1이 아니었다. 기존 예산 계약의 permits()는 전체 잔여가 있어도 정상 한도가 끝나면 새 정상 요청을 막고, permits(repair=True)는 같은 요청 체인의 보정 한도를 따로 판단한다(`cognition.py:164-176`). 경로 수정/전환, 단계 완료, 목표 완료, 작업 완료의 네 진입 조건이 remaining 대신 기본 permits()를 사용하여 실제 `_propose`와 같은 정상 요청 판단에 맞춰졌다(`engine.py:1871-1943`). 보정용 잔여를 정상 검토에 쓰지 않으며 상한·권한·완료 기준을 늘리지 않는다. 별도 예산 상태나 도구/모델별 조건도 추가하지 않았다.

조건이 닫히면 경로 수정은 등록/검토 전에 기존 path를 반환하고, 세 완료는 담당 함수를 호출하기 전에 같은 continue_planning 결과와 기존 상세 예산 진단을 반환한다. 따라서 검수 없이 경로 버전·단계 상태·작업 상태·목표 기준·완료 영수증을 저장하지 않는다. 다음 턴에서 제안이 재생성되어 검토될 수 있다는 뜻이며 이 제안을 영속 대기열에 저장하거나 완료로 예약하는 기능은 아니다. 기존 `_propose` 사전 실패도 `_budget_failure`를 재사용하여 정상/전체 소진 코드·trace·단계 횟수·이전 원인을 기존 계약으로 보존한다(`616-617,1602-1619`). 새 종료 원인이나 정상 종료 변환은 넣지 않았다.

경로 담당은 실제 구조·참조·기준을 검사하고 의미 검토 수용 뒤에만 기존 조정 커밋으로 저장한다(`register_path:1347-1538`). 단계 성공은 원본/기준 검증→completion_review→수용→조정 커밋을 계속 요구한다(`complete_step:2568-2679`). 작업/목표 완료도 실제 활성 작업·원본 출처·작업 범위·정리·주장/기준 검증과 각각 task_completion_review/goal_completion_review 뒤의 기존 커밋을 유지한다(`semantic_completion.py:525-661,912-1045`). 근거 있는 미결론 경로의 기존 판정도 변경하지 않았다. 검토 시작 뒤 보정·전송 실패는 DecisionFailure로 전파되며 이번 조건에서 잡아 성공/재개로 바꾸지 않는다. 경로 검토가 다시 수정안을 내어 추가 검토가 필요한 기존 재귀에서도 예산 실패를 그대로 전달한다. 이번 승인 범위는 네 진입 전 경계 정렬이며 모든 후속 호출 실패를 재개 대상으로 확대하는 변경이 아니다.
