# WHS 보안 에이전트 결과 전달·진단·검사 공백 구현계획

작성일: 2026-10-03 / 기준: dev, c3f9728634ee9bed5b11075aaf6db8936ff0199d

상태: 최종 설계 2차. GPT-6.1 Sol 독립 평가 100/100. 1.1차 90점의 여섯 계약 누락을 수정했다. 구현·테스트·검증 실행은 하지 않았다.

## 1. 목적과 범위

이번 구현의 목적은 기존 LLM 중심 조사 루프에서 도구 실행 결과, 자동 해석 상태, 지식 반영 상태와 검사 공백이 다음 루트 판단과 사용자 보고까지 이어지게 하는 것이다. 신규 자율 서브에이전트, 공격 기능, 브라우저·모바일 기능 확장은 포함하지 않는다. 이미 추가된 분석·모바일·브라우저·실행 도구 연동은 유지한다.

루트 LLM은 조사 경로·다음 행동·담당 역할을 제안한다. 코드 기반 후보는 참고이며 후보 부재는 루트의 제안이나 조사 종료를 결정하지 않는다. 코드는 구조·참조·실행 조건·정책과 기존 증거 기반 완료 조건을 검사한다. 관측, 사용자 제공 정보, 가설, 계획, 취약점 판정은 기존 구분을 유지한다.

집계는 판단 자료이며 완료 판정기가 아니다. 자동 해석기 부재는 도구 실행 미지원과 다르다. 원본을 LLM이 읽더라도 추론은 기존 검증·반영 절차 전까지 가설이나 계획으로 유지한다.

이 문서는 구현 지시의 구체화 결과다. 실제 코드를 바꾸는 승인으로 취급하지 않았다. 첨부 이미지와 이전 a1adba2c 분석은 참고자료이며 최신 코드 사실과 대조했다.

확정한 변경 대상은 자동 해석 상태의 명시적 전달, 반영 실패·부분 처리 기록, 기존 자료 기반 검사 공백 투영과 그 소비 경로다. 함수가 여러 곳에 흩어져 있거나 이름이 없다는 이유만으로 새 중복 체계·승인 검사·스케줄러·완료 판정기를 만들지 않는다.

## 3. 사용할 환경·SDK와 외부 근거

### 3.1 실제 설치와 선언의 구분

읽기 전용 패키지 메타데이터 조사에서 `.venv-ci314/Scripts/python.exe`의 Python 3.14.6과 아래 패키지를 확인했다.

| 기존 구성 | 확인 버전 | 이번 사용 |
|---|---:|---|
| LangGraph | 1.2.12 | 기존 StateGraph, Send, 결과 병합과 Overwrite 유지 |
| LangChain Core | 1.6.6 | 이미 설치된 기반 타입만 재사용. 별도 LangChain 에이전트 프레임워크로 이관하지 않음 |
| SQLite 체크포인터 | 3.1.1 | 기존 비동기 체크포인트·상태 직렬화 사용 |
| aiosqlite | 0.22.1 | 기존 SQLite 저장 계약 유지 |
| Pydantic | 2.13.5 | 추가 계약의 기본값·JSON 직렬화·기존 스키마 검사 활용 |
| MCP Python SDK | 2.2.0 | 기존 전송 어댑터와 결과 형식 사용 |
| NetworkX | 3.4.2 | 기존 그래프 구성 유지 |

기본 `.venv`는 인터프리터가 없는 잔여 디렉터리이고 시스템 Python 3.10에는 LangGraph가 없다. 같은 CI용 환경에서는 LiteLLM과 전체 LangChain 패키지가 확인되지 않았으며, 위 LangChain Core와 구분한다. 이 차이를 SDK 부재나 코드 결함으로 혼동하지 않는다. 실제 LLM 통합 확인에 필요한 LiteLLM은 이미 `pyproject.toml`에 선언돼 있으므로 마지막 단계에서 기존 설치 선택 항목으로 환경을 맞춘다. 전체 LangChain은 현 구현의 직접 사용 여부에 따라 필요한 기존 선택 항목만 설치하고 신규 에이전트 프레임워크는 도입하지 않는다. 이번 계획 작성 중 설치·업그레이드는 하지 않는다.

### 3.2 조사 자료를 적용하는 지점

- [LangGraph 공식 그래프 API](https://docs.langchain.com/oss/python/langgraph/use-graph-api): Send와 reducer, Overwrite의 역할을 참고한다. 기존 행동별 병렬 전달과 조정자 한 곳의 결과 초기화를 유지한다. 신규 병렬 엔진을 만들지 않는다.
- [LangGraph 공식 체크포인터 설명](https://docs.langchain.com/oss/python/langgraph/checkpointers): 기존 실행 식별자·체크포인트·대기 중 쓰기 구조를 유지한다. 요약 자료를 별도 실행 권한이나 재개 신호로 사용하지 않는다.
- [LangGraph 공식 중단·재개 설명](https://docs.langchain.com/oss/python/langgraph/interrupts): 노드 재실행과 부작용 중복 위험을 참고한다. 기존 승인 저장소·정책 재진입을 native interrupt로 교체하지 않는다.
- [공식 LangGraph GitHub 타입 구현](https://github.com/langchain-ai/langgraph/blob/main/libs/langgraph/langgraph/types.py): 사용 중인 Send·Overwrite 구조와 비교하는 오픈소스 참조다. main의 새 API를 통째로 복사하지 않는다.
- [공식 MCP Python SDK 클라이언트](https://github.com/modelcontextprotocol/python-sdk/blob/main/docs/client/index.md), [구조화 출력](https://github.com/modelcontextprotocol/python-sdk/blob/main/docs/servers/structured-output.md): 내용, 구조화 데이터, 도구 오류를 구분한다. [현재 전송 어댑터](../../../src/redteam/capability/adapters/mcp/transport.py)의 결과 우선순위와 별칭 직렬화를 재사용한다. 전송 오류와 서버가 보고한 도구 실패를 합치지 않는다.
- [Pydantic 공식 직렬화 설명](https://docs.pydantic.dev/latest/concepts/serialization/): 기존 JSON 모드·별칭 직렬화를 유지한다. 새 모델 필드는 옛 데이터에서 생략돼도 읽히도록 기본값을 둔다. 기본값과 구버전 처리 의미는 프로젝트 계약으로 직접 정의한다.

문서의 latest/main은 구현 패턴의 근거다. 실행 API는 확인된 로컬 패키지와 기존 어댑터 계약을 기준으로 한다. MCP wire 표기와 Python SDK 속성 이름 변환은 기존 전송 어댑터 안에 남겨 상위 해석 상태 모델에 퍼뜨리지 않는다. 위 자료의 라이선스·주석 코드를 복사하거나 SDK 버전을 일괄 올리는 작업은 없다.

실제 API 연결의 고정 근거는 로컬 설치 소스다. LangGraph 1.2.12의 [병렬 전달 타입](../../../.venv-ci314/Lib/site-packages/langgraph/types.py)은 현재 router.py에서, [결과 초기화 타입](../../../.venv-ci314/Lib/site-packages/langgraph/types.py)은 aggregate.py에서 소비한다. MCP 2.2.0의 [결과 타입](../../../.venv-ci314/Lib/site-packages/mcp_types/_types.py)은 현재 transport.py가 변환한다. 패키지 버전과 소비 위치를 함께 보존하고 latest/main 예제의 새 호출 형식으로 교체하지 않는다.

## 4. 최소 상태 계약 — 새 실행 엔진 대신 처리 결과를 구분

아래 계약은 추가 예정의 설계다. 기존 API가 이미 제공한다고 설명하지 않는다. 자동 해석 계약은 `observations/mapper.py`의 기존 모델 영역에 Pydantic 모델로 추가하고, 저장용 결과는 변경안 객체 없이 JSON으로 직렬화한다.

### 4.1 세 상태 축

| 축 | 값과 의미 |
|---|---|
| 실행 | 미실행, 성공, 실패, 기존 기록만으로 모름. 정책 차단·승인 대기는 기존 상태에서 읽음 |
| 자동 해석 | 미시도, 해석기 미등록, 정상 해석, 해석·변경안 검증 실패, 과거 기록 불명 |
| 반영 | 변경안 없음, 적용 확인, 일부 확인 후 실패, 적용 실패, 적용 결과 불명 |

정상 해석의 빈 변경안과 적용 실패는 다르다. 해석기 미등록도 정상 빈 변경안과 다르다. 그래프 쓰기가 확인돼도 동일한 사실의 재반영일 수 있으므로 새 정보가 생겼다고 단정하지 않는다.

상태 기록에는 실행·교전·작업·행동·호출·원본 증거·경로 버전·단계 참조, 해석 상태, 반영 상태, 안전한 진단, 시도한 변경 항목 수와 확인된 쓰기 항목 참조를 담는다. 원본 본문·자격 증명은 넣지 않는다. 참조를 증명할 수 없으면 모름으로 보존한다.

지식 변화는 기존 원본 내용 기반 진행 신호로 판단한다. 전체 그래프 변화는 병렬 형제의 결과일 수 있으므로 특정 행동의 새 사실 수로 환산하지 않는다. 제공된 변경안 수, 쓰기 확인 수, 의미 있는 새 정보 수를 같은 숫자로 취급하지 않는다. 마지막 항목을 행동별로 귀속할 근거가 없으면 모름으로 표시한다.

### 4.2 저장과 구버전 계약

기존 원본 증거와 검토 영수증, `mapper_failure`, `recovery_result`를 수정하거나 삭제하지 않는다. [기존 SYSTEM 동반 기록](../../../src/redteam/orchestration/recovery.py) 형식에 새 자동 해석 결과 기록을 추가한다. 신규 DB나 테이블은 만들지 않는다.

추가 예정 기록 종류는 `mapping_outcome`이다. 기존 검토 영수증을 복제하지 않고 해석·반영 단계만 기록한다. 기존 증거 조회에서 실행과 교전 소속 및 원본 참조를 확인한다. 같은 처리의 기록이 재개로 반복돼도 읽기 투영에서 한 처리로 묶는다. 원본에 대한 도구 실행, 최초 해석, 명시적 복구 시도는 각각 구분한다.

최초 처리의 연결 키는 기존 작업·행동·호출·원본 증거 참조를 재사용한다. 명시적 복구는 별도 처리 시도이며 기존 복구 동반 기록의 연결 정보와 현재 복구 요청 참조를 우선 사용한다. 같은 처리의 재개는 그 처리 시도 참조를 유지하고, 새 복구가 기존 처리를 대체할 때는 이전 처리 참조를 선택 메타데이터로 기록한다. 기존 참조로 구분할 수 없을 때만 처리 시도·이전 처리 연결을 추가한다. 연결을 증명할 수 없는 과거 기록은 시간순으로 덮어쓰지 않는다. 새 참조가 필요하면 처리 시작 때 확보해 동반 기록에 유지하며, 이는 행동 의미 키나 승인 식별자에 포함하지 않는다. [기존 복구 기록의 연결](../../../src/redteam/orchestration/recovery.py)을 공통 저장 계약의 출발점으로 삼는다.

행동·호출·원본 증거 식별자는 기록 연결과 투영 중복 제거에만 사용한다. `original-v1` 및 실행 정체성 버전 2 입력에는 추가하지 않는다. 새 SYSTEM 기록 종류가 [지식 수집의 진단 분류](../../../src/redteam/orchestration/knowledge.py)와 [내부 판정 재료](../../../src/redteam/orchestration/knowledge_validation.py)에서 감사 자료로 분류되도록 명시한다. 출처가 같다는 이유로 새 기록을 관측 사실이나 판정 근거로 승격하지 않는다.

과거 기록에 새 필드가 없으면 해석 미등록이나 실패로 추측하지 않고 `unknown`으로 읽는다. 기존 실패·복구 기록으로 확정할 수 있는 부분만 복원하고, 증거 접근 실패·표시 잘림·기록 부재·과거 형식 불명은 별도로 둔다.

## 5. 구현 작업과 순서

### 작업 A — 해석 결과를 호출별로 반환

변경 위치: [등록소](../../../src/redteam/orchestration/observations/mapper.py), 기존 갱신·복구 호출부.

입력은 현재 도구 식별자·대상·인자·결과 그대로다. 출력은 변경안과 호출별 해석 상태·진단을 함께 담는 추가 계약이다. 미등록은 명시적 상태, 정상 빈 결과는 정상 해석+빈 변경안, 예외·기존 변경안 검증 실패는 실패 상태다.

기존 `map_result`의 반환형을 튜플로 바꾸지 않는다. 추가 예정의 상태 반환 진입점을 내부 호출부에 사용하고 옛 진입점은 동일한 GraphMutation 반환 래퍼로 유지한다. `last_failure`는 기존 소비자 호환을 위해 유지하되 갱신·복구의 새 흐름은 반환된 호출별 결과만 읽는다. 공유 실패 슬롯에서 실제 동시성 결함이 발생했다고 단정하지 않는다.

기존 exact Tool ID 등록과 공유 함수 등록을 유지한다. 와일드카드 매핑과 도구별 전용 해석기 강제를 추가하지 않는다. 등록·검증 실패 처리는 기존 로직을 재사용한다.

산출물은 호환되는 호출별 결과 계약이며 새로운 도구 실행 차단 조건은 없다.

### 작업 B — 최초 처리와 복구의 해석·반영 결과 기록

의존: A. 변경 위치: [갱신](../../../src/redteam/orchestration/nodes/update.py), [기존 복구 반영](../../../src/redteam/orchestration/recovery.py), 기존 실패 기록 도우미 영역.

1. 원본 저장·검증 순서는 유지하고 A의 결과를 받는다.
2. 미등록·정상 빈 변경안·해석 실패에 대해 공통 최소 결과 기록을 남긴다. 해석 실패의 기존 기록과 이벤트는 유지한다.
3. 기존 그래프 서비스의 upsert·link·판정 처리 경로에서 성공이 확인된 항목을 수집한다. 단순히 변경안 길이를 적용 성공 수로 쓰지 않는다.
4. 중간 실패면 확인된 항목, 실패 지점, 미확정 항목을 기록한다. 롤백되지 않은 상태를 전부 실패 또는 전부 성공으로 꾸미지 않는다. 새 전체 그래프 트랜잭션은 도입하지 않는다.
5. 성공 시 최종 적용 결과를 기록하고 기존 이벤트 이름·기존 키는 유지하며 보조 필드만 추가한다.
6. 보조 기록 저장 실패는 기록 보존 실패로 표시하며, 이미 확인된 도구 실행·반영 결과를 실패로 재분류하지 않는다. 저장된 자료로 재구성할 수 없으면 해당 처리 상태만 불명으로 표시한다. 보조 기록의 존재를 목표 완료 조건에 추가하지 않는다. [최초 처리의 기존 감사 기록 저장 예외 처리](../../../src/redteam/orchestration/nodes/update.py)는 유지한다. 새 최초 처리 보조 기록 저장 실패도 안전한 런타임 진단을 남기고 이미 수행한 실행·반영을 재분류하거나 재실행하지 않는다. [복구 기록 저장의 기존 예외 전파](../../../src/redteam/orchestration/recovery.py)는 유지하고, 새 복구 보조 기록 실패도 복구 호출부로 전달해 해당 처리 결과의 기록 상태를 불명으로 표시한다. 이미 확인된 반영 사실과 기록 실패를 구분한다. 자동 도구 재실행은 유발하지 않는다.

복구는 저장된 같은 원본·제안·계획·호출·대상 연결을 기존 게이트로 확인한 뒤 A와 같은 상태 계약을 사용한다. 이전 부분 반영 참조는 감사 정보로 남긴다. 결정적 ID와 기존 병합 규칙을 재사용하지만, 이것만으로 모든 속성 갱신·가설 판정·증거 기록이 무조건 멱등하다고 주장하지 않는다. 기존 복구가 허용한 작업만 재처리하고 최종 단계에서 부분 실패 후 재복구 시나리오를 확인한다.

반영 상태는 처리 경로별 지원 항목을 기준으로 기록한다. 최초 처리의 [매퍼 판정 반영](../../../src/redteam/orchestration/nodes/update.py)과 달리 기존 복구의 매퍼 적용은 [노드·관계 처리](../../../src/redteam/orchestration/recovery.py) 중심이다. 복구가 처리하지 않는 매퍼 판정 항목은 미지원·미반영으로 남기고 전체 반영 완료로 표시하지 않는다. 이번 변경에서 그 반영 기능을 확장하지 않는다. 복구의 [검토 기반 판정 생성](../../../src/redteam/orchestration/recovery.py)은 매퍼 반영 상태와 별도로 전달한다. 반영 상태의 범위는 자동 매퍼 적용 단계이며 앞선 검증 단계의 가설·판정 처리 전체를 대표하지 않는다.

갱신의 부분 실패 진단은 예외 전파 전에 호출별 결과로 확보한다. 처리 기록 담당은 [기존 워커 예외 처리](../../../src/redteam/orchestration/nodes/worker.py)가 이 안전한 진단을 작업별 반환 결과에 보존하도록 연결한다. 필요할 때만 dispatch.py의 기존 반환 계약에 기본값 있는 선택 진단을 추가한다. 예외 본문 대신 예외 유형과 단계·확인된 처리 참조만 전달하고 기존 집계 순서·병합·배치 초기화는 유지한다. 단일 실행 경로에는 동일 진단을 기존 런타임 관측으로 반환하고, 예외 처리 정책은 유지한다.

도구 실패에서 유용한 출력이 있더라도 기존 실패 원본 보존·열람만 유지한다. 현재 성공 결과만 자동 매핑하는 정책을 이번에 바꾸지 않는다. 실행 실패와 자동 해석 미시도를 함께 표현한다.

### 작업 C — 저장된 상태를 다음 루트 판단에 전달

의존: B. 변경 위치: [루트 문맥](../../../src/redteam/orchestration/engine.py), [런타임 관측](../../../src/redteam/orchestration/runtime_observation.py), [원본 열람](../../../src/redteam/orchestration/evidence_access.py), [지식 수집](../../../src/redteam/orchestration/knowledge.py).

루트에 행동별 실행 상태, 자동 해석 상태, 반영 상태, 원본 참조, 복구 가능 여부의 근거와 현재 공백을 전달한다. 해석 미등록·실패에서 원본을 읽을 수 있다면 기존 증거 열람 행동을 제안할 수 있게 한다. 참고 후보가 없어도 루트 판단 경로는 그대로다.

원본 열람의 `ok/not_found/run_mismatch/no_raw`와 잘림 표시를 그대로 사용한다. 원본 위치를 알고 있는 것과 읽기가 허용되는 것을 구분한다. 만료를 조회 결과만으로 추측하지 않고, 잘림은 기존 offset/limit 경로의 추가 읽기로 이어진다. 접근 실패를 도구 재실행 명령으로 치환하지 않는다.

[최근 관측 12개 제한](../../../src/redteam/orchestration/runtime_observation.py)과 [증거·작업 표시 20개 제한](../../../src/redteam/orchestration/engine.py)은 화면·프롬프트 제한이다. 전체 집계의 근거로 사용하지 않는다. 표시 건수, 생략 건수, 조회 실패·불명 상태를 분리한다. 기존 민감 정보 제거와 허용 메타데이터 목록에 새 상태 필드를 명시적으로 연결한다.

생략된 작업·처리 요약을 확인할 추가 예정의 읽기 전용 조회 동작을 engine.py의 기존 증거 읽기와 같은 제어 동작 영역에 둔다. 입력은 현재 실행 안의 작업/처리 참조 또는 offset·limit이고, 출력은 같은 실행·교전으로 제한된 안전한 요약, 전체 건수·표시 범위·다음 위치다. 현재 완료된 루트 증거 읽기 계약을 변경하지 않고 새 선택 동작으로 등록한다. 목록 참조는 기존 작업·처리의 안정 참조를 사용하며 조회는 상태를 변경하거나 실행 예산을 도구 호출로 차감하지 않는다. 조회량은 문맥 표시의 기존 상한을 재사용한다. 원본 본문은 기존 증거 열람 경로에서만 읽는다. [현재 증거 색인·제한 이력 입력](../../../src/redteam/orchestration/engine.py)과 함께 새 조회 계약을 모델 응답 스키마에 연결한다.

복구 진입점에는 런타임 인자가 없으므로 복구 모듈이 루트 상태를 직접 고치지 않는다. 문맥 담당은 [루트 복구 호출부](../../../src/redteam/orchestration/engine.py)에서 기존 복구 반환 결과의 새 안전한 상태 요약과 전파된 기록 저장 예외를 런타임 관측·추가 문맥에 전달한다. 기존 오류 유형을 자유 형식 원문으로 노출하지 않는다. 신규 상태가 없는 과거 복구 결과는 구버전 불명으로 읽는다.

관측 변화와 종료 사유를 루트에 제공할 뿐 코드가 루트의 역할을 후보 제공자·역할 문맥으로 제한하지 않는다. 최신 분석 자산·실행 레시피 등의 기존 실행 전제·정책 게이트는 유지한다.

### 작업 D — 현재 공백과 과거 수행을 읽기 전용으로 투영

의존: B의 저장 계약. C와 일부 병렬 가능. 구현 위치는 기존 보고 모듈 옆의 추가 예정 `assessment_projection.py` 한 파일로 제한한다. 호출부는 루트 문맥·보고·CLI다. 새로운 저장소는 없다.

입력은 현재 실행·교전·임무에 해당하는 전체 작업 기록, 승인된 조사 경로와 버전, 과제 상태, 같은 실행·교전의 증거·해석·복구 기록이다. 기존 `list_items`, `list_paths`, `get_active`, `list_for_run`, 임무·과제 조회 계약을 사용한다. 내부 판정 자료는 이벤트나 체크포인트에 저장하지 않는다.

출력은 두 영역이다.

- 현재 목표 공백: 현재 유효한 승인 경로의 필수 단계·완료 조건, 완료 과제의 해당 유효 경로와 증거 연결, 미확정·차단·미시도·해석·반영 공백 및 사유.
- 과거 수행 이력: 비활성·이전 버전 경로를 참조한 실제 작업도 유지한다. 현재 목표의 필수 항목으로 다시 편입하지 않는다. 승인 여부나 버전 연결이 불명인 기록은 과거 출처 불명 항목으로 남기고 현재 완료 근거로 쓰지 않는다.

행동의 실제 기록과 시도 당시 경로 버전·단계·대상·주체를 연결한다. 현재 경로와 정의가 달라진 과거 결과를 새 조건의 완료로 옮기지 않는다. 전체 카탈로그·가능한 모든 operation을 의무 검사 항목으로 생성하지 않는다.

작업의 존재·임대 횟수·종료 상태만으로 실제 도구 호출을 확정하지 않는다. [원장의 시도 횟수는 임대 획득 때 증가](../../../src/redteam/orchestration/work/memory.py)하고, [승인 유보는 실행 전에 반환](../../../src/redteam/orchestration/nodes/worker.py)할 수 있다. 실제 호출·결과·실행 기록을 작업의 행동·호출 참조와 연결해 도구 시도를 판별한다. 실행 전 차단·승인 대기·임대 상실은 미실행으로 구분하고, 과거 자료로 입증할 수 없으면 시도 불명으로 남긴다. 해석 복구는 도구 시도 횟수에 포함하지 않는다.

재개와 이벤트 재전송에 따른 집계는 읽을 때 기존 작업·원본·처리 참조를 기준으로 결정적으로 재구성한다. 이벤트 수를 성공 행동 수로 세지 않는다. 같은 원본의 복구는 새 도구 실행이 아니다. 기존 최초 실패와 최신 유효 복구 결과를 각각 보존하되 현재 해석 상태는 유효한 후속 처리 연결을 따라 읽는다. 임의의 최신 시간만으로 이전 판정을 덮지 않는다. 서로 모순되거나 같은 처리에 다른 상태가 있으면 모름·충돌을 표시한다.

읽기 실패면 빈 배열로 속여 검사 공백을 만들지 않는다. 영역별 조회 성공·실패·과거 형식 불명·표시 제한을 반환한다. 한 페이지나 최근 목록 밖에 있다는 이유로 실제 기록 부재를 단정하지 않는다. 투영 결과가 상태·작업·예산·가설·경로를 변경하는 코드는 없다.

### 작업 E — 보고·CLI·외부 결과 연결

의존: C·D. 변경 위치: [최종 보고](../../../src/redteam/orchestration/reporting.py), [보고 저장·조회](../../../src/redteam/app/bootstrap.py), `app/report_store.py`, `app/cli/renderer.py`, `app/cli/commands/run.py`, `status.py`, `report.py`.

기존 보고 결과에 기본값 있는 검사 공백 요약을 추가한다. 기존 종료 사유·정책·승인·계획·예산·실행 실패 분류는 재사용한다. 자동 해석 미등록·실패·반영 불명을 세부 진단으로 연결한다. 기존 문자열 소비자와 보고 조회가 계속 읽히도록 기존 키를 삭제하지 않는다.

통합 담당은 bootstrap.py의 보고 발행 호출부에서 D의 읽기 전용 투영을 생성하고 reporting.py의 보고 생성기에 선택 입력으로 전달한다. 보고 생성기에서 작업·경로 저장소를 새로 소유하지 않는다. 새 입력은 기본값 None이며 과거 호출·과거 저장 보고에는 구버전 투영 없음/불명으로 표시하고 완전한 빈 검사 결과로 바꾸지 않는다. TerminalReportProjection 계열의 새 필드도 같은 기본값을 둔다. 부분 결과에서는 bootstrap.py의 기존 부분 상태 경로가 D를 직접 호출한다. report_store.py는 기존 JSON 저장을 유지하며 조회 시 생략 필드를 기본값으로 복원한다.

대기·부분 결과에서 최종 전용 보고 생성기를 호출해 말단 상태로 바꾸지 않는다. D의 투영을 기존 부분 상태 표시 경로에서 읽고 기존 종료·승인 대기 표시를 유지한다.

사용자에게 보여줄 내용은 현재 목표의 검사 상태, 자동 해석 상태, 남은 공백과 중단·대기 이유다. 원본 도구 본문·비밀·내부 심사 자료·자세한 저장 키를 사용자 흐름에 노출하지 않는다. 상세 참조는 기존 증거 조회 경로에서 확인한다.

예: 도구 실행 성공 / 자동 해석 미등록 / 원본 증거 열람 가능 / 목표 판정 미확정. 이 상태는 실행 불가도 취약점 부재도 아니다. 반대로 해석 실패와 성공적인 후속 복구가 모두 있을 때 최초 실패 이력과 현재 처리 상태를 나눠 표시한다.

## 6. 변경 금지 경계와 설계 반례 처리

- 완료 검증에 `mapping_outcome.applied`를 필수 조건으로 추가하지 않는다. 해석기 없는 도구의 증거도 기존 검증 조건에 맞으면 유효할 수 있다. 검토 영수증 존재는 그래프 반영 완료를 의미하지 않지만 반영 완료도 목표 완료를 대신하지 않는다.
- `progress.py`의 원본 의미 기준, 실행 정체성 버전, 구버전 보호, 승인 원본 복원·재진입, 정책·예산·속도 검사 순서는 유지한다. 새 proposal hash 검사나 기본값으로 승인 우회를 만들지 않는다.
- 기존 그래프 쓰기 통로와 변경안 검증을 사용한다. 원본 결과 재해석은 저장된 원본만 사용한다. 다른 실행의 원본·판정·경로가 섞이면 현재 근거로 쓰지 않는다.
- 신규 SYSTEM 기록은 감사 메타데이터다. 읽기 투영에는 포함하되 원본 의미 지문·관측 사실·가설 판정 근거에는 포함하지 않는다.
- Send의 행동별 결과 병합은 기존 행동 식별자 기준이고 집계는 배정 순서를 유지한다. 새로운 보조 결과를 전달해야 하면 기본값 있는 선택 필드만 추가한다. Overwrite로 배치 결과를 초기화하는 기존 조정자 한 곳을 유지하고 워커들이 각각 같은 채널을 덮어쓰게 만들지 않는다.
- 실제로 확인하지 않은 동시성 결함·전체 실행 시간 종료·성능 병목은 이번 수정의 확정 결함으로 넣지 않는다. 기존 동시 실행·재시도 상한을 바꾸지 않는다.

## 8. 계획 평가 기준과 상태

GPT-6.1 Sol 평가 에이전트는 루트의 추론 강도를 상속한다. 조사 워커는 Muse 1.3 Contributor Extra High다. 평가는 계획의 완결성만 채점한다. 테스트 수, 테스트 결과, 검증 실행, 테스트 커버리지는 점수에 포함하지 않는다.

| 배점 항목 | 만점 |
|---|---:|
| 최신 코드 사실·구버전 판단 분리 | 10 |
| LLM 중심 설계 일치·범위 | 15 |
| 설치 SDK 재사용·호환성 | 10 |
| 해석·루트 전달의 구체성 | 15 |
| 저장·중복·승인 계약 보존 | 15 |
| 진단·공백·종료의 정합성 | 10 |
| 파일별 변경·의존순서의 실행 가능성 | 15 |
| 공식 자료·GitHub 근거와 제안 연결 | 5 |
| 경계 상황·미지원·선택 완결성 | 5 |

1.1차 독립 평가: 90/100. 항목별로 10·15·10·13·13·9·12·4·4점이었다. 감점한 여섯 계획 누락은 처리 연결·생략 조회, 경로별 기록 저장 실패, 실제 도구 시도 판별, 예외·보고 연결과 담당, 설치 API 고정 근거, 복구 매퍼 반영 범위다.

2차 독립 재평가: **100/100**. 항목별로 10·15·10·15·15·10·15·5·5점이다. 평가자는 현재 파일을 다시 읽고 위 여섯 수정의 실제 반영을 대조했다. 첫 두 항목은 최신 소스 근거와 LLM 중심 경계를, SDK 항목은 설치·선언·소비 API 구분을 충족했다. 해석 전달 항목은 처리 연결과 생략 조회를, 보존 항목은 경로별 저장 실패와 기존 성공·승인 계약을, 진단 항목은 실제 호출·임대 구분을 충족했다. 파일·순서 항목은 워커 예외·루트 복구·보고 입력의 담당 연결을, 외부 근거 항목은 설치 소스와 공식 자료 연결을, 경계 항목은 복구 미지원·부분 반영·불명 처리를 충족했다. 추가 본문 수정 요구는 없었다.

테스트 수·결과·검증 실행·테스트 커버리지는 두 평가의 점수에 포함하지 않았다. 100점은 위 기준에 대한 계획 충족도이며 실제 구현 성공이나 무결함을 보장하지 않는다. 미확인은 모름으로 표현하고 점수를 맞추려고 사실로 바꾸지 않았다.

## 9. 마지막 단계 F — 구현 완료 후 테스트·검증

아래는 향후 구현 완료 후 수행할 계획이다. 이번 문서 작성에서 실행하지 않았다. A~E 중간에 테스트 체계·검증 점수를 추가하지 않는다. 마지막 단계에서 실패가 나오면 해당 변경을 고친 뒤 필요한 관련 검사만 다시 수행한다.

1. 환경: CI용 인터프리터와 선언 의존성을 맞추고 기존 dev/agent 선택 항목의 필요한 누락만 보충한다. SDK의 새로운 버전 업그레이드나 추가 에이전트 프레임워크 설치는 하지 않는다. 실제 공급자·API가 준비되지 않은 검사는 환경 미충족으로 구분한다.
2. 기존 관련 단위·통합 테스트를 우선 사용한다. 해석 등록·예외, 결과 갱신·복구, 보고, 승인 재개, 의미 중복 억제, 최신 모바일·브라우저·실행 연결의 기존 회귀 범위를 확인한다.
3. 실제 변경에 필요한 회귀만 추가한다: 미등록/정상 빈 결과/예외/정상 변경안/중복 반영 상태 구분, 부분 적용 실패와 저장 원본 복구, 원본 접근 거부·잘림·구키 호환, 신규 감사 기록이 진행·정체성에 영향 없음, 같은 승인·행동 재개 유지.
4. 집계 회귀: 현재 목표 공백과 과거 승인 버전 실행 분리, 반복 보고·재개·이벤트 재전송에서 중복 집계 없음, 복구가 새 실행으로 계산되지 않음, 과거 기록 불명·조회 실패·표시 제한 구분, 다른 실행·교전 자료 제외.
5. 대표 실행 흐름: 가짜 도구·저장소로 실행→해석→반영→루트 입력→최종/부분 보고를 확인한다. 자동 해석기 없는 원본도 기존 증거 검증·완료 경로를 사용할 수 있고 집계가 종료 조건을 대체하지 않는지 확인한다. 실서비스 공격은 이 검증 범위에 없다.
6. 변경 범위의 pytest, 기존 Ruff·Mypy 규칙을 실행하고 필요한 경우 저장소 CI 범위로 넓힌다. 도커 연동 파일을 바꾸지 않았다면 같은 도커 검사를 중복 추가하지 않는다. 오류와 환경 부족을 구분해 최종 결과에 남긴다.

최종 구현 보고는 실제 결손·재사용 기능·변경 파일·처리 상태 연결·검사 공백 표시·실행한 검사 결과·남은 미지원/미확인만 포함한다.
