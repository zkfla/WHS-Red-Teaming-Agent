> 이 문서는 작성 당시의 감사·검토·작업 기록이다. 중간 상태와 검증 수준을 그대로 보존한다. 최신 구현·CI·병합 상태는 [목차](../README.md)의 최종 계획을 기준으로 읽는다. 인용 행 번호는 검토 당시 기준이며 소스 링크에 현재 행 번호를 추정해 붙이지 않았다.

# impl-c — 모바일 벤더 정책 소비측 전환 보고서 (source-only)

> 소스 전용 보고서다. 소스 읽기와 편집만으로 작성했고, 테스트·컴파일·린트 실행은 하지 않았다.
> 따라서 아래 내용은 실행 결과가 아니라 소스 대조 기준의 동작 보존 근거다.
> 검증 실행 없이 소스 읽기와 편집만 했다는 점을 명시한다.

## 변경 파일 (1개)

- `src/redteam/orchestration/mobile_mcp_binding.py` — 유일한 소스 변경.
- 추가 허용 보고서인 이 파일 자체가 두 번째 산출물이다.
- 그 외 소스 생성·수정·삭제 없음. 루트 소유 조립부는 손대지 않았다.

## 함수·단위별 변경 요약

- 정책을 선언하는 자료형(역할: 벤더별 관리 조건 묶음): 기존 항목(벤더 식별자, 관리 서버 집합, 대체-주 서버 대응, 승인 보관 영역 참조, 버전)은 유지하고, 해시 검증이 필요한 서버 집합을 뜻하는 선택 항목 하나를 추가했다. 기본값은 내장 동작과 동일하게 mobsf 상당 1개만 포함한다. 내장 정책 값 자체는 바꾸지 않았고 기본값으로 동일 동작을 얻는다.
- 서버→소유 정책 맵 생성기(역할: 서버 소유권 판정, 신규): 선택된 모든 정책의 관리 서버 집합을 한 번에 모아 서버 id → 소유 정책으로 연결한다. 같은 서버가 두 정책에 있으면 서버 id와 두 벤더 식별자를 모두 포함한 메시지로 ValueError를 낸다.
- 적격성 판단 주체 생성자(역할: 실행 전 적격성 문지기 초기화, `MobileMCPEligibility.__init__`): 진입 즉시 서버→소유 정책 맵을 만들고 중복을 거절한다. 정책별로 승인 보관 영역에서 개별 설정을 검증하고, 켜진 설정 전부에 기존 범위 검사를 적용한다. 위반 시 기존과 동일한 문자열(`mobsf_agent_assets_outside_scope`)로 실패한다. 호환용 단일 설정 속성은 첫 정책 값으로 유지하되 판정에는 쓰지 않는다. 평탄 병합 맵은 호환용으로만 남기고 판정은 소유 정책으로 한다. 위치 인자 3개 호출과 카탈로그=게이트웨이 동일 객체 형태는 그대로 받는다.
- 적격 판정(역할: 도구별 통과 여부 판단, `eligible`): 서버→정책 맵에서 소유 정책을 찾고 없으면 통과한다. 소유 정책의 해시 요구 집합에 들면 켜짐+HEALTHY만 통과한다. 아니면 소유 정책의 대체-주 대응을 보고 대응이 없으면 통과, 도구 자체가 HEALTHY가 아니면 탈락, 도구가 광고한 역량 태그 전부로 카탈로그를 모아 주 서버 것만 남기고 도구 id로 중복 제거한 뒤 기존과 같은 의미(있고 전원 UNHEALTHY일 때만 통과)로 판단한다. 문자열 분기와 주 서버 이름에 따른 역량 갈아끼우기를 없앴다.
- 호출 관문(역할: 실행 시점 재확인, `invoke`): 서버→정책 맵으로 관리 여부를 보고, 있으면 건강 새로고침(있을 때만, 강제) 후 카탈로그 재조회와 적격 재판정을 한다. 소유 정책 데이터 기준 해시 요구 서버일 때만 기존 핀 해시·실행 검사(핀 해시 조회, 기대 해시 일치, 인게이지먼트 존재·일치)를 그대로 한다. 거절 시 기존과 동일한 오류 코드와 메시지로 반환하고 아니면 게이트웨이로 통과시킨다.
- 배선 함수(역할: 실행 의존성 묶음에 문지기 장착, `wire_mobile_mcp`): 중복 서버 검증을 조기 반환보다 먼저 한다. 역량 목록은 기본 2종과 실행 의존성의 역할 정의들이 광고하는 역량을 합쳐 카탈로그에서 모아 도구 id로 중복 제거한다. 원본 카탈로그·게이트웨이는 바꾸지 않고 문지기가 감싸 위임한다. 관리 서버가 하나도 없으면 그대로 반환한다. 관측 기여는 건강·해시 자격과 별개 축이라 실제 내장 mobsf 출력 도구 신원(서버 mobsf + 도구명 mobsf_report_summary)이 존재할 때만 등록하고, 등록 전 해석 등록부의 공개 중복 조회를 거친 뒤 카탈로그 결속을 건다(루트 후속 검토 반영, 아래 actual 절 참고). 정책 미지정 시 내장 정책을 쓴다.
- 정책 기여·선언(역할: 조립부에 정책 알림, `mobile_vendor_policy_contributions`·`builtin_extension_declaration`·`VENDOR_POLICY_KIND`): 형태와 의미 변경 없음.

## 정책 데이터 기반 전환 설명

- 이전: 첫 정책의 승인 참조만 읽고, 특정 서버 이름 분기와 주 서버 이름에 따른 역량 선택, 고정 역량 2종 조회, 특정 서버 존재 시 관측 등록이 하드코딩이었다. 새 정책이 등록돼도 소비 측 조건에 반영되지 않는 구조였다.
- 이후: 모든 조건이 정책 데이터에서 흘러나온다. 소유권은 서버→소유 정책 맵, 해시 요구는 정책별 집합, 대체-주 대응은 소유 정책의 대응표, 승인·범위는 소유 정책별 설정, 배선 조회 범위는 기본 2종+역할 정의 광고 합성, 관측 등록은 실제 내장 mobsf 출력 신원+공개 중복 조회 기준이다(자격 축과 출력 축 분리). 새로 추가한 전역 상태나 DI 장치는 없다. 공개 이름·시그니처는 유지했다.

## 남은 미검증 위험 (읽기만으로 단정 못한 부분)

- 실행 의존성의 역할 모음(역할: 가용 역할 정의 제공자, `deps.agents`) 실제 형태는 이 보고서 작성 시점에 읽기만으로 단정 못 했다. → 루트 후속 검토에서 전체 조회 경로와 광고 역량 직접 합성으로 단순화하며 실물 확인됐다(아래 actual 절). 방어 블록은 제거됐다.
- 인게이지먼트 메타데이터·범위(`metadata`·`scope.allowed_assets`·`denied_assets`)가 비어 있거나 None인 변형은 소스상 기존 가정을 그대로 따랐고 실행으로 확인하지 않았다.
- 카탈로그의 역량 조회가 미등록 역량에 빈 목록을 주는지, 도구 id 중복 제거 키가 전 케이스에서 안정적인지는 실행으로 확인하지 않았다.
- 같은 벤더 식별자를 가진 정책이 둘 이상 오는 변형은 서버 기준 맵은 정확히 갈리지만 벤더 식별자 기준 맵은 마지막 값이 남는다. 명세의 중복 거절 대상은 서버 기준이라 소스상으로는 맞췄으나 실행 변형은 미확인이다.
- 이 보고서는 소스 전용이며 테스트·컴파일·린트 결과를 포함하지 않는다.

## 루트 후속 검토 반영 — actual final state (2026-10-04)

> 이 절은 루트가 모바일 보완분을 직접 읽고 손본 뒤의 실제 소스 상태를 기록한다. 위 본문과 충돌하면 이 절이 실제 상태다. 소스 전용이며 테스트·컴파일·린트 결과는 포함하지 않는다.

1. 과잉 가드 단순화(모바일 결선 파일)
   - 적격/호출 판정의 설정 조회가 서버→설정 맵 직접 조회로 정리됐다. 존재 폴백(기본 설정 속성으로의 대체) 제거.
   - 배선의 역할 정의 조회가 방어 블록(호출 가능성 검사·예외 삼킴·타입 순회) 대신 역할 모음의 전체 조회 + 광고 역량 직접 합성으로 단순화됐다. 전체 조회와 역량 필드의 실물 존재는 소스로 확인됨.
2. 관측 mapper 연결 조건 복원(모바일 결선 파일)
   - 워커판은 "해시 요구 집합에 속한 서버 도구 존재"로 관측 기여를 등록했으나, 건강·해시 자격과 출력 규격은 서로 다른 축이므로 자동 연결하면 안 된다는 판단에 따라 실제 내장 mobsf 출력 신원 조건(서버 mobsf + 도구명 mobsf_report_summary 존재)으로 되돌려졌다.
   - 조건부 등록의 중복 방지는 해석 등록부의 공개 중복 조회로 보존하고, 등록 뒤 카탈로그 결속을 건다. custom 벤더 mapper는 각자 기여로 등록한다(자동 연결 없음).
3. 원격 인자 검사 중복 제거(대상 결속 파일, 루트 소유 — 워커 산출물 아님)
   - 원격 인자 이름 대응 때문에 생겼던 약 100줄 복제가 같은 필드 루프에 mapped names를 합성하는 단일 경로로 정리됐다. 인자 대응표(원격 이름→공통 이름)를 받아 각 필드 검사 집합에 합성하는 형태이며, 검사 의미(포트·주소·URL·정확 일치·충돌 거절)는 유지된다.
4. 유지 항목: 공개 이름·시그니처, 내장 정책 기본값, 오류 코드·메시지, 기여 선언 형태, 소유 정책별 판정 원칙은 그대로다.
