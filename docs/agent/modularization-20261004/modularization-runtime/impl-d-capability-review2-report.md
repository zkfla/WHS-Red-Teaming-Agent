## 함수별 변경 요약

### 1) 구성 후보 검증

- 변경 전: 명세 ID(2구간) 집합과 발견 ID(실제는 3구간) 문자열 집합을 직접 비교했고, 동작 바인딩 조회도 명세 ID 키로 했다.
- 변경 후: 예상 키=(명세 서버 ID, 원격 이름), 실제 키=(발견 서술자의 서버 ID, 발견 서술자의 원격 이름).
- 원격 이름은 명세 ID의 두 번째 구간이다. 명세 서버 ID는 고정 명세 사전의 dict 키이다.
- 키 집합이 다르면 기존 취지 그대로 거절하되 메시지에 서버 ID와 차이 목록을 담는다.
- 문구는 discovered tool IDs differ from manifest 를 유지하고 뒤에 missing/extra를 붙인다.
- 대응쌍 검사는 실제 발견 ID 문자열로 동작 바인딩을 조회한다. 스키마 검사는 기존 함수 그대로이며 원격 이름 키로 조회한다.

### 2) 대상 유형 선택 (server_id, tool_id 입력)

- 변경 전: 명세 ID(2구간)와 입력 ID 문자열을 직접 동등 비교했다. 실제 3구간 정식 ID와는 절대 일치하지 않았다.
- 변경 후: 기존 공용 ID 분리 함수를 재사용한다. 새 파서는 만들지 않았다.
- 입력 ID를 나누어 원격 이름과 서버 구간을 얻는다.
- 3구간이면 서버 구간이 요청 서버 ID와 같은 때만 후보로 본다. 다르면 미매칭이다.
- 2구간 legacy 입력은 서버 구간이 없으므로 원격 이름만으로 해당 서버 명세와 대조한다.
- 해당 서버 명세 안에서 원격 이름이 같은 명세의 대상 유형을 반환한다. 없으면 None이다.

### 3) 카탈로그 대상 유형 반영

- 변경 전: 명세 ID(2구간)가 바인딩 dict(실제는 3구간 키)에 있는지 직접 확인하고, 명세 ID 키로 결과 dict에 썼다.
- 변경 후: 핀된 서버가 아니면 그대로 no-op이다.
- 해당 서버 명세들을 원격 이름 기준으로 색인한다.
- 바인딩 dict의 각 실제 키를 기존 공용 ID 분리 함수로 나누어 원격 이름을 얻는다.
- 3구간이면 서버 구간이 요청 서버와 같은 것만 본다. 2구간 키도 원격 이름으로 본다.
- 매칭되면 결과 dict에 실제 바인딩 키 그대로 대상 유형을 쓴다.

### 4) 설정 소비자

- 변경 전: 묶음에 해당 프로필이 있어도 보정 함수가 있을 때만 early-return했고, 없으면 내장 기여자 경로로 떨어졌다.
- 변경 후: 묶음에 해당 프로필 묶음이 존재하면 등록 존재로 본다.
- 보정 함수가 있으면 실행 후 return이다. None이면 아무것도 하지 않고 return(no-op)이다.
- 등록된 선택 기능 부재를 미지원 오류로 만들지 않으며 일반 설정/어댑터/명세 검사 경로가 이어서 처리한다.
- 묶음 없음/묶음에 해당 없음일 때만 내장 기여자 경로를 탄다. 내장에도 없으면 기존과 동일한 문구로 명시 거절한다.

### 5) 발견 소비자

- 변경 전: 묶음에 해당 프로필이 있어도 바인딩 함수가 있을 때만 early-return했고, 없으면 내장 바인더로 떨어졌다.
- 변경 후: 묶음에 해당 프로필 묶음이 존재하면 등록 존재로 본다.
- 바인딩 함수가 있으면 결과 반환이다. None이면 None 반환(no-op)이며 일반 발견 경로를 유지한다.
- 묶음 없음/묶음에 해당 없음일 때만 내장 바인더 경로를 탄다.
- 내장에도 없으면 기존과 동일한 unsupported MCP server profile 문구로 명시 거절한다.

## 물리 신원 대조로 바뀐 지점과 정확 검사 보존

- 바뀐 지점: 구성 후보 검증의 집합 비교 키가 문자열 ID 동등에서 (서버 ID, 원격 이름) 쌍으로 바뀌었다.
- 동작 바인딩 조회 키가 명세 ID에서 실제 발견 ID 문자열로 바뀌었다.
- 대상 유형 선택과 카탈로그 반영이 문자열 동등에서 원격 이름 대조(+3구간 서버 일치 확인)로 바뀌었다.
- 보존한 정확 검사: 역량 포함 여부, 위험 등급 동등, 동작 1건 동등 검사를 그대로 둔다.
- 입력/출력 스키마 검사는 기존 전용 검사 함수를 그대로 호출한다. 검사 완화나 우회 분기는 추가하지 않았다.
- 오류 문구 조각 discovered tool IDs differ from manifest, input schema differs, operation differs 를 유지한다.
- 핀된 서버만 검사하고 다른 서버는 no-op인 기존 경계를 유지한다.
- 새 프로필 함수/DSL 추가 없음, 묶음에 새 필드 추가 없음, bootstrap 대상 유형 소비 로직 복제 없음도 지켰다.

## 기존 테스트 대비 호환 근거

- 대상 테스트 파일의 구성 후보 테스트들은 서술자를 2구간 명세 ID로 만들고 바인딩 dict도 2구간 명세 ID 키로 만든다.
- 본 수정은 그 형태와 실제 3구간 발견을 동시에 받아들인다.
- 키 비교가 (서버 ID, 원격 이름) 쌍이라 2구간 서술자와 3구간 서술자가 같은 쌍으로 수렴한다.
- 예: 2구간 서술자(서버 mobile-local, 원격 device_shell)와 3구간 서술자(같은 서버/원격)는 같은 쌍이다. 예상 키도 같은 쌍이므로 집합이 성립한다.
- 바인딩 조회가 실제 서술자 ID 문자열 기준이라 테스트에서는 2구간 키로, 실제에서는 3구간 키로 각자 성립한다.
- 출력 스키마 조회는 원격 이름 기준이라 두 경우 모두 동일하다.
- 오류 문구 조각을 유지했으므로 기존 match 조건이 깨지지 않는다.
- 위 호환은 소스 판독 근거이며 실행으로 확인하지 않았다.

## I13의 등록/미등록 구분 동작

- 등록 존재: 묶음 dict가 주어지고 그 안에 해당 프로필 키가 있으면 등록된 것으로 본다.
- 이때 없는 선택 기능(설정 보정 None, 발견 바인딩 None)은 no-op이다. 설정 쪽은 return만 하고, 발견 쪽은 None을 돌려 일반 경로를 살린다.
- 등록 부재: 묶음이 None이거나 묶음에 해당 키가 없고, 내장 표에도 없으면 기존과 같은 명시 거절이다.
- 내장 경로(묶음 없음/묶음에 내장 프로필 없음)는 기존 그대로이다. 내장 프로필의 정확 검사를 약화하지 않는다.

## 남은 미검증 위험

- 소스 전용 보완이므로 실행 미확인이다.
- 이스케이프된 서버/원격 이름이 있을 때 공용 분리자의 서버 구간 비교가 엄밀한 정식 파서와 같은지 추가 확인이 필요하다. 현재 핀된 서버 ID에는 점이 없어 실무상 같아 보인다.
- 동일 서버 안에 원격 이름 중복 명세가 생기면 물리 키가 충돌한다. 현재 명세에는 중복이 없어 보인다.
- 바인딩 dict에 형식이 깨진 키가 섞이면 해당 키는 건너뛴다. 조용히 건너뛰는 것이 맞는지 정책 판단이 남는다.
- I13 no-op 뒤에 이어지는 일반 설정/어댑터/명세 검사가 부분 프로필을 실제로 시작까지 데려가는지는 해당 일반 경로 소스를 따로 봐야 한다.
