이 판정은 **설계 결정을 마쳤으므로 구현을 시작할 수 있다는 뜻**이다. 기존 소스의 결함이 수정됐거나 확장·재개·저장 호환이 검증됐다는 뜻은 아니다. 실제 테스트는 기존 계획대로 통합과 코드 검토 뒤 마지막 단계에 둔다.

## 3. 단순성과 새 결합 여부

이번 변경이 불필요한 범용 장치를 새로 요구한다고 볼 근거는 확인하지 못했다.

- 확장 패키지·기여·업무 분야의 구분은 현재의 중복 선택 문제를 풀기 위한 최소 자료다. 다수 역할·도구와 단일 추론을 하나의 역할 목록으로 합치지 않는다.
- 복합 저장 제공자는 현재 함께 확정하는 상태 집합으로 제한됐다. 모든 저장소의 트랜잭션을 통합하거나 외부 도구의 롤백을 지원하는 프레임워크로 확대하지 않는다.
- 가역 신원 표기는 서버/원격 이름을 잃지 않기 위한 도구 신원 기능이며 별도 범용 resolver를 요구하지 않는다. 정확한 출력 의미는 명시적 도구 연결로 계속 처리한다.
- 설정의 하위 공통 입력 경계는 기존 공개 호출의 호환과 역참조 제거에 필요한 배치다. 제공자가 다시 각자 환경을 읽는 방식이나 앱에서 core로 역수입하는 방식은 채택하지 않았다.
- 구형 기록에만 적용하는 기본 구성 호환은 명시된 이관 규칙이다. 새 역할·새 서버를 추가할 때마다 중앙에 신원별 분기를 추가하는 일반 등록 방식과 구분된다.

선택적 개선도 구현을 줄이는 방향으로 결정됐다.

|---|---|---|

## 4. 소유 워커에게 남기는 구현 전 확인

다음은 **이미 정한 계약을 현재 저장·소비 경로에 적용하기 위한 확인**이다. 추가 계획 승인이나 새로운 범용 설계의 조건으로 취급하지 않는다.

### 도구 신원 표기와 소비자 이관 — R04

도구 소유자는 정식 신원의 가역 구간 표기와 기존 명시 도구 신원·구별칭의 대응을 소스에서 확정한다. 현재 명세 검사의 두 구간 제약, 카탈로그의 이름 기반 능력 조회, 도구 바인딩·해석·승인 재개의 신원 소비를 함께 이관한다. 원본 자료를 다시 쓰지 않고도 이전 실행의 정확한 서버/원격 도구 연결을 유지하는지 확인한다.

세 구간의 표기를 문서에서 임의로 더 고정할 필요는 없다. 현행 소스를 읽은 소유자가 한 신원 해석 경계에서 결정하고 공유 소비자 변경안을 루트에 전달할 수 있다. [계획의 확인 책임](../2026-10-04-WHS-modularization-implementation-plan.md), [공유 소비자 소유와 구현 전 확인](../2026-10-04-WHS-modularization-implementation-plan.md).

### 남은 관계 자료의 저장 이관 — R08

저장 소유자는 기존 관계 직렬화와 저장 키, namespace 경계의 조회·삭제·내보내기를 읽고 접속 시 이관 또는 일관된 호환 경계 중 최소 방식을 선택한다. 실제 소유 신원이 입증된 남은 자료만 변환하고 과거 덮어씀으로 유실된 관계를 추정 복원하지 않는다.

현재 저장 형식을 확인하기 전에 전 저장소 공통 migration 체계를 만들 필요는 없다. 구현 방식과 한계를 기록하면 된다. [관계 이관 결정](../2026-10-04-WHS-modularization-implementation-plan.md), [소유자의 실제 저장 형식 확인](../2026-10-04-WHS-modularization-implementation-plan.md).

다른 공개 계약의 세부 자료와 호출 형태도 각 소유자가 기존 소스에서 최소 구현을 선택할 수 있다. 선택 결과가 11절의 소유권·비용 소비·복원 규칙을 바꾼다면 그 변경만 다시 검토하면 된다.

## 5. 본문 표현의 작은 잔여 사항

5.C에는 여전히 “기존 ... 일회 claim”이라는 짧은 표현이 남아 있다. 11절 R05가 임대·경로 세대 claim·승인 일회 소비를 구분하고 외부 정확히 한 번 실행을 약속하지 않는다고 명시하므로, 이를 새 필수 모순으로 보지 않는다. 구현은 11절의 구체 결정에 따른다. 문서 정리 시 5.C를 “기존 승인 의도·ID·행동 연결과 경로 세대 claim을 보존” 정도로 맞추면 오독을 줄일 수 있다. **표현 정리이며 구현 착수 조건이 아니다.**

4.1의 “같은 역할의 중복”도 11절 R03이 업무 분야와 기여 신원·단일 구현 선택을 구분하여 해석 범위를 정했다. 같은 분야의 다른 신원 역할을 금지한다는 규칙으로 구현하지 않으면 된다. 이 역시 이미 결정된 등록 의미를 따를 사항이며 새 문제로 반복하지 않는다.

## 6. 다음 검토의 수준

후속 구현 검토에서는 실제 중앙 목록·도메인 특례·사설 접근이 이관됐는지, 새 등록이 기본 제공자와 같은 조립 경로를 사용하는지, 제안·회계·복원·원본 계약이 코드에 반영됐는지를 확인한다. 계획상 폐쇄 판정을 실제 구현 완료로 재사용하지 않는다.

현재 단계에서 추가 필수 지적을 만들거나 테스트 수로 계획을 다시 평가할 필요는 없다. 루트와 소유 워커는 개정 2의 결정에 따라 최소 골격·이관 구현을 시작할 수 있다. 실제 실행·테스트·릴리스 검증은 계획의 마지막 단계에 유지한다.
