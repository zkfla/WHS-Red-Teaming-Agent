## 3. M02 — 역할 등록 정보·기본 조립 분산

(1) 코드 확인 현재 동작. 역할 하나가 두 문서로 나뉘어 있다. 실행 명세 쪽은 builtin.py:28 주석에 능력치를 적고, 역할 정의 쪽은 definition.py의 내장 5종 정의에 능력치를 적는다. 어긋나면 등록 단계의 일치 검사(registry.py:57 _check_capabilities_agree, 호출은 register :83 과 register_definition :95)가 터져서 조용히 어긋나는 일은 없다. 기본 조립도 두 목록이다. 기본 역할 조립(registry.py:292 default_registry, 실행 명세 4개+정의 5개)과 기본 후보 제공자 조립(providers.py:302 default_provider_registry, recon·web_api 전용 + mobile·analysis·reporting 공용 플레이북)이 따로 논다.

(2) 감사 문서 주장 일치/정정. 두 곳 수정 + 일치 검사로 막음 + 기본 조립 분산이라는 주장과 완전히 일치한다. 테스트 얘기도 맞다. test_agents.py:449 기본 구성 기대는 실행 명세 4개·정의 5개·스케줄 가능이면 실행 명세 보유라는 불변식을 건다. 이게 사용자 정의 등록부를 4개로 묶는다는 뜻은 아니라는 단서도 맞다. 등록부 생성자가 임의 등록을 받으니 기본 샘플 기대값이지 확장 제한이 아니다. 감사 문서가 틀린 부분은 없다.

(3) 구체 이관안. 역할 1등록 단위(RolePackage)를 만든다. 한 단위 안에 역할 정의·실행 명세·제공자 연결·기본 포함 여부·필수/선택 제공자 선언을 다 넣는다. 능력치는 한 소유자(정의 쪽)에서만 적고 명세 쪽은 파생·검증만 한다. 바뀌는 파일은 agents/registry.py(단위 등록·검증), agents/providers.py(제공자 해결), app/runtime_components.py(기본 프로파일 조립이 단위 목록 소비), tests/unit/test_agents.py(기본 샘플 테스트 유지 + 단위 등록·결속 테스트 추가)다. 직접 주입 가능한 현 등록 API는 남긴다.

(4) 기존 규칙 유지. 정의·명세 일치 검사는 유지(값 어긋남 즉시 실패). 스케줄 가능이면 실행 명세 보유라는 불변식 유지. 등록 순서가 스케줄 정책이라는 점은 건드리지 않는다.

(5) 남는 한계·미검증. 기본 순서 보장(밴드 동점 시 등록 순서)을 단위 선언에서 어떻게 표현할지 못 정했다. 아래 루트 결정 1번으로 넘긴다. 중복 식별자 검사는 현재 역할·제공자 각각 있는데 단위 차원 중복(같은 역할 id에 다른 제공자) 규칙은 미정이다.

## 4. M03 — 도메인(정적 분석) 자격 판단의 중앙 엔진 배선

(1) 코드 확인 현재 동작. 자격 계산은 analysis_activation.py:44 한 곳이다. APK 자산(사실에 apk_ref 문자열이 있는 자산 노드)을 모으고, 적격 도구(is_static_analysis_tool :28, analysis 능력+static_analysis 동작+건강+asset 대상)를 고른다. 소비는 4곳이다. 프롬프트 가시성(engine.py:538 부근, 역할 가시성+도구 가시성+실행 준비 가시성 3중 필터), 참고 후보(engine.py:682 부근, 역할 숨김 스킵), 승인=행동 컴파일(engine.py:1587 부근, capability가 analysis이고 동작이 static_analysis면 APK 노드·적격 도구 인라인 비교 후 거절), 실행 직전(engine.py:2752 부근, 같은 비교 재검사)이다. 계획 시점과 실행 직전이 같은 규칙을 두 번 보는 구조다.

(2) 감사 문서 주장 일치/정정. 네 벌 전체 복제는 아니고 배선 반복+일부 조건 별도 소비라는 주장이 맞다. 행번호는 살짝 어긋났다. 승인 1616은 실측 1587 부근, 실행 직전 2752는 실측 2753 부근이다. 심볼(analysis_activation 호출·STATIC_ANALYSIS_OPERATION 비교)로 재확인했으니 내용은 맞고 번호만 드리프트다.

(3) 구체 이관안. 자격 술어와 가시성을 등록 가능한 제공자로 만든다. 공통 계약은 3개 함수짜리 Protocol 1개다. 역할 적격 판단(그래프 요약+카탈로그 요약에서 참거짓+사유), 도구 적격 판단(도구 기술서에서 참거짓+사유), 자산 범위(대상 자산 노드 집합)이다. 도메인 제공자 하나가 여러 역할·도구에 붙을 수 있게 적용 대상(capability·operation·서버 목록)을 선언에 넣는다. 중앙 엔진은 4개 수명주기 지점에서 호출만 하고 인라인 비교는 지운다. 바뀌는 파일은 analysis_activation.py(기본 도메인 제공자 구현으로 축소), engine.py(4곳 호출로 교체), 계약 1곳(위치는 루트 결정, core 권장)이다. 계획 시점 검사와 실행 직전 재검사는 둘 다 남긴다. 같은 규칙이라도 시점이 다르면 다른 검사다. 카탈로그 건강 상태가 사이에 바뀔 수 있어서 실행 직전 재검사를 지우면 TOCTOU 구멍이 난다.

(4) 기존 규칙 유지. 스키마·대상 일치·범위·승인·원본 증거 검사는 손대지 않는다(컴파일러·정책·검증 노드 그대로). 모르는 자산·도구는 계속 거절(기본 거부 유지). 루트 LLM 주도 원칙도 유지한다. 자격 제공자는 보여줄지만 정하고 실행해도 된다는 승인을 대신하지 않는다.

(5) 남는 한계·미검증. 계약 위치(core vs orchestration)는 루트 담당이라 제안만 한다(core 권장, 이유는 대상·정책 계약이 이미 core에 있기 때문). pluggy는 불필요하다. 호출 4곳이 엔진 안에 명시돼 있어서 훅 디스패처를 끼우면 추적만 어려워진다. pydantic-settings도 불필요하다. 자격 판단 입력이 런타임 그래프+카탈로그라 정적 설정이 아니다.

## 5. M04 — 모바일 벤더 정책이 오케스트레이션 내부에 위치

(1) 코드 확인 현재 동작. mobile_mcp_binding.py 한 파일에 벤더 정책이 박혀 있다. 주·대체 관계(:53 부근 primary 딕셔너리, analysis-local에서 apktool로, mobile-local에서 mobile-next로), 실행 관리 대상(:82 부근, mobsf·analysis-local·mobile-local), 연결 대상 조건부 해석 등록(:117 wire_mobile_mcp, :128 mobsf 있을 때만 해석 등록)이다. 승인된 해시 검사는 해시 형식 검증 + 스코프 대조(생성자) + 호출 시 핀 검사(apk_ref에서 고정 해시, expected_sha256 일치, engagement_id 일치)로 3겹이다. 비관리 서버는 eligible에서 primary None이면 True, 호출 시 관리 대상 아니면 게이트웨이 직통이라 차단하지 않는다. 앱 조립은 bootstrap.py:526·645 두 곳에서 감싸기만 호출한다.

(2) 감사 문서 주장 일치/정정. 서버 집합·관계·연결 조건을 고쳐야 새 대체 관계가 된다는 주장과 관리 대상 아닌 일반 서버는 차단 안 한다는 반례가 둘 다 맞다. 직접 읽고 확인했다.

(3) 구체 이관안. 서버 주·대체 관계와 관리 대상 집합만 확장 패키지 정책 데이터(VendorPolicy 선언)로 뺀다. 검사 로직(해시 형식·스코프 대조·핀 검사·건강 게이트)은 공통으로 남긴다. 파일 이동은 mobile_mcp_binding.py를 정책 데이터 주입식 일반 EligibilityView로 바꾸고, 벤더별 값은 확장 선언이 들고, app/bootstrap.py는 값만 전달한다. 조건부 해석 등록(:128)은 M05 선언으로 흡수한다.

(4) 기존 규칙 유지. 승인 APK 해시·범위 검사 자체는 그대로 둔다. 제공자 주장 상태와 운영자 승인 정책 자료 구분도 유지한다(건강 상태는 승인이 아니다). 이름 목록 삭제 같은 무검증 개방은 하지 않는다. 모르는 서버 처리는 현행 그대로(비관리는 통과, 관리는 검사) 유지한다. 현행 동작 보존이 우선이다.

(5) 남는 한계·미검증. 정책 데이터 스키마 위치(확장 선언 vs 앱 설정)는 루트 결정 5번으로 넘긴다. 권장안은 확장 패키지 선언이다. 모바일 승인 자산을 engagement.metadata로 읽는 현행과 맞물리기 때문이다. pydantic-settings는 불필요하다. 이건 운영자 승인 자료지 앱 정적 설정이 아니다. pluggy도 불필요하다. 호출 경계가 카탈로그·게이트웨이 포트 2개로 고정돼 있다.

## 6. M05 — 결과 해석 등록 중앙 목록·조건부 연결 분산

(1) 코드 확인 현재 동작. 해석 등록은 mapper.py:176 register(도구 식별자 정확 일치, 와일드카드 없음, 중복 등록은 거절)와 기본 목록 mapper.py:207 default_result_mapper_registry(약 20개 등록) + 모바일 조건부 등록(mobile_mcp_binding.py:128 mobsf 있을 때만 1개 추가)으로 나뉜다. 조립은 runtime_components.py의 내장 팩토리에서 기본 목록을 만든다. 미등록이면 map_result가 빈 변경안을 반환하고 끝이다. 도구 실행 자체는 막지 않는다. 원본 결과는 검증 노드(verify.py:74 부근 원본 저장)가 따로 보존하고 LLM 판독 경로(분석 검증자)도 별도라 구조화 그래프 반영만 빠지는 것이다.

(2) 감사 문서 주장 일치/정정. 기본 목록과 조건부 등록이 따로 있어 연결 누락이 생긴다는 주장과 미등록은 실행 차단이 아니고 원본·LLM 판독은 별도라는 반례가 둘 다 맞다. 폐쇄 루프 계획도 같은 말을 한다(해석기 부재는 미지원과 다르다). 일치한다.

(3) 구체 이관안. 도구와 함께 해석 제공자 등록 정보를 제출하고 조립 시 한 경로로 묶는다. 선언(메타데이터: 도구 식별자 목록·해석 버전·의미 변화 규칙)과 실제 제공자 팩토리(함수 참조, import 경로 문자열)를 분리한다. 구현 함수 자체를 직렬화 메타데이터에 넣지 않는다. 같은 해석기를 여러 도구가 공유할 수 있게 등록 키를 도구 식별자 목록으로 한다. 모바일 조건부 1건은 선언으로 흡수한다. 바뀌는 파일은 observations/mapper.py(선언형 등록 API 추가, 기존 register 유지), capability 등록 경로, runtime_components.py 조립이다.

(4) 기존 규칙 유지. 변경안 검증(노드 식별자·타입, 관계 양단, 판정 변경 형식)은 그대로 둔다. 정확 일치 원칙(검증 안 된 도구군에 추측 매핑 금지)도 유지한다. 실패는 관측 가능하게(현행 last_failure) 남긴다.

(5) 남는 한계·미검증. 선언 의무화(해석 없이 도구 등록 가능 여부)는 루트 결정 4번으로 넘긴다. 권장안은 의무 동봉이 아니라 없으면 구조화 반영 없음으로 명시하는 선택 동봉이다. 실행 차단을 걸면 폐쇄 루프 계약(원본·LLM 경로 존재)을 깨기 때문이다.

## 7. M07 — 제공자 연결 누락 결속 검사 부재

(1) 코드 확인 현재 동작. 역할 정의의 provider_id 문자열(definition.py:114 부근 필드)이 후보 제공자 등록부(providers.py:283 register, :302 기본 조립)와 문자열로 만난다. 참고 후보 수집 시점(engine.py:682 부근 루프, 실측 694 근처)에 제공자가 없으면 진단을 남기고 건너뛴다. 늦은 스킵이라서 조립은 성공한 것처럼 보인다.

(2) 감사 문서 주장 일치/정정. 문자열 연결 + 수집 시점 스킵 + 팀 분리 시 참고 후보 누락이라는 주장이 맞다. 근거 행번호 engine.py:694는 실측과 수 행 어긋나지만(provider None 분기) 심볼 기준 일치다.

(3) 구체 이관안. 시작 시 결속 검사를 넣는다. M02의 1등록 단위가 provider_id와 필수/선택 구분을 선언하고, 조립부(bootstrap)가 실행 시작 전에 전체 참조를 해결한다. 필수 제공자 누락은 시작 실패, 선택 제공자는 현행처럼 격리하되 누락 상태를 겉으로 표시한다. 바뀌는 파일은 agents/providers.py 또는 registry.py(resolve 추가) + app/bootstrap.py(시작 시 호출)이다.

(4) 기존 규칙 유지. 선택 제공자 격리(현행 스킵)는 유지한다. 이 검사가 루트 LLM의 모든 행동 생성을 막는다는 뜻이 아니다. 폐쇄 루프 원칙(후보 부재는 조사 종료가 아니다)을 그대로 둔다.

(5) 남는 한계·미검증. 실패 정책(경고 후 진행 vs 시작 실패)은 루트 결정 3번으로 넘긴다. 권장안은 필수면 실패·선택이면 표시 후 진행의 혼합이다.

## 8. M18 — 역할 재활성화 관측 지문이 중앙 키 목록 의존

(1) 코드 확인 현재 동작. 계획 관련 키 목록(observation.py:35 PLANNING_CONTENT_KEYS, 의도적 허용 목록)이 있고, 노드별 내용 해시(:95 _planning_content)에서 타입별 content_digests를 거쳐 역할별 지문 계산(progress.py:104 observation_fingerprint, 등록부의 revision_fingerprint registry.py:163이 역할 맥락 profile의 포함 목록으로 투영)으로 이어진다. 목록 밖 새 구조화 사실은 지문이 안 바뀐다. 시각·증거번호·시도 기록 같은 휘발성은 일부러 뺐다(observation.py 주석, VOLATILE_RELATION_KEYS, progress.py 무시 목록). 메인 실행 진행 지문은 별도(original-v1, progress.py:14, 원본 내용+완료 단계 기반)라서 역할 지문과 섞으면 안 된다.

(2) 감사 문서 주장 일치/정정. 목록 밖 사실은 지문 무변화 + 새 도메인의 의미 변화 등록 통로 없음이라는 주장이 맞다. 범위 단서(진행 지문 별도, 실행 정체로 단정 금지)도 맞다.

(3) 구체 이관안. 역할 또는 관측 제공자가 의미 있는 변화의 투영 규칙을 선언하고 일반 지문 계산기가 소비한다. M05 해석 등록과 같은 확장 단위에서 동봉한다. 선언 형태는 도구 결과에서 그래프 속성 키 목록(간단한 경우) 또는 투영 함수 참조(복잡한 경우) 중 하나로 한다. 바뀌는 파일은 observation.py(키 합성 선언 기반) + mapper.py 등록 API다. progress.py 원본 진행 지문은 손대지 않는다.

(4) 기존 규칙 유지. 시각·증거번호만으로 깨우지 않는 원칙은 그대로 둔다(휘발성 제외 목록 유지). 목록에 없는 모르는 키는 계속 무시(기본 거부)한다. 이름만 올린다고 깨우지 않고, 선언된 키의 내용 변화가 있어야 깨운다.

(5) 남는 한계·미검증. 키 목록 방식과 함수 방식 중 어디까지 허용할지는 루트 결정 4번과 묶어서 정한다. 권장안은 키 목록 기본+함수 예외다. 과설계 금지 때문이다.

## 9. M27 — 참고 자료 분야 어휘·역할 관련성 분산

(1) 코드 확인 현재 동작. 분야 어휘가 두 곳에 고정돼 있다. 자료 제공 쪽(capability/methodology.py:25 Domain 리터럴 8값)과 소비 쪽(orchestration/methodology.py ReferenceEntry domains 필드, 같은 8값 리터럴)이다. 역할 관련성 선택은 excerpts(:208, entry.domains와 general+역할 능력치 교차)다. 새 분야를 정식 태그로 넣으려면 양쪽을 고쳐야 한다. 기존 분야 안에서 문서 항목만 늘리면 항목 순회라 엔진 수정이 필요 없다.

(2) 감사 문서 주장 일치/정정. 전부 맞다. 분야와 실행 능력은 별개로 유지하고 정의·관련성 연결을 한 소유자로 모으라는 해결 방향도 타당하다. 분야를 능력치에 합치면 안 된다. 자료 분야(무슨 주제)와 실행 능력(무슨 도구를 쓸 수 있나)은 다른 축이다.

(3) 구체 이관안. 분야 정의 1소유자로 모은다. 공통 계약이 Domain 어휘를 소유하고 양쪽이 import하는 게 깔끔하다. 역할 관련성 연결(분야에서 능력으로의 매핑 규칙)도 한 소유자로 둔다. 바뀌는 파일은 capability/methodology.py와 orchestration/methodology.py 중 1곳이 공통 import로 바뀌는 것이다. 어느 쪽이 바뀌는지는 루트 결정 6번으로 넘긴다. 공통 계약 변경이라 루트 담당이라서 제안만 한다.

(4) 기존 규칙 유지. 출처·해시·검토 고정(신뢰 표시 untrusted_reference, 검토 상태 reviewed_reference_only, 실행 허가 False 리터럴)은 그대로 둔다. 모르는 분야 값은 계속 거절한다.

(5) 남는 한계·미검증. 관련성 규칙을 선언(확장 패키지가 자기 분야-능력 매핑 제출)으로 할지, 중앙 매핑표 1개로 할지 못 정했다. 권장안은 중앙 매핑표 1개다. 분야 어휘가 공통 소유면 매핑표도 옆에 두는 게 찾기 쉽다.

## 10. M28 — 참고 자료가 특정 읽기 도구·중앙 프롬프트 수명주기에 결속

(1) 코드 확인 현재 동작. 참고 자료 연결은 특정 파일 읽기 도구를 지목해서 확인한다(app/methodology.py:82, analysis.read_file 기술서·file_read 동작·asset_ref 고정값 대조, 불일치면 조립 실패). 전담 역할·제공자 조립(:102, 역할 정의+실행 명세+제공자 3점 등록)도 여기서 한다. 중앙 소비는 3곳이다. 맥락 묶음 소유(context.py RuntimeDeps.methodology_library 필드), 중앙 맥락 조립(engine.py:565 부근, reference_context + methodology_reference_options에 도구 식별자·인자 고정), 검증 갈무리(verify.py:118 capture 호출)다. 참고 자료의 SKILL.md는 실행 스킬 플러그인과 다르다. capability/methodology.py:1 독스트링(운영자 전용 제공, MCP 도구·스킬 자동 설치 없음)과 :88 부근 실행 허가 구분(execution_permission False 고정)이 근거다. 자동 설치가 없는 건 버그가 아니다.

(2) 감사 문서 주장 일치/정정. 같은 의미 다른 읽기 도구·새 검색 방식으로 교체하려면 여러 영역을 함께 고쳐야 한다는 주장과 SKILL.md는 실행 스킬이 아니라서 별도 등록 규격이 필요하다는 단서가 둘 다 맞다.

(3) 구체 이관안. 자료 읽기 계약과 맥락 기여·결과 처리 수명주기를 정의한다. 제공자는 승인된 원본·해시·문맥·내용 상한을 유지하면서 등록된 계약으로 기여한다. 특정 도구 식별자 고정이 아니라 읽기 역할(필요 스키마: asset_ref 바인딩 읽기)과 수명주기(진행·발췌·갈무리 제공자 참조)를 선언으로 푼다. 문서 1개 추가(기존 분야·기존 읽기 도구)는 선언 항목 추가로 끝나고, 새 검색 뒷단(새 읽기 도구·새 수명주기)은 새 계약 구현으로 들어온다. 바뀌는 파일은 app/methodology.py(조립이 선언 소비), orchestration/methodology.py(수명주기 제공), engine.py·nodes/verify.py·context.py(직접 호출에서 계약 호출로)이다.

(4) 기존 규칙 유지. 해시·문맥 일치·내용 상한·검증(capture·inspect·progress·excerpts 로직)은 그대로 둔다. 호출만 일반화하고 검사는 안 푼다. 참고 자료 등록에 실행 제공자를 강제하지 않는다. 읽기 계약은 읽기만 요구하고 도구 실행 권한을 요구하지 않는다.

(5) 남는 한계·미검증. 읽기 계약 모양(도구 식별자 선언 vs 스키마 선언)은 루트 결정 7번으로 넘긴다. 권장안은 스키마 선언이다. 같은 의미 다른 읽기 도구 교체를 하려면 식별자 고정을 풀어야 하기 때문이다. 단, asset_ref 고정 바인딩 대조 같은 안전 조건은 계약 안에 남긴다.

## 11. 확장 등록 선언 초안 (Pydantic/Protocol/JSONSchema로 표현 가능, 필수/선택 구분)

아래는 도메인·도구 측이 제공해야 할 최소 정보와 누가 읽는가다. 공통 계약(루트 담당) 변경은 제안만 하고, 여기서는 선언 필드와 소비자를 적는다. 참고 자료에 실행 제공자 필드는 없다(강제 금지).

### 11.1 역할 꾸러미 (M02+M07)

- role_id: 필수. 문자열. 소비: 등록부·중복 검사.
- definition: 필수. 역할 정의 필드(표시 이름·설명·활성화 규칙·능력치·제공자 식별자·맥락 상한·동시성·가중치·밴드). 소비: 스케줄러·맥락 투영.
- spec: 필수(스케줄 가능 역할만). 실행 명세(능력치·조사 단계). 능력치는 definition에서 파생, 어긋나면 등록 실패. 소비: 후보 컴파일러.
- provider_ref: 필수. 제공자 팩토리 import 경로 문자열(함수 직렬화 금지). 소비: 조립부.
- required_providers: 선택. 기본값 빈 목록. 이 역할이 반드시 필요로 하는 제공자 식별자 목록. 소비: 시작 시 결속 검사(누락 시 시작 실패).
- optional_providers: 선택. 기본값 빈 목록. 없어도 격리 후 진행, 누락 표시. 소비: 시작 시 결속 검사.
- default_include: 선택. 기본값 거짓. 참이면 기본 프로파일에 포함. 소비: 기본 조립.
- JSONSchema 변환: definition·spec은 현행 Pydantic 모델 그대로 쓰고, 꾸러미 겉장만 JSONSchema로 검증 가능하게 한다.

### 11.2 자격 제공자 (M03, 공통 계약은 Protocol, 선언은 데이터)

- Protocol(공통, 루트 소유 제안): role_eligible(역할 식별자·그래프 요약·카탈로그 요약에서 참거짓+사유), tool_eligible(도구 기술서에서 참거짓+사유), asset_scope(대상 자산 노드 집합). 비동기 3개다.
- 선언(도메인 측): provider_ref 필수(구현 참조), applies_to 필수(능력·동작·서버 목록, 한 제공자가 여러 역할·도구에 적용되는 통로), version 필수. 소비: 엔진 4개 지점(프롬프트·참고후보·승인·실행직전).
- 기존 검사(스키마·대상·승인·원본 증거)는 엔진·컴파일러·검증 노드에 남긴다. 제공자는 가시성만 정한다.

### 11.3 해석 묶음 (M05+M18 같은 단위)

- tool_ids: 필수. 문자열 목록(1개 해석기가 여러 도구 공유 가능).
- mapper_ref: 필수. 해석 함수 import 경로 문자열. 소비: 조립 시 등록.
- mapper_version: 필수. 문자열. 소비: 실행 구성 결속·재개 대조.
- meaningful_change_keys: 선택. 기본값 빈 목록. 그래프 속성 키 목록(간단한 경우). 비어 있으면 지문 기여 없음(현행과 동일). 소비: 지문 계산기.
- projection_ref: 선택. 복잡한 경우 투영 함수 참조. meaningful_change_keys와 둘 중 최대 1개. 소비: 지문 계산기.
- 선언 없이 도구만 등록하면 구조화 반영 없음으로 명시하고 실행은 막지 않는다(폐쇄 루프 계약 준수).

### 11.4 벤더 정책 (M04)

- vendor_id: 필수. 소비: 정책 선택.
- managed_server_ids: 필수. 관리 대상 집합. 소비: 감싸기 적용 여부·건강 게이트.
- fallback_map: 필수(빈 맵 허용). 주에서 대체 서버로의 관계. 소비: 대체 조건.
- approval_ref: 필수. 승인 검사(해시·범위) 구현 참조. 로직은 공통, 값(승인 해시·자산)은 운영자 선언. 소비: 호출 게이트.
- 비관리 서버는 현행대로 차단하지 않는다(기본 동작 보존).

### 11.5 참고 자료 꾸러미 (M27+M28, 실행 제공자 없음)

- reference_id·path·sha256·title·domains·source_id·source_commit·review_caveat: 필수. 현행 ReferenceEntry 그대로. domains 어휘는 공통 소유(루트 조율).
- read_contract: 필수. 읽기 역할 선언(필요 스키마: asset_ref 바인딩 읽기). 특정 도구 식별자 고정이 아니라 스키마 선언. 소비: 조립 시 읽기 도구 대조.
- lifecycle_refs: 필수. 진행·발췌·갈무리 제공자 참조. 소비: 엔진·검증 노드.
- max_context_chars·read_chars: 선택(기본값 현행). 소비: 프롬프트 예산.
- 실행 제공자 필드는 두지 않는다. 읽기 계약이 읽기만 요구하게 한다.

### 11.6 실행 스킬 꾸러미 (별도 규격, 참고 자료와 섞지 않음)

- 사용자 목표에 스킬 확장이 있으면 이 규격을 쓴다. 참고 자료 꾸러미(11.5)와 같은 경로로 등록하지 않는다.
- skill_id·required_capabilities·required_operations·permissions(필요 권한 선언)·context_contrib(맥락 기여 방식)·evidence_contract(증거·원본 첨부 약속): 필수. 소비: 승인·정책·검증.
- 전제 조건: 역할·도구·맥락·증거 계약을 전부 만족해야 등록된다. 하나라도 빠지면 등록 실패다.
- 이 규격은 제안만 한다. 사용자 목표에서 실행 스킬 요구가 확정되기 전에는 만들지 않는다(과설계 금지).

## 12. 루트가 확정할 최소 계약 목록 (선택지+추천)

1. 역할 1등록 단위 모양. A: 꾸러미 단일 모델(11.1). B: 현행 3등록 유지+조립 검증 강화. 추천 A. 작성자 2곳 수정이 실결함의 본체라서다.
2. 자격 제공자 규격. A: Protocol 3함수(11.2). B: pluggy 훅. 추천 A. 호출 4곳이 엔진 안에 박혀 있어서 훅이 추적만 어렵게 한다. pluggy 불필요.
3. 시작 결속 실패 정책. A: 필수 누락이면 시작 실패. B: 경고 후 진행. 추천 혼합(필수면 A, 선택이면 B). 선택까지 막으면 LLM 주도 원칙을 깬다.
4. 해석+변화규칙 동봉. A: 같은 단위 동봉(11.3). B: 각자 등록. 추천 A. 따로 놀면 M05·M18 누락이 재발한다. 의무가 아니라 없으면 구조화 반영 없음으로 명시한다.
5. 벤더 정책 데이터 소유자. A: 확장 패키지 선언(11.4). B: 앱 설정. 추천 A. 승인 자산이 engagement 메타데이터로 다니는 현행과 맞물린다. pydantic-settings 불필요.
6. 분야 어휘 소유자. A: 공통 계약. B: capability 소유. 추천 A. 양쪽이 import하면 중복이 사라진다. 공통 변경이라 루트와 조율 필요.
7. 읽기 계약 모양. A: 스키마 선언(11.5). B: 도구 식별자 선언. 추천 A. 같은 의미 다른 읽기 도구 교체를 하려면 식별자 고정을 풀어야 한다. 안전 대조(asset_ref 고정 등)는 계약 안에 남긴다.
8. pluggy·pydantic-settings 도입 범위. A: 내 영역 불필요. B: 일부 도입. 추천 A. 현행 src 사용 0건, 자격 판단은 런타임 기반, 호출 경계는 포트 2개라 둘 다 과설계다. 공통·앱 경계 최종 판단은 루트에 맡긴다.

## 14. 루트와 조율할 제안 (공통 계약 최소 변경, 분리 보고)

내부 사설 접근 우회는 안 쓴다. 아래 3건은 공통 계약을 건드려서 루트 담당 영역이라 제안만 한다.

1. Domain 어휘 공통 소유. capability/methodology.py:25 와 orchestration/methodology.py의 분야 리터럴 중 하나를 공통 계약 import로 바꾼다. 어느 쪽을 바꾸는지는 루트 결정.
2. 자격 제공자 Protocol 위치. core(입력·검증 계약 옆) 권장, orchestration도 가능. core 권장 이유는 대상·정책 계약이 이미 core에 있어서다.
3. VendorPolicy·해석묶음·참고꾸러미 스키마 위치. 확장 선언 스키마가 공통에 살지 capability/orchestration에 살지는 루트 결정. 권장안은 선언 스키마만 공통에 두고 구현은 각 팀에 둔다.

## 15. 미해소·미검증 목록 (자동 해소 과장 금지)

1. 엔진 행번호 드리프트. 승인 지점(감사 1616에서 실측 1587 부근), 실행 직전(감사 2752에서 실측 2753 부근)은 심볼로 재확인했으니 내용은 맞다. 번호만 어긋났다.
2. 참고 후보 연산(engine.py:902 부근)이 건강 상태+실행 준비 가시성만 보고 도메인 자격을 안 보는 것처럼 보인다. 상위 루프(682 부근 역할 스킵)에서 걸러지니 동작상 문제는 없어 보이는데, 코드 경로 전체를 안 읽어서 미검증으로 남긴다.
3. M04 승인 해시의 운영자 발급·회전 절차는 코드에 없어서 미검증이다. 검사 로직만 확인했다.
4. 실행 스킬(11.6)은 사용자 목표의 스킬 확장 요구가 확정돼야 만든다. 요구 문구가 참고 자료인지 실행 스킬인지 애매하면 루트 확인이 필요하다.
5. 테스트 실행 금지라 test_agents.py:449·463은 읽기만 했다. 통과 여부는 주장하지 않는다.
6. dev-mcp-audit 쪽은 담당 겹침(조건부 제약 중 내 영역)만 훑었다. 전문을 대조하지 않았다.
7. pluggy·pydantic-settings 최종 판단(공통·앱 경계)은 루트 몫이다. 내 영역 결론은 불필요다.
