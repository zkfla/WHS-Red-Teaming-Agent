## 2. 필수 수정

### I01. 선택 참고 후보가 없는 사용자 정의 구성도 조립 단계에서 거절됨

**실제 근거:** [확장 적용의 전체 역할 검사](../../../../src/redteam/app/runtime_components.py)는 모든 실행 가능 역할에 대해 참고 후보 제공자를 찾지 못하면 조립 오류를 낸다. 이 검사는 확장 선언이 비어 있어도 수행된다. 반면 현재 중앙의 [참고 후보 처리](../../../../src/redteam/orchestration/engine.py)는 제공자가 없으면 진단을 남기고 해당 참고 자료만 건너뛴다. 실제 행동은 중앙 추론이 별도로 제안·컴파일한다.

[개정 계획 4.2](../2026-10-04-WHS-modularization-implementation-plan.md)도 선택 참고 후보가 없다는 이유로 실제 실행 능력을 차단하지 않도록 한다. 새 확장 자료에는 [필수/선택 참조 선언](../../../../src/redteam/core/extensions.py)과 [명시 참조 검사](../../../../src/redteam/app/extensions.py)가 이미 있다.

**상황:** 기존 사용자 정의 실행 구성이 정상 실행 명세·역할 정의를 제공하고 참고 후보 등록부는 비워 둔다. 중앙 LLM이 실제 카탈로그에서 행동을 제안하는 구성이므로 이전에는 참고 후보 미등록 진단 후 진행할 수 있다. 새 코드에서는 확장을 하나도 선택하지 않아도 앱이 모든 역할의 참고 후보를 요구하여 시작 단계에서 거절한다. 명시적으로 빈 참고 후보 등록부를 주입하는 같은 구성도 영향을 받는다.

**필수 보장:** 실행 역할의 실행 명세 결속과 참고 후보의 필수 여부를 구분한다. 기존 사용자 정의 구성을 기본으로 대체하지 않는 것뿐 아니라, 새 선택 확장 적용이 그 구성의 허용된 동작을 불필요하게 좁히지 않아야 한다.

**최소 수정:** 모든 역할에 대한 참고 후보 강제 검사를 제거하고, 실제로 필수인 제공자 연결은 확장의 필수 참조 선언으로 검사한다. 선택 참고 후보는 현재 중앙의 진단·건너뛰기 의미를 유지한다. 필요한 실행 명세·정의 결속 검사는 유지한다. 확장이 비어 있는 경우만 특례 처리하는 방법은 새 역할의 선택 참고 후보 조합을 여전히 막으므로 충분하지 않다.

별도의 후보 대체 엔진이나 중앙 고정 후보를 추가할 필요는 없다.

### I02. 같은 신원·버전 집합이면 제공 항목의 소유 변경을 감지하지 못함

**실제 근거:** 확장 조립은 [각 제공 항목의 소유 패키지](../../../../src/redteam/app/extensions.py)를 알고 있다. 그러나 [재개용 등록 자료](../../../../src/redteam/app/extensions.py)는 패키지 신원→버전과 제공 종류/신원→버전만 평평한 사전으로 기록한다. 제공 항목이 어느 패키지에 속하는지와 필수/선택 참조는 빠진다. [재개 검사](../../../../src/redteam/app/runtime_components.py)는 이 버전 사전이 같으면 통과하며, 선택된 판단도 그 신원으로 조회한다.

**상황:** 같은 선택 패키지 A/B와 같은 버전을 유지한 상태에서 다음과 같이 선언의 소유 연결이 바뀐다.

| 선언 | 이전 실행 | 재개 시 |
|---|---|---|
| 패키지 A | 경로 판단 제공 항목 | 참고 후보 제공 항목 |
| 패키지 B | 참고 후보 제공 항목 | 경로 판단 제공 항목 |

두 제공 항목의 신원·선언 버전도 각각 유지되면 저장되는 패키지/제공 항목 버전 사전은 동일하다. 이전 실행이 선택한 경로 판단 신원을 재개 시 조회하면 다른 소유 패키지의 팩토리를 얻지만 현재 비교는 이를 구분하지 못한다. 제공 항목의 필수 연결을 바꾸는 선언 변경도 같은 이유로 기록에서 드러나지 않는다.

이는 “패키지 작성자는 버전을 올려야 한다”는 규율만으로 코드가 선언 내용의 변경을 거절한다고 주장할 수 없는 경우다. [계획 5.A](../2026-10-04-WHS-modularization-implementation-plan.md)는 내용이 바뀐 동일 버전을 거절하도록 한다.

**필수 보장:** 재개 대조는 선언의 신원/버전 집합뿐 아니라 제공 항목의 소유 연결과 실행에 필요한 선언 내용을 구분해야 한다. 판단 신원의 문자열이 같다는 이유로 다른 구현을 같은 선택으로 처리하지 않는다. 기존 기본/사용자 정의 구성의 복원 규칙은 그대로 유지한다.

**최소 수정:** 비밀·라이브 객체·함수를 제외한 등록 선언의 정규화된 내용에 소유 패키지와 제공 항목·참조를 포함하고, 그 스냅샷 또는 안정된 지문을 바인딩에 남겨 비교한다. 실제 구현을 식별하는 선언된 구현 신원·내용 버전도 그 연결 안에 둔다. 선언 내용을 바꾼 동일 버전은 불일치로 거절한다. 이미 존재하는 소유 연결 자료를 재사용할 수 있으며 새 범용 버전 협상기나 임의 Python 객체 직렬화는 필요 없다.

이 지적은 모든 Python 함수의 변경을 자동 탐지하라는 요구가 아니다. 현재 이미 수집하는 선언의 소유·참조 변경도 복원 대조에서 사라지는 문제를 먼저 고치자는 것이다.

### I03. 여러 단계 위임 판단에서 실제 모델 요청 예산이 한 단위로 축소될 수 있음

**실제 근거:** 기존 [판단 예산의 계약](../../../../src/redteam/orchestration/cognition.py)은 실제 LLM 요청마다 한 단위를 소비하고, 기본 구조화 판단은 [각 요청 전에 소비](../../../../src/redteam/orchestration/cognition.py)한다. 새 중앙 [위임 호출](../../../../src/redteam/orchestration/engine.py)은 공유 예산을 제공자에 전달하지만, 제공자가 소비하지 않으면 반환/예외 뒤에 [한 단위만 보충](../../../../src/redteam/orchestration/engine.py)한다. 팩토리 문맥에는 [원래 모델 호출 연결](../../../../src/redteam/app/runtime_components.py)이 그대로 전달된다.

**상황:** 정상적인 대체 판단 제공자가 여러 단계 절차를 구현하면서 팩토리에서 받은 모델 연결로 네 번 요청한 뒤 유효한 제안을 반환한다. 요청에 들어온 예산을 각 모델 호출에 직접 연결하지 않으면, 남은 예산이 두 단위여도 네 요청이 모두 수행되고 중앙은 한 단위만 소비한다. 반환 스키마가 유효하면 제안도 통과한다. 호출자가 소비하지 않는 제공자의 바깥 교정 루프는 유한하지만, 내부 모델 호출 수에는 기존 계약이 적용되지 않은 것이다.

**필수 보장:** 기본·대체 판단의 실제 모델 요청과 실패·교정 요청이 같은 예산을 소비해야 한다. 제안 한 번과 내부 모델 요청 여러 번을 같은 비용 단위로 몰래 바꾸지 않는다. 여러 단계 판단을 지원하되 기존 판단 예산을 단순히 제공자의 자율적인 수동 회계에만 맡기지 않는다.

**최소 수정:** 대체 판단이 사용할 수 있는 공식 모델 호출 경로를 현재 요청의 공유 예산에 결속한다. 기존 구조화 판단 호출을 재사용하는 요청별 호출 도우미 또는 예산이 연결된 모델 포트를 제공하고, 각 내부 모델 요청 전에 검사·소비하게 한다. 모델을 부르지 않는 제안 생성의 바깥 루프를 유한하게 만드는 현재 최소 한 단위 처리는 별도 의미로 유지할 수 있다. 기본 제공자의 기존 소비와 이중 과금하지 않아야 한다.

임의 플러그인 Python 코드 자체를 격리하거나 모든 외부 호출을 감시하는 장치를 요구하지 않는다. 정상 확장 작성자가 사용하는 공식 호출 경로에서 기존 요청 예산을 유지하는 최소 연결이 필요하다.

## 3. 이번 범위에서 보존된 경계

- **추론 교체는 실제 호출 지점에 연결돼 있다.** 기본·대체 제공자 모두 중앙의 제안 호출을 통과하고, 요청 문맥·작성 스키마는 분리 복사된다. [중앙 반환 검사](../../../../src/redteam/orchestration/engine.py)는 사전 형태·JSON 값·작성 스키마·완료조건 작성을 확인한다. 완료 확정과 경로 변경은 여전히 중앙의 검증·최신 상태 적용 경로에 남아 있다. I03은 이 긍정 판정과 별개인 내부 모델 요청 회계 문제다.
- **닫힌 이름 membership을 없앤 것만으로 실행 허가가 생기는 경로는 확인하지 못했다.** 현재 [중앙 행동 컴파일](../../../../src/redteam/orchestration/engine.py)은 실제 카탈로그와 도구 연결을 요구하고, [도구 관문의 동작 바인딩 검사](../../../../src/redteam/capability/gateway.py)도 남아 있다. 범위·ROE·위험·승인 경로는 별도다. 작성 스키마의 이름 안내가 실행 권위를 대신한다고 판정하지 않는다.
- **기존 사용자 정의 구성의 신원 조회는 유지됐다.** [재개 구성 조회](../../../../src/redteam/app/runtime_components.py)는 원래 프로필·버전·구성 식별자를 대조하며 기본 구성으로 조용히 바꾸지 않는다. CLI 재개도 저장된 확장 선택과 판단 신원을 다시 설정한다. I01은 그 뒤의 추가 조립 검사가 허용된 구성을 거절하는 문제이고, I02는 새 선언 기록의 비교 내용이 부족한 문제다.
- **현재 훅 수집이 범용 DI 컨테이너가 됐다는 근거는 없다.** 선택된 패키지만 로딩하고 선언을 수집하며, 실제 제공 항목은 목적별 등록부에 연결된다. 팩토리 문맥은 모델·증거·그래프의 명시적 입력이고 전역 서비스 탐색이나 임의 의존성 자동 생성은 없다. 등록 경로가 얇다는 사실 자체를 과결합으로 지적하지 않는다.

이 내용은 판독한 경로에 대한 판단이다. 모든 새 동작 의미·외부 도구·승인 재개·저장 이관의 구현 또는 안전성이 검증됐다는 뜻은 아니다.

## 4. 수정되어 제외한 후보와 미완료 범위

초기 판독에서는 명시 주입 구성에 확장을 적용하기 전에 기본 프로필을 먼저 검사/변경하는 순서가 보였다. 최종 확인에서는 [실행 조립](../../../../src/redteam/app/bootstrap.py)과 [제품 조립](../../../../src/redteam/app/bootstrap.py)이 명시 주입 구성을 먼저 합친 뒤 확장을 적용하도록 바뀌었다. 이 부분은 해결된 후보로 제외하며 이미 수정한 내용을 필수 문제로 남기지 않는다.

도구 프로필·신원·자격·도메인 해석 통합, 통제/저장과 설정의 미완료 배선은 이번 보고의 필수 결함에 포함하지 않았다. 기존 감사의 개별 결함도 해당 소유자가 구현 중이라는 이유만으로 재지적하지 않았다. 완료 보고 전 구현 검토와 마지막 검증에서 실제 결과를 확인할 대상이다.

후속 검토는 I01~I03의 수정과 새로 완성된 연결의 실제 계약을 소스로 확인하면 된다. 이 중간 보고를 이유로 테스트를 앞당기거나 새로운 범용 프레임워크를 추가할 필요는 없다.
