# WHS 모듈화 독립 평가자 준비 메모

작성일: 2026-10-04 (Asia/Seoul)

상태: **계획 검토 전 준비 조사**. 후속 계획 개정본을 아직 받지 않았다. 이 문서는 계획 승인·구현 검증·테스트 통과 결과가 아니다.

## 1. 조사 범위와 기준

다음 문서 두 개를 읽고, 등록·조립·중앙 계획·실행·증거·완료·승인 재개와 관련된 현재 소스 본문을 대조했다.

- [기존 결합성 감사](../2026-10-04-WHS-modularity-coupling-audit.md)
- 사용자 제공 시스템 감사（로컬 제공 자료: `dev-agent-system-audit-20261004.md`）

로컬 Git 참조 파일에서 `dev`와 `9eb70ed1f9fff1fbf15540731de87de89feaf7fe`를 확인했다. 판독 대상은 해당 커밋의 고정 사본이 아니라 **공유 작업 폴더의 당시 파일**이다. 준비 조사 첫 판독과 후속 판독 사이에 의존성 선언에 Pluggy 및 pydantic-settings가 추가되었다. 이 평가자가 변경한 것이 아니며, 환경 설치 완료나 전체 작업 트리의 무변경을 확인한 것은 아니다. 후속 구현 평가는 그때의 소스·개정본을 다시 기준으로 삼아야 한다.

이번 턴에는 이 메모만 작성했다. 에이전트를 추가 생성하지 않았고, 제품 소스·설정·Git을 변경하지 않았다. 제품 코드, 테스트, MCP, LLM 임무를 실행하지 않았다. 소스 탐색·파일 판독과 라이브러리 공식 문서 조회는 수행했다. 기존 감사의 실행·CI 결과는 그 작성자의 보고이며 이번 평가자가 재현한 결과가 아니다.

평가 축은 두 가지다.

1. **정확성**: 사용자 요구 누락, 설계 내부 모순, 실제 기능 누락, 잘못된 계약 보존 여부.
2. **단순성과 확장성**: 불필요한 중앙 수정, 하드코딩·중복·과도한 책임·구체 구현 의존 여부.

점수는 매기지 않는다. 문제와 권고 구현방법을 분리하고, 후속 답변에서 각 항목을 반영·대안·기각·후속과제로 판정할 수 있게 한다.

## 2. 이번 요구를 해석하는 경계

목표는 **기존 규격 안에서** 도구·MCP·스킬·플러그인·전문 역할을 확장 패키지의 구현·등록·설정으로 추가하고, 중앙 추론도 위임·교체할 수 있게 만드는 것이다. 개발자 편의가 현재 범위이며, 미래 사용자 추가 메뉴는 범위 밖이다.

기존 의미를 사용하는 새 도구·역할과, 새로운 최상위 동작·대상 종류·그래프 종류·완료조건을 도입하는 일은 다르다. 후자는 공유 규격의 확장 또는 버전 변경이다. 이번 요구를 근거로 모든 의미를 임의 문자열로 열거나, 미확인 미래 기능을 위한 등록부를 전부 만드는 것은 권고하지 않는다. 기존 감사의 M01·M15·M24가 모두 즉시 동적 규격 확장을 요구하는 것은 아니다.

설치·발견·등록·후보 노출·실행 승인·구조화 관측·목표 완료·재개 가능성은 각각 별개다. 이 중 하나를 만족했다는 이유로 전체 플러그앤플레이가 구현됐다고 판단하지 않는다. 특히 도구 발견은 실행 허가가 아니며, 참고 문서 제공은 실행 스킬 등록과 같지 않다.

## 4. 특히 피해야 할 설계 함정

아래는 현재 구조에서 도출한 **계획 확인 항목**이다. 아직 보지 않은 계획의 결함을 확정한 목록은 아니다.

### E01. 등록 창구를 추가하고 기존 중앙 목록은 그대로 유지

**문제·근거:** 기본 역할, 후보 제공자, 결과 해석기, 모바일 조건부 해석 연결, MCP 프로필 선택이 서로 다른 위치에 있다. 새 등록 창구가 기존 목록에 값을 복사하는 데 그치면 작성자는 여전히 여러 목록을 맞춰야 한다. 역할의 실행 능력 일치 검사 자체는 정상 계약이다.

**실제 상황:** 같은 규격의 새 역할을 패키지에 작성했는데 기본 역할 목록·제공자 목록·결과 해석 목록도 중앙에서 고쳐야 한다면 목표 미달이다.

**최소 권고:** 확장 패키지가 제공 항목과 참조를 한 등록 경로로 제출하고 기존 등록부를 채우게 한다. 기본 제공자도 같은 경로를 소비한다. 기존 중앙 목록의 삭제·이관 위치와 필수/선택 참조의 판정을 계획에 적는다. 도구만 제공하는 확장에 역할·완료·복구 제공자를 모두 강제하지 않는다.

근거: [역할 결속 검사](../../../../src/redteam/orchestration/agents/registry.py), [기본 제공자 목록](../../../../src/redteam/orchestration/agents/providers.py), [결과 해석 등록](../../../../src/redteam/orchestration/observations/mapper.py), [모바일 조건부 연결](../../../../src/redteam/orchestration/mobile_mcp_binding.py).

### E02. 모델 연결 또는 참고 후보만 교체하고 중앙 추론 교체라고 표현

**문제·근거:** 모델 호출 포트는 이미 교체 가능하다. 반면 계획 노드는 중앙 조사 구성요소를 직접 생성한다. 현재 실행 구성은 역할·참고 후보·의미 검증·결과 해석의 네 슬롯이며 중앙 조사 구성요소는 여기에 포함되지 않는다. 참고 후보 제공자는 중앙 계획에 자료를 제공하는 통로이므로 그 등록만으로 중앙 계획 전체를 교체한 것은 아니다.

**실제 상황:** 새 전문 추론 구현을 등록해도 기존 중앙 구성요소가 초안·검토·다음 행동·완료를 계속 독점하면 사용자 요구가 빠진다. 반대로 구성요소 통째 교체만 열고 정책·출처·최신 상태 검증까지 확장 책임으로 넘기면 기존 계약이 사라질 수 있다.

**최소 권고:** 교체할 추론의 입력과 출력, 위임 범위, 결정 적용 주체를 먼저 정의한다. 기존 경로·행동·완료 제안 형태를 재사용하고, 일반 수명주기가 승인·증거·버전 대조·상태 적용을 보유하게 한다. 현재 중앙 구성요소가 저장소 변경까지 수행하므로 생성자 주입 하나만 추가하면 모든 경계가 분리된다고 가정하지 않는다. 기본 추론 구현을 어댑터로 이관하는 범위부터 정하고, 기존 기능별 소유자와 재개 시 복원 식별자를 명시한다.

### E03. Pluggy와 별개의 플러그인 프레임워크를 다시 구현

**문제·근거:** 이미 기능별 등록부·팩토리·공개 포트와 LangGraph 수명이 있다. 여기에 별도 발견기·분배기·사건 통로·범용 상태 조작기를 모두 만들면 bespoke 코드와 책임이 늘어난다.

**실제 상황:** 모든 실행 단계에 수십 개 훅을 열고 전체 실행 의존성을 넘기면 확장이 중앙 사설 상태와 저장소에 다시 결합한다. 반대로 선언 데이터에 실제 함수·라이브 객체를 직렬화하면 저장·복원이 불명확해진다.

**최소 권고:** Pluggy는 승인된 패키지의 등록 선언·제공자 결속에 사용하고, 실행은 기존 공개 포트와 LangGraph를 재사용하는 얇은 경계부터 잡는다. 선언 자료와 제공자 팩토리를 구분한다. 등록 훅은 선언·팩토리를 돌려주고, 비동기 조사·연결의 실행과 종료는 기존 실행 수명이 맡도록 제안한다. 새로운 훅은 실제 소비 지점과 교체 필요가 확인된 경우만 추가한다.

이 제안은 WHS에 대한 설계 판단이다. Pluggy 공식 문서에서 확인한 기능은 훅 규격·구현의 등록과 호출, 패키지 entry point 연결이다. [Pluggy 공식 문서](https://pluggy.readthedocs.io/en/stable/).

### E04. 훅 호출 순서가 선택·정책·오류 처리의 숨은 규격이 됨

**문제·근거:** 다수 확장이 같은 제공자 슬롯·도구 신원·제약을 제출할 수 있다. Pluggy 기본 호출은 등록 역순이며 첫 결과 방식도 제공한다. 이 순서를 WHS의 정책 우선순위나 단일 추론 선택으로 암묵 사용하면 설치 순서에 결과가 좌우된다. [훅 순서와 첫 결과의 공식 설명](https://pluggy.readthedocs.io/en/stable/).

**실제 상황:** 두 추론 제공자 중 마지막 설치자가 자동 선택되거나, 한 자격 제공자의 허용이 다른 제공자의 거부를 덮는 상황.

**최소 권고:** 단일 구현 선택은 구성에 명시하고 중복을 검사한다. 기여 목록은 안정된 식별자·명시적 정렬로 조립한다. 제약 결합은 거부·오류·미지원의 의미를 정하고 승인 경계를 좁히는 방식으로 합성한다. 참고 후보 제공자의 실패 격리를 정책 검사의 실패에도 그대로 적용하지 않는다. 현재 정확한 해석 등록의 중복 거절도 유지한다.

근거: [참고 후보 실패 처리](../../../../src/redteam/orchestration/engine.py), [해석 중복 거절](../../../../src/redteam/orchestration/observations/mapper.py).

### E05. 새 실행에서만 작동하고 승인 대기 뒤 재개는 복원하지 못함

**문제·근거:** 현재 지속 실행은 구성 식별자·버전·슬롯 식별자를 저장하고 재개 시 대조한다. 지속 실행에 복원 불가능한 임시 객체를 넘기는 것은 정상적으로 거절한다. 상태 타입 허용은 내부 패키지 스캔에 제한돼 있고 기본 구성 식별자는 수동 버전이다.

**실제 상황:** 역할·추론·해석을 추가한 뒤 승인 대기 중 프로세스를 종료하면 다음 프로세스가 기본 구성으로 재개하거나 확장의 상태를 일반 사전으로 복원하는 상황.

**최소 권고:** 실행에 필요한 확장·추론 제공자의 안정된 식별자와 계약/내용 버전을 기존 구성 바인딩에 결속한다. 복원에 필요한 내용만 저장하고 라이브 객체·비밀·팩토리는 저장하지 않는다. 실행별 가변 객체는 새로 만든다. 외부 타입을 실제로 지속 상태에 저장할 필요가 있을 때만 명시적 타입·복원 등록을 추가한다. 지원 불일치 시 기본 제공자로 조용히 대체하지 않는다. 기존 네 슬롯 전체 구성과 부분 확장 기여를 구분한다.

근거: [실행별 구성 생성](../../../../src/redteam/app/runtime_components.py), [지속 실행의 임시 객체 거절](../../../../src/redteam/app/runtime_components.py), [구성 대조](../../../../src/redteam/orchestration/component_binding.py), [상태 타입 스캔](../../../../src/redteam/orchestration/checkpointing.py), [원래 제안으로 승인 재개](../../../../src/redteam/orchestration/graph.py).

### E06. 설정 라이브러리를 도입하면서 설정 의미를 조용히 바꿈

**문제·근거:** 현재 CLI는 이미 설정된 환경변수를 `.env`로 덮지 않는다. LLM·MCP·실행 설정은 각자 환경을 해석하고 동적 서버 접두사와 프로필별 정책 경로가 있다. 비밀값 대신 환경변수 이름을 설정에 보관하는 계약도 있다.

**실제 상황:** 각 기능이 독립적으로 `.env`를 다시 읽거나, 기존의 동적 서버 목록을 고정 필드로 바꾸거나, 같은 `.env`의 다른 기능 키 때문에 새 모델이 거절하는 상황. 공통 계약 모델 전체를 환경을 읽는 모델로 바꾸면 순수 계약 검증에도 외부 설정이 끼어든다.

**최소 권고:** pydantic-settings는 앱의 설정 수집 경계에 사용하고 기존 순수 계약 모델은 재사용한다. 현재 환경·파일·명시적 덮어쓰기·기본값의 우선순위, 별칭, 동적 서버 자료, 비밀 참조, 프로필별 추가 스키마의 소유자를 문서화한다. 실행·재개·도구 조회·사전 점검은 한 번 해석한 같은 구성을 소비한다. 다수 기능이 공유하는 `.env`의 미소유 키 처리도 명시한다. 기존 CLI 전면 교체는 이번 요구에서 필요성이 확인되지 않았다.

근거: [현재 환경 우선 처리](../../../../src/redteam/app/cli/_shared.py), [모델 설정과 비밀 참조](../../../../src/redteam/core/config.py), [MCP 환경 설정](../../../../src/redteam/capability/settings.py). 설정 자료의 우선순위·사용자 정의 자료원과 dotenv 미정의 키 처리는 라이브러리 공식 문서에서 확인했다. 버전별 세부 옵션을 현재 선언된 최소 버전에서 지원한다고 가정하지 않는다. [pydantic-settings 공식 문서](https://docs.pydantic.dev/latest/concepts/pydantic_settings/).

### E07. 서버별 분기를 등록부로 옮기며 정상 검사까지 삭제

**문제·근거:** MCP 연결기의 프로필 선택, 모바일 서버의 적격성·대체 관계·승인된 해시, 분석 역할의 자산 적격성은 중앙 배선과 도메인 의미가 섞여 있다. 다만 일반 미관리 서버는 모바일 자격 검사를 그대로 통과한다. 모든 새 MCP가 모바일 분기를 고쳐야 하는 것은 아니다.

**실제 상황:** 분석 역할을 일반화하면서 승인 APK·정상 주 서버·대체 서버 조건을 없애거나, 등록됐다는 이유로 계획·실행 직전 검사를 하나만 남기는 상황.

**최소 권고:** 도메인 의미와 프로필 팩토리를 확장 제공자에 이관하고 중앙은 일반 등록 계약을 소비한다. 후보 가시성·제안 검증·실행 직전의 검사 시점은 유지하며 규칙 계산의 소유자를 통합한다. 주 서버 미등록 또는 상태 미확인을 실제 장애로 간주해 대체 도구를 노출하지 않는다. MCP SDK 전송을 재구현하지 않는다.

근거: [프로필 선택](../../../../src/redteam/capability/bootstrap.py), [모바일 실제 호출 검사](../../../../src/redteam/orchestration/mobile_mcp_binding.py), [분석 적격성](../../../../src/redteam/orchestration/analysis_activation.py), [실행 전 분석 재검사](../../../../src/redteam/orchestration/engine.py).

### E08. 도구 이름을 바꾸면 신원 결합 문제가 모두 해결된다고 판단

**문제·근거:** 현재 도구 식별자는 능력 접두사와 정규화된 원격 이름으로 만들며 서버 신원이 없다. 같은 분야의 서로 다른 서버가 같은 원격 이름을 제공하면 충돌로 거절한다. 카탈로그는 도구 신원의 첫 구간을 실행 능력으로 해석한다.

**실제 상황:** 서버 이름을 새 접두사로 바꾸면 충돌은 줄어도 카탈로그에서 후보가 빠질 수 있다. 기존 바인딩·해석기·승인 기록·저장 증거도 옛 식별자를 사용한다.

**최소 권고:** 도구의 안정된 신원과 행동 의미를 구분한다. 식별자 형식을 변경한다면 모든 소비자와 기존 실행의 재개 호환을 함께 결정한다. 당장 형식을 유지한다면 다중 서버 충돌 제한을 명시하고 충돌 거절을 유지한다. 덮어쓰기나 원격 이름 접두사 추측으로 잘못된 해석기를 선택하지 않는다. 새 도구의 실제 출력 규격을 지원하는 해석 등록은 확장 측 책임으로 둔다.

근거: [도구 신원 생성](../../../../src/redteam/capability/adapters/mcp/naming.py), [서버 간 충돌 거절](../../../../src/redteam/capability/registry.py), [능력과 이름의 결합](../../../../src/redteam/capability/catalog.py), [정확한 결과 해석](../../../../src/redteam/orchestration/observations/mapper.py).

### E09. 증거 저장 편의 기능과 완료용 실행 증거를 같은 것으로 취급

**문제·근거:** 편의 저장 기능은 공통 변환 결과를 저장한다. 주 검증 단계는 원본 결과·제안·경로·단계·대상·계정·행동 연결을 추가한다. 원본 읽기와 완료 판정은 이 보강 자료에 의존한다. 해석기 미등록은 빈 구조화 변형을 반환하며 도구 실행·원본 보존을 모두 차단하는 것은 아니다.

**실제 상황:** 새 전문 추론이 직접 편의 저장을 호출해 만든 증거를 기존 완료·복구가 사용할 수 있다고 생각하는 상황. 또는 새 해석기가 사실을 보냈다는 이유로 같은 실행·계정·대상 출처 확인을 생략하는 상황.

**최소 권고:** 확장의 행동 결과도 기존 검증·증거·갱신 경로로 통과시킨다. 증거 형식과 보장 수준을 기존 원본 읽기 계약으로 모으고, 각 완료·의미 검증의 추가 조건은 유지한다. 구조화 해석이 없는 도구는 원본 읽기 가능성과 구조화 사실 미지원 상태를 구분해 표시한다. 관측 변화 투영이 필요한 역할은 그 의미를 등록하되 시각·증거 번호만 바뀌었다고 반복 활성화하지 않는다.

근거: [편의 기록](../../../../src/redteam/evidence/service.py), [주 검증 보강](../../../../src/redteam/orchestration/nodes/verify.py), [원본 읽기와 실행 일치](../../../../src/redteam/orchestration/evidence_access.py), [완료의 단계·원본 조건](../../../../src/redteam/orchestration/completion.py), [미등록 해석의 처리](../../../../src/redteam/orchestration/observations/mapper.py).

### E10. 스킬 파일의 존재를 실행 확장 또는 실행 허가로 취급

**문제·근거:** 현재 참고 자료는 운영자 제공·검토·해시 고정 자료다. 연결 시 특정 파일 읽기 도구와 자료 자산 연결을 검사하고 전담 역할·제공자를 조립한다. 현재의 자료 역할은 실행 코드 자동 설치와 다르다.

**실제 상황:** 문서 하나를 추가하는 데 도구·저장·완료 제공자를 모두 요구하거나, 반대로 SKILL.md 안의 명령·정책 변경을 실행 권한으로 소비하는 상황.

**최소 권고:** 개발자가 제공하는 실행 확장은 승인된 역할·도구·맥락 기여 계약으로 등록한다. 문서형 스킬은 자료 기여만 할 수 있게 한다. 둘을 한 확장 패키지에서 제공하는 것은 가능하지만 권한과 필수 연결은 따로 규정한다. 특정 읽기 도구 조건을 일반화할 때도 승인 자산·입력 스키마·해시·내용 상한은 보존한다. 사용자 추가 메뉴·자동 다운로드·자동 설치는 이번 범위에 넣지 않는다.

근거: [참고 자료의 현재 목적](../../../../src/redteam/capability/methodology.py), [자료 읽기 도구와 역할 결속](../../../../src/redteam/app/methodology.py), [주 검증의 자료 결과 처리](../../../../src/redteam/orchestration/nodes/verify.py).

### E11. 저장 포트가 있으니 저장소 교체·원자성이 이미 해결됐다고 판단

**문제·근거:** 원자적 조정자는 메모리/SQLite의 구체 타입과 내부 잠금·연결·직렬화에 의존한다. 저장 포트만 구현한 제3의 저장소는 현재 조정자가 지원하지 않는다. 이것은 역할 하나 추가와 다른 변경 종류다.

**실제 상황:** 타입 검사만 제거하거나 여러 저장소의 개별 저장을 순서대로 호출하고 원자적 변경이라 이름 붙이는 상황.

**최소 권고:** 저장소 교체를 이번에 제공할 경우 일관된 변경 세션·스냅샷·커밋 계약을 실제 저장소 제공자에 둔다. 그렇지 않으면 지원 저장소를 명시하고 관련 결합은 후속과제로 판정한다. 도구·역할 확장 요구를 이유로 분산 트랜잭션 프레임워크까지 새로 추가하지 않는다. 작업 장부 두 구현의 순수 전이·충돌 규칙을 통합할 때 저장소별 잠금·조회 책임은 유지한다.

근거: [원자적 저장소 조합 제한](../../../../src/redteam/orchestration/coordination.py), [내부 연결과 스냅샷 소비](../../../../src/redteam/orchestration/coordination.py).

### E12. 현재 결함을 호환 계약으로 고정하거나 반대로 무관한 기능까지 추가

**문제·근거:** 기존 감사에는 정상 제약과 실제 결함이 함께 있다. 코드의 현재 동작 전부를 보존 대상으로 삼으면 승인 시간·요약 완료·관측 신원 오류까지 남는다. 반대로 감사의 모든 보완사항을 이번 모듈화에 넣으면 범위가 무한히 늘어난다.

**최소 권고:** 다음 표의 문제를 계획에서 각각 관련 변경에 반영하거나, 명시적 후속과제로 남긴다. 후속과제로 남겼다면 그 기능의 문제가 해결됐다고 완료 보고하지 않는다. 정상 경계 검사 제거를 최소 구현으로 취급하지 않는다.

| F05: 임무 간 관계 신원 충돌 | 관계 양 끝은 namespace하지만 관계 식별자는 그대로다 | 그래프 저장 경계를 변경하면 관계 신원의 저장/조회/삭제/이관을 함께 처리. 단일 임무 신규 저장소만으로 완료 판단 금지 |
| F06: 모델 반환·종료 처리 | 현재 공급자 연결은 응답을 비동기 순회하고 delta를 수집한다 | 추론 교체와 모델 전송 결함을 구분. 공급자/SDK 실제 계약에서 실패 종료·부분 응답 처리 필요. 과거 실패 원인이 이것이라고 확정하지 않음 |
| F11: 실행별 정책 ID 조립 | 실행별 ID·승인 자산을 요구하는 도구들이 있고 일반 실행 시작과 provision은 별도다 | 새 조립 계약에서 실행 ID 예약→승인 프로필 준비→같은 실행에 연결. ID 일치 검사 삭제 금지 |

## 5. 라이브러리 재사용의 적정 범위

| 기존/추가 라이브러리·구조 | 권고 사용처 | 이번 목표에서 억지 사용하지 않을 영역 |

| Pluggy | 승인된 확장 발견·등록 선언·제공자 결속 | 모든 도메인 상태를 조작하는 거대 관리자, 독립 워크플로 런타임 |
| pydantic-settings | 앱 설정 수집·자료원 우선순위·동적 서버 자료를 기존 모델에 연결 | 공통 계약과 저장 모델 전체의 환경 의존화, CLI 전면 재작성 |
| 기존 Pydantic·JSON Schema·포트 | 선언·입출력·제안 검증과 기능별 계약 | 같은 규격의 자체 스키마 언어·대형 검증 프레임워크 |
| 기존 MCP SDK | 전송·발견·실제 호출·세션 수명 | 자체 MCP 프로토콜 구현 |

## 6. 계획 개정본을 받으면 확인할 최소 항목

1. 기존 기능별 최종 소유자와 이관·삭제 파일이 있는가. 기존 도메인 목록이 새 등록부 옆에 계속 남지 않는가.
2. 같은 규격의 새 도구와 역할이 확장 패키지·설정만으로 등록·조립되는가. 시작 시 필수 참조·중복·미지원 버전을 확인하는가.
3. 중앙 추론의 교체·위임 입력/출력이 정의되어 있는가. 행동·완료·상태 적용이 동일한 통제·증거·버전 검증 경로를 사용하는가.
4. 실행·재개·조회·사전 점검이 동일한 설정·제공자 구성을 소비하는가. 새 실행 ID가 필요한 도구의 조립 시점이 맞는가.
5. 실행별 가변 객체·연결 종료·승인 대기·복구·긴 실행·작업 임대·중복 회계의 책임이 빠지지 않았는가.
6. 참고 스킬과 실행 확장, 발견과 승인, 원본과 구조화 사실, 실행 종료와 목표 성공이 구분되어 있는가.
7. 기존 결함의 반영 또는 후속과제 판정이 있는가. 후속과제의 미해결 기능을 완료된 것처럼 설명하지 않는가.
8. 새로운 의미 규격·새 저장소·미래 사용자 메뉴 같은 범위 확대가 실제 요구 없이 추가되지 않았는가.

## 7. 이후 구현 검증에서 필요한 증거

아래는 향후 검증의 최소 방향이며 이번 턴에 실행한 검사가 아니다. 추가 기능을 가정한 장시간 시험이나 구현을 그대로 복제하는 테스트는 권고하지 않는다.

- **기존 규격의 확장 사례:** 같은 행동 의미의 새 MCP 도구·해석기와 새 역할을 외부 패키지에서 제공하고 중앙 소스 수정 없이 조립·후보 노출·실행 증거·구조화 관측을 확인한다. 해석기 미제공 사례의 원본 보존도 구분한다.
- **추론 교체 사례:** 기본과 대체 추론을 명시적 구성으로 각각 사용하되 동일한 행동·완료 검사를 거친다. 잘못된 도구·대상·증거 제안은 상태를 변경하거나 실행하지 못한다.
- **지속 재개 사례:** 새 확장 구성에서 승인 대기 후 프로세스 재시작, 원래 제안·승인·구성 복원, 버전 불일치 거절을 확인한다. 승인·속도·예산을 중복 소비하지 않는다.
- **최신 시점 사례:** 승인 대기·동시성 대기·재시도 사이의 기간·상태 변경에서 추가 호출이 나가지 않는지 확인한다. 등록 시 성공만으로 대체하지 않는다.
- **설정 사례:** 환경과 `.env`의 같은 키, 다수 동적 서버, 명시적 덮어쓰기, 서로 다른 진입점이 동일한 구성을 만드는지 확인한다. 비밀값을 출력하지 않는다.
- **기능 보존 사례:** 필수 작업·목표 완료와 원본 출처, 알려진 요약/관측 결함의 처리, 종료 상태·보고 구분을 확인한다. 변경한 저장소는 해당 격리·원자성 계약도 검증한다.
- **기존 품질 검사:** 구현 완료 후 저장소에서 요구하는 관련 테스트·정적 검사와 기존 CI 기준을 확인한다. 기존 감사의 통과 숫자를 새 구현의 결과로 재사용하지 않는다.

라이브 외부 MCP나 실제 LLM을 사용하지 않은 검증은 합성·연결 계약 검증이라고 표현한다. 같은 규격 확장 사례와 승인 재개 사례가 없는 테스트 통과만으로 목표 달성을 선언하지 않는다.

## 8. 후속 판정 형식

계획 또는 구현 검토 시 각 지적은 다음 항목으로 기록한다.

| 항목 | 기록할 내용 |
|---|---|
| 문제 | 누락·모순·불필요한 결합 자체 |
| 근거와 상황 | 해당 개정본/소스 위치, 문제가 발생하는 실제 조건 |
| 영향 | 어떤 사용자 요구·현재 기능·재개 계약을 충족하지 못하는지 |
| 최소 권고 | 통합·이관·삭제 우선의 구체적인 해결 방향 |
| 판정 | 반영 / 대안 / 기각 / 후속과제와 그 이유 |
| 남은 확인 | 문서상 해결, 소스상 해결, 실행 검증 중 어느 수준까지 확인했는지 |

계획 문장이 해결 방향을 약속했다면 계획상 반영으로 판단할 수 있다. 실제 소스 이관과 재개·출처·결합 감소까지 입증된 것으로 표현하지 않는다. 이번 준비 메모의 E01~E12도 같은 기준으로 채택하거나 기각할 수 있는 검토 대상이다.
