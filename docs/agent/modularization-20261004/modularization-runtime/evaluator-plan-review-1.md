> 이 문서는 작성 당시의 감사·검토·작업 기록이다. 중간 상태와 검증 수준을 그대로 보존한다. 최신 구현·CI·병합 상태는 [목차](../README.md)의 최종 계획을 기준으로 읽는다. 인용 행 번호는 검토 당시 기준이며 소스 링크에 현재 행 번호를 추정해 붙이지 않았다.

# WHS 모듈화 구현계획 초안 1 독립 검토

작성일: 2026-10-04 (Asia/Seoul)

검토 대상: [구현계획 초안 1](../2026-10-04-WHS-modularization-implementation-plan.md). 판독 시 193행이며 상태는 “초안 1. 조사 결과 통합 및 독립 평가 전”이었다.

검토 수준: **계획과 실제 소스의 정적 대조**. 준비 메모를 먼저 작성한 후 진행했으므로 블라인드 평가가 아니다. 제품 소스 수정·테스트·제품 실행·추가 에이전트 생성은 하지 않았다. 설치 버전·CI 환경 설명은 계획 작성자의 확인 기록으로 읽었고 이번 평가자가 독립 실행 확인하지 않았다.

## 1. 판단

초안의 큰 방향은 유지할 수 있다. 선택한 확장의 선언을 Pluggy로 수집하고 기존 목적별 등록부·포트·실행 흐름을 재사용하며, 동작·증거·정책·재개의 의미를 남기는 방향은 사용자 요구와 맞는다. 기본 제공자도 같은 등록 경로로 이관하고 기존 목록을 계속 소비하는 부분을 제거하겠다는 내용이 명시돼 있다. 이 점을 다시 미반영 문제로 지적하지 않는다.

다만 **공유 골격 구현 전에 결정해야 할 계약이 여덟 가지 남아 있다.** 가장 직접적인 모순 후보는 기존 구성 바인딩을 기본 제공자로 읽는다는 문장이다. 현재는 사용자 정의 구성도 기록하고 그대로 대조하여 재개할 수 있다. 가장 큰 책임 미확정은 제안만 반환하는 추론 계약과, 현재 경로·완료 상태를 변경하는 기본 판단 구현 사이의 이관 경계다.

아래 필수 항목은 새로운 기능을 많이 만들라는 요구가 아니다. 서로 다른 구현자가 공유 계약을 반대 의미로 구현하지 않도록 결정해야 할 사항이다. 테스트의 양·실행·통과 여부는 이번 계획 판정 기준에 넣지 않는다. 계획 9절의 마지막 검증 순서는 유지한다.

공통 core 계약의 최소 변경은 이번 전체 리팩터 범위에 포함된 것으로 판단한다. 과거 동결 주석을 이유로 구체 타입 분기·사설 저장 접근·비정형 정책 신호를 보존하라고 요구하지 않는다. 필요한 공개 자료·포트는 변경하되, core가 앱·도메인 구현을 역으로 가져오지 않는 방향을 유지하면 된다.

## 2. 구현 전 필수 결정

### R01. 기존 사용자 정의 구성을 기본 제공자로 바꾸지 않도록 복원 규칙 구분

**문제:** 계획 5.A의 “기존 바인딩 기록은 기본 제공자로 읽고”는 모든 구형 기록을 기본 제공자로 대체한다는 의미로 읽힐 수 있다. 이는 계획 1절의 내용·버전 불일치 시 조용히 대체하지 않는다는 원칙 및 현재 지원 기능과 맞지 않는다. 의도가 구형 기본 기록만 호환한다는 것이면 문장을 좁혀야 한다.

**근거:** [계획 5.A](../2026-10-04-WHS-modularization-implementation-plan.md). 현재 [재개 구성 결정](../../../../src/redteam/app/runtime_components.py)은 기록이 없는 경우만 기본 구성으로 간주한다. 기록이 있으면 [등록된 구성과 대조](../../../../src/redteam/orchestration/component_binding.py)하고 다른 프로필·버전·구성 식별자는 거절한다. 등록부는 기본 외의 프로필도 지원한다.

**실제 상황:** 사용자가 등록한 별도 역할·해석·검증 구성으로 실행하다 승인 대기에서 종료했다. 리팩터 후 구형 기록을 모두 기본 구성으로 바꾸면 재개는 되더라도 조사·해석·검증 담당이 바뀐다.

**필수 보장:** 기록 없음, 알려진 구형 기본 구성, 알려진 사용자 정의 구성, 미지원/불일치 구성을 구분한다. 기존 사용자 정의 구성과 등록부 주입 경로를 보존하거나 명시적 지원 이관을 제공한다. 기록의 식별자만 같다는 이유로 바뀐 내용이 호환된다고 간주하지 않는다.

**최소 대안:** 종류별 이관표 하나를 추가한다. 알려진 구형 기본 기록만 새 기본 제공자 선언에 대응시키고, 사용자 정의 기록은 등록된 호환 제공자/이관을 통해 복원한다. 미지원 기록은 사유를 표시해 거절한다. 범용 버전 협상기나 자동 최적 버전 선택기는 필요 없다.

### R02. 추론이 제안하는 것과 일반 실행기가 확정하는 것을 한 경계로 정함

**문제:** 계획 4.3은 경로·행동·완료 **제안**을 반환한다고 하지만, 기본 판단 구현을 그대로 제공자로 연결하는 방식은 아직 정해지지 않았다. 현재 기본 판단은 제안만 만들지 않는다. 반환 계약만 바꾸거나 객체를 주입하는 데 그치면 기본 제공자와 대체 제공자의 책임이 달라진다.

**근거:** [계획 4.3](../2026-10-04-WHS-modularization-implementation-plan.md). [계획 단계의 직접 생성과 반환 소비](../../../../src/redteam/orchestration/nodes/plan.py)는 현재 활성 경로·컴파일된 후보·종료/진행 결과와 별도의 사건·진단 속성을 소비한다. 중앙 구성요소의 [경로 등록](../../../../src/redteam/orchestration/engine.py), [단계 완료](../../../../src/redteam/orchestration/engine.py), [목표 완료](../../../../src/redteam/orchestration/engine.py), [작업 완료](../../../../src/redteam/orchestration/engine.py)는 실제 상태 검증과 변경까지 수행한다. 정책·실행 노드는 같은 모듈의 실행 전 검사를 가져온다.

**실제 상황:** 기본 제공자는 제안을 만들면서 작업을 완료 처리하고, 대체 제공자는 완료 제안만 반환한다. 호출자가 두 결과를 같게 다루면 대체 제공자는 상태가 반영되지 않거나 기본 제공자에 이중 적용이 생긴다. 위임된 경로 설계가 원본 자료를 읽어야 할 때, 증거 참조만 전달되고 기존 원본 읽기 수단이 빠질 수도 있다.

**필수 보장:** 추론 제안·구조 검증·도구 컴파일·의미 검토·최신 상태 대조·최종 확정의 담당을 구분한다. 경로 초안/검토/수정·다음 행동·원본 조회·참조 보완·단계/작업/목표 완료·보류·진단의 현재 기능을 누락하지 않는다. 비동기 위임이 끝난 뒤 최신 경로·지시 상태를 다시 대조한다. 위임된 판단에게 도구 실행이나 상태 직접 변경 권한을 필수로 주지 않는다.

**최소 대안:** 기본 판단에서 상태 적용을 일반 결정 적용 경계로 이관하고, 기본·대체 판단 모두 기존 제안 자료를 반환하게 한다. 한 번에 분리하기 어렵다면 기본 호환 어댑터와 새 제안 계약의 차이를 명시하고 적용을 두 번 하지 않게 한다. 마지막 사건·진단 등 현재 호출자가 사용하는 정보는 반환 자료에 포함한다. 원본 조회는 기존 제한된 읽기 계약으로 제공한다. 요청에 전체 실행 의존성과 저장소를 그대로 넣는 해결은 피한다.

구현 전에는 최소한 “어떤 제안을 누가 검증/확정하는가” 대응표가 필요하다. 새 추론 DSL이나 또 다른 조사 런타임은 요구하지 않는다.

### R03. 역할이라는 단어로 모든 제공자 선택을 뭉치지 않도록 기여 규격 확정

**문제:** 계획은 안정된 신원·제공 역할·필수 참조를 설명하지만, 업무 역할·실행 구성 슬롯·확장 패키지·도구 제공자를 어떻게 구분하는지는 아직 불명확하다. “같은 역할의 중복 제공은 명시 선택이 없으면 진단”만으로는 단일 선택과 다수 기여의 합성 규칙을 구현하기 어렵다.

**근거:** [계획 4.1~4.2](../2026-10-04-WHS-modularization-implementation-plan.md), [계획 5.A](../2026-10-04-WHS-modularization-implementation-plan.md). 현재 [역할 등록](../../../../src/redteam/orchestration/agents/registry.py)은 실행 역할의 신원으로 결속한다. [역할 정의](../../../../src/redteam/orchestration/agents/definition.py)는 업무 분류·능력·후보 제공자·맥락을 따로 가진다. 현재 [실행 구성 등록](../../../../src/redteam/orchestration/component_binding.py)은 네 슬롯 전체를 요구한다.

**실제 상황:** 한 패키지가 웹 도구 두 개와 전문 역할 하나를 제공하고 다른 패키지가 같은 분야의 역할을 하나 더 제공한다. 분야가 같다는 이유로 중복으로 거절하면 정상 확장을 막는다. 반대로 단일 중앙 판단 슬롯의 두 구현을 목록으로 합치면 선택이 모호하다. 도구만 기여하는 패키지가 네 슬롯 전체를 다시 만들게 되면 결합이 줄지 않는다.

**필수 보장:** 패키지 신원, 기여 신원, 업무 분류, 단일 구현 슬롯을 구분한다. 슬롯별 단일/복수 선택, 중복 식별자, 필수/선택 참조, 버전, 실패 시 조립을 중단하는 조건을 정한다. 선택한 패키지만 실제 로딩·조립하고 가변 등록부는 실행별로 만든다. 선언과 구현 팩토리의 저장/수명도 구분한다.

**최소 대안:** 현재 필요한 기여 종류만 열거한 선언과 조립표를 둔다. 중앙 판단은 명시적 단일 선택, 역할·도구는 안정된 신원별 다수 기여, 해석은 정확한 도구 계약별 연결로 나눈다. 기본 제공자도 같은 표를 채운다. 설치 패키지의 메타데이터 발견과 선택한 코드의 로딩을 나누고, 조립 중복·필수 누락은 결과를 조용히 선택하지 않는다. 부분 확장을 기존 네 슬롯 전체 프로필에 억지로 넣지 않는다.

이 결정은 공유 골격 전에 필요하지만 범용 의존성 해결기·전역 서비스 탐색기·모든 미래 기여 종류를 위한 플러그인 시스템은 필요 없다.

### R04. 새 도구 신원을 정하고 모든 소비자가 같은 해석 경계를 쓰게 함

**문제:** 계획 4.2는 서버/원격 이름을 포함한 신원과 구참조 호환을 약속하지만, 실제 새 식별 형식·기존 승인 바인딩의 입력 의미·별칭 해석 위치를 정하지 않았다. 현재 도구 등록 검사는 단순 접두사 소비보다 더 좁은 신원 규격을 갖는다.

**근거:** [계획 4.2](../2026-10-04-WHS-modularization-implementation-plan.md). 현재 [신원 검사](../../../../src/redteam/capability/manifest.py)는 능력과 원격 이름으로 이루어진 두 구간만 허용하고 원격 구간의 추가 점을 거절한다. [카탈로그](../../../../src/redteam/capability/catalog.py)도 첫 구간을 실행 능력으로 소비한다. [정확한 해석 등록](../../../../src/redteam/orchestration/observations/mapper.py), 승인 제안·호출·원본 결과 역시 도구 신원을 소비한다.

**실제 상황:** 서버 신원을 끼워 세 구간으로 만들면 기존 명세 검사가 거절한다. 접두사를 서버 이름으로 바꾸면 기존 능력 후보 필터가 제외한다. 조회에서만 별칭을 해석하고 승인된 호출에서는 해석하지 않으면 다른 단계가 서로 다른 도구를 가리킨다.

**필수 보장:** 정식 도구 신원과 동작 의미를 분리하고, 설정·등록·모델 후보·컴파일·위험 판단·호출·해석·재개가 동일한 신원 해석을 소비한다. 두 서버의 같은 원격 이름과 이름 정규화 충돌을 구분한다. 승인된 구제안의 대상 도구를 다른 서버로 재해석하지 않는다. 원본 증거의 식별자를 바꾸며 원본 다이제스트를 무효화하지 않는다.

**최소 대안:** 하나의 정식 식별 형식과 한 개의 구별칭 해석 규칙을 계획에 적는다. 행동 의미는 도구의 등록 자료로 읽고 이름 파싱은 제거한다. 구별칭은 해당 실행의 저장된 바인딩 또는 단일하게 확인된 대응에서만 해석한다. 충돌 별칭은 명시 거절하고 원본 자료는 보존하며 정규화된 조회 결과를 별도로 제공한다. 기존 이름을 무조건 다시 쓰거나 소비자마다 별칭 조건문을 추가하지 않는다.

### R05. 현재 허용 검사와 회계를 분리하고 일회 claim의 실제 의미를 정의

**문제:** 계획 5.C는 모든 실행 시점의 허용 검사와 중복 회계 방지를 함께 요구하지만, 최초 평가·승인 해결·실제 호출·추가 재시도의 소비 지점을 정하지 않았다. 또한 “기존 ... 일회 claim을 유지”는 현재 기록 저장의 보장보다 강한 표현이다.

**근거:** [계획 5.C](../2026-10-04-WHS-modularization-implementation-plan.md). 현재 [최초 허용 평가](../../../../src/redteam/control/service.py)는 허용 시 속도와 행동 예산을 소비하고 [승인 해결](../../../../src/redteam/control/service.py)도 별도 소비한다. [추가 호출 가능 검사](../../../../src/redteam/control/service.py)는 호출 수를 확인한다. [실행 직전](../../../../src/redteam/orchestration/nodes/execute.py)은 동시성 자리를 얻은 뒤 최신 상태를 검사하고 claim을 기록한다. [claim 기록](../../../../src/redteam/orchestration/engine.py)은 같은 행동 키에 값을 저장하며 이 코드 자체에는 이미 기록한 같은 행동을 거절하는 조건이 없다.

**실제 상황:** 현재 검사에 기존 최초 평가를 다시 호출하면 이미 승인된 행동에 승인을 새로 만들거나 예산을 재차 소비할 수 있다. 반대로 호출 전에 과거 허용 판정만 재사용하면 시간 종료를 놓친다. 같은 행동의 합법적인 추가 재시도와 동일 시도의 중복 실행을 모두 “한 번”으로 처리하면 둘 중 하나의 의미가 깨진다.

**필수 보장:** 승인 의도/ID·행동 신원과 실제 호출 시도를 구분한다. 현재 시점의 범위·ROE·기간·현재 실행 상태 검사는 호출 직전에 소비하고, 회계는 정의된 단계에서 한 번씩 예약/차감한다. 추가 재시도의 호출 비용은 별도로 처리한다. 작업 임대·현재 경로/지시 검사·claim이 각각 막는 상황을 분명히 한다. 긴 실행의 결과 조회는 재제출과 다르게 취급한다.

**최소 대안:** 기존 통제 포트에 현재 허용/회계 경계를 명시하는 최소 공개 계약을 추가하고, 단계별 소비표를 문서화한다. 기존 최초 승인 생성과 현재 시점의 재검사를 나누며, 실행 노드는 동시성 대기 후 현재 허용과 상태 claim을 사용한다. action-level 재사용과 invocation-attempt 추가 소비의 멱등 규칙을 같은 소유자에 둔다. 단순히 최초 평가를 반복하거나 “기록이 있으니 일회 실행 보장”이라고 설명하지 않는다.

외부 도구 호출은 로컬 저장 커밋과 하나의 원자적 동작이 아니므로 일반적인 정확히 한 번 실행을 약속하지 않는다. 제출 여부가 불명확한 긴 실행은 기존 작업 신원으로 상태/결과를 확인하는 경로를 유지한다. 이번 검토가 현재 동일 행동의 중복 호출을 실행 재현한 것은 아니다.

### R06. 공개 변경 세션을 원자적으로 묶을 상태와 외부 I/O 경계로 제한

**문제:** 계획 5.D의 “경로/과제/조사/지시/outbox ... 읽고 검증·변경·커밋 또는 롤백”은 필요한 방향이지만, 조사에 그래프·증거·승인·체크포인트까지 포함되는지, 세션 안에서 임의 비동기 호출을 해도 되는지 불명확하다. 너무 넓은 변경 세션은 새 저장 뒷단을 위한 범용 트랜잭션 프레임워크가 된다.

**근거:** [계획 5.D](../2026-10-04-WHS-modularization-implementation-plan.md). 현재 [변경 자료](../../../../src/redteam/orchestration/coordination.py)는 임무·과제, 경로, 실행 연결·지시 세대·입장 기록·outbox를 다룬다. [SQLite 변경](../../../../src/redteam/orchestration/coordination.py)은 분리된 메모리 상태에 판단을 적용한 뒤 한 연결에 저장한다. [메모리 변경](../../../../src/redteam/orchestration/coordination.py)도 공유 잠금과 분리 사본으로 확정한다. 별도 지시 이력은 [복구 가능한 투영](../../../../src/redteam/orchestration/operator_intents/store.py)이며 사건 발행과 실제 소비자 처리도 별도다.

**실제 상황:** 전문 추론이나 사건 발행을 열린 변경 세션 안에서 기다리면 저장 잠금·취소·외부 부작용의 롤백을 함께 처리해야 한다. 반대로 저장소별 개별 호출을 연결한 세션은 중간 실패 때 경로와 과제의 부분 확정을 남길 수 있다.

**필수 보장:** 원자적 상태 집합, 동일 저장 제공자의 세션 소유권, 읽기/변경과 버전 검사, 종료/롤백 의미를 정의한다. 외부 LLM·MCP·사건 발행은 열린 확정 경계 밖에 둔다. 공개 변경 경로가 같은 잠금/버전 규칙을 사용해야 하고, 조정자가 사설 저장 구조를 읽지 않게 한다. outbox 기록의 원자성과 소비자 처리 성공을 구분한다.

**최소 대안:** 현재 원자적 상태 집합만 다루는 변경 세션 포트를 추가하고, Memory/SQLite가 그 집합의 스냅샷·검증·확정을 제공하게 한다. 업무 상태 전이 규칙은 저장 구현과 분리해 공통으로 재사용한다. 지시 원본 상태와 이력 투영은 구분한다. 그래프·증거·승인·체크포인트를 모두 한 트랜잭션에 넣거나 임의 외부 I/O의 롤백까지 지원하지 않는다. 저장 제공자 내부에서 자기 구현의 연결·자료 구조를 사용하는 것은 정상이다.

과거 core 동결 또는 현재 저장 포트가 충분히 좁다는 이유로 사설 접근을 남기는 것은 대안으로 채택하지 않는다.

### R07. 단일 설정 로더의 위치와 기존 환경 호출의 호환 방식을 정함

**문제:** 계획 4.4는 환경/파일 읽기를 조립 영역이 소유하고 기존 공개 환경 변환은 호환한다고 하지만, core 안의 현재 환경 호출이 어느 하위 경계로 위임하는지는 정해지지 않았다. 새 앱 로더를 core의 옛 메서드에서 import하면 계획 자체의 역참조 금지와 충돌하고, 옛 로더를 그대로 남기면 설정 규칙이 두 벌이 된다.

**근거:** [계획 4.4](../2026-10-04-WHS-modularization-implementation-plan.md). 현재 [공통 모델의 환경 변환](../../../../src/redteam/core/config.py)과 [MCP 동적 서버 설정](../../../../src/redteam/capability/settings.py)이 따로 존재한다. [CLI dotenv 처리](../../../../src/redteam/app/cli/_shared.py)는 프로세스 환경에 누락 키를 추가한다. MCP에는 별도 [자식 프로세스 환경 설정](../../../../src/redteam/capability/settings.py)과 프로필별 경로·정확한 바인딩 검사가 있다.

**실제 상황:** CLI는 기존 dotenv의 전역 변경을 거쳐 새 로더를 쓰고 라이브러리 호출은 새 로더만 쓴다. 같은 입력 파일에서도 모델·서버·자식 환경이 달라질 수 있다. 각 제공자가 자기 방식으로 환경을 다시 읽으면 실행과 재개에서 서로 다른 구성을 선택할 수 있다.

**필수 보장:** 환경·dotenv·명시 입력의 우선순위와 경로 기준, 동적 서버 목록, 프로필별 설정 스키마, 비밀 이름 참조, 자식 프로세스 환경을 같은 해석 결과에 결속한다. 읽기 전용 진입점이 모델 설정을 불필요하게 요구하지 않아야 한다. 순수 공통 계약 모델은 외부 환경을 읽지 않게 한다. 호환 호출이 앱/팀 구현을 core로 역수입하지 않아야 한다.

**최소 대안:** 환경 자료 수집과 공통 모델 검증을 한 방향으로 나누고 옛 공개 호출은 그 하위 입력 자료 경계에 얇게 위임한다. 앱은 한 번 해석한 결과를 제공자에 넘긴다. CLI의 기존 전역 dotenv 변경을 제거할지 호환 진입점으로 제한할지 명시한다. 동적 서버별 설정을 고정 필드 목록으로 바꾸거나 프로필 검사를 일반 문자열 변환만으로 대체하지 않는다. 설정 모델과 CLI 전체를 합친 새 프레임워크는 필요 없다.

### R08. 관계 신원 이관은 이미 유실된 관계의 복구와 구분

**문제:** 계획 5.C는 기존 그래프 자료와 조회·삭제·내보내기 변환을 함께 처리하겠다고 하지만, 기존 데이터의 이관 방식을 정하지 않았다. 현재 신원 충돌로 덮어진 관계는 남아 있는 관계 ID를 바꾸는 것만으로 복구할 수 없다.

**근거:** [계획 5.C](../2026-10-04-WHS-modularization-implementation-plan.md). [현재 저장](../../../../src/redteam/attack_graph/stores/namespaced.py)은 관계 양 끝만 조사 namespace로 바꾸며, [관계 조회](../../../../src/redteam/attack_graph/stores/namespaced.py)와 [관계 삭제](../../../../src/redteam/attack_graph/stores/namespaced.py)도 구형 관계 신원을 쓴다. 기존 시스템 감사 F05는 같은 관계 기록의 덮어씀을 재현했다고 보고한다. 이번에는 저장·조회·삭제 코드를 대조했고 덮어씀을 재실행하지 않았다.

**실제 상황:** 기존 SQLite에 일부 관계만 남아 있다. 새 namespace를 붙이면 이후 충돌은 방지할 수 있지만 과거에 사라진 관계가 자동으로 생기지는 않는다. 조회만 구별칭을 지원하고 삭제가 옛 ID를 지우면 이관 후 새 기록이 남거나 다른 조사 기록을 건드릴 수 있다.

**필수 보장:** 남아 있는 자료의 소유 조사와 신원을 일관되게 저장·조회·삭제·내보내기한다. 이관 방식/버전과 미확인·유실 자료의 처리 한계를 명시한다. 추정으로 과거 관계를 다른 조사에 만들어 넣지 않는다.

**최소 대안:** 알려진 소유 신원이 있는 구기록의 명시적 이관 또는 일관된 호환 읽기 경계 중 하나를 선택한다. 모든 입출력은 같은 변환을 사용한다. 유실 복구는 보존된 증거가 실제로 입증하는 경우의 별도 기능으로 남기고, 이번 변경을 충돌 방지와 남은 기록의 이관으로 설명한다. 전체 그래프 재구축기나 증거 자동 재생기를 이번에 추가할 필요는 없다.

## 3. 선택적 개선과 과도한 범용화 축소

아래 사항은 R01~R08의 필수 보장을 충족하는 한 다른 구현을 선택할 수 있다. 필수 결함처럼 처리하지 않는다.

### O01. 경로 설계 위임에 호스트가 하위 그래프 수명을 추가로 관리하지 않아도 됨

**문제:** 계획 3절·4.3은 여러 단계 전문 조사에 LangGraph 하위 흐름을 언급한다. 현재 필요한 위임이 경로 제안이라면 독립적인 도구 실행·체크포인트·작업 장부 수명을 하나 더 만드는 것은 과하다.

**근거·상황:** 현재 [LangGraph 부모 흐름](../../../../src/redteam/orchestration/graph.py)과 [승인된 긴 실행 계약](../../../../src/redteam/orchestration/long_jobs.py)이 이미 있다. 한 전담 추론이 여러 내부 생각 단계를 수행해도 외부 계약은 한 번의 경로 제안 반환일 수 있다.

**필수 보장:** 위임 결과가 같은 결정 적용 경계를 거치고 부모 실행의 취소·판단 예산·진단 의미를 보존한다. 부모/자식이 현재 경로를 따로 확정하지 않는다.

**최소 대안:** 호스트에는 비동기 판단 제공자 계약만 둔다. 제공자가 내부적으로 하위 그래프를 사용하는 것은 허용하되, 호스트 전용 하위 그래프 등록부와 별도 조사 실행기는 실제 필요가 확인될 때 추가한다. 하위 그래프의 구현을 이번 범위에 반드시 포함하려면 상태·예산·취소·복원의 소유자를 먼저 적는다.

### O02. 단순 요약 결함 해결에 새 범용 집계 단계 계약은 필요하지 않을 수 있음

**문제:** 계획 5.C의 “별도 집계 지원”을 새 경로 단계·완료조건·receipt 타입 도입으로 구현하면 F02 해결에 필요한 변경보다 커진다.

**근거·상황:** [기존 작업 완료](../../../../src/redteam/orchestration/engine.py)와 [목표 완료](../../../../src/redteam/orchestration/engine.py) 경로가 이미 있다. 완료 검사는 [같은 실행·경로·단계의 원본 증거](../../../../src/redteam/orchestration/completion.py)를 요구한다. 도구가 없는 필수 요약 단계를 계획에 넣는 현재 조합이 문제다.

**필수 보장:** 실행할 수 없는 요약을 필수 도구 실행 단계로 등록하지 않고, 기존 완료된 필수 단계의 출처를 사용해 작업/목표를 판단한다. 다른 단계 증거 검사를 무조건 없애지 않는다.

**최소 대안:** 요약은 작업/목표 완료 제안으로 전달하고 실행 단계 등록에서 해당 불가능 조합을 거절한다. 새로운 집계 단계 종류는 별도 요구가 있을 때만 추가한다. 현재 단계 완료와 작업/목표 집계의 담당 분리는 R02에서 반드시 정하되 새 집계 프레임워크는 선택이다.

### O03. 기존 의미 제공과 새 의미 규격 확장을 별도 결정으로 표현

**문제:** 계획 M01·M15·M24와 “등록된 동작”이라는 표현이 모든 동작·대상 종류·완료조건을 임의 이름으로 여는 구현으로 확대될 수 있다.

**근거·상황:** [현재 동작 어휘](../../../../src/redteam/core/action_semantics.py)와 [완료조건](../../../../src/redteam/orchestration/paths/models.py)은 닫힌 공통 규격이다. 사용자 목표는 기존 규격 안에서 새 제공자를 추가하는 경로다. 같은 동작의 새 도구를 넣는 일은 새 대상 종류나 완료 의미를 정의하는 일과 다르다.

**필수 보장:** 기존 의미의 도구·역할·대상 인자 연결이 등록 자료로 확장되고 안내·컴파일·정책·실행이 같은 의미를 소비한다. 새로운 의미를 지원한다면 정의와 검증·정책 적용을 함께 등록하며 미지원 의미는 실행하지 않는다.

**최소 대안:** 우선 현재 의미를 제공자의 등록 자료로 옮기고 복사본을 공통 정의에서 파생한다. 실제로 필요한 새 의미만 추가한다. 모든 공통 enum·그래프 종류·완료조건을 확장 문자열로 바꾸는 것은 이번에 필수로 삼지 않는다. 필요한 최소 core 변경을 금지하자는 뜻이 아니다.

### O04. 실행 스킬과 보고 분류에 독립 실행기·거대 공통 역할 목록을 추가하지 않음

**문제:** 계획은 실행 스킬이 기존 제안 계약으로 절차를 반환하도록 이미 제한했다. 이 방향을 유지하면 별도의 스킬 실행기·도구 우회 경로가 필요하지 않다. 보고 업무 분류, 조사 역할, 서버 실행 프로필도 같은 이름이라는 이유로 하나의 목록에 합칠 필요가 없다.

**근거·상황:** 기존 [참고 후보 계약](../../../../src/redteam/orchestration/agents/providers.py), [자료 역할 조립](../../../../src/redteam/app/methodology.py)과 목적별 도구·역할 등록부가 있다. 문서만 제공하는 스킬과 절차를 제안하는 스킬의 수명 요구는 다르다.

**필수 보장:** 문서는 참고 데이터, 실행 절차는 승인 전 제안으로 소비하고 같은 행동 컴파일·정책·증거 경로를 사용한다. 보고 분류를 추가한다고 실행 역할이나 서버 프로필이 자동 생성되지 않는다.

**최소 대안:** 스킬 패키지는 실제로 제공하는 참고 자료·맥락·후보/계획 기여만 선언한다. 보고 분류·서버 실행·역할을 각각의 목적별 등록 자료로 유지한다. 새 종류의 가변 상태를 갖지 않는 스킬에 체크포인트 타입·복원 제공자를 강제하지 않는다.

## 4. 이미 반영돼 추가 지적하지 않은 사항

- 선택된 패키지의 선언 수집에 Pluggy를 사용하고 실행·정책 순서를 훅 호출 순서에 맡기지 않는다는 방향.
- 목적별 등록부·기존 MCP SDK·LangGraph·모델 연결을 재사용하고 별도 DI 컨테이너·DB·병렬 런타임을 만들지 않는다는 방향.
- 기본 제공자도 같은 등록 경로를 쓰고 중앙 기본 목록을 계속 소비하는 부분을 이관한다는 방향.
- 필수 참조와 선택 해석/참고 후보를 구분하고 빈 결과·미등록·실패의 의미를 나눈다는 방향.
- 도메인 자격·벤더 조리법을 제공자에 이관하면서 승인·해시·범위·실행 직전 검사를 유지한다는 방향.
- 실행 종료와 목표 성공, 원본 증거와 구조화 사실, 관측·선언·가설·판정을 구분한다는 방향.
- 알려진 HTTP 신원·완료·승인 기간·재시도·관계 격리 결함을 현재 호환 동작으로 동결하지 않는다는 방향.
- 계획·구현 리뷰 뒤 마지막에 필요한 테스트·정적 검사·릴리스 검증을 하고 실제 검증 수준을 구분한다는 순서.

이 사항들은 계획상 반영으로 읽었다. 실제 코드 이관이나 기능 검증이 완료됐다는 판정은 아니다.

## 5. 루트의 개정 판정에 필요한 기록

R01~R08마다 다음 내용을 한 줄씩 결정표에 추가하면 다음 검토를 진행할 수 있다.

| ID | 필요한 결정 결과 |
|---|---|
| R01 | 구기록 종류별 복원 대상과 미지원 기록 처리 |
| R02 | 제안·검증·의미 검토·최신 대조·확정 담당과 기본 구현의 이관 방식 |
| R03 | 현재 기여 종류의 단일/복수 선택·신원·필수 참조·조립 실패 규칙 |
| R04 | 정식 도구 신원 형식·동작 자료·구별칭 소비 위치·저장 원본 보존 |
| R05 | 최초 평가/승인 해결/최종 호출/재시도의 검사·예약·회계·claim 역할 |
| R06 | 원자적 상태 집합·변경 세션의 입력/종료·외부 I/O 제외·공개 경로의 확정 규칙 |
| R07 | 로더 소유 영역·구공개 환경 호출 위임·전역 dotenv 처리·해석 결과 소비 |
| R08 | 남은 관계 기록의 이관 방식/버전·입출력 변환·과거 유실의 한계 |

판정은 반영·대안·기각·후속과제로 남기면 된다. 이 문서의 최소 대안과 다른 구현도 필수 보장을 충족하면 수용할 수 있다. 구체 API의 모든 필드나 클래스명을 먼저 고정할 필요는 없지만, 서로 다른 담당자가 같은 단어를 다른 의미로 구현할 여지는 닫아야 한다.

선택 개선 O01~O04는 채택 여부만 기록하고 기본 요구를 충족하는 대안을 불필요하게 막지 않는다. 이 단계에서 테스트 수를 늘리거나 실제 실행으로 모호한 설계를 대신 결정하라고 요구하지 않는다. 최종 구현 검증은 계획의 마지막 단계에 유지한다.
