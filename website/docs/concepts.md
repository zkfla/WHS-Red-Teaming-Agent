# 핵심 개념

이 문서를 읽고 분석하려면 아래 용어를 먼저 알아두는 게 좋다. 이후 모든 장에서 같은 뜻으로 쓴다.

## 바탕 기술

- **MCP (Model Context Protocol).** 도구를 표준 프로토콜로 노출해 에이전트가 균일한 방식으로 호출하게 하는 규약이다. 이 프레임워크는 모든 외부 도구를 MCP 서버로 감싸고, `MCPAdapter`로 연결한다.
- **ReAct.** 추론(Reason)과 행동(Act, 도구 호출)을 번갈아 반복하는 에이전트 루프다. 여기서는 `MODEL → TOOLS → SETTLE`로 구현한다. "네이티브"는 모델이 제공하는 도구 호출 기능을 직접 쓴다는 뜻이다.
- **LangGraph.** 노드와 엣지로 상태 기계를 구성하는 워크플로 런타임이다. 여기서는 Observe, Plan, Policy, Execute 같은 노드를 잇는 데만 쓰고, 도메인 데이터는 담지 않는다. 노드 사이로 흐르는 것은 ID와 phase뿐이다.

## 이 시스템의 핵심 용어

| 용어 | 뜻 | 아닌 것 |
| --- | --- | --- |
| 가설 (Hypothesis) | 확인하려는 가능성 | 확정된 취약점이 아님 |
| Probe (원자 작업, `MissionTask`) | 가설을 검증하기 위한 최소 조사 단위 | 취약점 입증 전체가 아님 |
| 워커 (Worker) | Probe를 실행하는 역할의 인스턴스 | 역할 그 자체가 아님. 한 역할이 여러 인스턴스일 수 있음 |
| 관측 (Observation) | 도구가 돌려준 원본 사실 | 해석이 아님 |
| Finding | 증거로 뒷받침된, 검증된 결론 | 관측이나 가설이 아님 |

!!! note "용어 통일"
    이 문서는 위 표를 기준으로 쓴다. "검증 작업"과 "원자 작업"은 모두 **Probe**, "실행 인스턴스"는 **워커 인스턴스**로 부른다.

## 자주 혼동되는 두 쌍

- **`binding_mode` (`selected_tool` vs `legacy_action`).** 행동이 도구에 묶이는 방식이다. `selected_tool`은 오케스트레이션이 구체 `tool_id`를 직접 지정한 상태이고(이때 `operation`은 비운다), `legacy_action`은 `capability.operation`이라는 표준 형태의 의도(어떤 능력으로 무슨 동작)만 두고 실제 도구는 나중에 `tool_id`로부터 해석한다.
- **`input_digest` vs `execution_fingerprint`.** `input_digest`는 "정확히 이 proposal"을 식별하는 해시로, 멱등성과 재개의 기준이 된다. `execution_fingerprint`는 `(tool_id, target, arguments)`를 정규화해 만든 해시로, 사람이 승인한 행동과 실제 실행이 같은지를 보증한다(인자를 문자열로 바꿔치기해 승인을 위조하지 못하게 정규화한다).

## 행동은 두 번 심사된다

행동 하나는 통제를 두 번 통과한다. 제안 시점의 `evaluate`와 실행 직전의 `admission`이다. 승인을 사람이 누르는 사이에 허용 시간대가 끝나거나 예산이 소진될 수 있으므로, 실행 직전에 현재 상태로 범위, 시간, 대상, 외부 전송, 지속시간을 다시 본다. 자세한 내용은 [실행 통제](control-plane.md) 장에서 다룬다.
